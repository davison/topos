## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `plugins/mock/plugin.go`'s Fetch FULL variant claimed `Available: false` despite returning real extracted text**
- **Found during:** Task 1, while implementing the acceptance criterion "the spec asserts a distinctive substring of the mock plugin's own `mockFullText` entry for item `1` is visible in the detail pane"
- **Issue:** Empirically verified (booted a standalone kernel + mock plugin, curled `GET /api/items/mock:1`) that `content.available: false` was returned alongside a fully-populated `content.text`. `web/src/lib/format.ts`'s `detailPaneState` checks `content.available === false` FIRST, before ever computing a body variant — so this routed every mock item's detail pane into the `deleted` state (an advisory `Alert` reading "No longer available", showing `item.preview` — the stale stream snippet — never `content.text`). `plugins/proton/plugin.go` and `plugins/silverbullet/plugin.go` both set `Available: true` for their own "no rendition, but usable text" Fetch responses; only `plugins/mock` diverged from that convention, and its own file-header comment says it is "deliberately written to be read as documentation" of correct contract usage — the divergence undermined that stated purpose. (`plugins/paperless/plugin.go` shares mock's OLD pattern — Available keyed to rendition presence — but that is a separate, out-of-scope, real plugin not touched by this fix.)
- **Fix:** `Fetch`'s `CONTENT_VARIANT_FULL` case now returns `Available: true` with no `UnavailableReason` (mirroring `plugins/proton`'s plain-text-preferred response shape exactly); `PREVIEW`/`THUMBNAIL` (which genuinely have no byte rendition to offer) are unchanged. Updated the file's doc comments (`Fetch`'s own comment, `noRenditionReason`'s comment) to describe the corrected semantics.
- **Files modified:** `plugins/mock/plugin.go`, `plugins/mock/plugin_test.go` (its `TestFetch_FullVariantForKnownIDReturnsTextAndNoRendition` had locked the old, incorrect behavior)
- **Verification:** `go test ./plugins/mock/... ./kernel/...` all pass; `go build ./...` and `go vet ./...` clean; empirically re-verified via the same standalone curl repro (now shows `"available":true`); `git diff --stat HEAD -- web/src` remains empty
- **Committed in:** `1dbd7b8` (Task 1 commit)

## Issues Encountered

- `page.getByRole('button'/'heading', {name})` matches substrings of the FULL accessible name by default (a `StreamRow` button's accessible name concatenates its title, metadata line, and preview text) — used `.filter({ hasText })` + `.first()` for rows sharing a title across two mock instances, and `exact: true` for chip-button lookups (`getByRole('button', {name: 'Mock One', exact: true})`) to avoid accidentally matching the sibling "Refresh Mock One"/"Edit Mock One" buttons, whose `aria-label`s contain "Mock One" as a substring.
- A search-result row renders both its title and its FTS snippet as separate paragraphs; for a short, fully-matched title the snippet excerpt is the title text again verbatim, so an exact-count `getByText` assertion over-counted (4 instead of 2 per pair of rows) — resolved by asserting presence (`.first()`) for title text and leaning on the `rows` locator's exact row-count assertion for precision instead.
- The webspace's `Clear filters` control (source-chip selection) and the search box's own `Clear search` control are two distinct, similarly-named affordances in the header — kept their locators separate by exact accessible name (`'Clear search'` vs. `'Clear filters'`) to avoid cross-matching.
