## Summary

This phase has almost no framework-discovery risk (Playwright is a known quantity) and almost all of its real risk in **kernel boot mechanics that are project-specific and only discoverable by reading the actual Go source**. The single most load-bearing fact this research surfaces: `topos serve` takes **no CLI flags at all** — the *only* way to control which port it binds, which config file it reads, and which plugins directory it scans is the `XDG_CONFIG_HOME` environment variable plus the contents of `$XDG_CONFIG_HOME/topos/config.toml` (`[server].listen`, `[plugins].dir`, `[index].path`). Every hermetic-kernel fixture the planner designs must be built around that fact, not around an imagined `--port`/`--config` flag.

A second load-bearing fact: `[plugins].dir` is resolved **relative to the running executable**, not the process cwd, and defaults to `plugins` (i.e. `bin/plugins/` next to `bin/topos`) — the **real, production plugin set**, including the cgo Signal plugin. If a fixture's generated `config.toml` omits `[plugins].dir` or leaves it relative, a "hermetic" test kernel will discover and (if any `[sources.*]` block names them) launch real plugin binaries. The harness MUST always write an **absolute** `[plugins].dir` pointing at a scratch directory containing only `topos-plugin-mock` and the new e2e plugin binary (D-07). The same collision risk exists for `[index].path`: its default (`~/.local/share/topos/index.db`) is the developer's real, live index — every generated config MUST set an absolute, per-run temp path, or parallel/concurrent hermetic kernels will corrupt (or silently share) the operator's real data.

A third fact, confirmed by reading `kernel/pluginhost/discover_binaries.go`: the plugin-type picker (`GET /api/config/plugin-types`, backing the UI's "+ New <plugin type>…" list) filters on two things — the binary must be named with the literal prefix `topos-plugin-` (`PluginBinaryPrefix`), and it must **not** be named exactly `topos-plugin-mock` (`ExcludedPluginBinaries`). The new e2e plugin (D-06) must therefore be built as a binary named `topos-plugin-<something-not-mock>` to be discoverable and offered in the "+" picker at all — this is a hard constraint on the plugin's naming, not just a discretionary choice.

A fourth fact, confirmed by reading `kernel/config/config.go`'s `Validate`: every `[sources.<id>]` block must declare **either** (`base_url` AND `token`) **or** `path` — there is no third shape. Since D-05/D-06 describe the e2e plugin as having "a required connection field with a seeded default," the natural, contract-compliant shape is to model it exactly like `plugins/signal`: a single required `path` field with a seeded default value, guarded by a fatal pre-`goplugin.Serve` exit when empty (mirroring `plugins/signal/main.go`'s `cfg.Path == ""` guard) — not a `base_url`/`token` pair, which would require two fields to seed/clear instead of one and doesn't match "declares a required connection field" (singular) in the CONTEXT.md decision text.

On the Playwright/CI side (WebSearch-sourced, Context7 unavailable this session, so MEDIUM confidence): there is no built-in Playwright primitive for "one server per test file" — `webServer` in `playwright.config.ts` boots exactly one shared server for the whole run. The idiomatic way to get D-02's fresh-kernel-per-file isolation is a **custom fixture** (a `test.extend()` worker- or test-scoped fixture that spawns/tears down the kernel child process itself and exposes its `baseURL`), not the built-in `webServer` option. `route.fulfill()` has no built-in delay parameter (open feature request), so UAT item 10's race test needs a manual `setTimeout`-based delay inside a `page.route()` handler, registered before the triggering UI action.

**Primary recommendation:** Build a TypeScript Playwright fixture module (not `webServer`) that: (1) allocates an ephemeral port, (2) writes a temp `$XDG_CONFIG_HOME/topos/config.toml` with absolute `index.path`/`plugins.dir` and the ephemeral `server.listen`, (3) spawns the pre-built `bin/topos` binary with `XDG_CONFIG_HOME` set to that temp dir and nothing else inherited from the developer's real environment, (4) polls `GET /api/webspaces` until 200 before yielding control to the test, and (5) kills the process (and any child plugin subprocesses) on teardown. Build the new e2e plugin exactly like `plugins/signal`'s shape (single required `path` field, seeded default, fatal-exit guard) so it satisfies `kernel/config.Validate` with zero extra kernel changes.

### Pattern 1: Ephemeral-kernel-per-spec-file fixture (not Playwright `webServer`)
**What:** A `test.extend()` fixture, scoped per test file (or per worker if D-02's "may share within a file" is read as worker-scoped), that owns the full spawn→poll→yield→kill lifecycle described in the diagram above.
**When to use:** Every spec file in `web/e2e/specs/`.
**Example (WebSearch-sourced pattern, MEDIUM confidence, no project-specific verification possible until Task 1 implements it):**
```typescript
// web/e2e/fixtures/kernel.ts — illustrative shape only, not a verified snippet
import { test as base } from '@playwright/test';
import { spawn, ChildProcess } from 'node:child_process';
import { mkdtempSync, rmSync } from 'node:fs';
import { tmpdir } from 'node:os';
import * as path from 'node:path';

type KernelFixture = { baseURL: string; configPath: string };

export const test = base.extend<{ kernel: KernelFixture }>({
  kernel: async ({}, use) => {
    const port = await allocateEphemeralPort();       // node:net listen(0) trick
    const tmp = mkdtempSync(path.join(tmpdir(), 'topos-e2e-'));
    const configDir = path.join(tmp, 'topos');
    const configPath = writeTempConfig(configDir, { port, tmp }); // smol-toml stringify
    copyPluginBinaries(tmp);                            // mock + <e2e-name> only (D-07)

    const child: ChildProcess = spawn(KERNEL_BIN, ['serve'], {
      env: { XDG_CONFIG_HOME: tmp, PATH: process.env.PATH ?? '' }
    });

    await waitForReady(`http://127.0.0.1:${port}/api/webspaces`); // fetch-retry loop

    await use({ baseURL: `http://127.0.0.1:${port}`, configPath });

    child.kill();                                        // + process-group cleanup
    rmSync(tmp, { recursive: true, force: true });
  }
});
```

### Pattern 2: Config-effect assertion (D-04) via real TOML parsing
**What:** Read the fixture's `configPath` after a UI action, `smol-toml.parse()` it, assert on the parsed object — never `expect(fileContents).toContain(...)`.
**When to use:** Every spec porting a UAT item whose pass condition names a file outcome (items 3, 6 explicitly; several others implicitly).
**Example:**
```typescript
import { parse } from 'smol-toml';
import { readFileSync } from 'node:fs';

const doc = parse(readFileSync(kernel.configPath, 'utf-8')) as any;
expect(doc.webspaces['new-webspace-name']).toBeDefined();
expect(Object.keys(doc.webspaces['new-webspace-name'])).toEqual([]); // D-20 empty shell
```

### Pattern 3: Delayed-response race test (UAT item 10) via manual `page.route` delay
**What:** `route.fulfill()` has no built-in delay parameter (open Playwright feature request as of this research); simulate one manually inside the handler.
**When to use:** The one spec porting UAT item 10 (chip-edit `describePlugin` race).
**Example (WebSearch-sourced, MEDIUM confidence):**
```typescript
await page.route('**/api/config/describe-plugin', async (route) => {
  if (isFirstChipRequest(route.request())) {
    await new Promise((r) => setTimeout(r, 500)); // delay only the first click's request
  }
  await route.continue();
});
// Route handlers must be registered BEFORE the UI action that triggers the request —
// registering after navigation/click risks missing the request entirely.
```

### Anti-Patterns to Avoid
- **Using Playwright's built-in `webServer` config for the kernel:** it boots one server, once, for the entire run and exposes one global `baseURL` — incompatible with D-02's per-file isolation. Use a custom fixture instead.
- **Relying on `[plugins].dir` defaulting to `"plugins"` (relative):** resolves relative to the running executable's directory, i.e. `bin/plugins/` — the real production plugin set. Every generated fixture config MUST set an absolute `plugins.dir`.
- **Omitting `[index].path` in the generated config:** defaults to `~/.local/share/topos/index.db` — the developer's REAL index. Every generated fixture config MUST set an absolute, per-run temp `index.path`.
- **Building the e2e plugin as `topos-plugin-mock2` or reusing `plugins/mock`'s binary name in any form that collides with `ExcludedPluginBinaries`:** the picker hardcodes exclusion of the exact string `"topos-plugin-mock"` (`kernel/pluginhost/discover_binaries.go:29`) — any other `topos-plugin-*` name is fine, but the plugin must still carry the `topos-plugin-` prefix (`PluginBinaryPrefix`, line 16) to be discovered at all.
- **String-matching `config.toml` content for D-04 assertions:** the phase's decisions explicitly require parsed-TOML assertions — a canonical-writer bug (e.g. reordered keys, changed quoting) must not be masked by a substring match that happens to still pass.
- **`make e2e` depending on the full `make plugins` target:** that target chains to the `signal` target, which requires `CGO_ENABLED=1` and the system `sqlcipher` library/headers — forcing a C toolchain + sqlcipher install onto every CI runner for a harness that (per D-07) never uses the Signal plugin at all. Build only `bin/topos`, `bin/plugins/topos-plugin-mock`, and the new e2e plugin binary directly in the `e2e` Makefile target.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| TOML parsing for D-04 assertions | A hand-rolled TOML-subset regex/line parser | `smol-toml` | TOML has real syntax (arrays, nested tables, inline tables, comments, multiple string-quoting rules) — regex parsing will silently mis-assert on a canonical-writer edge case exactly like `07-13-PLAN.md`'s own guard-file culture warns against. |
| Ephemeral port allocation | A fixed hardcoded port range with retry-on-EADDRINUSE loops | `node:net`'s `.listen(0)` OS-assigned-port trick (same technique `dev-guard-smoke.sh`'s `free_port()` already uses via Python) | The OS already solves "give me an unused port" atomically; a manual retry loop reintroduces the exact TOCTOU race the ephemeral-port trick exists to avoid. |
| Kernel readiness detection | A fixed `sleep(N)` before running tests | A `fetch`-retry poll against a real endpoint (`GET /api/webspaces`) until `200`, bounded by a timeout that fails loudly | `dev-guard-smoke.sh`'s own header comment states this exact house ethos: "no vacuous passes... a vacuous pass burned a session once." A sleep either wastes time (too long) or flakes (too short); a real readiness poll does neither. |
| Playwright browser/dependency install idempotency in `make e2e` | A custom "is playwright installed" shell check reading `~/.cache/ms-playwright` internals | `npx playwright install --with-deps` (idempotent — no-ops when already current) | Playwright's own CLI already tracks its cache state correctly; reimplementing that check is exactly the kind of "don't hand-roll" trap this project's own culture warns against elsewhere in `CLAUDE.md`. |

**Key insight:** every one of this phase's real "don't hand-roll" risks is in the harness's own plumbing (TOML, ports, readiness, browser install), not in application logic — the application-level behavior under test is already fully built (Phase 7); this phase is pure test infrastructure, and test infrastructure bugs (a flaky readiness poll, a mis-parsed TOML assertion) are exactly the kind of thing that erodes trust in the "fail loud, no vacuous passes" ethos this repo has enforced everywhere else (`dev-guard-smoke.sh`, the RPC allowlist, the read-only AST guards).

## Common Pitfalls

### Pitfall 1: A "hermetic" kernel silently reaches real production data
**What goes wrong:** A generated `config.toml` omits `[index].path` and/or leaves `[plugins].dir` at its default, and the spawned kernel opens/writes the developer's real `~/.local/share/topos/index.db` and/or discovers/launches the real production plugin set (including the cgo Signal plugin, which could reach a real Signal Desktop database).
**Why it happens:** `applyDefaults` (`kernel/config/config.go:157-165`) silently fills in sane-looking defaults for any key left unset — there is no load-time error for "you forgot to isolate this," because from the kernel's point of view an unset key is a perfectly normal, supported state (a real deployment's own config.toml).
**How to avoid:** The fixture's config-builder must **always** emit absolute, explicitly-generated values for `[index].path` and `[plugins].dir` — never rely on `applyDefaults` for either key in a test fixture.
**Warning signs:** A test run that appears to "work" but a subsequent `make dev` shows unexpected webspaces/sources, or sync-run history containing rows the developer never created.

### Pitfall 2: `topos serve` has no CLI flags — env var is the only lever
**What goes wrong:** A fixture attempts to pass `--port`, `--config`, or similar flags to `bin/topos serve`, which silently ignores unrecognized arguments after `serve`/`sync` (the CLI dispatch in `cmd/topos/main.go` only branches on `os.Args[1]`) or, worse, hangs waiting on stdin/behaves unpredictably.
**Why it happens:** Assuming a Go CLI binary has the conventional flag surface without reading `cmd/topos/main.go` first.
**How to avoid:** `configPath()` (`cmd/topos/main.go:51-59`) resolves `$XDG_CONFIG_HOME/topos/config.toml` (or `~/.config/topos/config.toml` if unset) — set `XDG_CONFIG_HOME` in the spawned child's `env`, and nothing else.
**Warning signs:** The kernel process boots against the developer's own real config regardless of what the test intended.

### Pitfall 3: The new e2e plugin isn't offered in the "+ New <plugin type>…" picker
**What goes wrong:** The plugin binary is built and placed in the plugins directory, but `GET /api/config/plugin-types` never lists it, so UAT item 5's two-step modal flow has nothing to select.
**Why it happens:** `DiscoverBinaries` (`kernel/pluginhost/discover_binaries.go:38-63`) filters on `strings.HasPrefix(name, PluginBinaryPrefix)` (must start with `"topos-plugin-"`) and excludes any name in `ExcludedPluginBinaries` (currently just the literal string `"topos-plugin-mock"`).
**How to avoid:** Name the new plugin's build output `topos-plugin-<anything-other-than-"mock">` — e.g. `topos-plugin-mockstrict` per the CONTEXT.md example name.
**Warning signs:** `curl .../api/config/plugin-types` (or the equivalent Playwright API assertion) doesn't include the new plugin binary name.

### Pitfall 4: The e2e plugin fails `kernel/config.Validate` because it declares the wrong connection shape
**What goes wrong:** The new plugin's `[sources.<id>]` block in a generated fixture config declares some field kernel-side validation doesn't recognize, and config load fails before the kernel even boots.
**Why it happens:** `Validate` (`kernel/config/config.go:326-368`) hard-codes exactly two accepted shapes per source: `base_url`+`token`, OR `path` — there is no generic "any custom field" escape hatch at the kernel-config layer (the kernel doesn't know a source's field *names* beyond these two fixed shapes; a plugin's own arbitrary keys live inside `WEBSPACES_SOURCE_CONFIG`'s JSON blob, but the *presence check* at config-validate time only looks at these two shapes).
**How to avoid:** Model the new plugin exactly like `plugins/signal` — declare `path` as its one required connection field (matching D-05/D-06's "a required connection field," singular), with a seeded default value the UI pre-fills, exactly mirroring `plugins/signal/main.go`'s `cfg.Path == ""` fatal-exit guard and `web/src/lib/plugin-fields.ts`'s `CONNECTION_FIELDS['topos-plugin-signal']` row shape.
**Warning signs:** `config.Load`/`LoadRaw` returns an error naming the offending source at kernel-boot time, before any HTTP request is even possible.

### Pitfall 5: `page.route()` delay registered after the triggering navigation/click
**What goes wrong:** UAT item 10's race test intercepts `describe-plugin`, but the delay never applies because the route handler was registered after the click that triggers the request already fired.
**Why it happens:** Playwright route handlers only intercept requests made *after* `page.route()` is called; a handler registered inside a `click()` callback (or after `await page.click(...)`) can lose the race against the browser's own request dispatch.
**How to avoid:** Always call `page.route(...)` before the action that triggers the intercepted request, per the WebSearch-sourced best practice (MEDIUM confidence — not project-specific, general Playwright guidance).
**Warning signs:** The race test passes even when the underlying bug (first click's stale response winning) is deliberately reintroduced — a vacuous pass.

### Pitfall 6: `make e2e` accidentally requires a C toolchain in CI
**What goes wrong:** `make e2e`'s build step depends on (or shells out to) `make plugins`, which unconditionally chains to the `signal` target (`CGO_ENABLED=1`, `-tags libsqlcipher`) — a GitHub Actions `ubuntu-latest` runner without `libsqlcipher-dev` installed fails the build entirely, even though the harness never uses the Signal plugin (D-07).
**Why it happens:** `plugins:` in the Makefile is written as one bundled target (`build` delegates to it) specifically so `dev`/`build` can't drift — but that same bundling becomes a liability for a target that deliberately wants a narrower plugin set.
**How to avoid:** `make e2e`'s own build step should invoke `go build` directly for `bin/topos`, `bin/plugins/topos-plugin-mock`, and the new e2e plugin — bypassing the `plugins` target entirely — or install `sqlcipher` as a CI step if the team prefers keeping `make plugins` as the single source of truth (a real tradeoff the planner should decide explicitly, not by accident).
**Warning signs:** CI fails on a fresh runner with a cgo/linker error mentioning `sqlcipher`/`openssl`, despite the harness itself never touching Signal.

## Code Examples

### e2e plugin skeleton (models `plugins/signal/main.go`'s required-field guard shape)
```go
// plugins/<e2e-name>/main.go — illustrative shape, not a verified snippet;
// mirrors plugins/signal/main.go's fatal pre-Serve guard exactly (see
// Pitfall 4 above for why `path`, not `base_url`/`token`, is the correct shape).
package main

import (
	"encoding/json"
	"fmt"
	"os"

	goplugin "github.com/hashicorp/go-plugin"

	"github.com/davison/topos/sdk"
)

type sourceConfig struct {
	Path string `json:"path"`
}

func main() {
	raw := os.Getenv("WEBSPACES_SOURCE_CONFIG")
	if raw == "" {
		fatal(fmt.Errorf("WEBSPACES_SOURCE_CONFIG is not set"))
	}
	var cfg sourceConfig
	if err := json.Unmarshal([]byte(raw), &cfg); err != nil {
		fatal(fmt.Errorf("parse WEBSPACES_SOURCE_CONFIG: %w", err))
	}
	if cfg.Path == "" {
		fatal(fmt.Errorf("WEBSPACES_SOURCE_CONFIG: path is empty")) // zero network requests possible past this point
	}

	goplugin.Serve(&goplugin.ServeConfig{
		HandshakeConfig: sdk.Handshake,
		Plugins: map[string]goplugin.Plugin{
			"source": &sdk.SourcePluginGRPCPlugin{Impl: NewSourcePlugin(cfg.Path)},
		},
		GRPCServer: sdk.GRPCServer,
	})
}
```

## Open Questions

1. **Should `[plugins].dir`-referenced binaries be copied or symlinked into each per-file temp directory?**
   - What we know: the fixture needs the temp plugins directory to contain exactly `topos-plugin-mock` and the new e2e plugin binary (D-07), built once by `make e2e`'s build step.
   - What's unclear: whether per-spec-file temp dirs should each get a fresh copy (safer against one test's fixture accidentally mutating shared state, slower) or a symlink back to one shared build output (faster, matches `dev-guard-smoke.sh`'s reuse of already-built `bin/plugins/topos-plugin-mock`).
   - Recommendation: symlink — the plugin binaries are read-only artifacts for the duration of the suite; nothing in this phase's scope needs a mutable per-file copy, and symlinking avoids N-way binary duplication for a 15+-instance test.

2. **Worker-level vs test-file-level fixture scope for "fresh kernel per spec file"?**
   - What we know: D-02 says "fresh kernel per spec file: each file boots its own kernel," and Playwright by default runs test files in separate worker processes when parallelized.
   - What's unclear: whether a `worker`-scoped fixture (one kernel per Playwright worker, reused across every file that worker happens to run) satisfies D-02's literal wording as well as a `test`-scoped-but-shared-within-file fixture would — Playwright's worker/file assignment is not guaranteed 1:1 unless `fullyParallel` and worker count are tuned to match file count.
   - Recommendation: use a fixture scoped to run once per test **file** via a `beforeAll`/`afterAll`-equivalent (Playwright's `test.beforeAll` hook, or a fixture with `scope: 'test'` reused across a file's tests but re-created for each new file) rather than relying on worker-process boundaries as a proxy for file boundaries — left as an explicit Task 1 design decision for the plan, not resolved definitively here.
