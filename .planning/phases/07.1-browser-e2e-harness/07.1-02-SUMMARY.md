## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `kernel/pluginhost.DiscoverBinaries` did not discover symlinked plugin binaries**
- **Found during:** Task 3, running `web/e2e/specs/mockstrict-discovery.spec.ts` for the first time
- **Issue:** `GET /api/config/plugin-types` returned an empty list even though the fixture's temp plugins directory genuinely held `topos-plugin-mock` and `topos-plugin-mockstrict`. Root cause: `DiscoverBinaries` filtered entries with `e.Type().IsRegular()`, and `os.DirEntry.Type()` reflects an `Lstat` — it is `os.ModeSymlink`, never `IsRegular()`, for a symlink, even when the link target is a plain executable file. `web/e2e/fixtures/plugin-binaries.ts` (07.1-01) populates its temp plugins directory entirely via `symlinkSync`, so every fixture-driven spec that exercises plugin-type discovery (not just launching an already-configured source, which uses a different code path and was unaffected) was silently broken. This plan's own `key_links` named the exact chain ("plugin-binaries fixture symlink -> kernel plugin discovery") as something that must not break.
- **Fix:** Switched `DiscoverBinaries` to `os.Stat` (follows the link) instead of the `os.DirEntry`'s own `Type()`. A broken symlink or a symlink-to-directory is skipped exactly like any other non-regular entry — never surfaced as a discovery error.
- **Files modified:** `kernel/pluginhost/discover_binaries.go`, `kernel/pluginhost/discover_binaries_test.go` (three new regression tests: symlinked regular file discovered, broken symlink skipped without error, symlink-to-directory excluded)
- **Verification:** `go test ./kernel/pluginhost/...` (all cases, including the three new ones, plus the three pre-existing cases) — green; `go test ./...` at the repo root — green; the discovery spec's API-level assertion — green after the fix
- **Committed in:** `087a996` (Task 3 commit)
