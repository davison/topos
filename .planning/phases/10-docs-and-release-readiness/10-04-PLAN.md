Close the milestone-sync gap and write the one page that explains this
repository's release process.

Purpose: Success criterion 5. GSD has no native mechanism for keeping GitHub
milestones in step with `.planning/` milestones, so the repository carries its
own: a committed, idempotent `gh api` wrapper plus a written process describing
when to run it. `docs/releasing.md` additionally becomes the home for what Plan
10-01 built — the tag-triggered release path, the change-gated nightly, and the
recorded answer to the Signal-binary question — so those decisions live in a
document a maintainer will actually find rather than only in a plan SUMMARY.

Output: `scripts/sync-milestones.sh` and `docs/releasing.md`.

The starting state is not a clean slate and the script must be written against
the real one: milestone `#1` titled `v1.0` already exists on `davison/topos`,
open, with an empty description, and `.planning/STATE.md`'s frontmatter records
`milestone: v1.0` — the titles already match. A script that assumes it is
creating milestones from scratch will either fail on a duplicate-title
validation error or create a second, differently-numbered `v1.0`.

Direction of authority is one-way and must stay that way: `.planning/` is the
source of truth, GitHub milestones are a mirror. The script writes to GitHub and
reads from `.planning/`; it never writes to `.planning/` and never treats a
GitHub-side edit as authoritative.
</objective>

Create `scripts/sync-milestones.sh`, executable, following
`scripts/signal-readonly-smoke.sh`'s header and boilerplate conventions exactly.

Header comment block, before any code: what the script does (reconciles one
GitHub repository milestone with `.planning/`'s milestone state), the direction
of authority (`.planning/` is the source of truth; this script only ever writes
to GitHub and never the reverse), when it is intended to be run (manually at
milestone boundaries, paired with milestone-open and milestone-close events —
deliberately not on a schedule and deliberately not as a GitHub Action reacting
to `.planning/` commits, because milestone boundaries are infrequent
human-triggered events), the two positional arguments and their accepted values,
the `TOPOS_REPO` environment override and its default, and the two safety
guarantees: the script is idempotent and safe to re-run, and it never deletes a
milestone.

Then `set -euo pipefail` and the `SCRIPT_DIR`/`REPO_ROOT` resolution idiom from
the analog, retained even where not strictly needed so the script can read
`.planning/` later without restructuring.

Arguments: first positional is the milestone title, second is the action,
accepting exactly `open` or `close`. Validate both before touching the network:
a missing or empty title, or an action that is neither accepted value, exits
non-zero with a usage line naming what was actually received. Resolve the target
repository from `TOPOS_REPO` defaulting to `davison/topos`, and echo the
resolved repository and the intended operation before performing any mutation,
so a mis-targeted run is visible in the output rather than discovered afterwards.

Core logic, in this order. Look the milestone up by exact title across all
states, extracting its number. If no milestone with that title exists: create it
with the given title and the given state. If one exists: patch that milestone
number's state to the requested action, reporting the number it found. Either
way, print what was done and the resulting milestone number and state. The
lookup-before-write is the idempotency mechanism and is not optional — an
unconditional create against the already-existing `v1.0` returns a
duplicate-title validation error.

Implement no delete path at all. `.planning/` closes milestones and never
deletes them; a delete would orphan every issue assigned to the milestone, and
the capability being absent from the script is the mitigation.

Make the script executable, matching the mode of the existing scripts in that
directory.

release or crossing a milestone boundary. Four sections.

**Milestones.** State the one-way authority rule first: `.planning/` is the
source of truth for milestone state and GitHub milestones are a mirror kept in
step by an explicit step, never the reverse — a milestone edited in the GitHub
UI will be overwritten on the next sync. Explain that GSD has no native
mechanism for this, which is why the repository carries its own. Then the
process: at a milestone boundary, run `scripts/sync-milestones.sh` with the
milestone title from `.planning/STATE.md`'s frontmatter and the appropriate
action, once when a milestone opens and once when it closes. Give both
invocations concretely. State the two guarantees a reader needs before trusting
it: it is idempotent, and it has no delete path. Note the real current state as
the worked example — milestone `v1.0` already exists as number 1 and the script
reconciles it rather than creating a second one.

**Cutting a release.** The trigger is pushing a tag matching the version-tag
pattern the release workflow watches; nothing in CI creates that tag, a human
does, deliberately, at milestone-close time. Give the sequence: confirm the
portable gate is green, push the tag, watch the run, verify the published
assets. Name what the resulting release contains — the kernel binary, the
operator-facing plugin binaries, and a `checksums.txt` — and state the
verification a downloader performs with it. State that the fixture plugin
binaries are deliberately not published, because they are contract-reference and
harness fixtures rather than installable sources, matching the kernel's own
exclusion of them from the operator's plugin picker.

change gate in terms of the mechanism actually built: a moving `nightly` git tag

what makes "only when code has changed" true. Note the practical consequence: a

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator's shell → GitHub repository metadata | The sync script mutates repository milestones with the operator's own `gh` credentials |
| `.planning/` → GitHub milestones | One-way mirror; a reversal of direction would make an unreviewed GitHub-side edit authoritative over the project's planning state |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-17 | Tampering | An unconditional milestone create clobbering or duplicating the pre-existing `v1.0` milestone | medium | mitigate | Lookup-by-title across all states before deciding create-versus-patch; verified by running the script twice against the real milestone and asserting exactly one `v1.0` still exists at number 1. |
| T-10-18 | Tampering | A milestone delete orphaning every issue assigned to it | high | mitigate | The script has no delete path at all — the capability is absent rather than guarded, asserted by a gate over the script source. |
| T-10-19 | Elevation of Privilege | Script run against an unintended repository | medium | mitigate | Target repository is pinned in-script, overridable only through one named environment variable, and echoed alongside the intended operation before any mutation is performed. |
| T-10-20 | Repudiation | The Signal-artifact decision surviving only in a plan SUMMARY, so a later maintainer silently reverses it | medium | mitigate | `docs/releasing.md` records it as a dated decision with its reason, in the document a maintainer editing the workflows would read. |
| T-10-21 | Information Disclosure | Credentials leaking through the sync script | low | mitigate | The script stores no token and reads no secret file — it delegates authentication entirely to the already-authenticated `gh` CLI. |
</threat_model>
