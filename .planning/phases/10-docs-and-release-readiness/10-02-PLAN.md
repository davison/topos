<objective>
Create `docs/plugins/` — a template plus one operator-facing page for each of the
five real source plugins.

Purpose: Success criterion 3. Today a person configuring, say, Proton has to
read a 460-line `config.example.toml` and infer which parts apply to them, or
find `plugins/signal/README.md` and notice that no equivalent exists for any
other plugin. One page per plugin, all the same shape, closes that.

Output: `docs/plugins/_template.md`, `docs/plugins/README.md`, and five pages —
`paperless.md`, `silverbullet.md`, `proton.md`, `signal.md`, `whatsapp.md`.

Scope note: exactly five pages. `mock` and `mockstrict` do not get one — they are
test fixtures, not installable sources. `mock` is the PLUG-05 reference plugin
whose audience is plugin *authors*, served by `docs/plugin-contract.md`;
`mockstrict` is built only by the `e2e` Makefile target. Both are excluded from
the operator's picker catalog by `kernel/pluginhost.ExcludedPluginBinaries`, and
these pages follow that same operator/author split.

The single hardest discipline here is link-don't-duplicate. `config.example.toml`
and `docs/plugin-contract.md` are already excellent and are edited every phase.
A page that copies their content will be wrong within one phase and nobody will
notice. Every page summarises and points; none reproduces.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Documentation → operator's config file | An operator copy-pastes a documented config block into their own `config.toml`; whatever the doc models, they will reproduce |
| Documentation → operator's trust decisions | A doc that offers an insecure shortcut for a self-signed instance becomes the path of least resistance |
