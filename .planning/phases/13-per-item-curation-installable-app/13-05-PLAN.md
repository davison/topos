<objective>
Move trusted-tier status off "which directory did this resolve from" and onto "was this binary built together with this kernel", and make an unverifiable trusted-directory binary refuse to run.

Purpose: Phase 11 shipped a filesystem-location proxy for repo provenance. Three paths bypass it — editing `plugins.dir` in config, dropping a binary into the trusted directory, and shadowing a pinned external plugin with a same-named trusted-directory file. A link-time manifest of the plugin hashes the kernel was built alongside closes all three at once, with no network call at load time.
Output: the manifest mechanism and its generator, the reordered build recipes that produce it, the launch-time verification gate with a named refuse-to-load failure, and the structured shadowing advisory the UI plan will render.
</objective>

## Requirement traceability

This plan and 13-06 implement the **folded todo** `.planning/todos/pending/2026-08-13-plugin-trust-tier-is-directory-location-not-provenance.md`, which has no requirement ID of its own. The `requirements` field names **PLUG-07** deliberately and honestly: PLUG-07 is the shipped requirement "kernel derives a plugin's trusted/untrusted status from provenance… never from anything the plugin declares about itself", and the folded todo is the finding that Phase 11 delivered only a filesystem-location *proxy* for the trusted half of it. These two plans close that gap, so PLUG-07 is the requirement they strengthen. The phase's own four requirement IDs (KERN-09, KERN-10, UI-13, UI-14) are carried by plans 13-01 through 13-04.

## Planner decisions recorded for this phase

- **PD-03** — The manifest is embedded via `go build -ldflags "-X github.com/davison/topos/kernel/pluginhost.buildManifest=<spec>"` against a committed, default-empty package variable — **not** a generated `.go` source file. 13-RESEARCH.md's Pattern 4 proposed a generated, git-ignored `manifest_generated.go`; that shape fails on this repo's own gates: a git-ignored generated file makes `go build ./...` fail on a clean checkout (which is exactly what `make test-portable` and CI run), and a committed one makes every build dirty the working tree with machine-local hashes. `-ldflags -X` is literally the "link time" D-12 asks for, needs no file, and leaves `go build ./...` compiling unchanged.
- **PD-04** — A kernel with no manifest embedded (a bare `go build`, or a build recipe that skipped the generator) refuses every trusted-tier launch with `manifest_unverified` and logs it by name. There is deliberately no "no manifest means dev build, trust the directory" fallback: a silent downgrade of a security control is exactly what this project's fail-loudly-by-name convention forbids, and every supported build path (`make build`, `make build-portable`, `make dev`, `make e2e`) generates one.
- **PD-05** (named deviation from 13-UI-SPEC.md's transport sketch) — The D-14 shadowing state is transported on a **new sibling field `launch_advisory`** on `GET /api/sources`, not as a `launch_failure` value. `launch_failure` is published in `docs/api.md` and in `kernel/httpapi/sources.go`'s own doc comment as "the CLOSED-VOCABULARY reason this instance never launched at all"; a shadowed source *did* launch, so putting `shadowed` there would contradict shipped documentation and break the SPA's remedial-action gating, which keys on that field alone. The rendered outcome 13-UI-SPEC.md E6 specifies — warning-tone dot, that exact tooltip sentence, routed through the existing `isAdvisoryOnly`/`healthTone` precedence chain — is delivered unchanged; only the wire field differs from the spec's prose sketch.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| filesystem → kernel launch gate | Any binary present in a configured plugin directory is a candidate for execution as a subprocess with full OS access |
| config file / `PUT /api/config` → plugin directory resolution | An operator-editable value chooses which directories are consulted |
| build pipeline → kernel binary | The manifest's contents are decided at build time and cannot be changed afterwards without rebuilding |

| T-13-06 | Elevation of Privilege | file drop into the trusted plugin directory | critical | mitigate | The launch gate re-hashes every trusted-tier binary and refuses to construct a subprocess when it is absent from, or does not match, the link-time manifest (D-12/D-13).
