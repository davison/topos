# Phase 13 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Design system already fully established (Phases 1–12); this phase introduces zero new spacing values, zero new type sizes/weights, and zero new palette hex values.** It does introduce genuinely new interaction surfaces — desktop multi-select on the stream, a floating bulk-action bar, the app's first toast primitive (undo + error + update feedback), an excluded-items view toggle, a single-item exclude/include control on the detail pane, two new named trust-failure states on the existing source chip, and the PWA manifest/icon/update contract. Every one of these extends an already-load-bearing pattern from Phase 1–12 rather than inventing a new visual language — see "New UI Elements" for each, and "Explicit Reuse" for what needs nothing new at all.

**Accent reserved for (cumulative list, Phase 1–13):** CTAs (`Add source`, `Save as filter`, and now the action bar's primary **Exclude**/**Include** button — see rationale below), links, focus rings, the currently-open stream row's left-border indicator, the selected/active filter chip, checkbox checked-fill (Phase 12's `recursive` checkbox, and now the bulk-select checkbox's checked-fill — same shadcn-svelte recipe, not a new category), and the excluded-view toggle's pressed/active state (mirrors the selected-chip precedent). **No other additions this phase.**

**Why Exclude/Include is accent, not destructive:** Exclude is instant and trivially reversible (D-02: undo toast + a durable excluded-items view — never a one-way door), unlike this app's actual destructive actions (`Remove from this webspace`, which *does* carry `variant="destructive"` because removing a source has no in-app undo). Painting Exclude red would misrepresent it as more dangerous than it is and would dilute the destructive token's meaning everywhere else it appears in this app. Exclude/Include are therefore styled as the ordinary primary CTA of the floating bar — the same treatment `Add source` already gets.

## New UI Elements

### E1 — Multi-select on `StreamRow.svelte` (desktop, pointer-input only)

**What's new:** Two props, `bulkSelected: boolean` and `bulkModeActive: boolean` (true whenever the selection set is non-empty across the whole stream), plus an `onbulktoggle: (id: string, mode: 'toggle' | 'range') => void` callback. `StreamRow`'s existing `onselect`/`selected` props (which drive "this item is open in the detail pane," the left-border accent indicator) are **unchanged and orthogonal** — a row can be simultaneously the open item and bulk-selected; the two states render additively, never conflicting, because they use different visual channels (border vs. fill+checkbox).

**Trigger rule (click-handler branch, replacing the single unconditional `onclick={onselect}`):**
- **Plain click** (no modifier): unchanged — calls `onselect`, opens the detail pane. Does **not** clear an existing bulk selection (D-01 lists only Esc and the action bar's own Clear as what empties it — an unrelated plain click on another row is not a clearing action).
- **Ctrl/Cmd-click**: toggles this row's bulk-selected state, does **not** call `onselect`. Becomes the new anchor for a subsequent shift-click.
- **Shift-click**: selects the contiguous range between the current anchor (the most recently ctrl-clicked row, or the currently-open item if no ctrl-click has happened yet this session, or the first row if neither exists) and this row, inclusive — **replacing** the current selection with that range (matches the simplest native file-manager convention, not an additive union). Does not call `onselect`.

**Visual (bulk-selected state):**
- Row surface gains `bg-secondary/60` (new usage of the existing `--secondary` token — see Color table) — deliberately **not** the accent color, so it can never be mistaken for the "currently open" left-border indicator when both happen to coincide on one row.
- A checkbox (shadcn-svelte's stock `Checkbox`, same primitive Phase 12's F1 already introduced) renders in a leading `size-9` slot before the thumbnail, `size-4` control centered inside it, checked-fill uses `--primary` (existing checkbox recipe, no override).
- **Reveal rule:** the checkbox slot is invisible (`opacity-0`) at rest and becomes visible on row hover/focus **or** whenever `bulkModeActive` is true (any item anywhere in the stream is selected) — this is the exact same hover/focus-revealed-affordance discipline `SourceChip.svelte`'s own overflow menu already establishes in this codebase, applied to a new control rather than invented fresh.
- Entirely `max-md:hidden`, matching the thumbnail's own existing breakpoint — multi-select is desktop/pointer-input only. Below 768px, the single-item exclude/include button in the detail pane (E5) is the only exclude path; this is an accepted, explicit limitation (see UI Considerations), not an oversight, and mirrors the phase's own UI-14 stance that a capability can be honestly desktop-scoped where the interaction model does not translate to touch.

### E2 — `SelectionActionBar.svelte` (new component) — the floating bulk-action bar

**Where:** Rendered by the stream route whenever `bulkModeActive` is true, positioned `sticky bottom-4` **within the stream pane's own scroll container** (not viewport-fixed) — so it never visually strays into the detail pane's region, consistent with the app's existing "each pane is its own independently-scrolled region" discipline.

**Composition, left to right, one row, `bg-popover` surface, `border border-border`, `rounded-lg`, `shadow-lg`, `px-4 py-3`, `gap-3`:**
1. Count label: `{N} selected` (Label role, `text-foreground`).
2. A `Separator` (existing shadcn primitive, vertical, `h-4`) — visually groups the count from the actions, matching `FilterChip`'s own internal-divider discipline.
3. Primary action button (`Button size="sm"`, accent/primary-styled — see Color rationale): **Exclude** in the normal stream, **Include** when viewing the excluded bucket (E4) — same component, label driven by which view is active.
4. Clear button (`Button variant="ghost" size="sm"`): **Clear**.

**Behavior:**
- Esc (global keydown while any row has focus, or while the bar itself has focus) and the Clear button both empty the selection and dismiss the bar — the only two dismissal paths, per D-01.
- Clicking the primary action fires the bulk write immediately (D-02: no confirm dialog). Both buttons disable for the duration of the in-flight request (prevents a double-fire double-submit); on success the bar dismisses and the selection clears; on failure the bar **stays** (selection is preserved so the user can retry) and a destructive toast reports the failure (see E3).
- Never renders while the selection is empty — appearing and disappearing is the entire signal that selection mode is active or not, no separate mode indicator needed.

### E3 — Toast layer (Sonner) — undo, write-failure, and PWA-update feedback

**What's new:** The app's first toast primitive, mounted once at the root layout (`+layout.svelte`), `bg-popover`/`border-border` themed to match this app's own tokens (not the library's default light theme) — position `bottom-right`, matching where transient status is conventionally least likely to occlude the stream or detail pane.

**Three copy shapes, one primitive:**
1. **Undo toast** (D-02/D-08, exclude or include, single or bulk): fires immediately on a successful write. Body: `Excluded {N} item` / `Excluded {N} items` (or `Included …`, mirrored) — pluralized, one shared helper for both the single-item detail-pane action and the bulk action-bar path, so the two can never drift in wording. Carries one action: **Undo** (with a small `Undo2` icon), which re-issues the mirror write (include if the toast was an exclude, and vice versa) for the exact same item id(s). Auto-dismisses after 5 seconds if not acted on; the excluded-items view (E4) remains the durable, always-available reversal path after that (D-02's own framing — the toast is a convenience, not the only way back).
2. **Write-failure toast** (destructive variant, `text-destructive`): `Couldn't exclude {N} item — try again.` / `Couldn't exclude {N} items — try again.` (or `include`, mirrored) — matches this app's existing terse "Couldn't {verb} — {next step}" failure-copy convention (`Couldn't open`, `Couldn't load this item`). No action button; the action bar itself (still visible, buttons re-enabled) is the retry path.
3. **PWA update toast** (informational, default/neutral variant, no destructive/accent tone): fires once, automatically, after the ServiceWorker has silently swapped in a new build and reloaded the page (E8's `autoUpdate` strategy). Body: `topos updated to the latest version.` No action button — the reload has already happened by the time this renders; the toast exists purely so an unexpected page refresh is explained rather than silently jarring. Auto-dismisses after 4 seconds.

### E4 — Excluded-items view toggle

**Where:** A `Button variant="outline" size="sm"` in `WebspaceHeader.svelte`'s existing trailing reserved group, alongside `Refresh all` (not merged into the per-source chip row, which answers a different question — "which sources am I looking at" — from this toggle's "which bucket of this webspace am I looking at").

**Visibility (D-06):** renders **only** when the webspace's excluded count is greater than zero. A webspace with zero exclusions shows nothing here — looks exactly like today, no permanently-reserved empty slot.

**Copy:** `Excluded ({count})`, e.g. `Excluded (7)` — count sourced from the same response that drives the stream fetch (no separate count-only round trip).

**States:**
- **At rest (viewing the normal stream):** `Button variant="outline"`, unchanged neutral chrome.
- **Pressed (viewing the excluded bucket):** `aria-pressed="true"`, accent-tinted border/text (mirrors the existing selected-chip precedent — the same visual language `SourceChip`'s filter-selected state already uses, not a new toggle style).

**Behavior:** clicking flips the stream's own `view` state between `included` (default) and `excluded` — reusing `StreamList`/`StreamRow`/`DetailPane`/the multi-select machinery (E1/E2) **wholesale** (D-05: no modal, no new route). Ordering stays chronological with the same date markers (D-07). If the count reaches zero while the excluded view is showing (the last item is un-excluded, and its undo window lapses or is never used), the view **auto-flips back** to the normal stream and the toggle disappears — there is no sustained "excluded view, but empty" state to design copy for; see UI Considerations.

### E5 — `DetailPane.svelte` single-item exclude/include button

**Where:** Alongside `OpenInSource` in both header positions it already occupies — the desktop header row (`max-md:hidden`, icon + label, `Button variant="ghost" size="sm"`) and the mobile slim takeover bar (icon-only, `size-11` touch target, trailing `OpenInSource`'s own icon-only instance — same row, same sizing precedent).

**States:**
- Item not excluded: `EyeOff` icon, label `Exclude from webspace`.
- Item excluded (only reachable while viewing the excluded bucket, E4): `Eye` icon, label `Include in webspace`.

**Behavior:** instant, no confirm (D-02) — fires the same single-item write E2's bulk path uses (N=1), same undo-toast copy path (E3), same optimistic-removal-then-possible-auto-flip behavior as E4 if this was the last excluded item.

### E6 — Trust-tier hardening: two new named chip states

Both extend `SourceChip.svelte`'s existing `isPinMismatch`-style branch (`source.launch_failure === 'pin_mismatch'`) verbatim in shape — a new `launch_failure` value drives an analogous tooltip string and health-dot tone, no new component, no new visual pattern.

**`manifest_unverified` (D-12/D-13 — a trusted-directory binary that fails build-manifest verification, refuses to load):**
- Health dot: destructive tone (same as `pin_mismatch` today).
- Tooltip: `{display_name} — binary not in the trusted build manifest` (same sentence shape as the existing `{display_name} — binary changed since it was trusted`).
- The source cannot sync (the binary never launched) — its stream rows degrade exactly as any other launch-failed source already does today (existing "unreachable"/sync-failed treatment, no new copy needed there).
- Remedy affordance: reuses the **existing** external-tier consent + pin flow verbatim (D-13 — "the explicit consent + pin flow is the only path to running it") — no new dialog, no new copy beyond the tooltip above; the existing untrusted-add interstitial (11-UI-SPEC.md E1–E5) is what the user is routed through to accept and pin this binary as external-tier.

**`shadowed` (D-14 — a same-named trusted-directory binary is shadowing a pinned external plugin, previously log-only):**
- Health dot: **warning** tone (not destructive — the pinned external plugin the user actually consented to may still be the one running; this is an ambiguity advisory, not a failure), mirroring Phase 12's own zero-match warning-tone precedent.
- Tooltip: `{display_name} — a same-named trusted-directory binary is shadowing this pinned plugin`.
- Consulted through the same `isAdvisoryOnly`/`healthTone` precedence chain (`format.ts`) Phase 12's CR-01 fix established as the one rule every future health-adjacent surface must defer to — this state is a new branch feeding that existing chain, not a parallel gate.

### E8 — PWA update flow and "kernel not running" shell state

**Update flow (UI-13's "never stale" criterion):** `registerType: 'autoUpdate'` (matches 13-RESEARCH.md's primary recommendation) — the ServiceWorker silently activates a new build and triggers a reload with no user action required, followed by the informational toast (E3.3) explaining what just happened. This is the stronger of the two "never stale" guarantees discussed in research (a `prompt`-based flow can sit un-acted-on indefinitely in a long-lived installed-app session); the toast exists specifically to soften the one real cost of that choice — an unannounced reload — without weakening the guarantee itself.

**"Kernel not running" (installed app launched while the kernel process is down):** **Explicit reuse, not new UI.** `StreamError.svelte`'s existing copy — `Couldn't load this webspace` / `The topos service didn't respond — check that it's running, then retry.` with a `Retry` button — already states exactly the right thing for this case and needs no new component or copy. The only new requirement is a build-time one (not a visual one): the ServiceWorker's precache must cover the app shell (HTML/JS/CSS/icons) so this component can render at all when the kernel's HTTP server isn't listening — verified during implementation, not a design decision.

| zero-one-many | E4 toggle count | ✅ covered | `Excluded ({count})` renders the live count directly — 1 vs. many is not specially pluralized in the label itself (a plain integer reads unambiguously either way, unlike the toast copy which needed pluralization for grammatical correctness). |

| partial | E5 (item excluded but viewed from the normal stream — structurally unreachable) | ✅ covered | An excluded item never appears in the normal stream (D-03: exclusion is the final filter tier everywhere) — the detail pane can only ever be showing an excluded item while the excluded view (E4) is active, so the "Include" branch has exactly one reachable context, not an ambiguous one. |
| loading | E6 (manifest verification, launch-time) | ✅ covered | Verification happens before the source ever appears with a health state — a source that fails it never transitions through a visible "checking…" state, it simply surfaces already in the `manifest_unverified` state (same launch-gate timing as the existing `pin_mismatch` state). |

| error (advisory) | E6 (`shadowed`) | ✅ covered | Warning-tone dot + named tooltip, deliberately distinct from destructive — per E6's spec and the `isAdvisoryOnly` precedence chain. |
| zero-one-many | E6 (multiple sources simultaneously affected by either state) | ✅ covered | Each chip renders its own state independently — the mechanism is per-source, identical to how `pin_mismatch` already scales across multiple affected chips today. |
| long-text | E6 tooltip (`display_name` substituted in) | ✅ covered | Native `title`/`TooltipContent` wrapping behavior, same as every other chip tooltip in this app — no fixed-width truncation concern. |
