<objective>
Close the PLUGIN half of `08-VERIFICATION.md`'s new regression (gap **G-08-5**), which is also
`08-REVIEW.md`'s never-fixed findings **WR-01** and **WR-02** — the review pass committed at
`e748545` has no `08-REVIEW-FIX.md` and no commit after it touches `connect.go`.

Plan 08-11 added a bounded 15-second wait for a real `*events.Connected` on
`startBackgroundClient`'s already-paired success path, deliberately *before* `goplugin.Serve`, so
that the go-plugin handshake would mean "ready". The blast radius was not traced: the handshake is
what `kernel/pluginhost.launch` blocks on, `Discover`/`Reconcile` launch sources sequentially, and
`cmd/topos/main.go` does not reach `http.ListenAndServe` until `NewSupervisor` returns. So every
kernel restart with an already-linked WhatsApp source pays up to 15 seconds before ANY source's
routes exist (WR-01), and every re-link's resume closure pays it again while holding the kernel's
supervisor mutex (the more severe manifestation `08-VERIFICATION.md` found independently).

This plan takes the review's own second suggested direction: move the login wait off the
synchronous launch path entirely, and lean on the kernel-side absorber that 08-12 built for exactly
this window. That is safe because G-08-4's user-visible symptom is closed by two *other* legs that
this plan leaves completely intact — `healthStateConnecting` being the Go zero value plus the
explicit pre-dial assignment (so a connecting instance can never emit the false pairing
instruction), and `Scheduler.firstRefresh`'s 2s/5s bounded retry (so a Match that lands inside the
connecting window is superseded by an ok sync run seconds later, not pinned for the 15-minute
interval). The blocking wait was the third, belt-and-braces leg; retiring it costs a stricter
reading of "handshake means ready" and buys back the availability of every other source.

This plan therefore **deliberately supersedes `08-11-PLAN.md`'s `must_haves.truths[2]`** ("the
go-plugin handshake genuinely means ready in the normal case"). That guarantee is retired, on
purpose, and replaced by the pair of guarantees above. Stating it here rather than letting a later
verification discover the contradiction is the point.

Purpose: make a WhatsApp plugin launch cost what every other plugin launch costs, and finish
cleaning up after the waiter that was introduced with it.

Output: a non-blocking serve-mode login wait with symmetric handler cleanup, a structural guard
that keeps it off the launch path, and three corrected doc comments that would otherwise assert
things this change makes false.

Scope note — Playwright: this plan touches no frontend file and changes no route, response shape
or user-visible copy. The one artifact under `.planning/` it edits is a planning document, not
shipped UI. The standing "any UI-touching phase extends the Playwright e2e suite" rule
(`.claude/CLAUDE.md`, `docs/testing.md`) therefore adds no new spec here; the existing suite must
still pass unchanged, which plan 08-15 runs as this wave's gate. Recorded rather than assumed.

Scope note — COVERAGE.md: this plan integrates no new external API or SDK surface — it removes a
call site's blocking position, adds a `RemoveEventHandler` call that the phase's existing
`connect` capability row already covers, and adds no whatsmeow capability. The phase's
`COVERAGE.md` matrix is unchanged and deliberately left as-is.
