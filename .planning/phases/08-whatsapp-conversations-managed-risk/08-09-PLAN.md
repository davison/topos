<objective>
Close the kernel half of `08-UAT.md` gap G-08-3: after a real-device WhatsApp
pairing, opening a webspace surfaced
`whatsapp: match against source "whatsapp": rpc error: code = Canceled desc =
grpc: the client connection is closing`.

`supervisor.SuspendInstance` — the seam every link session on the named-instance
/ Re-link path (D-03) goes through — kills the named instance's go-plugin client
via `Host.Reconcile` → `Plugin.Kill()` (a local gRPC `ClientConn.Close`) while
deliberately leaving the scheduler generation running and the `syncer.Coordinator`
un-rebuilt, and the resume closure it returns relaunches the instance in the
plugin host *only*. Because `syncer.Coordinator` captures its `*pluginhost.Plugin`
handles once at construction and `Host.Reconcile` creates brand new `*Plugin`
values, every sync path from the moment of suspension onward — scheduled tick,
`POST /api/sources/{name}/refresh`, eager resync — issues `Match` through the
killed client and fails with grpc-go's `ErrClientConnClosing`. Only a config save
(`Apply` → `commitGeneration`) or a kernel restart heals it, and a re-link never
saves config, so a *successful* pairing leaves that source's sync broken
indefinitely with the error pinned as its latest `sync_runs` row.

The codebase already owns the correct seam and documents it at length:
`commitGeneration`'s own comment states that `s.host`, `s.coord`, `s.cfg` and the
running scheduler generation must always reflect one and the same generation, and
`Supervisor.Refresh`'s comment states that a coordinator has no in-place update
seam. `SuspendInstance` is the one mutation of the launched plugin set that opted
out of that contract. This plan puts it back inside it, and fixes the two latent
siblings that opting back in makes load-bearing: an uncancellable background
resync that `stopScheduler` would otherwise be able to block on, and resume calls
that ride the HTTP request's own context.

Purpose: a re-link must leave the source syncing, not silently dead until the
next restart — success criterion 4's "every other source is unaffected" read
back at the source the session actually touched.
Output: a generation-correct suspend/resume, cancellable background syncs,
detached lifecycle contexts, and the regression test whose absence
(`suspend_test.go` asserts host membership and nothing else) let this ship.
</objective>

**The fix — `SuspendInstance` (supervisor.go).** Make the suspension itself a
generation change, using the three functions the file already owns and the

**The fix.** Give each scheduler generation ownership of the background syncs
dispatched into it.

Add two fields alongside the existing `cancel` and `done` generation fields on
`Supervisor`: the generation's own context, and a wait group for goroutines
dispatched against that generation. Document them in the struct as
generation-scoped — replaced wholesale by `startScheduler`, drained by
`stopScheduler` — under the same "caller must hold s.mu" convention the
neighbouring fields already state.

In `startScheduler`, store the derived context and a fresh wait group into those
fields alongside `s.cancel` and `s.done`.

In `stopScheduler`, after the existing wait on the generation's `done` channel,
also wait on the generation's wait group. Ordering matters and must be commented:
`s.cancel()` has already fired by that point, so every tracked goroutine's
context is already done and the wait is bounded by how fast an in-flight `Match`

the pre-`startScheduler` state, exactly as the existing code guards `s.cancel`
and `s.done`.

In `Apply`'s eager-resync dispatch, replace the detached background context with
the generation's context, and register each dispatched goroutine on the
generation's wait group (add before the `go`, done inside it). Read both values
into locals immediately before the loop, next to the existing coordinator
capture — they must be re-read there because `commitGeneration` has already run
by that point and installed a *new* generation, which is exactly the one these
goroutines belong to.

Extend that dispatch's comment with the consequence: a resync cancelled by the
next generation change is not work lost, because every fresh generation's
`Scheduler.Run` fires each configured source's first refresh immediately anyway —
so the cancellation costs at most a duplicate that single-flight would have
coalesced.

Change nothing else about the dispatch: the match-only-edit condition, the
suspended-instance skip (WR-02), and the byte-identical-source comparison all

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → kernel link endpoints | An HTTP request drives a real subprocess reconcile and a scheduler-generation rebuild; the request can vanish at any moment |

- **Live-falsification path not exercised.** The debug session documented a live
  repro (suspend a mock instance on a dev kernel, resume, refresh, observe the
  exact error, then heal it with any config save). This plan replaces that with a
  hermetic Go test driving the identical path against real launched mock plugin
  subprocesses — stronger as regression armor and reproducible in CI. No
  `<human-check>` is requested: unlike `08-08`, every layer here is reachable
  from a Go test, and the user-visible confirmation belongs to the phase's UAT
  re-run of test 3, not to this plan.
