<objective>
The final gate for this gap-closure wave, and for the two human items `08-VERIFICATION.md` leaves
open.

Plans 08-13 and 08-14 close gap G-08-5 from opposite sides — the kernel stops making every source's
routes wait on a plugin launch, and the WhatsApp plugin stops making its launch slow. Neither can
be confirmed against a real device by any automated harness in this repo: `topos-plugin-whatsapp`
is structurally excluded from the Playwright harness's plugin set, and a live QR scan needs a
phone. `docs/testing.md` already records "a real pairing against a real WhatsApp account" as one of
three permanently manual items, for exactly this reason.

This plan therefore does two things and changes no file: it runs every automated gate the
repository has, and then puts a human in front of a real re-link with a second, unrelated source
open beside it — which is the only way to observe the thing phase success criterion 4 actually
promises.

It also discharges, in the same sitting, the item carried forward from the PREVIOUS verification
cycle (`08-UAT.md`'s still-open real-device re-test of the resume/re-link flow), which has now
survived two verification passes unperformed.

Purpose: convert "the code says every other source is unaffected" into "a person watched every
other source stay unaffected".

Output: `08-15-SUMMARY.md`, carrying the four gates' output and the human's verbatim observations.

Scope note — Playwright: this wave adds no new spec, a decision recorded in both 08-13 and 08-14
because neither plan changes a component, a route, a response shape or user-visible copy. Task 1
below is what makes that decision falsifiable rather than merely asserted: if `make e2e` regresses,
the "no UI-visible change" claim was wrong and the decision must be revisited before this phase can
pass.
</objective>

  <what-built>
    Plan 08-13 moved the supervisor's reader path (`Host()`/`Coordinator()`, and through them every
    source's item-fetch, health-probe and manual-refresh route) off the mutation lock that a
    re-link's resume closure holds across a plugin subprocess relaunch, and made
    `pluginhost.Host` internally synchronised so those reads are race-free. Plan 08-14 moved the
    WhatsApp plugin's bounded serve-mode login wait off the synchronous launch path onto its own
    goroutine and retired the waiter's event handler on both dial outcomes, so an already-linked
    instance's launch no longer performs a blocking network wait before the go-plugin handshake.

    Together these mean: a real re-link's completion should no longer freeze anything, and kernel
    start with an already-linked WhatsApp source should no longer stall before the UI is reachable.
    Every Go-level and browser-level gate for this is green (Task 1), but the felt behaviour on a
    live account has never been observed — and the previous verification cycle's own real-device
    item is still open, unperformed across two passes.
  </what-built>
  <how-to-verify>
    Run `make dev` and open the SPA. Have a second browser tab open on a webspace fed by a
    NON-WhatsApp source (paperless, SilverBullet, Signal or email) before you start.

    1. **Boot latency (WR-01).** Time, roughly, from `make dev` starting the kernel to the SPA
       first answering. With an already-linked WhatsApp source configured this should feel like any
       other start — a second or two — not a multi-second stall. Report the felt duration and
       whether it differed from before this wave.

    2. **The main check — every other source is unaffected (criterion 4).** Start a re-link of the
       WhatsApp source from its chip menu ("Re-link…"), scan the QR with the phone, and accept the
       pairing. **At the exact moment the panel reports the pairing accepted and completes** —
       this is the window that used to freeze the kernel — switch to the second tab and, in quick
       succession: open an item from the other source, look at that source's health chip, and
       trigger a manual refresh of it. Report whether any of the three visibly hung, and roughly
       for how long if so. The expected result is that all three answer promptly, exactly as they
       would at any other moment.

    3. **The carried-forward item (previous cycle's open UAT).** Once the re-link completes, open
       the WhatsApp webspace. Report: whether it loads normally; whether any outage banner appears;

       device with WhatsApp to start syncing") for a device you have just successfully paired; and
       whether the source settles to healthy with its stream populated within a few seconds rather

    4. **Restart.** Restart the kernel and confirm the WhatsApp source reconnects with no second QR,

    5. **Repeat once (idempotency).** Run the re-link flow a second time in the same session and
