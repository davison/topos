<objective>
Close the three findings `08-REVIEW.md` raised against the G-08-1 gap-closure
diff and `08-VERIFICATION.md` promoted: the blocking unmount-during-in-flight-start
race in `QRPanel.svelte` (CR-01), the stale declined-link notice that can
co-render with a connection-failure alert in `AddSourceModal.svelte` (WR-01), and
a comment in the e2e spec describing a mechanism this phase deleted (IN-01).

CR-01 is the one that matters. `QRPanel` (D-01's single component, mounted from
both D-02's inline Add-Source step and D-03's Re-link dialog) owns a kernel
resource from the instant `POST /api/config/whatsapp-link` returns — the kernel
has already spawned the link subprocess and, on the Re-link path, already
suspended the real source instance before it answers 200. Its teardown path
guards on `sessionId`, which is only assigned *after* that call resolves, so a
dialog closed inside the request window discards the id and cancels nothing. The
component's own `onDestroy` comment states the invariant this violates: an
unmount must never leave a subprocess alive holding the WhatsApp store lock.
Ordinary use — open the dialog, change your mind, press Escape — strands the
subprocess and the suspended instance for up to five minutes, and a few
repetitions exhaust the four-slot concurrency cap and answer an unrelated later
attempt with 429. That is the phase goal's "everything else keeps working"
clause failing on the linking feature's own resource pool.

Purpose: make the client release what it created, and pin that behaviour with
armor at two levels (a structural guard that cannot drift, and a hermetic
browser case that exercises the real race window) so the regression cannot
return silently — the failure mode this finding already demonstrated once, by
being found, documented, and then shipped unfixed.
Output: a five-line guard in one function, two new Playwright cases, two new
test guards, and one corrected comment.
</objective>

**The fix (QRPanel.svelte).** In `beginSession`, the branch taken when `retired`
is already true at the moment `startWhatsAppLink` resolves must release the
session it has just learned about before returning. Call `cancelWhatsAppLink`
with the resolved response's own `session` field, guarded on that field being
non-empty (mirroring how `retireSession` guards on `sessionId`), and swallow the
rejection with the same empty-catch treatment `retireSession` already uses —
the session may already be retired server-side, which answers 404 and is
harmless here.

Do **not** assign `sessionId` in that branch. Leaving it null is load-bearing
twice over: it is what keeps a later `retireSession` from issuing a second
DELETE for the same id (the exactly-one-cancel guarantee), and it keeps
`poll()`'s own early return in force so no poll is ever issued for a session the
panel has abandoned.

Comment the branch with why it exists, not what it does: the kernel has already
spawned the link subprocess — and, on the Re-link entry point (D-03), already
suspended the real source instance — by the time it answers 200, so a session id
learned after teardown is still a live resource this component owns. The
alternative is the kernel's five-minute reaper, and repeated dialog open/close
cycles exhaust the four-slot concurrency cap long before that. Cite
`08-REVIEW.md`'s CR-01 and point at the `onDestroy` invariant comment already in
the file.

Change nothing else in the component. `retireSession`, the phase state machine,
the fixed poll cadence, the countdown gating, and the Cancel-affordance markup
all stay byte-identical. In particular, do **not** add a per-session token or
generation counter to guard `beginSession` against a stale start resolving into
a newer session: that path is unreachable today (`beginSession` runs only from
`onMount` and from the Retry/Restart controls, which are reachable only from
terminal phases that a start response has already produced), and adding it would
widen a deliberately surgical pass. Record that reasoning in the SUMMARY, not in
new code.
