<objective>
Close the KERNEL and FIXTURE halves of `08-UAT.md` gap G-08-4.

The diagnosis (`.planning/debug/whatsapp-paired-session-not-picked-up.md`) records this as an
AND-gate. Plan 08-11 fixes the plugin's own dishonest health state and makes its handshake mean
ready. This plan fixes the other two legs:

- **Root cause 2 (kernel).** There is no readiness gate between launching a plugin subprocess and
  issuing its first Match. `supervisor.commitGeneration` calls `startScheduler`, and
  `Scheduler.runSource` refreshes immediately (scheduler.go:73-74) — at kernel boot, on every
  config Apply, and (new since 08-09) on every link suspend/resume.
- **Root cause 3 (pinning).** The errored `sync_runs` row that races writes is what
  `LatestSyncRunPerSource` returns and `kernel/httpapi/stream.go`'s banner renders, and
  `DefaultSyncInterval` is 15m — so a sub-second lifecycle artifact becomes a pinned, false
  outage notice.
- **`missing[3]` (gate gap).** `plugins/mock`'s Match is unconditionally ready, so its readiness
  window is exactly zero. That is structurally why 08-09 and 08-10 went green while the real
  device did not: no fixture in this repo can express "the relaunched plugin is not ready yet".

**The decision G-08-4's `missing[2]` asks for, made explicitly:** a first-refresh failure is still
recorded as an errored `sync_runs` row — the kernel does not learn to suppress or special-case a
plugin's self-reported "connecting" state, and no third `sync_runs` status is invented (that would
ripple through the store schema, `docs/api.md`, the HTTP surface and the SPA for no additional
honesty). Instead the scheduler **supersedes** it: a generation's first refresh is retried a
bounded number of times with backoff, and because `LatestSyncRunPerSource` selects `MAX(id)` per
source, the successful retry becomes the latest row within seconds instead of 15 minutes. A source
that is genuinely broken still ends on an errored row and looks exactly as it does today, a few
seconds later. This is a general fix for the whole class, not a WhatsApp special case.

Purpose: make the kernel tolerant of the launch-readiness window every subprocess plugin
inherently has, and give this failure class a fixture so it can never regress silently again.

Output: a bounded first-refresh retry, an opt-in launch-readiness mode on the reference mock
plugin, and a hermetic end-to-end gate that drives a real mock subprocess through that window.

Scope note: this plan touches NO frontend file — the SPA and the Playwright suite are unchanged,
so the project's standing "any UI-touching phase extends the Playwright e2e suite" rule
(`.claude/CLAUDE.md`, `docs/testing.md`) does not apply. The behaviour is instead gated at the
Go layer where the defect actually lives, over a real plugin subprocess.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process env → plugin subprocess | `pluginhost.launch` forwards the kernel's whole environment to every plugin; a fixture-only variable must be inert when unset |
| scheduler → plugin Match | The retry loop issues additional RPCs against a source that just failed; unbounded retrying would be a self-inflicted request amplifier |
| sync_runs history → stream banner | What the user is told about a source's health is whatever the latest persisted row says |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-4-04 | Denial of service (self-inflicted) | `Scheduler.firstRefresh` retry loop | medium | mitigate | The schedule is a fixed two-element delay slice, consumed once per source per generation, with `<-ctx.Done()` in the same select as every delay. Pinned by `TestScheduler_FirstRefreshGivesUpAndLeavesTheErrorRecorded` asserting an exact `1 + len(delays)` call count and by the context-cancel test. |
| T-08-4-05 | Tampering | `plugins/mock`'s readiness window in a real installation | low | mitigate | Default off: absent/empty/"0" yields a nil window and a nil receiver reports ready, so the shipped binary's behaviour is unchanged. `make e2e` never sets the variable. A malformed value fails startup loudly rather than silently altering behaviour. |
| T-08-4-06 | Repudiation | Superseded errored `sync_runs` rows | low | accept | A superseded first-attempt error is not erased — it stays in `sync_runs` history and each retry is logged with source and delay; only "latest per source" changes, which is exactly the pinning this gap is about. |
| T-08-4-07 | Information disclosure | New scheduler log lines | low | mitigate | The retry log line carries the source instance id and the delay only — never config, token, or item content, matching `refreshAndLog`'s existing T-02-10 discipline. |
| T-08-4-SC | Tampering | npm/pip/cargo installs | n/a | accept | No new dependency of any kind is introduced by this plan — stdlib `time` and the existing test fixtures only. No package-legitimacy gate applies. |
