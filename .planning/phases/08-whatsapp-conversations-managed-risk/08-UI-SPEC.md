# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Inheritance note:** Phases 1–7 already established the design system, spacing scale, typography, color palette, the merged source-chip mechanics (`SourceChip.svelte`), the Add-Source picker/two-step modal, and — most load-bearingly for this phase — the **chat-transcript content shape** (`CONTENT_SHAPE_CHAT_TRANSCRIPT`, Phase 4/5). `08-RESEARCH.md`'s own Architectural Responsibility Map is explicit that this phase reuses that existing renderer/policy pair verbatim: "Mirrors Signal's `render.go` pattern exactly (D-11: sanitization/wrapping/theming is the kernel's job via `ContentShape`)." Nothing in this document introduces a new spacing value, font size, font weight, or hex color. This phase's real new surface area is (a) a fourth `source_type` flowing through already-generic components, (b) a new, wider health-state taxonomy the existing single-dot/tooltip pattern must name, (c) the Add-Source picker gaining "WhatsApp" as a connectable plugin type, and (d) one genuinely **unresolved** architectural question (QR-linking UX) that this document deliberately does not force a premature answer to — see "Open Design Decision" below.

**Scope (per ROADMAP.md / REQUIREMENTS.md SRC-03):** WhatsApp groups appear in the stream via the existing chat-digest/transcript pattern; matching is groups-only (no 1:1 chats, per SRC-03's own wording); de-link/ban/session-expiry surface as distinguishable health states while previously-captured messages remain browsable. **No `08-CONTEXT.md` exists for this phase** (checked this session) — every default below is either inherited verbatim from Phases 1–7 or derived directly from `08-RESEARCH.md`'s own findings; nothing here re-litigates a decision `REQUIREMENTS.md`/`ROADMAP.md`/`08-RESEARCH.md` already made.

**No new agent-facing UI surface.** SRC-03 has no AGENT-01/02 dimension — same "no UI surface" note every prior source-plugin phase made for its own non-agent requirements.

**No new destructive UI actions.** Read-only source; the existing Phase 7 "Remove from this webspace" / "Delete source instance" affordances apply to a WhatsApp instance identically to any other — no new destructive copy needed.

## Chat-Transcript Reuse Contract (hard constraint — read before planning `plugins/whatsapp/render.go`)

`kernel/httpapi/rendition.go` locks the `CONTENT_SHAPE_CHAT_TRANSCRIPT` policy to a **fixed, closed class-token vocabulary** enforced by a regexp allowlist (`chatTranscriptClassTokens`): `run`, `own`, `other`, `sender-name`, `bubble`, `tombstone`, `quote`, `timestamp`, `edited-suffix`, `attachment`, `reaction`, `body` — and nothing else. Any class token this plugin emits outside that set is stripped by the sanitizer (bluemonday matches the *entire* class-attribute value, so one forged/novel token silently drops the whole `class` attribute, not just the offending token). Consequences for this phase's design contract, all inherited unchanged from `plugins/signal/render.go`'s already-shipped, already-tested structural pattern (confirmed by reading it this session):

- **The WhatsApp plugin must reuse the exact same structural markup Signal's `renderTranscript`/`renderBubble` already produce** (own/other run grouping, one `sender-name` per non-own run, bubble-per-message, quote/tombstone/attachment/reaction sub-elements) — not a reimplementation with its own class names. The recommended approach (per `08-RESEARCH.md`'s "Don't Hand-Roll" table) is to extract or directly reuse Signal's transcript-builder logic rather than hand-rolling a second copy with any drift in class vocabulary.
- **No per-participant color coding, avatar-color, or accent-tinted sender name is possible or permitted**, even for a WhatsApp group with many distinct senders (unlike Signal's own groups, which already established this same constraint in Phase 4). Ownership/identity is signaled *only* by alignment (own = right, others = left) + background tier + the once-per-run `sender-name` text — never by color. `kernel/httpapi/rendition_test.go`'s `TestChatStylesheet_NoAccentColourOnBubbleSenderOrTimestamp` is the standing regression guard for this rule; nothing in this phase relaxes it.
- **The plugin ships zero new CSS.** Bubble radius (~12px), padding (8px/16px), max-width (75%), run/bubble spacing (16px between runs, 4px between bubbles in a run), and every sub-element's typography (sender-name 14px/600, timestamp/edited-suffix/quote/reaction 14px/400 muted, body/tombstone 15px/400/1.6) are already defined once in `renditionChatDelta` and apply automatically to any conforming markup — this phase adds no new rule to that stylesheet.
- **Multiple distinct senders within one WhatsApp group already work with the existing pattern**: each contiguous run from a different sender gets its own `sender-name` label (Phase 4's E2 "populated" resolution — a run boundary is "sender differs OR gap > 5 min," which already generalizes past Signal's own conversations-vs-groups distinction to any number of distinct senders).

## New Health-State Taxonomy (extends the existing single-dot/tooltip pattern)

**No new visual states.** `web/src/lib/format.ts`'s `HealthTone` stays exactly four values (`success` / `warning` / `destructive` / `unknown`) — this phase does not add a fifth dot color or a new chip variant. WhatsApp's four new named causes all map onto the **existing `destructive` tone** (the `reachable: false` branch of `healthTone()`), exactly the same "one dot, several plugin-named causes disambiguated by `last_error` text" pattern Phase 4 already established for Signal's three causes (keyring failure / missing DB / unrecognised schema version):

| Named cause | When | Tone | UI treatment |
|---|---|---|---|
| Not yet linked | No paired device found in the plugin's `sqlstore` at boot | `destructive` | Existing health dot + tooltip, `last_error` verbatim |
| De-linked (`events.LoggedOut`) | Remote unpair (user unlinked from phone, or WhatsApp itself force-logged-out the session) | `destructive` | Same |
| Banned (`TempBanReason`) | WhatsApp reports a temporary/account restriction | `destructive` | Same |
| Session expired | Primary phone offline past WhatsApp's own session-durability window | `destructive` | Same |
| Linked and healthy | Normal operation | `success` (or `warning`/`unknown` per the existing generic sync-status rules, unchanged) | Same as any other source |

**This document does not dictate the literal `last_error` string for each cause** — consistent with every prior phase's rule ("specific, actionable wording is entirely the plugin's `Health()` responsibility, not a UI design choice," 04-UI-SPEC.md, reaffirmed for Signal's three causes and SRC-01 criterion 5 before it). The one **new** requirement this phase adds to that standing rule, because success criterion 4 explicitly calls it out: **whichever cause fires, the `last_error` text must never imply previously-captured messages were lost or are now inaccessible** — de-link/ban/expiry are transient-connectivity states, not data-loss events, and the copy should read that way (e.g. naming the cause and, where true, that syncing will resume once resolved) — mirroring the reassurance Signal's own unrecognised-schema-version message already gives by naming the exact version found rather than a bare "failed."

**Recommended (non-binding) templates**, offered as a starting point for the plugin implementation, not a locked contract:
- Not linked: `"Not linked — pair this device with WhatsApp to start syncing."`
- De-linked: `"Unlinked from WhatsApp — re-link to resume syncing. Previously captured messages are still here."`
- Banned: `"WhatsApp restricted this account — re-check later. Previously captured messages are still here."`
- Session expired: `"Linked session expired (phone offline too long) — re-link to resume syncing. Previously captured messages are still here."`

## Add-Source Picker — "WhatsApp" as a new connectable plugin type

Extends Phase 7's existing two-step modal (`07-UI-SPEC.md` "Two-step modal — configure a new plugin-type instance") with one new row in its Step 1 field table — **no new modal, no new step, no new component**:

| Plugin type | Fields (all optional unless marked required) |
|---|---|
| WhatsApp | Display name, Local Path *(required — default shown as placeholder text, e.g. `~/.config/topos/whatsapp`)* |

This mirrors Signal's own Step 1 field set exactly (`Display name` + `Local Path`), since — per `08-RESEARCH.md`'s Pattern confirmation — `Describe` carries only static match vocabulary (`groups`), never connection-field shape or live link-state, so **trial-launch and Step 2 (`Match settings`) succeed identically whether or not the device has been paired yet.** This produces one genuinely new sequencing state this phase introduces to the Add-Source flow: a WhatsApp instance can be fully saved (Step 1 + Step 2 both succeed) while still functionally unlinked. See "UI Considerations" E5 below for how that state reads to the user afterward (it resolves into the existing not-linked health-dot state above — no new modal-level branching).

## Open Design Decision — QR-Linking UX (NOT resolved by this document)

`08-RESEARCH.md`'s Open Question 1 leaves the pairing mechanism itself explicitly unresolved, to be settled at a Task 1 spike checkpoint (the same pattern Phase 4 used for its own SQLCipher driver decision) rather than guessed here. This section exists so planning does not silently default either way:

- **Option A (research's recommended default): a standalone one-time CLI linking step**, invoked directly by the user in a terminal against the same compiled plugin binary (e.g. `topos-plugin-whatsapp -link -path ~/.config/topos/whatsapp`), rendering the QR code as ASCII via `qrterminal`. **Zero SPA impact** — every contract in this document (chip, health states, Add-Source Step 1 fields, digest/transcript rendering) is already complete and correct under this option with no further UI work. The only thing this option changes is the wording of the "not linked" health-state copy's actionable next step (name the CLI command).
- **Option B: a kernel-mediated, in-app QR flow** — a new kernel HTTP endpoint plus a new frontend QR-display surface (likely a dedicated panel inside the Add-Source two-step modal's Step 1, shown when the trial-launch reports "not linked," polling/streaming a rotating QR code until scanned or expired). **This option is NOT designed by this document.** If the Task 1 spike selects Option B, this UI-SPEC requires an amendment (new component contract: QR image sizing, rotation/expiry countdown copy, scan-success transition) before the wave that implements it is planned — do not let a plan silently improvise that surface against this document's silence.

**Recommendation to the planner:** default to Option A unless the Task 1 spike checkpoint explicitly overrides it — this keeps the phase's UI risk surface at zero for the pairing mechanism itself, consistent with ROADMAP.md's own "Managed Risk" framing of this phase.
