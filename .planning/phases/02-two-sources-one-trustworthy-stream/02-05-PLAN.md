<objective>
Close the single BLOCKER gap from `02-VERIFICATION.md`: `plugins/silverbullet/plugin.go`'s
`Match` swallows every per-page `ReadFile` failure identically to "page not found", so a
SilverBullet outage, revoked token, or TLS failure occurring *after* `ListFiles` already
succeeded returns a **successful, empty** `MatchResponse`. The kernel then does exactly
what an empty successful match means — calls `ReplaceWebspaceSourceItems` with zero items,
deleting every previously-synced SilverBullet row for every webspace, and records the run
as `ok` with `item_count: 0`.

Everything downstream of the plugin is already correct and already tested: `SyncSource`
skips persistence entirely when `Match` errors, and the coordinator records `status: "error"`
when any `WebspaceResult` carries an error. The plugin is the only link in that chain that
never produces the error. This plan supplies it, plus the regression tests whose absence
(`no TestMatch* function exists at all`) is why the bug shipped.

Purpose: restore the phase's core guarantee — "tell at a glance whether what you are looking
at is complete and current" — for the case where the failure happens *inside* a plugin's own
`Match` call, not just when a sibling source is offline (SRC-05, UI-05).
Output: a fixed `Match` error path and `plugins/silverbullet/match_test.go`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| SilverBullet instance → plugin subprocess | Every `/.fs` response (listing and page bodies) is untrusted input crossing into the plugin: status codes, Content-Type, and body bytes are all attacker- or fault-controlled if the instance is down, spoofed, MITM'd, or misconfigured. This plan changes how the plugin interprets *failures* at this boundary. |
| Plugin subprocess → kernel (gRPC `Match`) | The `MatchResponse`/status pair the plugin returns is the sole input the kernel uses to decide whether to replace a webspace's rows for this source. A successful-but-empty response is a destructive instruction. |
