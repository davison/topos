<objective>
Establish the permission model now, while there are only two plugins to grant,
so Phases 3-5 add their grants declaratively instead of retrofitting a
permission model across five plugins — and produce the reference mock plugin
that makes the published contract provably self-sufficient.

Two independent things ship here because both are contract-shaped and neither
touches the UI: AGENT-01's default-deny per-source grants behind a separate
`/agent/v1` namespace, and PLUG-05's proof that a third party can build a
working plugin from the published artifacts alone.

Purpose: AGENT-01 (per-plugin permission model, default-deny, defined in config,
granting read and hand-off separately) and PLUG-05 (a third party can build a
plugin from the contract docs plus reference mock plugin alone).
Output: `kernel/httpapi/agent.go`, `[sources.*.agent]` config, `plugins/mock`,
and a contract document validated by an isolated build exercise.

Locked decisions this plan implements (from `02-CONTEXT.md`):
**D-11** the TOML grant shape is a per-source `[sources.<name>.agent]` block with
two independent booleans, `read` and `handoff`, where an absent block or an absent
key means false; **D-12** the agent-facing API is a separate `/agent/v1` route
namespace mirroring the read API with grants enforced structurally — ungranted
sources absent from source and health listings, their items absent from streams,
and direct item or content requests returning the same error as a nonexistent item
so there is no existence leak — while the UI's `/api/*` routes stay unaffected and
grant-free, `docs/api.md`'s Phase-1 "there is no separate agent API" statement is
revised, and `handoff` is recorded and exposed as capability metadata only, with
actual agent actions deferred to v1.x.
</objective>

The `/agent/v1` namespace reuses `docs/api.md`'s existing envelope and the same
`schema_version` counter — there is no second versioning scheme, because nothing
in this phase requires the two surfaces to evolve independently:

```
GET /agent/v1/sources                       -> { schema_version, sources: [ ...sourceStatus, capabilities:{read,handoff} ] }
GET /agent/v1/webspaces                     -> same shape as /api/webspaces, counts restricted to granted sources
GET /agent/v1/webspaces/{webspace}/stream   -> same shape as /api/webspaces/{w}/stream, items restricted to granted sources
GET /agent/v1/items/{id}                    -> same shape as /api/items/{id}
GET /agent/v1/items/{id}/content            -> same bytes + same hardened headers as /api/items/{id}/content
GET /agent/v1/items/{id}/thumbnail          -> same as its /api counterpart
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| agent process → `/agent/v1` | An automated caller with no authentication, whose access is bounded solely by config-declared grants. |
| config → authorization decision | A TOML file is the entire source of truth for what an agent may read. |
| third-party plugin author → kernel | A plugin built from published docs runs as a kernel-launched subprocess with full local OS access. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-19 | Elevation of Privilege | `kernel/httpapi/agent.go` grant filtering | high | mitigate | Default-deny by Go zero value: an absent block, an absent key and an explicit false are structurally identical, so a grant can only exist by being written. Filtering happens after the index read and before any response is composed, in one helper used by every agent route. Asserted by the three-way-equivalence and handoff-without-read tests. |
| T-02-20 | Information Disclosure | `/agent/v1/items/{id}` and its rendition children | high | mitigate | An ungranted source's item returns a response byte-identical in code, status and message to a genuinely nonexistent id, so the namespace is not an enumeration oracle. Asserted by a test that captures both bodies and compares them. Listing order is preserved with entries removed rather than re-sorted, so ordering does not leak a removal either. |
| T-02-21 | Elevation of Privilege | `handoff` capability | medium | mitigate | `handoff` is published as metadata and consumed by nothing. No action route exists in this phase and no placeholder is added, so a `handoff = true` grant cannot cause a source mutation via any code path that ships here. |
| T-02-22 | Spoofing | `/agent/v1` has no authentication | medium | accept | Accepted and unchanged from Phase 1's documented model: the listener is loopback-bound and v1 has no authentication anywhere. `AGENT-01` is an authorization control layered on that boundary, not an authentication mechanism, and `docs/api.md` must say so explicitly so the grant model is not mistaken for auth. Revisit if the listener is ever bound beyond loopback. |
| T-02-23 | Tampering | third-party plugin subprocesses | medium | accept | A plugin built from the published contract runs with full local OS access — `go-plugin` is a subprocess transport, not a sandbox. Accepted for v1: the user builds and installs plugin binaries themselves, at the same trust level as the kernel binary. The read-only guarantee is enforced at the contract level (RPC allowlist) and, for in-repo plugins, mechanically by the AST scan; `docs/plugin-contract.md` must state that a third-party binary is trusted code, so an adopter is not misled into thinking it is contained. |
| T-02-24 | Information Disclosure | `docs/plugin-contract.md` | low | mitigate | The contract document must restate the logging rule (a token is never logged at any level) so a third-party author does not have to infer it from an existing plugin's code, which they are explicitly told not to read. |
