<objective>
Close gap G-06-3: restore a clearly visible selected state on the merged source chip (D-01's single
per-instance affordance, D-02's multi-select filter).

Three conjoint causes, per `.planning/debug/chip-selected-state-visibility.md`:

1. **Colour (primary).** The selected treatment reaches for the token literally named "accent", but
   in this palette `--accent` is a deliberately NEUTRAL dark slate that is byte-identical to
   `--border` — the colour the chip already paints when unselected. The ring adds no colour at all,
   and the 10%-alpha wash shifts the fill by under 2/255 per channel. `web/src/app.css` documents
   this exact trap in advance: the real accent blue lives in `--primary` and `--ring`.
2. **Clipping (secondary, explains the reported shape).** Tailwind's ring is an outset box-shadow.
   The chip is the tallest child of `WebspaceHeader.svelte`'s unpadded `overflow-hidden` row, so the
   ring's top and bottom 2px are clipped away and only the two semicircular pill end-caps survive —
   verbatim the "left and right rounded edges" the user reported.
3. **Spec contradiction (origin).** 06-UI-SPEC.md's component prose spells a class that cannot
   produce the colour its own Color table assigns to the selected chip's ring. Fixing only the code
   leaves the contradiction live to reintroduce the bug on the next spec re-read.

Purpose: a multi-select filter whose selected state is invisible is a trap — the user cannot tell a
narrowed stream from a complete one. The pre-Phase-6 component used a solid blue fill and the user
explicitly remembers and asks for it back.

Output: a solid `--primary` fill with every child re-toned to stay legible on it, the spec
contradiction resolved, a standing note at the palette comment that already anticipated this
confusion, and the first automated guard this component has ever had.

**No tracer task.** Surgical fix to one shipped component whose wiring, ARIA and behaviour are all
already correct — only the rendered contrast is wrong.
</objective>

**SourceChip.svelte — the fill.** Replace the entire selected branch of the wrapper `div`'s `cn()`
call. Selected chips get a solid `bg-primary` fill plus a matching `border-primary`, restoring the
treatment the retired `SourceFilterChips.svelte` produced through shadcn's filled Button variant —
the "contrasting blue shade" named in the UAT report. Drop the neutral-token ring and the
10%-alpha wash entirely; they are the defect. A background paints inside the border box, so this
sidesteps the outset-box-shadow clipping outright. **Do not touch `WebspaceHeader.svelte`** — its
row's `overflow-hidden` must stay exactly as it is, because 06-04's overflow measurement depends on
the row clipping its own children.

Note for the implementer: `cn()` runs tailwind-merge, and the conditional string is composed after
the base string, so the filled background correctly wins the background-colour conflict group
against the chip's default card background. Verify this holds rather than assuming it.

**SourceChip.svelte — the children.** A near-white label on a mid-blue fill is unreadable, so
`selected` must be threaded into all three children rather than only the wrapper:

- *Display name span*: its foreground class becomes conditional — the existing foreground token when
  unselected, `text-primary-foreground` when selected. Keep the truncation, the type role and the
  native `title` attribute unchanged.
- *Health dot*: the four tone classes stay exactly as they are (the dot's colour still encodes
  health, and reordering or remapping tones is forbidden). Because those tones lose separation
  against a mid-blue ground, add — when and only when selected — a 1px ring in
  `--primary-foreground` around the 8px dot, so its tone stays identifiable as a distinct pip rather
  than blending into the fill. This ring is on an inner element well inside the chip and is not
  affected by the row's clipping.
- *Refresh button*: its icon must re-tone to `text-primary-foreground` when selected, and its
  ghost-variant hover surface must be one that reads on blue rather than the neutral dark slate the
  ghost variant uses by default. Keep every behaviour untouched: the opacity-0-until-hover/
  focus-within reveal (D-03), the always-visible spinning state while syncing, the `aria-label`, and
  the `stopPropagation` that keeps a refresh click from also toggling the filter.

Everything else in this component is correct and must not change: `aria-pressed`, the filter
`onclick`, the five tooltip branches and their copy (D-04, no rewording), the 44px control sizing,
and the fact that the popover renders this same component unforked.

**app.css — the standing note.** The palette comment above `--accent` already anticipated exactly
this confusion. Extend it with one short sentence recording that a real defect (G-06-3, Phase 6 UAT)
was caused by reaching for the literally-named token for a selected-state treatment, and naming
`--primary`/`--ring` as the tokens to use for selected/active affordances. Comment text only — do
not add, remove or change any declaration in this file, and do not touch the `@theme inline` block.

**06-UI-SPEC.md — the contradiction.** The chip anatomy bullet describing the selected/filtered
state spells a class literal that cannot produce the colour the document's own Color table assigns
to the selected chip. Rewrite that bullet to describe the shipped treatment: a solid fill in the
accent blue with the label, dot ring and refresh icon re-toned to the fill's foreground, and
unselected chips keeping the plain bordered card treatment. Update the Color table's chip row so it
reads "fill" rather than "ring". Add a short dated note naming G-06-3 as the source of the
amendment. Use scoped `Edit` calls only; do not rewrite the file.
