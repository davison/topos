# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Inheritance note:** Phases 1–5 already established the design system, spacing scale, typography, and color palette — `web/src/app.css` ships these as live CSS custom properties today, and 05-UI-SPEC.md's Rendition Content Contract governs the kernel-owned iframe stylesheet. This phase does **not** re-derive any of that; it is the first phase to genuinely redesign a primary chrome surface (the webspace header) and adds exactly one new interaction mechanism (kernel-side text highlighting) and one new visual affordance (scrollbar date markers). Every table below states plainly whether it is unchanged, extended, or new.

**Scope (per ROADMAP.md / 06-CONTEXT.md):** UI-07 (merged per-instance source chip, scalable to 10+ instances), UI-08 (deep-link fidelity differentiation), UI-09 (search-term highlighting in the detail pane across content variants), UI-11 (themed scrollbars + stream date markers — base theming already shipped via quick task 260805-j98; only the date-marker affordance is novel). No config-writing UI (Phase 7), no new sources (Phase 8), no contract change to `LINK_FIDELITY_*` or the sanitizer.

## Header Redesign — Combined Source Chip (UI-07)

**Replaces** `SourceHealthChip.svelte` + `SourceFilterChips.svelte` (two rows) **with one `SourceChip.svelte` component**, one instance per configured source, rendered in a single row in `WebspaceHeader.svelte`. Chips render in config-declared instance order (never reordered by health state or alphabetically — reordering as health changes would make a chip's position an unreliable target for repeat interaction).

### Chip anatomy (at rest)

`[● dot][display_name, truncated][refresh icon — hidden until hover/focus]` inside the existing pill container (`rounded-full border border-border bg-card`, unchanged from `SourceHealthChip.svelte`).

- **Health dot** (unchanged tone mapping — `healthTone`/`DOT_TONE_CLASS`): success/warning/destructive/unknown. Passive indicator only, per D-01 — clicking the dot does not do anything different from clicking the rest of the chip body.
- **Display name**: Label role (14px/400/1.4), `truncate` + native `title` attribute for the full string (carries forward 05-UI-SPEC.md's long-text resolution verbatim — `display_name` is user-authored and may be long).
- **Refresh control** (D-03): a `RefreshCw` icon button, `opacity-0` at rest, `opacity-100` on chip hover, or keyboard focus on any control inside the chip, **always visible and spinning** (never hidden) while `source.syncing` is true — the syncing spinner is the sole in-place syncing indicator this phase (see Copywriting Contract; the old inline "Syncing…" text label is retired to keep the chip compact at scale). *(2026-08-07, G-06-3b: this bullet originally scoped the reveal to the wrapper's `:focus-within` state. `:focus-within` also matches the persistent focus a mouse click leaves behind, so after a refresh click the icon stayed pinned visible until the user clicked elsewhere on the page. Scoping the reveal to keyboard focus (`:focus-visible`) keeps the D-03 keyboard path intact and drops the click-pin.)*
- **Selected/filtered state** (D-02): when a chip's source is in the active filter set, the chip gets a solid `--primary` fill (`border-primary bg-primary`) with its display name, health-dot ring and refresh icon re-toned to `--primary-foreground` so they stay legible on the fill — an extension of Phase 2's already-reserved "active filter chip" accent-blue usage, not a new accent site. Unselected chips keep the plain `border-border bg-card` treatment. *(2026-08-07, G-06-3: this bullet originally spelled `ring-2 ring-accent` plus `bg-accent/10`, a class literal that resolves through the neutral `--accent` token — byte-identical to `--border` in this palette — rather than through `--primary`/`--ring`, the tokens this document's own Color table assigns to the selected chip. That contradiction shipped an invisible selected state; this bullet now agrees with the Color table and the shipped code.)*
- **Chip geometry (2026-08-07, G-06-3b constraint):** the pill declares its own `h-11` (44px) height, matching the overflow trigger's, rather than inheriting a height from its tallest child; the filter button stretches (`self-stretch`) to the pill's full content height and carries the pill's own inner padding. Every pixel of the chip body is therefore a filter target. The pill itself MUST carry no vertical padding of its own — padding on the pill puts a band inside the visible chip that sits outside the filter button and is therefore click-dead, which is precisely what G-06-3b reported. Any size override applied to the refresh control must also declare a radius: the shared `Button` base supplies a rectangular radius, and a size-without-radius override paints a rounded square inside the oval.

### Interaction model (D-01, D-02, D-03, D-04 — locked)

- **Click chip body** → toggles that source in/out of the multi-select filter set (D-02). Keyboard: `Enter`/`Space` on the focused chip does the same (the chip's clickable body is a real `<button>`, not a `<div onclick>`, so this is native, not bolted on).
- **Hover/focus chip** → reveals the refresh icon (D-03) and, after the existing tooltip delay, the health tooltip (D-04, copy unchanged from 02-UI-SPEC.md, see Copywriting Contract below).
- **Click refresh icon** → triggers refresh for that source only; `stopPropagation` so it never also toggles the filter. Refresh stays reachable by keyboard: `Tab` from the chip body reaches the refresh button next (it is a real focusable child, not purely a hover reveal — a keyboard-focus-scoped reveal (`:focus-visible`) keeps it visible for keyboard users per D-03's own "and keyboard focus" clause, without also pinning it visible after a mouse click; see G-06-3b above).
- **No dedicated "All" chip** (D-02) — all-off means show-everything. When at least one chip is selected, a text button **"Clear filters"** (Label role, `variant="ghost" size="sm"`, `X` icon leading, same icon already used by `SearchBox.svelte`'s clear affordance) appears at the trailing end of the chip row, after the last chip/overflow trigger — this is the fast path back to "show everything" at 10+ instances without un-toggling every chip individually. Hidden when the filter set is empty.
- **"Refresh all"** button (unchanged copy, `variant="outline" size="sm"`) stays pinned at the trailing end of the row, after "Clear filters" — it is never counted toward the overflow threshold (see below); it must always be reachable in one tab stop from the chip row regardless of instance count.

### Scaling to 10+ instances (Claude's Discretion — resolved)

**Strategy: single-line row + measured overflow into a popover ("+N more").** The chip row is `flex flex-nowrap overflow-hidden` (never wraps to a second line — a wrapping row is exactly the "unbounded chip rows" the success criterion rules out, since row height would grow without bound as instances are added). A `ResizeObserver`-driven measurement (component-owned, no new package — same technique class as any shadcn overflow-menu pattern) determines how many chips fit in the available header width; chips beyond that count are not rendered inline. Instead, a trailing overflow-trigger chip renders: `[≡ Ellipsis icon]["+N"]`, visually chip-shaped (`rounded-full border border-border bg-card`) but muted (`text-muted-foreground`), where N is the count of hidden sources.

- Clicking/focusing the overflow trigger opens a **Popover** (new shadcn-svelte wrapper over the already-installed `bits-ui` `popover` primitive — see Registry Safety) anchored below the trigger.
- Popover content: a vertical list of the same `SourceChip` component (full anatomy — dot, name, hover-reveal refresh, click-to-filter, tooltip), one per hidden source, in the same config order. The popover's own content area scrolls (`max-h-80 overflow-y-auto`, using the app-wide themed scrollbar tokens — no new scrollbar styling needed) if the hidden count is itself large.
- The overflow trigger's own tone reflects the **worst health tone among the hidden chips** (e.g., if any hidden source is `destructive`, the "+N" trigger shows a small destructive-tone dot) so a problem never hides silently behind the fold — this reuses the existing `DOT_TONE_CLASS` mapping, just reduced (worst-of) over a set instead of one source.
- **Reserved trailing space:** the measurement always reserves width for "Clear filters" (when active) and "Refresh all" (always) before computing how many chips fit — those two controls are never themselves pushed into the overflow popover.
- Every instance stays reachable in at most two interactions (open popover, click chip) regardless of count — satisfies success criterion 1 literally ("no unbounded chip rows" + "every instance reachable").

## Deep-Link Fidelity Differentiation (UI-08)

**Changes `OpenInSource.svelte`.** Two fidelity classes, not three, drive the *visual* differentiation (the existing three-value `Badge` text is retained unchanged for the power-user detail — see Copywriting Contract):

| Fidelity value | Class | Button icon | Button label | Button title/tooltip |
|---|---|---|---|---|
| `exact` | navigates to the item | `ArrowUpRight` (leading, 16px) | `Open in {displayName}` | `Open in {displayName}` |
| `anchored` | navigates to the item | `ArrowUpRight` (leading, 16px) | `Open in {displayName}` | `Open in {displayName}` |
| `conversation-only` | raises the app window only | `AppWindow` (leading, 16px) | `Show in {displayName}` | `Raise {displayName} — opens the app/conversation, not this exact message` |

- Icon color: inherits the button's existing foreground (no new color token; the icon is decorative-adjacent to the label, not a standalone status signal, so it does not draw from the success/warning/destructive palette).
- The secondary `Badge` (currently `exact`/`anchored`/`conversation-only`, `variant="secondary"`) is unchanged in copy and styling — it remains the precise, power-user-facing enum value; the icon+label change above is the primary, at-a-glance differentiation the requirement asks for (a user must be able to tell the difference *before* clicking, which the icon and verb ("Open" vs "Show") both satisfy without reading the badge).
- `aria-label` is not needed beyond the existing `title` — the button's visible text already changes per class, so screen readers get the differentiation for free.

## Search-Term Highlighting (UI-09)

Two independently-implemented mechanisms for one consistent visual result — see 06-RESEARCH.md's Pattern 2/3 for *why* they must differ; this section fixes *how they look and what they touch*.

> **Surface set extended 2026-08-07 (G-06-1, plan 06-05).** The shared visual
> contract below now also covers the SPA-rendered **item title**, in both the
> detail-pane header and the stream/search-result row — not only the
> detail-pane body variants this section originally scoped. Why: the local
> index full-text-searches both `title` and `preview`
> (`kernel/index/schema.go`), and the search API's `snippet()` call
> auto-selects the best-matching column, so a title-only match is a routine,
> first-class search outcome — not an edge case — for which the app must
> still visually explain why the item surfaced. On the SPA side this half of
> the contract is delivered by exactly one class, `.search-highlight`,
> declared once in `web/src/app.css` (`@layer components`) rather than as a
> component-scoped Svelte `<style>` block — a scoped class cannot be shared
> across `DetailPane.svelte` and `StreamRow.svelte`, which is what let the
> two components drift onto different match vocabularies in the first place.
> The kernel's own rendition-iframe `mark` rule (below) is unchanged and
> continues to paint the identical amber/near-black pair from the same two
> tokens.

### Shared visual contract (both mechanisms)

- Highlighted text is wrapped in a bare `<mark>` element (no class, no attribute — per RESEARCH.md Pitfall 2, an unstyled/attribute-free element needs no sanitizer-policy entry).
- Style: `mark { background: #fbbf24; color: #020617; border-radius: 2px; padding: 0 1px; }` — reuses the existing `--warning` (amber-400) and `--background`/dominant (`#020617`) tokens verbatim; **no new color is introduced**. Amber-on-near-black gives strong contrast and reads unambiguously as "this text matched your search," distinct from the accent blue already reserved for links/CTAs/selection (this phase does not add highlighting to that reserved list).
- All matches highlight uniformly — **no prev/next match navigation, no "N of M" counter** in this phase (REQUIREMENTS.md UI-09 asks only for highlighting; navigation is out of scope, keeping the phase's surface area matched to its requirement).
- Term extraction: case-insensitive, whitespace-split on the live search query (mirrors the kernel's own `ftsQuery` tokenization — `strings.Fields`-equivalent, no stemming) — both the client-side and kernel-side highlighters must derive terms the same way so what highlights matches what the search actually matched.
- No highlighting renders when there is no active search query — the detail pane looks exactly as it does today.

### Plain-text / media variant (client-side)

Applies to `DetailPane.svelte`'s `bodyVariant === 'text'` and the trailing text block of `'media'`. A new `highlightText(text, query): SnippetSegment[]` helper (reuses the existing `SnippetSegment` type from `parseSnippet`) renders via the same `{#each segment}` pattern `StreamRow.svelte` already uses for search-result snippets — matched segments render inside `<mark>` with the style above, applied via a shared CSS class (not inline style) so the SPA and iframe visual treatments stay in sync from one source of truth conceptually, even though they're two separate stylesheets by necessity.

### Sanitized-HTML / markdown / chat-transcript variant (kernel-side, `bodyVariant === 'html'`)

Applies to email HTML, SilverBullet markdown, and Signal chat transcripts — all served through the sandboxed rendition iframe. Per RESEARCH.md's load-bearing finding, this **cannot** be done client-side (the iframe's `sandbox` CSP with no `allow-same-origin` forces an opaque origin) and must not be attempted that way. The kernel inserts `<mark>` as real DOM tree nodes (via `golang.org/x/net/html` parse/walk/render) into already-sanitized text nodes only, between `bluemonday.SanitizeBytes` and the existing document-wrap step — never as a second sanitizer pass, never as string/regex splicing over HTML bytes. The `mark` CSS rule above is added once to the shared base of the kernel-owned rendition stylesheet (05-UI-SPEC.md's "shared base" block), not duplicated per content-shape delta.

## Themed Scrollbars + Stream Date Markers (UI-11)

**Base theming already shipped** (quick task 260805-j98) — thin, theme-matched scrollbars app-wide including inside rendition iframes, `--scrollbar-thumb`/`--scrollbar-thumb-hover`/`--scrollbar-track` tokens. **Unchanged this phase.** The only new work is the stream pane's date-marker overlay.

### Date marker overlay (new)

*Amended 2026-08-07 (G-06-6): the treatment below superseded the section's original marker-visual and placement bullets, whose 1.86:1 rest tone and 2px scrollbar inset shipped a ruler users read as "CSS artifacts from a broken stylesheet" — the constraints below are stated as measurable floors rather than a token name and a vague placement, precisely because prose alone let both defects through unnoticed until a live UAT pass caught them. Full diagnosis: `.planning/debug/date-marker-tick-styling.md`.*

Native `::-webkit-scrollbar`/`scrollbar-color` cannot host arbitrary child markup, so this is a separate overlay rendered as a **dedicated lane** in a right gutter the stream scroll region reserves — never on top of the row list and never on the native scrollbar's own track.

- **Data source:** `StreamItem.timestamp_unix` on the already-fetched, already-in-memory stream items — no new API call. Positions are computed as `(item index / total visible items) × track height`, valid because `StreamList.svelte` renders a non-virtualized, fixed-row-height list (confirmed in 06-RESEARCH.md) — index-proportional position accurately maps to scroll offset.
- **Granularity (adaptive):** one marker per calendar-date boundary (the first item of each new UTC date, using the existing `formatItemDate` day boundary — consistent with how dates are already computed elsewhere in the app, not a new date scheme). If adjacent date markers would land closer than 24px apart (dense multi-year history), thin adaptively: drop to one marker per ISO week, then — if still too dense — one marker per calendar month, choosing the coarsest granularity that keeps every rendered marker at least 24px from its neighbor. A stream spanning a single date renders zero markers (nothing to navigate between).
- **Marker tone (measurable floor):** ticks use dedicated `--stream-marker`/`--stream-marker-strong` tokens (`web/src/app.css`), derived via `color-mix()` from `--muted-foreground` so the palette gains no new hex value — never the scrollbar thumb tokens, whose reuse is what forced the original 1.86:1 rest tone. The rest tone MUST clear 3:1 contrast against both `--background` and `--card` — computed and asserted by `web/src/lib/components/marker-overlay.test.ts`, not merely stated in prose.
- **Lane placement (measurable floor):** a dedicated 12px-wide lane whose trailing edge clears the native scrollbar entirely (at least the scrollbar's own declared width, so it can never again sit on top of it), sitting inside a right gutter the stream scroll region reserves so the ruler composites against one uniform surface — never the row list, whose alternating card/background tones would band the ruler across its length.
- **Form:** a faint rail in the `--border` token spans the lane's full height, grouping the ticks into a ruler; ticks render in two grades — a minor tick for a plain date boundary, a major tick (spanning the lane's full width, in `--stream-marker-strong`) for a month boundary at day/week granularity or a year boundary at month granularity — so the ruler carries a visual hierarchy instead of one flat dash repeated at irregular offsets. `cursor-pointer` on the tick announces the click affordance; a real focus-visible ring (`--ring`, inset) accompanies the tone swap rather than replacing it, since a colour-only focus signal is not itself a floor this section states.
- **Render gates (measurable floors):** (1) the overlay renders zero markers unless the stream scroll region actually overflows its track — a stream short enough to fit its pane has no scrollbar to annotate, so decorating it with ticks is itself the artifact; (2) every tick's vertical position is inset from both the pane's top and bottom edges by half the tick hit-area's height, so no tick is ever half-rendered beyond the pane — closing the previously-shipped defect where a tick at the very top spilled, unclipped, into the pane's own padding on every render.
- **Interactivity:** click a tick → `scrollIntoView({ block: 'start' })` on that date's first stream row (no drag-to-scroll needed — the native scrollbar thumb already handles dragging; this overlay is a navigation aid, not a scrollbar replacement). Hover/focus a tick → a small Tooltip (existing `bits-ui` Tooltip primitive, already installed) shows the full date via `formatItemDate` (e.g. "6 Aug 2026").
- **Touch target exception (spacing floor):** the tick's clickable hit-area is 16px tall (not the standard 44px floor) — this project is desktop-only by hard constraint (`.claude/CLAUDE.md`: "Runs on the user's desktop machine"), and this is a secondary, pointer-precision navigation aid alongside the primary scrollbar, not a primary action control; the 44px floor continues to apply to the chip **body** (now a single 44px filter target — see G-06-3b's chip geometry constraint above), the overflow trigger, and "Clear filters"/"Refresh all". *(2026-08-07, G-06-3b: the chip's inline refresh control is this phase's **second** documented desktop-only exception, alongside this tick. A 44px control nested inside a 44px pill forces the pill past 44px, which is what made the chip overshoot the adjacent overflow trigger and opened click-dead bands above and below the filter button. The exception holds on the same two grounds as the tick's: the project is desktop-only by hard constraint (pointer input), and refresh is the chip's secondary control — the primary action is the filter toggle, which now owns the full 44px pill, and the full-size "Refresh all" button remains on the row.)*
- **Declined: date labels at major boundaries.** Considered and rejected — the 12px lane cannot host legible 14px label text, and widening the gutter enough to fit one would either steal meaningful width from a 480px stream pane or push the ruler back over the row list, reintroducing the two-tone banding defect the lane placement floor above exists to prevent. The instant tooltip already carries the full date on hover/focus, and the major/minor hierarchy carries the grouping visually — no label is needed.
- **Not a scrollbar-thumb decoration.** The overlay is its own ruler, mapping item order onto the pane — it never claimed to track the native scrollbar thumb's travel, so the previously-noted mismatch between tick positions and thumb position is not a defect: the thumb's travel is a function of `(trackHeight - thumbHeight)`, while a tick's position is a function of the item's stream index, and the two are only expected to agree at the pane's very top and bottom.
- Renders only in the stream pane (not inside detail-pane rendition iframes, and not duplicated on the overflow popover's internal scroll region).

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
