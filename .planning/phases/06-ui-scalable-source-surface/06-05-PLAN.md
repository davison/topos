<objective>
Close gap G-06-1: unify search-match emphasis across every SPA surface, and extend UI-09's
surface set to include the item title.

Two independent causes, per `.planning/debug/search-highlight-title-and-stream.md`:

- **RC-1 (scope gap, this phase).** `DetailPane.svelte`'s `<h2>` renders `{item.title}` through a
  plain text binding. `highlightText` is imported in that very file and applied to the body block
  only, because 06-01-PLAN.md scoped UI-09 to `detailBodyVariant` branches. The amplifier that makes
  this functional rather than cosmetic: `items_fts` indexes title AND preview
  (`kernel/index/schema.go`), and `snippet(items_fts, -1, ...)` auto-selects the best-matching
  column — so a **title-only match is a routine search outcome for which the app currently renders
  zero highlight on any surface**, leaving the user no explanation for why the item surfaced.
- **RC-2 (cross-phase vocabulary drift, pre-existing).** `StreamRow.svelte`'s snippet match
  treatment is Phase 3 code implementing a recorded contract (03-UI-SPEC.md:69 — weight, "rather
  than introducing a highlight color", to keep the "exactly 2 weights" rule literally true). Phase 6
  then introduced a much stronger amber vocabulary for the same concept in the kernel iframe and the
  SPA text body and never reconciled the two.

Purpose: one concept — "this text matched your search" — must have exactly one treatment, and it
must appear on the surface that actually carries the match.

Output: a single project-wide `.search-highlight` component class, applied to the detail-pane title,
the stream-row title and the search-result snippet; the retired weight-only rule struck from
03-UI-SPEC.md with its rationale addressed; UI-09's ambiguous wording disambiguated; and a
comment-stripped source-scan guard so the treatment cannot drift apart again.

**No tracer task.** Gap closure against four already-shipped, already-wired components — the
architecture is proven and a thin end-to-end slice would add no information. Every task below is a
surgical edit to a live surface.
</objective>

**app.css.** Add the match-emphasis class to the existing `@layer components` block, alongside
`.stream-row-surface`. Its declarations are exactly the ones the scoped block in DetailPane holds
today — background from `var(--warning)`, foreground from `var(--background)`, a 2px radius and 1px
horizontal padding — resolved through those existing theme tokens, never a literal hex value, so
this stays consistent with the derived-token discipline `scrollbar-theme.test.ts` already guards.
Head the rule with a comment naming the three surfaces that now share it (kernel rendition
stylesheet, detail pane, stream/search row) and stating that a change here is a change to all
three. Do not introduce a new colour token: the amber and near-black already exist and the kernel's
own rule in `kernel/httpapi/rendition.go` already paints the identical pair — that file is NOT in
this plan's scope and must not be edited.

**DetailPane.svelte.** Delete the component-scoped `<style>` block outright — a Svelte-scoped class
cannot be shared with a sibling component, which is the mechanical reason the vocabularies drifted.
Relocate its explanatory comment into the app.css rule. Then apply highlighting to the title: the
`<h2>` keeps its own type-role classes unchanged and its text is replaced by an each-block over
`highlightText(item.title, searchQuery)`, rendering one `<span>` per segment with the shared class
on matched segments only and no class on unmatched ones — structurally identical to the existing
`loadedTextBlock` treatment. Segment text renders through Svelte's default text binding; `highlightText`
returns plain strings and never markup, so no raw-HTML directive is introduced anywhere. Update the
comment above `loadedTextBlock` that currently says the class is "defined below" — it now resolves
from the global stylesheet.

**StreamRow.svelte.** Add an optional `searchQuery` prop, typed `string`, defaulting to the empty
string, so the unfiltered stream (which never passes it) is byte-identical to today. Import
`highlightText` from `$lib/format`. Apply it to the title exactly as in DetailPane: the `<p>` keeps
its own type-role classes and its text becomes an each-block of segments carrying the shared class
on matches. In the snippet branch, replace the weight-based match treatment on matched
`parseSnippet` segments with the same shared class — the treatment changes colour only, never size
or weight, so the row's fixed 152px height and two-line clamp are untouched. Rewrite the file's
head comment, which currently documents the retired weight-not-colour rule, to describe the shared
amber treatment and to state that the class lives in app.css.

**SearchResults.svelte.** Pass the live `query` down to each rendered row as the `searchQuery` prop,
so a search-results row can highlight its own title. `StreamList.svelte` is deliberately NOT
modified: search results replace the stream entirely while a query is active, so the plain stream
has no query to highlight against and needs no prop.

Prohibition: do not reach for a raw-HTML directive on any of these surfaces. Item titles are
source-controlled data (email subjects, chat names, document filenames) and the whole reason this
change is safe is that every segment stays a text binding (T-06-11).
