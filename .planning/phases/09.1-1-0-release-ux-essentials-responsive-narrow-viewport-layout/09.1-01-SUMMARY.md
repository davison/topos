## Decisions Made

- Followed all three `planner_resolutions` (R1 `invisible` not `hidden`, R2 per-spec viewport not a new Playwright project, R3 route owns the close decision) exactly as locked.
- e2e interaction with the header while the takeover is open (filter-chip toggle, case 6; reassigning selection via a second row, case 5) uses `locator.dispatchEvent('click')`, not `.click({ force: true })`: the concealed elements sit both outside Chromium's accessibility tree (`visibility:hidden`) and behind the detail pane's own `fixed inset-0 z-20` overlay, so a real (even force-flagged) mouse click's hit-testing lands on the overlay, not the target. `dispatchEvent` fires the event directly at the DOM node, exercising the real handler without needing either check to pass.
- Case 6 (backstop truth) opens the takeover BEFORE toggling the filter chip (not after) — with 2+ mock instances (bumped for the checkpoint fixes), neither chip fits inline in the header's row even before any filter is applied, so the interaction now goes through the "N more sources" overflow popover (whose content portals to `document.body`, unaffected by the header's `visibility:hidden`) rather than the row directly.
- Checkpoint issue 1's fix is root-caused, not guess-patched: `overflow-hidden` added directly to `<header>` (a DOM ancestor, but not `measureEl`'s containing block, since nothing in this app sets `position: relative`) was verified LIVE to have zero clipping effect, before landing on the correct fix (making the wrapper itself the containing block via `position: relative`).
- Checkpoint issue 2 ships as an instant snap (no CSS transition): reproduced live that an active multi-frame transition re-triggers the browser's own reflow-driven scrollTop reset on every intermediate frame, arriving after a one-shot rAF restore and silently overwriting it. A smoothly animated version is a real, tracked follow-up (needs the restore to track the transition itself, e.g. bounded by `transitionend`), not implemented in this checkpoint-fix pass.
- Checkpoint issue 2's header-collapse feature is scoped to the STREAM pane's own scroll container only (`streamScrollEl`, already bound in `+page.svelte`) — this app has no window-level scrolling. Extending the same collapse behaviour to DetailPane's own internal scroll (relevant at 768-1024px side-by-side, when reading a selected item) is a documented, deliberate gap: `DetailPane.svelte` exposes no scroll-container ref today, and wiring one is a larger change than this checkpoint fix warrants.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `navigateFilters` silently closed the takeover on a filter change**
- **Found during:** Task 3, writing the e2e spec's backstop case (case 6)
- **Issue:** `goto(url, { replaceState: true, keepFocus: true, noScroll: true })` never set `state`, and SvelteKit's `goto` defaults an omitted `state` option to `{}` — every filter-chip toggle replaced the takeover's history entry with an empty state object, clearing `page.state.itemOpen` and closing the takeover as a side effect. This directly contradicted 09.1-UI-SPEC.md's own design description ("a `replaceState` call does not disturb `page.state`, so it cannot accidentally close the takeover") and would have failed the backstop truth outright.
- **Fix:** Added `state: page.state` to the `goto` options in `navigateFilters`, so the replaceState-driven URL write carries the CURRENT `page.state` (including `itemOpen`) forward instead of defaulting to `{}`.
- **Files modified:** `web/src/routes/w/[webspace]/+page.svelte`
- **Verification:** `web/e2e/specs/09-1-mobile-takeover.spec.ts` case 6 passes; `npm run check`/`npm run test` both green.
- **Committed in:** `4b64440` (Task 3 commit)

**2. [Checkpoint round 1, issue 1 — Rule 1 bug] Horizontal page overflow at narrow viewports**
- **Found during:** Checkpoint response — human reported a horizontal scrollbar and content bleeding past the viewport edge on a real phone, in both the plain stream and takeover states.
- **Root cause (verified live, not guessed):** `WebspaceHeader.svelte`'s off-screen chip-width measurement clone (`measureEl`) is `position: absolute` with no `position: relative` ancestor anywhere in this app, so its containing block was the initial containing block, not any nearby DOM element. Its full, deliberately-unclipped natural width leaked into `document.documentElement.scrollWidth` once 2+ source instances made that width exceed the viewport. `overflow-hidden` added directly to `<header>` (a real DOM ancestor) was confirmed to have **zero** effect, since it isn't the clone's containing block.
- **Fix:** Wrapped `measureEl` and its sibling overflow-trigger clone in a new `relative h-0 overflow-hidden` container, making it their real containing block. `app.css` also gained `overflow-x: hidden` on `html`/`body` as a defense-in-depth backstop.
- **Files modified:** `web/src/lib/components/WebspaceHeader.svelte`, `web/src/app.css`
- **Verification:** `web/e2e/specs/09-1-mobile-takeover.spec.ts` cases 9 and 11; `scrollWidth <= clientWidth` at 390x844 (stream and takeover) and 844x390; a horizontal wheel gesture confirmed unable to move `scrollX`.
- **Committed in:** `713625f`

**3. [Checkpoint round 1, issue 2 — approved deviation, not in original must_haves] Auto-collapsing webspace header on scroll**
- **Requested during:** Checkpoint response — human reported the header consuming too much of a landscape-phone viewport (768-1024px side-by-side), leaving little room for stream/detail content, and asked for a standard "collapse on scroll-down, re-inflate on scroll-up" pattern below 1024px.
- **Implementation:** `WebspaceHeader.svelte` gains a `collapsed` prop; below 1024px, the chip row/search box/saved filters/filter-error alert collapse away (the switcher stays visible), scoped entirely under `max-lg:` so desktop is provably unaffected. `+page.svelte` owns the scroll-direction decision, hooked to the stream pane's own scroll container.
- **Two further bugs found and fixed live while stabilizing this against the existing D-01 scroll-preservation test:** (a) collapsing/expanding changes `<main>`'s available height, which changes the stream's own `clientHeight`, which the browser responds to by resetting that same element's `scrollTop` — fixed by capturing and restoring `scrollTop` across two animation frames after each toggle; (b) that restore's own reflow could itself trigger a spurious `scroll` event, creating a self-sustaining collapse/expand loop — fixed with a ~200ms re-entrancy guard, plus a dead-end guard that forces the header back open if collapsing would leave nothing left to scroll.
- **Files modified:** `web/src/lib/components/WebspaceHeader.svelte`, `web/src/routes/w/[webspace]/+page.svelte`
- **Verification:** `web/e2e/specs/09-1-mobile-takeover.spec.ts` cases 10 and 11 (collapse/re-inflate, both at portrait and landscape-phone widths) and case 7 (desktop unaffected); stable across repeated runs.
- **Committed in:** `b67cef9`
