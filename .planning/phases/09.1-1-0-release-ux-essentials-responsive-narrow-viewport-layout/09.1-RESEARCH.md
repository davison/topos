# Phase 09.1: 1.0 Release UX Essentials - Research

**Researched:** 2026-08-11
**Domain:** SvelteKit 2/Svelte 5 responsive layout (shallow routing + Tailwind v4 breakpoints) and Go kernel first-run config bootstrap
**Confidence:** HIGH

## Summary

This phase is two independent, additive changes with no new dependencies. Both are grounded
entirely in code already in this repository — no new library, no new plugin, no new kernel
surface.

**Narrow-viewport layout**: `web/src/routes/w/[webspace]/+page.svelte` (~lines 799-895) holds
a two-pane `flex` layout with zero media queries anywhere in the app today — this phase
introduces Tailwind's responsive system for the first time. D-02's breakpoints (768px/1024px)
are Tailwind v4's *unmodified default* `md`/`lg` values, so no `@theme` breakpoint override is
needed. The takeover (D-01/D-03/D-04) needs a SvelteKit shallow-routing history entry
(`pushState`/`replaceState` from `$app/navigation`, surfaced via `page.state` from
`$app/state` — already imported in this route) — this is a genuinely new pattern for the
codebase: no `pushState`/`popstate` call exists anywhere in `web/src` today, and the *only*
existing URL-persisted state is the `?sources=` filter param, written via `replaceState`
(never a new history entry) — selection state (`selectedId`) and search query are currently
**not** in the URL at all. The compact-card work (D-05/D-06/D-07) touches a component
(`StreamRow.svelte`) whose fixed height (`152px`, not `~110px`) lives in `app.css`'s
`@layer components`, which Tailwind v4's layer order guarantees loses to any `@layer
utilities` class placed on the row — so a responsive Tailwind height utility on the row
element itself is sufficient without touching that CSS rule. Three structural source-scan
tests (`pane-layout.test.ts`, `source-chip-pill.test.ts`, `marker-overlay.test.ts` — comment-
stripped substring scans over raw component source, no DOM/component-mount harness exists in
this repo) assert exact class strings and will need deliberate updates, not workarounds.

**First-run bootstrap**: `cmd/topos/main.go`'s `setup()` calls `config.NewStore(configPath())`
unconditionally; `config.NewStore` → `LoadRaw` → `os.ReadFile(path)`, and a missing file
returns a wrapped (`%w`) `os.ErrNotExist`-compatible error with no bootstrap branch anywhere in
the call chain today. The fix is small and entirely mechanical using code that already
exists: on `errors.Is(err, os.ErrNotExist)`, `os.MkdirAll` the config directory (nothing in
`kernel/config` does this today — only `kernel/index/store.go:30` creates its own directory),
build a default `*config.Config{}` from the four already-exported `Default*` constants plus
empty (non-nil) `Sources`/`Webspaces` maps, and call the existing `config.WriteCanonical`
(unchanged) to write it, then continue to `config.NewStore` normally so the just-written file
round-trips through the real load/validate path. `Load` accepting a config with **zero**
webspaces is already proven: `validateWebspaces` loops over `cfg.Webspaces` and returns `nil`
trivially when that map is empty, and `TestValidate_EmptyWebspaceShellIsAcceptedWithZeroSourcesConfigured`
proves a config with zero sources plus a single empty-shell webspace loads — an *even
emptier* config (zero webspaces too) validates for the identical structural reason (nothing to
iterate). No new kernel validation logic is needed. The existing root route
(`web/src/routes/+page.svelte`) **already** renders exactly the greeting this phase needs
("No webspaces yet" + `CreateWebspaceModal`) the moment `GET /api/config` reports zero
webspaces — this is very likely pure reuse, not a new component, confirming CONTEXT.md's own
framing that Phase 7 already ships this piece.

**Primary recommendation:** Implement the takeover via Tailwind `md:`/`lg:` responsive
prefixes plus `pushState`/`page.state` shallow routing (no new libraries); implement the
compact card via a `max-md:`-scoped Tailwind height/typography override directly on
`StreamRow.svelte`'s existing elements (the `@layer utilities` vs `@layer components` cascade
makes this safe without editing `app.css`); implement bootstrap as a ~15-line addition to
`cmd/topos/main.go`'s `setup()` using only exported `kernel/config` symbols that already
exist. The one design decision requiring explicit resolution before planning proceeds is the
**e2e harness's fixed-port conflict** with the bootstrap default (see Common Pitfalls #1) —
every other finding below is close to mechanical.

### Locked Decisions

- **D-01: Takeover + back, not literal stacking.** At mobile width, tapping a stream item opens the detail as a full-viewport takeover with a back affordance; the stream's scroll position is preserved for the return trip. The roadmap's "stacks below" wording is superseded by this decision — no half-visible side-by-side or scroll-down-to-detail states.
- **D-02: Breakpoint is 768px, with a proportional mid-range band.** Below 768px (Tailwind `md`): takeover layout + compact cards. Between 768–1024px: side-by-side survives, but the stream pane gives up its fixed `w-[480px]` and shrinks proportionally so the detail pane stays usable. At ≥1024px: today's layout exactly (fixed 480px stream when a detail is open).
- **D-03: Back = visible control + browser history entry.** Opening the takeover pushes a history entry so the phone's back gesture/button closes the detail and returns to the stream instead of leaving the app. A visible back control in the detail bar does the same. (No edge-swipe gesture — explicitly declined as extra work that can fight rendition-iframe scrolling.)
- **D-04: Takeover hides the app header.** While the takeover is open, the webspace switcher / chip row / search header gives way to one slim detail bar: back control, item title, open-in-source affordance. Back restores the full header with the stream. Maximum reading height for renditions on a phone.
- **D-05: Compact cards apply below 768px only.** The 768–1024px band and desktop keep today's card geometry exactly (20px title, 14px meta, 16px two-line snippet). Compact is part of the mobile layout, not a global density change.
- **D-06: Compact card composition: title + one merged meta line + one-line snippet.** Target ~55–60px per card (vs ~110px today), title ~16px, meta ~12px, snippet clamped to a single line at ~13–14px. Search highlighting still lands in title + snippet segments exactly as today.
- **D-07: The merged meta line keeps everything, truncating to fit:** plugin icon + source display name + group label + date on one line, with source name / group label truncating first when space runs out. Rationale: the plugin icon alone is ambiguous when two instances share a plugin type (Home email vs Work email). The degraded-sync warning dot survives at every width — health honesty is not negotiable.
- **D-08: Search-result rows adopt the compact geometry below 768px** (highlighting intact); **the date-marker scrollbar ruler is hidden below 768px** — reclaims its 12px lane and avoids building touch affordances for a hover-designed control. The ruler is unchanged at ≥768px.

### Pattern 1: Breakpoint-driven pane composition (Tailwind prefixes, no new state machine)

**What:** Extend the existing conditional class strings on the stream-wrapper and detail-
wrapper `div`s in `+page.svelte` with `md:`/`lg:` prefixes rather than introducing a
JS-computed "layout mode" variable. Below `md` (768px), the stream pane is full-width
(`w-full`) and the detail pane, when open, becomes a `fixed inset-0` (or `absolute inset-0`
within a suitable positioned ancestor) full-viewport overlay. Between `md` and `lg`
(768–1024px), the stream pane loses its unconditional `w-[480px]` in favor of a proportional
width (e.g. a percentage or `clamp()` via an arbitrary Tailwind value) that only takes effect
in that band; at `lg` and above, `lg:w-[480px]` restores today's exact fixed width.

**When to use:** Any layout decision that depends purely on viewport width, not on
asynchronous data — matches every requirement in D-01/D-02.

**Why this is safe against the existing structural test:** `pane-layout.test.ts`'s
`FIXED_PX_WIDTH` regex (`/w-\[\d+px\]/`, unanchored) matches `w-[480px]` as a **substring**
regardless of a `lg:` prefix in front of it — so `lg:w-[480px]` still satisfies a check written
against the unprefixed literal. The test's `findUniqueClassAttr(marker)` helper requires the
marker string (`'overflow-x-hidden'`, `'border-l'`) to appear in **exactly one** `class="..."`
attribute in the whole route file [VERIFIED: web/src/lib/pane-layout.test.ts:42-56, full file
read] — any new element introduced for the takeover (e.g. a wrapping wrapper for the slim
detail bar) must not accidentally introduce a second occurrence of either marker string, or
the test's own uniqueness assertion fails before reaching the width assertions. Plan tasks
must update this test's assertions (not merely hope they still pass) once the class strings
gain viewport-conditional structure, since the test today asserts the ≥1024px-only fixed-width
behavior as if it were universal.

### Pattern 2: Takeover via `pushState`/`page.state`, not a boolean `$state`

**What:** Rather than a plain `let takeoverOpen = $state(false)`, drive the takeover's
visibility from `page.state` (SvelteKit's shallow-routing state, from `$app/state` — already
imported as `page` in this route [VERIFIED: web/src/routes/w/[webspace]/+page.svelte:2]).
Opening the takeover calls `pushState('', { ...page.state, itemOpen: true })` (or a
similarly-named `App.PageState` field); the back button, back gesture, and the visible back
control's own `history.back()` call all converge on the same `popstate`-driven state
transition, so there is exactly one code path that closes the takeover, not two independently-
maintained ones.

**When to use:** Exactly D-03's requirement — "a visible control + browser history entry" that
must behave identically whichever one the user triggers.

**Example (illustrative, from official docs, adapted to this repo's imports):**
```svelte
<!-- Source: https://svelte.dev/docs/kit/shallow-routing (CITED, fetched this session) -->
<script lang="ts">
  import { page } from '$app/state';
  import { pushState, replaceState } from '$app/navigation';

  function openTakeover(id: string) {
    selectedId = id;
    // '' keeps the URL unchanged — only page.state changes, no real navigation
    pushState('', { itemOpen: true });
  }

  function closeTakeover() {
    history.back(); // symmetric with the back button/gesture — same popstate path
  }
</script>
```
`page.state` is empty during SSR and on initial load [CITED:
https://svelte.dev/docs/kit/shallow-routing] — irrelevant here since this app is
`adapter-static` SPA mode with no SSR, but worth the plan noting explicitly so a task doesn't
assume `page.state.itemOpen` is meaningful before the client router has mounted.

**Composing with existing URL state (the discretion item CONTEXT.md flags):** the `?sources=`
filter param is written via `goto(..., { replaceState: true, ... })`
[VERIFIED: web/src/routes/w/[webspace]/+page.svelte:644-654, quoted below] — a **real**
navigation that replaces the current history entry, not shallow routing. `pushState`/
`replaceState` from `$app/navigation` operate on `page.state` independent of the URL's query
string, so a chip toggle while the takeover is open does not by itself disturb the takeover's
own history entry, and vice versa — but the plan should verify this interaction explicitly
(e.g., toggling a filter chip while the takeover is open, then pressing back) rather than
assume it, since this is new-to-the-codebase territory with no existing precedent to lean on.

```
// VERIFIED quote, web/src/routes/w/[webspace]/+page.svelte:651-654
// replaceState (not a new history entry) so toggling a chip
const url = new URL(page.url);
...
goto(`${url.pathname}${url.search}`, { replaceState: true, keepFocus: true, noScroll: true });
```

### Pattern 3: Compact-card override lands in `@layer utilities`, wins over `@layer components` automatically

**What:** `StreamRow.svelte`'s fixed height comes from a CSS class, not an inline utility:

```css
/* VERIFIED quote, web/src/app.css:236-251 */
@layer components {
	/*
	 * Fixed-height stream row surface (01-03 StreamRow.svelte /
	 * StreamList.svelte loading skeleton). ...
	 * = 32 + 24 + 8 + 40 + 48 = 152px.
	 */
	.stream-row-surface {
		height: 152px;
	}
```

Tailwind v4's built-in layer order is `theme, base, components, utilities` — a class emitted
into `@layer utilities` (any Tailwind utility, including arbitrary-value ones like
`max-md:h-[58px]`) always wins over a rule in `@layer components`, regardless of source order
or specificity tie-breaking, because CSS layers are ordered by declaration, not specificity
[CITED: tailwindcss.com — v4's `@layer` cascade documentation; cross-checked via WebSearch
results confirming the `@theme`/layer model]. This means the compact-card height/typography
override can be applied directly on `StreamRow.svelte`'s own elements (`class="... max-md:h-
[58px] ..."` alongside the existing `stream-row-surface` class) without editing `app.css`'s
rule at all — no specificity fight, no `!important`.

**When to use:** Any compact-card sizing override (D-06's ~55–60px target, D-07's meta-line
reflow). This is also the **CSS/Tailwind-breakpoint-driven** option CONTEXT.md's discretion
note names as an alternative to a prop-driven variant — research supports it as the lower-
friction choice given the app has zero JS-computed layout state today and D-05's rule
("compact applies below 768px only, nothing else changes") is a pure width predicate, exactly
what a CSS breakpoint expresses natively.

**Alternative (prop-driven) if the planner prefers it:** pass a `compact: boolean` prop
computed once from a `matchMedia('(max-width: 767px)')` listener (or SvelteKit's own resize
observable pattern already used in `WebspaceHeader.svelte` — see `resize-observer.ts`
[VERIFIED: web/src/lib/components/WebspaceHeader.svelte:2, 277-282]) and branch JSX/classes
in the component. This trades a CSS-cascade dependency for a JS listener + an extra render
path; either is workable, but the CSS-only route needs zero new state and zero new listeners.

**before** calling `WriteCanonical`. This is a concrete, easy-to-miss implementation step —
flag it explicitly as a plan task, not an assumed side effect of `WriteCanonical`.

### Anti-Patterns to Avoid

- **Do not write `cfgStore.Expanded()` (or any expanded/secret-resolved `*Config`) to disk.**
  `WriteCanonical`'s own doc comment states this is a one-way privacy breach (D-05) — the
  bootstrap default has no secrets in it regardless (a fresh install has zero sources
  configured), but the pattern must stay identical to every other write path in this codebase:
  raw form only, ever.
- **Do not overwrite an existing `config.toml`.** The bootstrap branch must trigger *only* on
  `errors.Is(err, os.ErrNotExist)` — any other `LoadRaw` failure (malformed TOML, a failed
  validation on an existing file, a permission error) must continue to fail loudly exactly as
  today; silently replacing an operator's malformed-but-present file with a fresh default would
  be silent data loss.
- **Do not hand-roll a `window.addEventListener('popstate', ...)` listener for the takeover.**
  SvelteKit's own `page.state` already reacts to `popstate` for entries created via
  `pushState`/`replaceState` [CITED: shallow-routing docs] — a hand-rolled listener would
  either duplicate or race SvelteKit's internal router.
- **Do not introduce a JS-computed viewport-width `$state` variable duplicating what Tailwind's
  `md:`/`lg:` prefixes already express as pure CSS** for layout decisions that need no JS
  branching (pane width, card height). Reserve JS/`matchMedia` for behavior that genuinely
  cannot be expressed in CSS (e.g., conditionally attaching/detaching an edge-swipe gesture —
  which is explicitly out of scope per D-03's deferred item).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Back-button/back-gesture closing a modal-like view | A manual `popstate` listener + a boolean open/closed store | SvelteKit's `pushState`/`replaceState` + `page.state` (`$app/navigation`, `$app/state`) | Purpose-built for exactly this shape (modal/gallery-style shallow routes) in the official docs; avoids desyncing from SvelteKit's own router state |
| Writing a "default" config.toml | A literal hand-written TOML string / template file | `config.WriteCanonical` + the four exported `Default*` constants | `WriteCanonical` already owns the canonical header, backup rotation, and atomic write — every other config-writing surface in this codebase (the UI's `PUT /api/config`) goes through it; a hand-rolled writer would be a second, divergent implementation of the same contract |
| Detecting "config file is missing" vs. "config file is broken" | String-matching the error message | `errors.Is(err, os.ErrNotExist)` against the `%w`-wrapped error `LoadRaw` already returns [VERIFIED: kernel/config/config.go:57-60, `fmt.Errorf("config: read %s: %w", path, err)`] | The wrap chain already supports `errors.Is`; string matching is fragile against message wording changes and doesn't distinguish ENOENT from EISDIR/EACCES |
| Responsive breakpoint values | Custom pixel breakpoints via a `@theme` override | Tailwind v4's default `md` (768px) / `lg` (1024px) | D-02's exact numbers are the framework defaults — introducing a custom `@theme --breakpoint-*` would be pure unnecessary divergence |

**Key insight:** every mechanism this phase needs (shallow routing, layered CSS cascade,
canonical config writing, wrapped-error detection) already exists in this codebase or its
locked dependencies — the entire phase is composition of existing primitives, not new
infrastructure.

## Common Pitfalls

### Pitfall 1: The bootstrap default config's fixed port breaks the e2e harness's ephemeral-port invariant

**What goes wrong:** `DefaultListen = "127.0.0.1:7777"` [VERIFIED: kernel/config/types.go:249]
is a **fixed** port. The Playwright harness's entire hermeticity model depends on an
OS-assigned ephemeral port per kernel instance: `kernel.ts`'s `launchKernel` always calls
`allocateEphemeralPort()` and then `buildConfig`/`writeConfig` **always** writes a
`config.toml` containing that port *before* spawning the kernel
[VERIFIED: web/e2e/fixtures/kernel.ts:261-276, full file read;
web/e2e/fixtures/config-builder.ts:53-58, "opts.port ... [server].listen binds"]. A genuine
"no config file present" e2e spec — which CONTEXT.md's code_context explicitly calls for
("the bootstrap spec inverts this: boot with no config file...") — cannot use this existing
fixture path unmodified: if the fixture simply skips `writeConfig`, the kernel bootstraps its
own default at the **fixed** `127.0.0.1:7777`, not the fixture's OS-assigned port, and the
fixture's `baseURL` (built from the port it allocated, never used) will not match where the
kernel is actually listening — `waitForKernelReady` will poll the wrong address and time out.
Worse, running this spec on a developer's own machine while `make dev` (which binds the same
fixed default) is already running on `127.0.0.1:7777` would collide outright.

**Why it happens:** the bootstrap feature is deliberately writing the *package* default, and
the package default was never designed with a test harness's ephemeral-port requirement in
mind — these two concerns (a friendly first-run default vs. a hermetic, parallel-safe test
environment) are structurally in tension.

**How to avoid — the plan must pick one of these explicitly, not discover this at execution
time:**
1. Test the bootstrap *logic* (missing file → written default → loads cleanly) at the Go
   level — a `kernel/config` or `cmd/topos` test that points `configPath()`/`NewStore` at a
   temp dir with no file present and asserts the resulting file + successful load — and let
   the **e2e** spec assert only the *UI-visible* consequence (the greeting), using the
   **existing** empty-shell fixture shape (`emptyShellWebspace` or an equivalent zero-webspace
   `configSpec` — no genuinely-missing file needed for the browser-level assertion, since the
   SPA-visible behavior is identical either way: `GET /api/config` returning
   `{webspaces: {}}`).
2. If a true missing-file e2e spec is wanted, extend the fixture to spawn the kernel with an
   env-based listen override (this requires a **new** kernel capability — an environment
   variable read in `cmd/topos/main.go`, or a `-listen` flag — that does not exist today
   [VERIFIED: grep of `cmd/topos/main.go` and `kernel/config/*.go` — no `TOPOS_LISTEN` or
   equivalent found]), and have the fixture set it before deleting/never-writing
   `config.toml`. This is real new kernel surface, not a pure test-only change — flag it to
   the user as a discretion/scope decision if the planner goes this route, since it slightly
   grows the kernel's config surface beyond what CONTEXT.md scoped.

### Pitfall 2: Structural source-scan tests will fail (correctly) the moment class strings gain breakpoint prefixes — treat failures as the update signal, not as unrelated flakiness

**What goes wrong:** `pane-layout.test.ts`'s uniqueness assertions
(`findUniqueClassAttr('overflow-x-hidden')` / `'border-l'` must each match **exactly one**
`class="..."` attribute in the whole route file [VERIFIED: web/src/lib/pane-layout.test.ts:42-
56]) will break if the takeover introduces a second element carrying either marker string (a
plausible outcome — a slim detail-bar wrapper might reasonably also want `border-l` or an
overflow utility). Separately, `source-chip-pill.test.ts`'s reveal-scoping assertions
(`group-hover:opacity-100`, `group-has-[:focus-visible]:opacity-100`, explicitly asserting
`group-focus-within:opacity-100` is **absent** [VERIFIED:
web/src/lib/components/source-chip-pill.test.ts:175-190]) describe a **hover-only** reveal
model for the chip's overflow-menu trigger — CONTEXT.md's discretion area requires a touch
equivalent for exactly this affordance. Whatever touch-reveal mechanism the plan adds (e.g. a
`@media (hover: none)` fallback, or a persistently-visible-below-768px variant) must be
reflected as a **new**, deliberately-added assertion in this file, not left for the existing
assertions to (possibly) still coincidentally pass.

**Why it happens:** this repo's house pattern for UI structural proof is comment-stripped
source-text scanning (no component-mount harness exists — `vite.config.ts`'s test block runs
`environment: 'node'` [cited in both test files' own header comments]) — these tests are
*exact-string* contracts, not behavioral/rendered-DOM assertions, so any change to the literal
class list is a contract change by definition, whether or not the visual behavior is "still
correct."

**How to avoid:** treat every one of `pane-layout.test.ts`, `source-chip-pill.test.ts`, and
`marker-overlay.test.ts` as a file the plan **will** touch, with tasks that state which new
assertions are added and which old ones are widened/relaxed to admit the breakpoint-prefixed
strings — mirroring CONTEXT.md's own instruction: "update them as behavior contracts, not
obstacles."

### Pitfall 3: `errors.Is` must be checked before assuming "file missing" — a permission error or a directory-instead-of-file must still fail loudly

**What goes wrong:** `os.ReadFile` returns different underlying errors for "path does not
exist" (`ENOENT`/`os.ErrNotExist`), "permission denied" (`EACCES`), and "path is a directory"
(`EISDIR`) — a bootstrap implementation that treats *any* `LoadRaw` failure as "must be
missing, let's write a default" would silently paper over a real misconfiguration (e.g. a
config directory the user cannot read) by writing a *second*, different file the user never
asked for, or attempting a write that itself fails confusingly.

**Why it happens:** it's tempting to write `if err != nil { bootstrap() }` since that's the
simplest code — but `LoadRaw`'s wrapped error [VERIFIED: kernel/config/config.go:57-60,
`fmt.Errorf("config: read %s: %w", path, err)`] preserves the underlying `%w`-wrapped cause
specifically so callers *can* discriminate, and the existing fail-loud discipline throughout
this codebase (named validation errors everywhere in `kernel/config/config.go`) argues strongly
for keeping that discipline here too.

**How to avoid:** gate the bootstrap branch strictly on `errors.Is(err, os.ErrNotExist)`;
every other error from `config.NewStore` must continue to propagate to `fatal(err)` exactly as
today.

**Warning signs:** a test that only exercises "file present but empty/malformed" would not
catch a `bootstrap()` call gated too broadly — the plan's Wave 0/verification pass should
include a negative case (unreadable file, or a directory at the config path) proving the
bootstrap path is *not* taken there.

### Pitfall 4: `.stream-row-meta`'s existing `max-height: 40px` clip is tuned for the desktop meta line, not the compact one

**What goes wrong:** D-07's compact meta line adds a new visible element (the source display
name, today only present as a `title` attribute for hover, not rendered text
[VERIFIED: web/src/lib/components/StreamRow.svelte:113, `<span class="shrink-0"
title={sourceDisplayName || undefined}>`]) into the same flex-wrap strip that already clips at
`max-height: 40px` [VERIFIED: web/src/app.css:255-258]. At the compact card's target overall
height (~55-60px vs. today's 152px), a `max-height: 40px` clip on just the meta line would
consume nearly the entire card, leaving no room for the title and single-line snippet D-06
also requires.

**Why it happens:** `.stream-row-meta`'s clip height was tuned against the desktop row's own
152px budget (the comment breaks down `32 + 24 + 8 + 40 + 48 = 152`
[VERIFIED: web/src/app.css:236-247]); reusing the class unmodified at compact size inherits a
budget that was never sized for it.

**How to avoid:** the compact variant needs its own meta-line height budget (D-06 targets
~12px meta text on roughly one line, not a wrapping multi-line clip) — either a
`max-md:`-scoped override on the meta strip's own class list, or restructuring the compact
meta line to `flex-nowrap` + `truncate` (matching D-07's own "source name / group label
truncate first" requirement) rather than the desktop's `flex-wrap` badge-clip approach. This is
a genuinely different layout strategy for the meta line at compact size, not a smaller version
of the same one.

## Code Examples

### Bootstrap branch in `setup()` (illustrative shape, using verified exported symbols only)

```go
// Illustrative — composed from VERIFIED exported symbols in kernel/config
// (types.go:248-253, writer.go:40) and the existing setup() shape
// (cmd/topos/main.go:108-121). Exact placement/helper-function boundary is
// a planning decision (see Pattern 4's "design choice for the planner").
func setup(ctx context.Context, logger hclog.Logger) (*config.Store, *index.Store, error) {
	path := configPath()
	cfgStore, err := config.NewStore(path)
	if err != nil {
		if errors.Is(err, os.ErrNotExist) {
			if mkErr := os.MkdirAll(filepath.Dir(path), 0o700); mkErr != nil {
				return nil, nil, fmt.Errorf("bootstrap config dir: %w", mkErr)
			}
			defaultCfg := &config.Config{
				Server:    config.ServerConfig{Listen: config.DefaultListen},
				Index:     config.IndexConfig{Path: config.DefaultIndexPath},
				Plugins:   config.PluginsConfig{Dir: config.DefaultPluginsDir},
				Sync:      config.SyncConfig{Interval: config.DefaultSyncInterval},
				Sources:   map[string]config.Source{},
				Webspaces: map[string]config.Webspace{},
			}
			if wErr := config.WriteCanonical(path, defaultCfg); wErr != nil {
				return nil, nil, fmt.Errorf("bootstrap config write: %w", wErr)
			}
			cfgStore, err = config.NewStore(path) // re-load through the normal path
		}
		if err != nil {
			return nil, nil, err
		}
	}
	cfg := cfgStore.Expanded()

	store, err := index.Open(cfg.Index.Path)
	if err != nil {
		return nil, nil, err
	}
	return cfgStore, store, nil
}
```

## Open Questions

1. **Should `topos sync` also bootstrap, or only `serve`?**
   - What we know: both `runServe` and `runSync` call the same `setup()` function
     [VERIFIED: cmd/topos/main.go:137 (`runSync`), 172 (`runServe`), both call `setup(ctx,
     logger)`] — so whatever branch is added to `setup()` automatically applies to both
     entry points with no extra code.
   - What's unclear: whether that's actually *desired* UX — a user running `topos sync`
     (e.g. from a cron job or a scripted first-install check) with no config file might prefer
     a clear "run `topos serve` first" error rather than a silent bootstrap-and-exit-with-zero-
     items result.
   - Recommendation: CONTEXT.md explicitly lists this as a discretion item — the research
     finding is that bootstrapping in `setup()` naturally covers both without extra code, so
     the only real decision is whether `runSync` should specifically *opt out* of the shared
     bootstrap branch (a small, easy carve-out if the user/planner wants `sync` to keep
     failing loudly on a missing file rather than silently succeeding with zero synced
     sources).

2. **Does the mid-range band (768–1024px) need a literal proportional-width formula, or is a
   simpler fixed intermediate width (e.g. `w-[320px]`) an acceptable reading of "shrinks
   proportionally"?**
   - What we know: D-02 says "shrinks proportionally so the detail pane stays usable" —
     no exact formula is specified in CONTEXT.md.
   - What's unclear: whether "proportionally" means a CSS percentage/`clamp()` of the viewport
     width, or simply "smaller than 480px, however achieved."
   - Recommendation: a `clamp()`-based Tailwind arbitrary value (e.g. `md:w-[clamp(240px,30vw,400px)]`)
     satisfies "proportional" literally and degrades gracefully across the whole 768-1024px
     band without a hard-coded midpoint; flag this specific CSS value as something the planner
     should propose and the UAT/checkpoint step should visually confirm, since it's a genuine
     design judgment call, not something this research can verify from existing code (no
     current usage of `clamp()` anywhere in this codebase to pattern-match against).
