# Phase 09.1: Code Review Report

**Reviewed:** 2026-08-12T00:00:00Z
**Depth:** standard
**Files Reviewed:** 18
**Status:** issues_found

## Summary

This phase makes the web UI responsive below 768px (mobile detail takeover,
compact 60px stream rows, touch-adapted header) and turns a missing
`config.toml` into a first-run bootstrap event in `cmd/topos`. The Go side
(`bootstrapConfig`, `DefaultConfig`, the `os.ErrNotExist` gate) is careful
and well-tested: `go build ./...` is clean, `go test ./cmd/topos/...
./kernel/config/...` passes, the gate correctly declines on every non-ENOENT
error (malformed TOML, permission denied, an existing-but-broken file), the
written directory/file permissions are 0700/0600 as intended, and only the
raw (secret-free) `DefaultConfig()` is ever passed to `WriteCanonical` —
consistent with D-05's secret-discipline requirement. No source-mutation or
privacy-constraint violation was found (plugins are not touched by this
phase; the bootstrap path only ever writes the kernel's own local
`config.toml`).

The frontend changes (scroll-driven header auto-collapse, mobile takeover,
compact rows) are unit- and e2e-tested (`vitest` passes for the three
structural guard files reviewed here; `svelte-check` reports 0 errors) and
the re-entrancy guard around the collapse/scroll interaction is mostly
sound. Two real correctness gaps remain in that interaction, plus a
keyboard-accessibility gap in the same collapsed-header region and a minor
data-integrity race on the Go bootstrap path. None of these rise to
data-loss/security/crash severity, so there are no Critical findings, but
all four Warnings below are worth fixing before this ships as the
narrow-viewport UX gets architecturally locked in.

## Warnings

### WR-01: Filter-save error alert is hidden by header auto-collapse, unlike its sibling alerts

**File:** `web/src/lib/components/WebspaceHeader.svelte:407-414` vs `web/src/lib/components/WebspaceHeader.svelte:441-443,626-630`

**Issue:** `reloadError` (line 393) and `unknownConfigKeys` (line 407) render
as destructive `Alert`s *before* the new collapsible wrapper
(`<div class="max-lg:overflow-hidden ...">` at line 441), so they stay
visible even while the header is scroll-collapsed below 1024px. `filterError`
was moved *inside* that same wrapper (line 626-630, confirmed by the diff —
it used to sit outside, at the `</header>` level, before this phase). The
component's own doc comment for `reloadError` explicitly claims "shares the
identical header-region treatment" with `filterError` (lines 74-76), but the
two now behave differently: if a "Save as filter" write fails while the user
has scrolled the stream pane (or scrolls immediately after triggering it),
the destructive alert reporting the failure becomes `max-h-0 opacity-0`
along with the rest of the collapsed region, and the failure is invisible
until the user scrolls back to the top of the stream — which they have no
reason to do, since nothing on screen indicates an error occurred.

**Fix:** Render `filterError`'s `Alert` outside the collapsible wrapper,
matching `reloadError`/`unknownConfigKeys`'s placement:

```svelte
{#if unknownConfigKeys.length > 0}
	<Alert variant="destructive" class="mt-3">...</Alert>
{/if}

{#if filterError}
	<Alert variant="destructive" class="mt-3">
		<AlertDescription>{filterError}</AlertDescription>
	</Alert>
{/if}

<div class="max-lg:overflow-hidden {collapsed ? ... : ...}">
	<!-- chip row / search box / filter chips only -->
</div>
```

### WR-02: The "never stay collapsed" correction bypasses its own re-entrancy/scroll-preservation guard

**File:** `web/src/routes/w/[webspace]/+page.svelte:496-549` (the `if (streamScrollEl.scrollHeight <= streamScrollEl.clientHeight) { headerCollapsed = false; }` branch at lines 539-540)

**Issue:** `setHeaderCollapsed` is the one sanctioned way to toggle
`headerCollapsed` — it captures `scrollTop` before the toggle, restores it
across two `requestAnimationFrame`s after the browser's own reflow-driven
scrollTop reset (documented at length in this same function, lines 496-522),
and sets `suppressScrollHandling` for `HEADER_COLLAPSE_TRANSITION_MS` so that
reflow-driven "spurious native `scroll` events" (the function's own comment,
line 483-489) cannot re-trigger this same logic recursively.

The "never stay collapsed when there's nothing left to scroll" correction
inside `setHeaderCollapsed`'s own `setTimeout` callback (lines 536-547)
mutates `headerCollapsed` **directly** (`headerCollapsed = false;`, line
540), one line *after* `suppressScrollHandling` has already been reset to
`false` (line 526) and the timer has already been nulled (line 527). This
direct mutation:
- never captures `preToggleScrollTop`,
- never schedules the double-rAF restore, and
- runs with `suppressScrollHandling` already `false`,

so the exact "spurious native scroll event from a pure reflow side effect"
this file's own header comment describes as "confirmed live" is no longer
suppressed for this specific re-expand. In the general case this is
low-impact (if `scrollHeight <= clientHeight`, there is nothing to scroll to
begin with, so the lost restoration is usually a no-op), but it reintroduces
exactly the code path the guard exists to prevent, and the two mutation
sites (`setHeaderCollapsed` vs. this raw assignment) are now inconsistent
with each other — the next person to touch this function has to know this
one call site is deliberately exempt.

**Fix:** Route this correction back through `setHeaderCollapsed(false)`
rather than assigning `headerCollapsed` directly, so every mutation site
shares the same guard:

```js
if (streamScrollEl.scrollHeight <= streamScrollEl.clientHeight) {
	setHeaderCollapsed(false);
} else {
	lastStreamScrollTop = streamScrollEl.scrollTop;
}
```
(Note `setHeaderCollapsed` already no-ops when `headerCollapsed` is already
`false`, so this only fires the extra rAF/suppression machinery when it is
actually needed — and the `lastStreamScrollTop` re-baseline in the current
code needs to move to the `else`/always-run path so it doesn't get skipped
when this branch is taken.)

### WR-03: Collapsed header content is invisible but stays keyboard-focusable

**File:** `web/src/lib/components/WebspaceHeader.svelte:441-443`

**Issue:** The collapsible wrapper (`max-lg:overflow-hidden`,
`max-lg:max-h-0 max-lg:opacity-0` when `collapsed`) visually conceals the
chip row, the search box, "Save as filter", the filter-chip row and (see
WR-01) the filter error alert — but none of these interactive elements are
given `tabindex="-1"`, `inert`, or `aria-hidden="true"` when collapsed.
`max-height: 0` + `overflow: hidden` + `opacity: 0` removes the content from
view but does not remove it from the tab order or the accessibility tree, so
a keyboard user tabbing through the page while the header is
scroll-collapsed (any width below 1024px) can land focus on the (invisible)
search box, a source chip's filter button, or "Save as filter" with no
visual indication of what is focused — a real WCAG 2.4.3/2.4.7 gap, and a
worse experience than simply not being able to reach those controls at all.

**Fix:** Toggle `inert` (or `aria-hidden` + a loop clearing `tabindex`) on
the wrapper alongside `collapsed`:

```svelte
<div
	class="max-lg:overflow-hidden {collapsed ? 'max-lg:max-h-0 max-lg:opacity-0' : 'max-lg:max-h-[480px] max-lg:opacity-100'}"
	inert={collapsed}
>
```
(`inert` is broadly supported in evergreen Chromium/Firefox/Safari and is
the standard fix for exactly this "visually collapsed but still
focusable/interactive" class of bug.)

### WR-04: `bootstrapConfig` has a narrow TOCTOU window between the ENOENT read and the write

**File:** `cmd/topos/main.go:115-139` (`bootstrapConfig`), called from `setup` at `cmd/topos/main.go:156-178`

**Issue:** `bootstrapConfig` is invoked with `loadErr` already captured from
an earlier `config.NewStore(path)` call (i.e., the `os.ReadFile` inside
`LoadRaw` already ran and returned `os.ErrNotExist`). `WriteCanonical`
itself does read `path` again immediately before writing (to produce a
`.bak` backup, `kernel/config/writer.go:49-55`), but it does **not** treat
"the file now exists" as a reason to abort — it always proceeds to
back-up-then-overwrite. If a second process (e.g., `topos serve` and
`topos sync` launched together on a machine's very first run — a real
scenario `setup`'s own comment calls out as sharing one bootstrap gate,
lines 149-153 of `cmd/topos/main.go`) wins the race and creates
`config.toml` in the window between the first `NewStore` failing and this
call's `WriteCanonical`, the second process to reach `WriteCanonical` will
silently replace that just-created file with `DefaultConfig()` (preserving
the loser's content only as a `.bak`, which nothing surfaces to the user).
For a genuinely fresh install this is low-impact (both processes would
write byte-identical defaults), but it stops being low-impact the moment a
user has started editing the freshly-bootstrapped file (e.g. via the UI's
`PUT /api/config`) while a second `topos` invocation is still mid-bootstrap.

**Fix:** Either serialize the two entry points (a single bootstrap step
shared before `runServe`/`runSync` fork, rather than each calling `setup`
independently), or have `bootstrapConfig` re-check existence immediately
before calling `WriteCanonical` and decline (returning `wrote=false`, no
error) if the file has appeared in the interim, letting the caller's normal
`config.NewStore` retry pick up whatever now exists.

## Info

### IN-01: Compact stream-row height comment's arithmetic doesn't add up to the value it claims

**File:** `web/src/lib/components/StreamRow.svelte:69-75`

**Issue:** The comment documenting the below-768px row budget reads: "4px
padding (p-1) + 16px title + 4px gap + 14px meta + 4px gap + 14px snippet =
60px." Summed literally that's `4 + 16 + 4 + 14 + 4 + 14 = 56`, not 60 —
`p-1` is 4px *per side*, so vertical padding contributes 8px (top + bottom),
not the 4px the comment states; `8 + 16 + 4 + 14 + 4 + 14 = 60` is what
actually reconciles. The row's real height is hardcoded via
`max-md:h-[60px]` (line 91) and `overflow-hidden` clips any discrepancy, so
this has no runtime effect — but the wrong derivation could mislead a future
editor who changes one of these values expecting the comment's arithmetic to
still hold.

**Fix:** Correct the comment to `8px padding (p-1, both sides) + 16px title
+ 4px gap + 14px meta + 4px gap + 14px snippet = 60px`.
