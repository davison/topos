# Phase 09.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Inheritance note:** Phases 1–9 already established the design system, spacing scale, typography, and color palette — `web/src/app.css` ships these as live CSS custom properties today. This phase does **not** re-derive any of that. It is the app's **first responsive phase**: zero media queries and zero shallow-routing usage exist anywhere in `web/src` before this phase (confirmed, 09.1-RESEARCH.md). Every table below states plainly whether it is unchanged, extended, or new. No new hex color values are introduced and **no new font size** is introduced — the compact card reuses the app's existing 14px/16px sizes at a new, compact-only line-height ratio (1.0) rather than adding a 5th size (see Typography for the explicit CONTEXT.md D-06 resolution: D-06's "~12px" meta target is honored as a density *target*, not a pixel contract, per CONTEXT.md's own Specifics framing — the 4-size-maximum constraint takes precedence).

**Scope (per 09.1-CONTEXT.md, which supersedes ROADMAP.md's "stacks below" wording per D-01):**
1. Narrow-viewport pane composition — a full-viewport detail **takeover** below 768px (not literal stacking), a proportional mid-band (768–1024px), and a byte-identical desktop layout at ≥1024px.
2. Compact stream/search-result cards below 768px only (60px vs. today's 152px).
3. Header touch adaptation below 768px — every existing affordance (chip menu, filter toggle, refresh, manage-sources) stays reachable on touch; nothing silently disappears.
4. First-run bootstrap greeting — reuses Phase 7's existing zero-webspaces empty state verbatim; no new component, no new copy.

No new sources, no new correlation behavior, no agent-surface change, no new colors.

## Narrow-Viewport Pane Composition (D-01, D-02)

Three width bands, driven entirely by Tailwind breakpoint prefixes on the two existing pane wrapper `div`s in `web/src/routes/w/[webspace]/+page.svelte` (~lines 799–885) — no new `$state` variable duplicates what CSS already expresses for pure width-driven layout (RESEARCH.md's own anti-pattern guidance).

| Band | Width | Stream pane | Detail pane (when `selectedItem` is set) |
|------|-------|-------------|-------------------------------------------|
| Mobile | < 768px (`max-md`) | Hidden entirely (not unmounted — see Scroll Preservation below) whenever a detail is open; full-width (`flex-1`) when nothing is selected, unchanged | Full-viewport takeover: `fixed inset-0 z-20` overlay, own scroll region, slim bar replaces the app header (see Mobile Takeover) |
| Mid-band | 768–1024px (`md:` only) | `md:block md:w-[clamp(240px,30vw,400px)] md:shrink-0` — proportional width (D-02's "shrinks proportionally"; this exact `clamp()` formula is this document's resolution of 09.1-RESEARCH.md's Open Question 2), never the fixed 480px | `md:static md:inset-auto md:z-auto md:min-w-0 md:flex-1 md:border-l md:border-border md:pl-8` — same sibling-flex treatment as desktop, just narrower stream sibling |
| Desktop | ≥ 1024px (`lg:`) | `lg:w-[480px] lg:shrink-0` — today's exact fixed width, byte-identical (D-02 requirement) | Same sibling-flex treatment; `lg:` override on width restores the fixed 480px |

**No selection, any width:** stream pane is `flex-1` (full width) at every band — unchanged from today.

**Class-string shape (illustrative, for the planner/executor — not literal file diffs):**
```
<!-- stream wrapper -->
class={selectedItem
  ? 'hidden md:block md:w-[clamp(240px,30vw,400px)] md:shrink-0 lg:w-[480px]'
  : 'flex-1'}

<!-- detail wrapper -->
class="fixed inset-0 z-20 flex flex-col overflow-hidden bg-background
       md:static md:inset-auto md:z-auto md:min-w-0 md:flex-1 md:border-l md:border-border md:pl-8"
```
`lg:w-[480px]` and `border-l` remain present as literal substrings (just breakpoint-prefixed) — `pane-layout.test.ts`'s existing substring/uniqueness assertions match a prefixed class exactly as they match the unprefixed one today (RESEARCH.md Pattern 1), but the test's own assertions must be **widened**, not merely hoped to still pass, since today they assert the ≥1024px-only behavior as if universal — this is a required test update, not optional cleanup.

**Positioning caveat (implementation note, not a design decision):** `fixed inset-0` positions relative to the viewport unless an ancestor establishes a new containing block (a CSS `transform`/`filter`/`perspective`). No ancestor between the takeover wrapper and `<body>` currently sets any of these. If one is added later, the takeover must gain `isolation: isolate` or move to a portal — flag this explicitly if any future phase adds a transform to an ancestor of this route.

### Scroll Preservation (D-01's "stream's scroll position is preserved")

No new mechanism is needed. The stream scroll `div` is never unmounted when a detail opens today (only conditionally *rendered alongside* via `{#if selectedItem}` on the detail sibling) — hiding it with `max-md:hidden` (a CSS display toggle, not a Svelte `{#if}` removal) keeps its DOM node, and therefore its native scroll offset, alive underneath the takeover for the entire time it is open. Returning from the takeover reveals the stream exactly where the user left it, with zero explicit scroll-restoration code.

## Mobile Takeover: Slim Detail Bar (D-03, D-04)

Replaces the full app header (`WebspaceHeader.svelte` — webspace switcher, branding lockup, chip row, search box, filter chips) with **one slim bar** while the takeover is open below 768px. `WebspaceHeader` itself gains `max-md:hidden`, gated on the same takeover-active condition.

### Bar anatomy

`[back control][item title, truncated][open-in-source icon-only]` — exactly D-04's three elements, nothing more.

| Element | Spec |
|---------|------|
| Bar container | `sticky top-0 z-10 flex h-14 shrink-0 items-center gap-2 border-b border-border bg-card px-4` (56px height, multiple of 4) |
| Back control | `ArrowLeft` icon, `size-11` (44×44px, the primary-control touch floor — no exception), `variant="ghost"`, `aria-label="Back to stream"`, `onclick={() => history.back()}` — the **same** code path the phone's native back gesture/button uses (D-03's "identical behaviour whichever one the user triggers") |
| Item title | `text-[16px] leading-[1.2] font-semibold text-foreground truncate min-w-0 flex-1` — search-highlighted via the existing shared `.search-highlight` class/`highlightText` segments, same mechanism as the desktop detail-pane `<h2>` |
| Open-in-source | Icon-only variant of `OpenInSource` (new prop or sibling usage — reuses `fidelityAffordance(link.fidelity, displayName)` unchanged): `size-11` (44×44), `variant="ghost"`, icon only (`ArrowUpRight` or `AppWindow` per fidelity, unchanged icon-selection rule from 06-UI-SPEC.md), no visible label, `aria-label`/`title` = the existing full copy (`Open in {displayName}` / `Show in {displayName}` / the window-only tooltip) — the text label is dropped only from *view*, never from the accessible name |

**DetailPane.svelte's own `<header>` block** (unchanged desktop markup: `<h2>` title, `group_label`, date/labels row, full `OpenInSource`) gets exactly two elements hidden below 768px to avoid duplicating the bar: the `<h2>` and the full `<OpenInSource>` button both gain `max-md:hidden`. The `group_label` paragraph and the date/labels `div` **stay visible**, unchanged, now reading as secondary metadata beneath the bar inside the scrollable content — D-04 names only title/back/open-in-source for the *bar*, not for the whole header.

**Content padding:** below 768px, the scrollable content area beneath the bar gains `max-md:p-4` (16px) so rendition/text content is never glued to the viewport edge (today's edge padding comes entirely from the desktop-only `pl-8` on the outer wrapper, which is absent at this band).

### History-entry mechanics (D-03)

- Selecting an item while the viewport is narrow (`matchMedia('(max-width: 767px)')`) calls `pushState('', { itemOpen: true })` **in addition to** setting `selectedId` — exactly RESEARCH.md's Pattern 2. Selecting at ≥768px sets `selectedId` only, unchanged from today, no history entry.
- **Reusing the entry across selections:** selecting a *different* item while the takeover is already open (e.g., a related-item link inside a rendition) reassigns `selectedId` without a second `pushState` call — one history entry per takeover *session*, not per item, so one back-press always returns to the stream regardless of how many items were viewed inside it.
- Closing — via the visible back control (`history.back()`), the phone's back gesture, or the phone's back button — all converge on the same `popstate` transition. The `page.state.itemOpen` effect that observes this transition clears `selectedId` on close, so a closed takeover and a deselected stream are the same state, never two states that can drift apart.
- **Composing with existing URL state:** opening/closing the takeover never touches the URL — `pushState('', ...)` keeps the path/query unchanged. Toggling a source filter chip or editing the search query while the takeover is open uses the existing `goto(..., { replaceState: true })` path (query-param writes, unchanged from today) — a `replaceState` call does not disturb `page.state`, so it cannot accidentally close the takeover, and the takeover's own `pushState` does not disturb the `?sources=`/search query string. This composition must be verified by an explicit e2e case (toggle a filter chip while the takeover is open, then press back), not merely assumed — flagged identically in 09.1-RESEARCH.md.
- **Resizing across the breakpoint while a takeover-opened item is still selected** (e.g., rotating a tablet from portrait to landscape past 1024px): no special handling — the CSS bands above already revert the `fixed inset-0` overlay to the normal sibling-flex layout purely via the `md:`/`lg:` prefixes, with `selectedId` unchanged. The stale history entry from the narrow-width open remains on the stack; a later back-press deselects even at desktop width, which is harmless (equivalent to closing the detail pane) and needs no special-casing.

### Transition (Claude's discretion — resolved, lowest-priority item in this contract)

A 200ms ease-out slide-in, using Svelte's built-in `svelte/transition` `fly` (`{ x: 300, duration: 200 }}`) on the takeover wrapper, applied **only** when the takeover is active (the same narrow-viewport check gating `pushState` above) — never at ≥768px, where D-02 requires the pane to appear exactly as it does today (instant, no animation). Skip the transition (`duration: 0`) when `matchMedia('(prefers-reduced-motion: reduce)').matches`. This is explicitly the most descopable item in this contract: if the conditional-transition wiring adds meaningful complexity, an instant show/hide is an acceptable, contract-compliant fallback — D-01/D-02/D-03/D-04 do not require motion, only correct final states.

## Compact Stream Card (D-05, D-06, D-07, D-08)

Applies **only** below 768px (`max-md:`), to `StreamRow.svelte` and, by shared-component reuse, `SearchResults.svelte`'s rows (D-08). The 768–1024px band and desktop keep today's exact geometry (152px row, 20/14/16px text) — this is a `max-md:`-scoped override living directly on `StreamRow.svelte`'s own elements, winning over `.stream-row-surface`'s `height: 152px` purely through Tailwind v4's `@layer utilities` > `@layer components` cascade order (no edit to `app.css`, no specificity fight — 09.1-RESEARCH.md Pattern 3).

### Compact row: fixed height, three lines, no thumbnail, no tag badges

| Region | Spec |
|--------|------|
| Row height (fixed) | `max-md:h-[60px]` (60 = 15×4, a multiple of 4; supersedes `.stream-row-surface`'s 152px below 768px only) |
| Row padding | `max-md:p-1` (4px all sides — the `xs` spacing token) |
| Thumbnail | `max-md:hidden` on `<Thumbnail>` — the 52px-tall image does not fit the 60px budget and is not part of D-06's explicit 3-element composition (title/meta/snippet); the row is text-only at this density |
| Tag `Badge` pills | `max-md:hidden` on the `{#each item.labels}` block — not part of D-06's explicit composition; visible again in the detail pane, unchanged |
| Title | `max-md:text-[16px] max-md:leading-none max-md:font-semibold` (16px reuses Body's existing size value; 600 reuses Heading's weight; 1.0 is a new tight leading ratio scoped to compact only), `truncate`, unchanged `.search-highlight` segments |
| Gap | `max-md:mt-1` (4px) between title and meta |
| Meta line | See composition below — `max-md:text-[14px] max-md:leading-none` (14px reuses Label's existing size value at 400 weight, 1.0 leading — **not** a new size; see the size-budget note below) |
| Gap | `max-md:mt-1` (4px) between meta and snippet |
| Snippet | `max-md:text-[14px] max-md:leading-none max-md:line-clamp-1` (14px reuses Label's existing size at 400 weight; single line, not the desktop two-line clamp) — same `.search-highlight`/`parseSnippet` segments, unchanged mechanism |

**Size-budget note (checker fix, supersedes an earlier draft of this section):** CONTEXT.md D-06 names "~12px" as the meta line's target size, but CONTEXT.md's own Specifics section frames every compact density number as "a target, not a pixel contract." Introducing a genuine 12px size would push the app's total distinct font-size count to 5, violating the standing "no more than 4 font sizes" design-system rule (Typography below). Resolved in favor of the global typography constraint: the meta line reuses the already-declared 14px **Label** size (not a new 12px size) at the same new `leading-none` (1.0) ratio the title and snippet use — still visibly more compact than the desktop 14px/1.4 Label treatment, still legible, and it keeps the app at exactly 4 declared font sizes app-wide (14/16/20/28).

Budget check (all values above, multiples of 4 for spacing): 8 (padding) + 16 (title) + 4 (gap) + 14 (meta) + 4 (gap) + 14 (snippet) = **60px** — exactly the fixed row height above (a true multiple of 4, correcting an earlier draft's arithmetic error), landing at the top of D-06's "~55–60px" target.

### Compact meta line composition (D-07)

Single `max-md:flex max-md:items-center max-md:gap-1.5 max-md:flex-nowrap` line, in this exact order:

1. **Plugin icon** (`PluginIcon`, `size-3.5`, unchanged, `shrink-0`) — never truncates, never dropped.
2. **Source display name + group label, combined and jointly truncated:** rendered as one text node, `{sourceDisplayName}{item.group_label ? ' · ' + item.group_label : ''}`, inside a single `min-w-0 flex-1 truncate` span — CSS ellipsis truncates the *combined* string as space runs out, which is D-07's "source name / group label truncating first" resolved as one truncating unit rather than two independently-truncating spans (simpler, no JS text-measurement needed, and the two pieces of information degrade together rather than one disappearing silently while the other stays full-length).
3. **Date** (`formatItemDate`, `shrink-0`) — never truncates, always fully visible, trailing.
4. **Stale/warning dot** (unchanged `Tooltip`-wrapped `bg-warning size-2` marker, `shrink-0`) — trailing, after the date, rendered whenever `stale` is true regardless of how tight the row is: D-07's "the degraded-sync warning dot survives at every width — health honesty is not negotiable" is satisfied by giving it `shrink-0` and placing it last, after every truncating element, so it is never the thing that gets clipped.

No separator glyph between the icon and the name (the icon itself is the visual break); the `·` interpunct inside the combined name/group-label string is the only new separator character this phase introduces, matching a common truncation-boundary convention already implied by the desktop row's comma-free, gap-based layout.

### Search-result rows (D-08)

`SearchResults.svelte` renders through the same `StreamRow` component with its `snippet` prop set — every rule above (compact height, dropped thumbnail/badges, meta composition) applies identically and automatically below 768px, with search highlighting intact (unchanged mechanism, smaller font only).

### Date-marker ruler (D-08)

`StreamDateMarkers.svelte`'s wrapper gains `max-md:hidden`. The stream scroll `div`'s `pr-6` gutter (reserved today for the ruler's 12px lane) becomes `max-md:pr-0` below 768px, reclaiming that width for the compact row content — matching D-08's "reclaims its 12px lane" wording exactly. Unchanged at ≥768px.

## First-Run Bootstrap Greeting (Claude's Discretion — resolved)

**Resolution: reuse `web/src/routes/+page.svelte`'s existing zero-webspaces empty state verbatim.** No new component, no new copy, no visually distinct "Welcome to topos" treatment. This is the lowest-risk, most mechanical reading of CONTEXT.md's own framing ("the friendly first-webspace greeting... reuse vs a distinct welcome treatment") and matches 09.1-RESEARCH.md's Assumption A1 (confirmed low-risk): the mechanism this phase's kernel-side bootstrap work exists to enable — `GET /api/config` returning `{webspaces: {}}` — already renders exactly this state today, for the unrelated case of a user who deletes their last webspace. A genuinely first-run visitor and a returning user with zero webspaces configured see the identical, already-correct screen; distinguishing them visually would require the kernel to somehow flag "this file did not exist a moment ago," which is not information worth threading through the API for a one-time cosmetic difference.

| Element | Copy (unchanged, reused verbatim) |
|---------|------|
| Heading | `No webspaces yet` |
| Body | `A webspace pulls related items from your sources into one view. Create one to get started.` |
| CTA | `Create webspace` (opens the existing `CreateWebspaceModal`) |

**The one UI-relevant constraint on the kernel-side default:** the written default config must be a genuine empty shell (`Sources: {}`, `Webspaces: {}}`) — never a seeded example webspace — so that this exact empty state is what a fresh install actually reaches. A seeded example would instead render the populated webspace-switcher/stream view for a webspace the user never asked for, defeating the "friendly prompt to create first webspace" framing entirely. This constraint is stated here because it is a UI-visible consequence of a backend decision; the mechanics of writing it (directory creation, `WriteCanonical`, `Default*` constants) are 09.1-RESEARCH.md's territory, not this document's.

A bootstrap **write failure** (unwritable config directory, disk full) happens before the kernel ever starts serving HTTP — the process exits at the CLI, and no browser page is ever reached to design a state for. Out of this document's scope by construction.
