<objective>
Rework the "+" picker from one flat list into two separately-headed groups, so
that adding an instance of something already installed and installing a new
plugin type read as different kinds of action — and so an instance row finally
tells the user which instance it is (its configured URL or directory) rather
than repeating a binary name that is identical across two instances of the same
plugin.

This is the only plan in the phase that changes a flow's shape rather than
correcting a defect in one. The flows themselves are untouched: the one-step
existing-instance add, the two-step new-plugin-type add, the WhatsApp link
branch, and every save path below the popover keep their current behaviour
byte-for-byte. Only the picker's presentation changes.

Dependency on 09-01 is a real one: `PluginIcon.svelte` must exist.

Purpose: ROADMAP success criterion 4.
Output: a two-group picker with location-bearing instance rows and bordered
catalog tiles.
</objective>

<assumption_delta_decision>
This plan is the user-facing half of the seam 09-01 recorded. See
`09-01-PLAN.md`'s `<assumption_delta_decision>` block for the full decision: the
**plugin binary** is promoted to a first-class addressable noun, and the
picker's two-group split is the UI expression of that promotion — "installed
plugin type" and "configured instance" become separately presented nouns
instead of two row shapes in one list.

The accepted debt shows up here concretely and visibly: a Group 2 catalog tile
cannot show its plugin's real icon, because a plugin type with zero configured
instances has never reached `Describe`. This plan renders `Puzzle` there and
treats that as the correct, honest state rather than routing around it. What
would force a further promote is a catalog that must show real icons before
configuration — the mechanism exists in one plugin already
(`plugins/whatsapp/describeonly.go`) and is explicitly out of scope.

Advisory. Records the decision; blocks nothing.
</assumption_delta_decision>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-24 | Information Disclosure | instance row location line | low | accept | `base_url` and `path` are rendered verbatim. Both are marked non-secret in `CONNECTION_FIELDS` (unlike `token`, which is never rendered anywhere and is not touched by this change), the value is the operator's own instance address, and topos is loopback-only and single-user. Accepted, with the explicit constraint that no secret-marked field may be added to this line. |
| T-09-25 | Elevation of Privilege | location line rendering | low | mitigate | A `base_url` containing markup could inject if rendered as raw HTML. It is rendered through Svelte's default text binding and as a native `title` attribute — never a raw-HTML directive — so markup in a config value is escaped by construction. |
| T-09-26 | Spoofing | catalog tiles | low | mitigate | A tile invites the user to install a plugin type. The list comes solely from the kernel's own `GET /api/config/plugin-types`, which enumerates binaries in the operator's own plugins directory and already excludes the mock fixture. This component adds no client-side list and re-implements no exclusion rule, so there is no second place for the catalog's membership to drift. |
| T-09-27 | Denial of Service | picker scroll height | low | accept | The two-section split reduces visible rows per scroll height. Recorded as the phase's one backstop consideration rather than mitigated now — adequate at six plugin types, revisit with an explicit per-group max height if the catalog grows well past that. |
</threat_model>
