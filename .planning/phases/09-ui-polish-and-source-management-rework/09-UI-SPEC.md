# Phase 9 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**No CONTEXT.md / RESEARCH.md exist for this phase** (discuss-phase was skipped) — every decision below is derived directly from ROADMAP.md's Phase 9 success criteria, `TODO.md`'s "Web"/"Current Plugins" v1.0 sections, and a direct read of the shipped `web/src` implementation (Phases 1–8's design system, unchanged in kind — dark-only, `--card`/`--popover`/`--primary` token palette, Tailwind v4, `bits-ui` primitives, `@lucide/svelte` icons). This is a **polish/rework phase, not a new-feature phase**: every fix below is either (a) correcting a small, precisely-diagnosed visual/copy defect in an already-shipped component, or (b) reworking one already-shipped flow (the "+" source picker) whose shape the roadmap explicitly calls out as wrong. Nothing here introduces a new spacing value, font size, or font weight; exactly **one** new color token is introduced (`--popover`, see Color below), because the defect it fixes (menus indistinguishable from panes) is literally "two roles sharing one hex value."

**Scope (per ROADMAP.md Phase 9 / TODO.md "Web" + "Current Plugins" v1.0 sections):** 8 named small fixes, the PDF/media previewer's sizing model, per-plugin identity icons (incl. WhatsApp's Topos-branded icon), and the "+" add-source picker's instance-vs-catalog rework. No new sources, no kernel contract change, no agent-surface change — every fix below is `web/src` (Svelte/CSS) plus two small static assets (`favicon`, `robots.txt`); the only cross-cutting non-`web/` touch is `docs/api.md`/`config.example.toml` if any copy quoted there goes stale (none identified).

## Fix 1 — Favicon

**Defect:** `web/src/routes/+layout.svelte` imports `$lib/assets/favicon.svg` (the stock SvelteKit-scaffold Svelte wordmark logo) and sets it as `<link rel="icon">` — a topos user's browser tab shows the Svelte logo, not topos.

**Fix:** Point the favicon link at the already-present `web/static/app-icon.png` (served at `/app-icon.png` since anything under `web/static/` is a root-relative static asset) instead of the imported SVG:

```html
<link rel="icon" type="image/png" href="/app-icon.png" />
```

`web/src/lib/assets/favicon.svg` is retired (deleted; no other reference to it exists in `web/src`).

## Fix 2 — Search Clear Button Vertical Jump

**Defect (root cause, diagnosed by reading the code, not guessed):** `SearchBox.svelte`'s clear `Button` is positioned `absolute top-1/2 right-0 -translate-y-1/2` inside a `relative` wrapper — a standard "center vertically" idiom. But `ui/button/button.svelte`'s own base class includes `active:not-aria-[haspopup]:translate-y-px` — a 1px "press" affordance shared by every button in the app. Both utilities write the **same** CSS custom property (`--tw-translate-y`): the resting value is `-50%` (from `-translate-y-1/2`), but on `:active` (mousedown) the press utility overwrites it to `1px`, wiping out the centering offset outright. The button doesn't move 1px on press — it snaps from `-50%` of its own height to `+1px`, a jump of roughly its own half-height (for a `size-11`/44px button, ≈22px; the "15px" the roadmap names is the visually-perceived jump, close enough to confirm this is the exact defect).

**Contract:** the clear affordance must hold an **identical vertical center position across every interaction state** (rest / hover / active / focus-visible) — no positioning transform may share an axis with the press affordance's transform. Fix direction (implementation detail for the executor, not prescribed class-by-class): center the button via a non-transformed technique — e.g. wrap it in `absolute inset-y-0 right-0 flex items-center` (flex-centers on a fixed-height track, no `translate-y` involved) rather than `top-1/2 -translate-y-1/2` — so the shared Button press affordance can no longer collide with positioning. Do **not** special-case this one button's press affordance off (`active:translate-y-0`) as the fix — that quietly loses the app-wide press affordance's consistency for one control; decouple the positioning technique instead.

## Fix 3 — Duplicated "ago" in Sync Alt Text

**Defect:** `SourceChip.svelte`'s tooltip copy appends a literal `" ago"` after `formatRelativeTime(...)`, but `formatRelativeTime` (via `Intl.RelativeTimeFormat({ numeric: 'auto' })`) already returns a complete, correctly-worded phrase — `"5 minutes ago"`, `"3 days ago"`, but also `"yesterday"`, `"last week"`, `"now"` for the `numeric: 'auto'` special-cased deltas. The literal `" ago"` suffix was wrong in **every** case, not just the commonly-hit ones — `"synced yesterday ago"` and `"synced now ago"` are latent instances of the identical bug, surfaced less often only because those exact deltas are hit less often.

**Fix — Copywriting Contract change**, `SourceChip.svelte`'s `tooltipText`:

| Branch | Old | New |
|---|---|---|
| `success` | `` `${display_name} — synced ${relative} ago` `` | `` `${display_name} — synced ${relative}` `` |
| `warning` | `` `${display_name} — last error ${relative} ago: ${last_error}` `` | `` `${display_name} — last error ${relative}: ${last_error}` `` |
| `destructive` | `` `${display_name} — unreachable since ${relative}` `` | unchanged (never had the bug) |
| `unknown`/default | `` `${display_name} — not yet synced` `` | unchanged |

`formatRelativeTime` itself needs no change — the bug is purely the extra literal suffix at the call site.

## Fix 5 — Chip Refresh Moves into the 3-Dot Menu

**Defect / ask:** today `SourceChip.svelte` reveals **two** hover/focus-visible controls trailing the filter button — a standalone `RefreshCw` icon button and the `EllipsisVertical` edit-menu trigger. The roadmap wants exactly one: refresh folds into the existing menu.

**Fix — `SourceChip.svelte`:**
- Remove the standalone `RefreshCw` `Button` entirely.
- Add `Refresh now` as the **first** item in the existing `DropdownMenu` (leading `RefreshCw` icon, `class="animate-spin"` while `source.syncing`, `disabled={source.syncing}` — refreshing something already mid-refresh is a no-op, same guard the removed standalone button never had but should have), calling the chip's own existing `onrefresh(source.name)` — no prop-shape change to `SourceChip`'s public interface (`onrefresh`/`onedit` stay exactly as `WebspaceHeader.svelte` already threads them through).
- New menu order: `Refresh now` → separator → `Edit connection…` → `Edit match settings…` → (`Re-link…`, WhatsApp only) → separator → `Remove from this webspace`.
- The chip's remaining trailing control collapses from two `size-8` hover-revealed buttons to **one** (the `⋮` trigger) — same `size-8`, same hover/focus-visible reveal treatment, same nested-inside-the-44px-pill sub-floor exception 06-UI-SPEC.md's G-06-3b / 07-UI-SPEC.md already establish. Its `aria-label` broadens from `Edit {display_name}` to `{display_name} actions`, since it's no longer edit-only.

## Fix 6 — robots.txt

**Defect (semantic, not syntactic):** the shipped file —
```
# allow crawling everything by default
User-agent: *
Disallow:
```
— is syntactically valid but **backwards for what this app is**. topos is a locally-run, personal-data viewer (email, chats, documents) whose entire premise (per `.claude/CLAUDE.md`'s Constraints) is that content never leaves the user's machine. If an instance is ever LAN/tailnet-reachable (the repo's own `make dev` already exposes the Vite dev server to the tailnet per Quick Task `260806-f2`), a robots.txt that explicitly invites full crawling of a personal data browser is the wrong default.

**Fix:**
```
# topos is a local, personal-data tool — nothing served here is meant
# for public indexing, even if this instance is reachable on a LAN/tailnet.
User-agent: *
Disallow: /
```
Both `web/static/robots.txt` and its embedded-build twin `kernel/webui/build/robots.txt` (the file `go:embed`'s copy — currently identical, both must change together or the embedded binary keeps serving the old file regardless of the source-tree edit).

## Fix 7 — "Reload Config" to the Dropdown Root

**Defect:** `ManageSourcesModal.svelte`'s own `Reload config` button lives in a footer nobody sees without first opening "Manage sources…" — a two-click, buried path to an action a user reaching for hand-edited-`config.toml` changes wants in one click.

**Fix — `WebspaceSwitcher.svelte`:** gains a new `onreload: () => void` prop and a `Reload config` `DropdownMenuItem` (leading `RotateCw` icon — the same icon `ManageSourcesModal` already used for it, kept deliberately distinct from the per-source `RefreshCw`, per 07-UI-SPEC.md's existing "two reload concepts must never be visually conflated" rule) placed at the menu **root**, alongside `New webspace` (both are single-click, no-modal actions), **before** the separator that precedes `Manage sources…`:

1. webspace list items (unchanged)
2. separator
3. `New webspace` (`Plus`)
4. `Reload config` (`RotateCw`)
5. separator
6. `Manage sources…` (text-only, unchanged — still the plainest item, still the one item that opens a modal)

`ManageSourcesModal.svelte` **drops its own duplicate Reload-config control** (button + footer helper text + its local `reloading`/`reloadError` state) — one entry point for this action, not two. The parent route (`+page.svelte`) becomes the owner of the reload call (mirroring how it already owns `oncreate`/`onmanage`), surfacing success/failure through the **same modal-less pattern** 07-UI-SPEC.md already defined for chip-menu-remove and filter writes: a destructive `Alert` in the header region below the chip rows, fixed copy `` `{kernel's verbatim error message}. The previous configuration is still running.` ``, cleared on the next successful action. This is reload becoming another instance of an *existing* pattern, not a new one.

**Contract note — supersedes a locked prior rule:** 07-UI-SPEC.md's D-13 ("no other global settings surface … exactly two static `DropdownMenuItem` entries outside the per-webspace loop") is explicitly **widened to three** by this phase (`New webspace`, `Reload config`, `Manage sources…`). `web/src/lib/components/webspace-switcher.test.ts` currently asserts the two-item count by name — that assertion must be updated to three as part of this fix, not treated as a regression.

## Fix 8 — Dropdown Menus Need Their Own Background

**Defect:** `dropdown-menu-content.svelte` and `popover-content.svelte` both render `bg-card border-border` — and `--card` (`#0f172a`) is the *exact same* token every pane surface uses (`WebspaceHeader`'s header bar, `DetailPane`'s content boxes, every `StreamRow`). A menu opened over any of those panes is visually camouflaged against what's behind it. Checking `app.css`, `--popover` is declared as a **separate token** (`#0f172a`) — but it was given the literal same hex as `--card`, so the separation the token exists for was never actually realized.

**Fix — one new color value, `app.css`:**
```
--popover: #172033;
```
This extends the palette's existing dark-elevation staircase by one real step rather than inventing an unrelated hue: `--background` (`#020617`) → `--card`/pane surfaces (`#0f172a`) → **`--popover`, new** (`#172033`) → `--secondary`/`--border`/`--muted`/`--accent` (`#1e293b`). It sits strictly between `--card` and `--border` in lightness, so it reads visibly lighter than any pane behind it, while `--border` (unchanged, `#1e293b`) stays visibly lighter still than the new `--popover` fill — the menu's own border frame stays legible against its own new background (had `--popover` simply been bumped all the way to `#1e293b`, it would have collided with `--border` and erased the frame instead of fixing the pane-collision problem).

`dropdown-menu-content.svelte` and `popover-content.svelte` switch `bg-card` → `bg-popover`; `border-border` is unchanged in both. `Dialog`/`AlertDialog` are **out of scope** for this fix — both already render behind their own full-screen `bg-background/80` scrim (`dialog-content.svelte` line 26), which already visually separates them from whatever pane sits behind them; they correctly keep `bg-card`.

## Fix 9 — PDF/Media Previewer: Bounded Aspect Ratio, Text Flows Around It

**Defect:** `DetailPane.svelte`'s `bodyVariant === 'media'` branch wraps its PDF `<iframe>`/image `<img>` in a fixed `h-72` (288px), `w-full`, `shrink-0` box, itself the first child of a `flex flex-col` stack with the extracted-text block stacked directly below it. Width is effectively unbounded (fills the flex-1 detail pane, which itself can be very wide on a large viewport) while height is pinned at exactly 288px regardless — a portrait PDF page renders "very wide and very short," and the text block, being a separate stacked flex child, can never occupy the horizontal space beside the preview even when there's plenty of it.

**Fix — `DetailPane.svelte`'s `media` branch:**

1. **Bounded, aspect-locked sizing** replaces the fixed-height box: `w-full max-w-sm aspect-[3/4]` (max-width 384px, scaling down on a narrower detail pane; height is *derived* from the 3:4 portrait ratio, never set independently again). `3/4` is chosen as the one declared "sensible ratio" for this box — a reasonable stand-in for a document page, close to both US Letter (8.5:11 ≈ 0.77) and A4 (210:297 ≈ 0.71) without hardcoding either. Applies uniformly to **both** content types this box already renders (the PDF `<iframe>` and the plain `<img>` fallback) — same container, same rule, whichever the item actually is, so the fix reads as one consistent box treatment rather than a PDF-only special case.
2. **Text flows around it, only when there is text to flow.** When `content?.text` is present, the box becomes `float-left mr-6 mb-4` **inside** the existing scroll container (which already carries `overflow-y-auto`, and therefore already establishes the block-formatting context a float needs to be contained by its parent's scroll height — no additional clearfix required) instead of sitting in a separate `flex flex-col` stack above a full-width text block. The extracted text (`loadedTextBlock`) becomes a plain flowing block within that same container, wrapping in the remaining line-box space beside and, once the float's height is exhausted, below the preview — ordinary CSS float behavior, not a bespoke layout. When there is **no** text (`content?.text` falsy), the box is **not** floated — it stays centered/block exactly as it renders today, since there is nothing for it to wrap around.
3. **No separate `max-height`** beyond what the aspect ratio already implies: `max-w-sm` (384px) × `4/3` height ratio caps the box at 512px tall on its own, which is already "a maximum size with a sensible ratio maintained" per the roadmap's own wording — no extra viewport-relative cap needed on top.

## Fix 10 — Per-Plugin Identity Icons

**Ask:** every plugin (paperless-ngx, SilverBullet, email/Proton, Signal, WhatsApp, mock) gets its own recognizable icon, used consistently in chips and menus; WhatsApp's icon is topos's own app icon, not a WhatsApp/whatsmeow mark.

**Decision (locked, per STATE.md's 2026-08-11 roadmap-evolution entry, "icons decided over badges"):** icons, not colored-letter/text badges. Given the app already draws every icon in the product from `@lucide/svelte` (a generic outline icon set, not brand marks), plugin identity icons continue that convention — five plugin types get a distinct, thematically-apt Lucide glyph; the one plugin type whose real-world identity the roadmap explicitly wants **de-branded away from** (WhatsApp/whatsmeow) instead uses the app's own raster mark.

**New lookup — `web/src/lib/plugin-icons.ts`** (or co-located in `plugin-fields.ts`; either is fine, same binary-name key space as `pluginTypeLabel`):

| Plugin binary | Icon | Kind | Rationale |
|---|---|---|---|
| `topos-plugin-paperless` | `Scan` | Lucide, vector | paperless-ngx is a scanned-document archive |
| `topos-plugin-silverbullet` | `NotebookText` | Lucide, vector | personal wiki / notes app |
| `topos-plugin-proton` | `Mail` | Lucide, vector | email |
| `topos-plugin-signal` | `MessageCircle` | Lucide, vector | chat (distinct glyph from WhatsApp's, since both are chat sources) |
| `topos-plugin-whatsapp` | `/app-icon.png` | **Raster, topos's own mark** | Explicit de-branding ask: the plugin's UI identity is topos, never a WhatsApp trademark or the underlying `whatsmeow` library's own name/mascot |
| `topos-plugin-mock` / `topos-plugin-mockstrict` | `FlaskConical` | Lucide, vector | reference/test fixture, never a real user-facing source |
| any unrecognised/future plugin binary | `Puzzle` | Lucide, vector | generic fallback — a new plugin type must never render with no icon at all |

**Sizing/placement:**
- **Source chip** (`SourceChip.svelte`): the icon sits between the existing health dot and the display name — `[dot][icon][name]` — at `size-3.5` (14px), `text-muted-foreground` (never health-toned; the dot's sole job stays reporting health, the icon's sole job is reporting identity — the two are never merged into one glyph or one color channel). The raster WhatsApp variant renders at the identical box size (`class="size-3.5 object-contain"` on an `<img>`) so it reads as "the same kind of glyph in the row," not a visually foreign inclusion.
- **Add-source picker rows** and **Manage Sources instance rows** (below): `size-4` (16px), matching the existing `Pencil`/`Trash2` icon sizing already used in those list contexts.
- `pluginTypeLabel`'s existing text labels are **unchanged** by this fix (`WhatsApp` stays `WhatsApp` as a label — only its *icon* changes; the label already correctly describes what data the source pulls from, and Signal/WhatsApp remaining textually distinguishable by name is still required regardless of icon).

## Fix 11 — "+" Add-Source Picker Rework

**Ask (ROADMAP.md success criterion 4):** instances show their configured URL/directory, not the plugin name (which "is of no use"); adding a **new** source type is visually separated as picking from a plugin catalog — "they're being added to the software installation."

**Defect today** (`AddSourceModal.svelte`'s `PopoverContent`): one flat list. Each already-configured instance row shows `display_name` / `source.plugin` (the raw binary string, e.g. `topos-plugin-paperless` — genuinely not useful to a user picking between two same-type instances, e.g. two paperless instances would show the identical second line). New-plugin-type rows sit in the same list, separated only by a 1px divider, styled near-identically to the instance rows above them (same plain `hover:bg-muted` row).

**Fix — `AddSourceModal.svelte`'s picker popover** splits into two visually distinct, separately-headed groups:

### Group 1 — "Add to this webspace"
Section header: Label role, `text-muted-foreground`, small-caps/uppercase-tracking treatment (a group label, not a clickable row). One plain row per available existing instance (`hover:bg-muted`, unchanged interaction/click target):
- Leading plugin icon (`size-4`, Fix 10's lookup).
- Line 1 (Label role, `text-foreground`): `display_name`.
- Line 2 (Label role, `text-muted-foreground`, `truncate` + native `title` for an overlong value) — **replaces** the old plugin-name line — the instance's own configured location: `source.base_url ?? source.path`, falling back to `pluginTypeLabel(source.plugin)` only in the (never normally reached, since every real plugin type requires one or the other) case where an instance has neither field set. `base_url` is never a secret field (`CONNECTION_FIELDS`'s own `secret: false` marking), so displaying it verbatim here introduces no new exposure.

### Group 2 — "Install a new source"
Section header, same treatment as Group 1's. Each still-undiscovered plugin binary renders as its own small bordered tile (`rounded-md border border-border p-2 hover:border-primary hover:bg-muted`) — deliberately heavier chrome than Group 1's plain rows, so "picking a new plugin type" visibly reads as a different *kind* of action (installing something into the app) from "connecting an already-installed one again":
- Leading plugin icon (`size-4`).
- `pluginTypeLabel(plugin)` (e.g. `paperless-ngx`, `Signal`) — the literal `New {label}…` copy is retired; the group's own header already establishes "these are things you can install," so the row label is just the plugin's name.
- `plugins/mock` stays excluded from this catalog (07-UI-SPEC.md's existing, unchanged rule — a developer reference fixture, never a real source a user knowingly installs).

**Layout:** the popover widens `w-72` → `w-80` (320px) to comfortably hold Group 1's two-line rows without cramping the location string. `pickerEmpty`'s copy is unchanged: `All available sources are already in this webspace.`
