search clear button that jumps on mouse-down, and the PDF/image previewer that

  <action>
Change how the clear control is centred inside `SearchBox.svelte`'s `relative`
wrapper. Today it is absolutely positioned at the vertical midpoint and pulled
back by half its own height with a transform. That transform and the shared
Button press affordance both write the same underlying CSS custom property, so
on mousedown the press value replaces the centring value outright and the
control snaps by roughly half its own height — the "15px jump" the roadmap
names.

Replace the transform-based centring with a non-transformed technique: wrap the
clear `Button` in an absolutely positioned element that stretches the full
height of the input (`absolute inset-y-0 right-0`) and centres its child with
`flex items-center`. The button then sits on a fixed-height track with no
vertical transform of its own, so the press affordance has nothing to collide
with and applies exactly the 1px press it was designed to.

Do **not** neutralise the shared press affordance on this one control. That
would trade a positioning bug for an inconsistency, silently making one button
in the app behave differently from every other. The whole point of the fix is
that the two concerns stop sharing an axis. `ui/button/button.svelte` is
deliberately absent from this plan's file list; leave it alone.

Keep everything else in the component identical: the render condition, the
aria-label from `searchCopy.clearLabel`, the size, the ghost variant, the
immediate non-debounced clear handler, and the leading Search icon's own
centring (which is correct as-is — it is a plain icon, not a Button).

Write `web/src/lib/components/search-box-clear.test.ts` covering the
`<behavior>` list with this repo's comment-stripped source-scan pattern.
Include a positive assertion that the wrapper carries the full-height inset and
flex centring utilities, and a positive assertion that `button.svelte` still
declares its press affordance — the second one is what turns "we did not take
the shortcut" into a guarded invariant rather than a promise.

Fix 9's three points.

**Sizing.** Replace the fixed-height box with `w-full max-w-sm aspect-[3/4]`.
Height becomes derived from the ratio and is never set independently again.
`3/4` is the phase's one declared "sensible ratio" for a document page — close
to both US Letter and A4 without hardcoding either. Apply it to the container
that wraps *both* content types, so the PDF iframe and the img fallback share
one box treatment rather than the PDF becoming a special case. Keep the
existing rounded corners, border, overflow-hidden and card background on that
box.

**Float, conditionally.** When `content?.text` is present, the box becomes
`float-left mr-6 mb-4` **inside** the existing scroll container, and the
extracted text renders as a plain flowing block within that same container
instead of as a separate stacked flex child below it. The container already
carries `overflow-y-auto`, which already establishes the block-formatting
context a float needs in order to be contained by its parent's scroll height —
no clearfix element is needed, and adding one would be dead markup. When
`content?.text` is falsy the box is **not** floated; it renders block/centred
exactly as today, because there is nothing for text to wrap around.

Note that `loadedTextBlock` is shared with the text-only branch, where it
correctly takes the pane's full remaining height via its own flex utilities.
Make the media branch's text render as a flowing block without changing how the
text-only branch renders — if that means the media branch renders the text
inline rather than through the shared snippet, keep the typography classes
byte-identical between the two so the shared-typography property Phase 3
established is preserved.

**No extra cap.** Do not add a viewport-relative max-height. 384px of width at
a 3:4 portrait ratio already caps the box at 512px tall, which satisfies the
roadmap's "bounded size with a sensible aspect ratio maintained" on its own.
