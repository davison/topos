<objective>
Complete the install surface: resolve the latest published stable release when
no version is given (INST-02), remove exactly what was installed and nothing
else (INST-05), and widen the published artifact set so an installed instance
gets the same operator-facing plugin set a checkout build produces (INST-01).

Purpose: 15-01 proved the layout with an explicit tag and a fixture release.
What is still missing is the no-argument path the operator will actually type,
the removal path that must be provably data-safe, and the fact that the
filesystem plugin — shipped in Phase 12 and built by `make build-portable` —
is absent from every published release, so today an installed instance would
silently lose that source.

Output: latest-tag resolution with host and tag-shape guards, `scripts/uninstall.sh`
plus `make uninstall`, hermetic smoke cases proving a seeded home/XDG tree is
byte-unchanged across an install/uninstall cycle, and the widened release and
nightly asset lists with their docs.
</objective>

  <action>
Add latest-tag resolution to `scripts/install.sh`, fired only when no version argument is given.

Give the script a source-guard so its functions are testable in isolation: wrap the top-level entry point so the script only runs its main flow when executed directly, and does nothing but define functions when sourced. This is the seam the offline test cases below use.

Write two separate functions so the network step and the safety check are independently testable:

- A resolver that issues a redirect-following HEAD request with `curl -fsSLI` against the release root's `latest` path and reports the final effective URL. Nothing in this function decides whether the answer is acceptable.
- A validator taking that effective URL and reporting the tag, refusing by name in each of these cases: the URL's scheme and host are not exactly `https` and `github.com`; the path is not this repository's own release-tag path; the trailing segment does not match a three-part `v<digits>.<digits>.<digits>` shape with nothing appended. The three-part shape assertion is the second, independent guard against a prerelease — the `latest` endpoint already excludes prereleases by definition, and this makes that exclusion something the script itself enforces rather than something it trusts.

Wire the two together: with no version argument, resolve, validate, then continue into the existing tag-based flow. With a version argument, neither function runs. Print the resolved tag before downloading, so the operator can see which release they are about to get.

Make the Makefile's `install` target work with an empty `VERSION` — `make install` and `make install VERSION=1.1.0` are both first-class. Extend the target's comment block to say which path each form takes and that no credential, token, or GitHub CLI is involved.

Extend `scripts/install-smoke.sh` with two offline cases that source the script and call the validator directly with a table of effective URLs: this repository's own three-part release-tag URL is accepted and yields the tag; a nightly-shaped tag, a prerelease-suffixed tag, a different host, a different repository path, and an empty string are each refused with a message naming the reason. Add one network case that runs the real resolver end to end and asserts the returned tag matches the three-part shape; when the network is unreachable, that case must skip loudly, naming itself, rather than passing silently — the same skip-loudly discipline the gdrive rehearsal spec already uses.

  <files>scripts/uninstall.sh, scripts/install-smoke.sh, Makefile</files>
  <read_first>
    - scripts/install.sh — specifically the placement step: the exact set of destination paths install writes is the exact set uninstall may remove. Read it before writing a single removal line.
    - scripts/install-smoke.sh — the fixture-release builder, the temp-prefix handling, and the cleanup trap this task reuses for the install/uninstall cycle case.
    - scripts/dev-guard-smoke.sh — the safety-assertion pattern: a baseline captured at script start and re-asserted after every case, failing loudly on any drift. The seeded-tree digest comparison in this task is the same idea applied to files instead of ports.
    - Makefile — the `install`/`install-check` targets and `.PHONY` line, so `uninstall` is registered and commented in the same style.
  </read_first>
  <action>
Create `scripts/uninstall.sh` (`set -euo pipefail`), reading `PREFIX` with the same default the install script uses. Its removal set is closed and explicit — it removes only:

- the file at the kernel's installed path under the prefix's `bin` directory, and
- each file directly inside the prefix's `lib/topos/plugins` directory whose name starts with the plugin binary prefix.

After removal, attempt to remove the `lib/topos/plugins` and `lib/topos` directories with a non-recursive directory removal only. A non-empty directory therefore survives, and the script reports what remains and why rather than forcing it. No recursive removal appears anywhere in this script, and it never descends into subdirectories.

The script must name no directory outside the prefix. It takes no flag, and offers no path — not even an opt-in one — that removes the operator's configuration, index, or plugin stores; the absence of that capability is the guarantee, not a default that could be overridden.

Make it idempotent and quiet about it: a path that is already absent is not an error. Report a per-path outcome (removed, or already absent) and exit 0, so a second run is a clean no-op with visible reasoning. Removal is by unlink, so running it while the installed kernel is live succeeds and leaves that process running on its already-open files.

Add the `uninstall` target to the Makefile with the explanatory comment block this file's targets carry, stating explicitly that it removes prefix artifacts only and that config and state are never touched. Register it in `.PHONY`.

Extend `scripts/install-smoke.sh` with a data-safety cycle case, which is the real gate for INST-05:

1. Build a seeded home/XDG tree inside the temp work directory: a config file at the XDG config location for topos, an index database file and a plugin store directory holding a file at the XDG data location for topos.
2. Take a recursive digest manifest of that tree — every file's path plus its SHA-256 — sorted for a stable comparison.
3. Run the fixture install into a temp prefix with `HOME`, `XDG_CONFIG_HOME` and `XDG_DATA_HOME` pointed at the temp tree.
4. Run the uninstall against the same prefix.
5. Re-take the digest manifest and assert it is byte-identical to the first. Any difference fails the case naming the differing path.
6. Assert the prefix no longer contains the kernel binary or the plugins directory.

Add three more cases: an idempotent second uninstall exits 0 and leaves the prefix digest manifest identical to after the first; an uninstall with a hand-placed unrelated file inside the installed plugins directory leaves that file in place, leaves the directory in place, exits 0, and says so; an uninstall run while the just-installed kernel is serving exits 0 and the kernel keeps answering requests until it is torn down.
  </action>
