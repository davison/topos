<objective>
Give the installed instance Signal support without weakening the trust model:
`make install-signal` builds the cgo plugin locally and places it where the
installed kernel can actually run it, and the base install stays provably
toolchain-free (INST-04).

Purpose: there is a real architectural constraint here that the requirement's
wording does not surface. The published kernel is linked with a build manifest
covering only the binaries built beside it on the release runner. A locally
built `topos-plugin-signal` dropped into the installed *trusted* plugins
directory is refused before a subprocess is created — `VerifyTrustedBinary`
returns an unverified error and the source reports `manifest_unverified`. This
is not a bug to route around; it is the deliberate Phase 13 gate, and
docs/plugins/signal.md already records the supported path: the external plugin
directory plus the existing one-time consent-and-pin flow. This plan automates
exactly that path.

Output: `scripts/install-signal.sh`, `make install-signal` and
`make uninstall-signal`, a hermetic proof that the base install needs no
toolchain, and docs that state the constraint and the one-time step plainly.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Locally built binary → the installed kernel's plugin tiers | A binary this machine compiled crosses into a process the operator trusts with source credentials. |
| Build toolchain → the base install path | A compiler on PATH during an install would silently widen the base install's dependency surface. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-11 | Elevation of Privilege | Signal binary placement | high | mitigate | The binary is placed in the external plugin directory, so it launches only through the existing untrusted-add consent flow under a content pin re-verified at every launch. The trusted-directory build-manifest gate is not touched, relaxed, or given an override by any change in this plan; the installer refuses outright if pointed at a prefix trusted plugins directory. |
| T-15-12 | Tampering | Signal binary replaced on disk after install | high | mitigate | The external tier's existing SHA-256 pin is recomputed from disk before every launch; changed bytes surface as a named per-instance failure with a two-click re-pin, which is exactly the state a re-run of `make install-signal` produces and which the docs state up front. |
| T-15-13 | Denial of Service | replacing the binary under a live kernel | medium | mitigate | Placement copies to a temporary name in the destination directory and completes with a rename, so a live subprocess is never truncated and the target never aborts with a text-file-busy error. |
| T-15-14 | Tampering | base install growing a build step | medium | mitigate | A toolchain-tripwire case runs the fixture install with failing shims for the Go tool and conventional C compilers first on PATH, and fails if any is invoked — a behavioural gate, not a text assertion. |
| T-15-15 | Denial of Service (data destruction) | `make uninstall-signal` | medium | mitigate | Exactly one path is removed; the directory and every other file in it survive, asserted by a case that plants an unrelated marker file and compares its digest. No recursive removal appears in the script. |
| T-15-SC | Tampering | package-manager installs | low | accept | This plan adds no npm/pip/cargo dependency. The system SQLCipher package is an operator-installed distro package documented in docs/plugins/signal.md, unchanged by this plan. |
</threat_model>

  needs operator confirmation).** INST-04 says the Signal binary is built
