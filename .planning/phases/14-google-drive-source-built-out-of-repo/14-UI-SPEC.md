# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Design system already fully established (Phases 1–13); this phase introduces zero new spacing values, zero new type sizes/weights, zero new palette hex values, and zero new shadcn components.** Phase 14 is unlike every prior source phase in one important way: the plugin that actually implements Google Drive lives **out of this repository** (D-08) — this document is not a spec for code this repo's executor writes for the plugin itself. It has two jobs instead:

1. **Real code in this repo** — exactly one item, G1 below: the folded tooltip-suppression todo touching `SourceChip.svelte`.
2. **The copywriting/content contract this repo's PRD-authoring task hands to the separate `topos-plugin-gdrive` GSD project** (D-08's "the PRD is the only hand-off document") — the exact `Describe.extras` field declarations, match vocabulary, and `Health.LastError` message templates the out-of-repo plugin should implement so it reads and behaves indistinguishably from every in-repo plugin. This is UI contract content, not kernel internals, so it belongs in the PRD hand-off without violating D-08's clean-room boundary.

Every other surface a Google Drive source touches — the picker catalog, the untrusted-confirm interstitial, the generic extras-field form, match-vocabulary editor, stream row, thumbnail, PDF/image previewer, office-format fallback, deep-link button, trust badge — **already exists and needs no change**. See "Explicit Reuse — Zero New UI" below.

### G1 — Native-Tooltip Suppression on `SourceChip.svelte` (folded todo, real code in this repo)

**Where:** `web/src/lib/components/SourceChip.svelte` only — the todo's own declared scope (`.planning/todos/pending/2026-08-14-suppress-native-tooltips-under-chip-popovers.md`). No other component in this repo pairs a native `title` with an app-rendered hover popover on the same hover target (`ManageSourcesModal.svelte` and `WebspaceSwitcher.svelte`'s own `title` attributes are truncation-legibility-only, with no competing `Tooltip` on the same element — out of scope, left unchanged).

**Problem:** two competing hover affordances fire on the same chip: the app's own `TooltipProvider`/`Tooltip` (visible, styled popover) AND the browser's native tooltip rendered from `title={tooltipText}` on the outer button — reported live during Phase 13 UAT as the native one often rendering *on top of* the app's own popover.

**Fix (interaction contract):**
1. **Outer chip button** (currently `title={tooltipText}`, line ~310): remove the `title` attribute entirely; add `aria-label={tooltipText}` in its place. This preserves the exact same accessible-name text for assistive tech and keyboard-focus users while eliminating the native hover tooltip that duplicated the app's `Tooltip`.
2. **Inner display-name span** (currently `title={source.display_name}`, line ~339): remove the `title` attribute; add **no replacement attribute**. Once the outer button carries `aria-label={tooltipText}` (which already contains `source.display_name` as its lead clause in every branch), the button's own computed accessible name supersedes any inner element's text for assistive tech — no accessibility regression. The visible truncated name text stays exactly as rendered today (`class="truncate"` unchanged); only the redundant native tooltip is removed.
3. **Pinned-hash footer span** (`title={source.pinned_hash}`, line ~410): **left unchanged.** This sits inside an already-open `DropdownMenuContent`, not behind a hover-triggered popover — it is the documented (E5) manual-copy fallback, not the duplication the todo reports. Do not touch.
4. **DropdownMenu trigger button** (`aria-label={...} actions`) and the copy-hash button (`aria-label="Copy pinned hash"`): already carry no `title` — no change.

**Test contract:** extend `source-chip-tooltip.test.ts` (already declared in this file's own header comment as part of 13-06's scope) to assert (a) the outer chip button carries no `title` attribute, (b) the outer chip button's `aria-label` equals the same string the `TooltipContent` renders, and (c) the inner name span carries no `title` attribute. This closes the todo's own "Add/extend a component test asserting the popover-bearing elements carry no `title` attribute" requirement.

**Why this belongs in Phase 14 and not a standalone quick task:** the todo's own file explicitly names this component as already in 13-06's declared scope; 13-06 shipped without it (confirmed: `13-06-PLAN.md` executed before this todo was filed), so it stands alone here, folded into Phase 14 per `14-CONTEXT.md`'s "Folded Todos" section.

### G2 — Google Drive `Describe.extras` Field Declarations (content contract → plugin repo PRD, zero code in this repo)

**Design decision:** `topos-plugin-gdrive` gets **no row in `web/src/lib/plugin-fields.ts`'s `CONNECTION_FIELDS` table.** Every prior source phase (Paperless, SilverBullet, Proton, Signal, WhatsApp, and even the *trusted, in-repo* Filesystem plugin in Phase 12) added a hardcoded `CONNECTION_FIELDS['topos-plugin-<name>']` row. Google Drive is different by design: it is the phase whose entire point is proving PLUG-09's promise — *"external plugins can receive provider-specific settings without kernel changes"* — for real, against a third party's own binary. Declaring a `CONNECTION_FIELDS` row for it in this repo would be topos-repo code reacting to a plugin's existence, which undercuts exactly the proof SRC-06 asks for. Instead, `topos-plugin-gdrive` relies **entirely** on Phase 11's already-shipped generic `Describe.extras` declared-fields editor (E6, `ConnectionForm.svelte` + `SecretField.svelte`): an unrecognized plugin binary degrades to `[DISPLAY_NAME_FIELD, SYNC_INTERVAL_FIELD]` (per `connectionFieldsFor`'s own documented fallback) plus whatever fields its own `Describe` response declares — rendered with real labels, placeholders, secret-masking, and required-field submit-blocking, with zero new code in this repository.

**The three `ExtrasField` entries the PRD should specify** (proto `topos.v1.ExtrasField`: `key`, `label`, `required`, `secret`, `placeholder`):

| `key` | `label` | `required` | `secret` | `placeholder` |
|-------|---------|------------|----------|---------------|
| `client_id` | `OAuth Client ID` | `true` | `true` | `GDRIVE_CLIENT_ID` |
| `client_secret` | `OAuth Client Secret` | `true` | `true` | `GDRIVE_CLIENT_SECRET` |
| `folder_id` | `Drive Folder ID` | `true` | `false` | `e.g. 1a2B3cD4EfGhIjKlmNoPQRstuVwxYZ — the id segment of the folder's Drive URL` |

`secret: true` on `client_id`/`client_secret` is deliberate and required, not optional polish: it routes both fields through `SecretField.svelte`, which — per this codebase's established, non-negotiable convention ("Secrets are environment-only `${VAR}` references") — stores and displays only the **environment variable name**, never a literal value, with the existing live set/unset badge. The `GDRIVE_CLIENT_ID`/`GDRIVE_CLIENT_SECRET` placeholders are display-only hints (never auto-filled, per the contract's own D-14 rule) matching D-01..D-04's locked env-var vocabulary exactly — the same names the standalone `topos-plugin-gdrive auth` CLI reads from the shell.

`folder_id` (not a path) is this document's explicit recommendation for how a source instance targets its root: a Drive folder id (the segment in `https://drive.google.com/drive/folders/<id>`) is copy-pasteable, globally unambiguous across My Drive/Shared Drives/shortcuts, and needs no path-resolution logic — unlike a path, which is ambiguous the moment two folders share a name. This resolves Claude's Discretion's "folder ID vs path" item for the *instance-targeting* field only; it is orthogonal to the match-vocabulary decision below.

**Fields deliberately NOT declared here** (left to the PRD/plugin repo's own architecture decisions, since they don't change this UI contract): a subfolder-recursion toggle, a Shared-Drives-inclusion toggle, or a sync-cadence override beyond the existing generic `Sync Interval Override` field every plugin type already gets. If the plugin repo's own planning adds any of these, they render through the identical E6 generic mechanism with no topos-repo change required — same proof, more fields.

### G4 — Auth-State Health Message Templates (content contract → plugin repo PRD, zero code in this repo)

**Mechanism (unchanged, verified against `plugins/whatsapp/health.go`/`plugin.go` and `kernel/httpapi/sources.go`):** a plugin-internal `healthState` enum, surfaced two ways — `Health()` returns `Reachable: false` + a specific `LastError` string for every non-healthy state (never a generic message), and `Match()` returns `codes.Unavailable` wrapping the identical cause text, which the kernel's syncer records as that sync run's `Error`. The **live** `Health.LastError` text itself is not persisted or shown on chip hover (confirmed: `sourceStatusesFrom` in `kernel/httpapi/sources.go` populates `LastError` from the recorded **sync run's** own error, not the live probe) — a not-yet-authorized/expired Drive source therefore reads `destructive` tone and the chip's existing terse `"{display_name} — unreachable since {relative}"` tooltip (unchanged code, G-independent). The **specific**, actionable remedy text still reaches the operator through two existing, unmodified surfaces, exactly as it does for WhatsApp today: (a) `sync_runs.error` (visible via any future debug/log surface and via `StreamSyncDegraded.svelte`'s `syncError` banner when the affected webspace's stream goes empty because of it) and (b) whatever the plugin's own `-h`/`auth` CLI mode prints directly to the operator's terminal. **No kernel or web code change is needed to support this** — it is the identical shape Phase 8 already proved.

**Recommended message templates** (mirroring `plugins/whatsapp/health.go`'s established shape: short lead clause naming the cause, then the exact remedy action, never implying data loss):

| Cause | `Health.LastError` / `Match` error text |
|-------|------------------------------------------|
| Never authorized (no token file found) | `Not authorized — run "topos-plugin-gdrive auth" in a terminal, then use this source's "Refresh now".` |
| Authorization expired or revoked (`invalid_grant`, cause not distinguishable — see 14-RESEARCH.md Open Question 2) | `Authorization expired or was revoked — run "topos-plugin-gdrive auth" again, then use this source's "Refresh now".` |
| Rate-limited / quota exceeded (transient, Pitfall 6) | `Rate limited by Google Drive — retrying automatically. No action needed.` |
| Configured folder no longer exists or access was removed | `The configured Drive folder is no longer accessible — check the folder still exists and is shared with this account.` |

Each names an exact, already-shipped-and-visible UI affordance ("Refresh now" is `SourceChip.svelte`'s existing dropdown-menu item, unchanged) rather than inventing new remedy language — the same discipline WhatsApp's `"Use this source's chip menu (\"Re-link…\")..."` templates already established.
