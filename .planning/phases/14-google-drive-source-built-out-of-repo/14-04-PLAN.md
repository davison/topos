<objective>
Prove the Google Drive plugin on the untrusted external path: hermetically for everything a browser can drive without Google credentials, and by a recorded live run for the three criteria that need a real Drive.

Purpose: SRC-06 is only proven by the real binary walking the real install path, and SRC-05's three behavioural criteria — authorize once and survive restart, previews including Workspace exports with deep links, incremental syncs after the first — cannot be faked. The project convention is that any UAT item a browser can drive becomes a spec rather than a remembered manual check, so this plan splits on exactly that line and writes down what falls on the manual side, mirroring the WhatsApp pairing precedent already in docs/testing.md.

Output: a binary-gated Playwright spec, its make entry point, the testing-map entry that explains both, and a live UAT script whose human-check block carries the phase's remaining proof.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → untrusted plugin subprocess | The two credential variables' values are handed to a binary this project did not build and does not sandbox |
| untrusted plugin subprocess → Google Drive API | The plugin's own network egress, invisible to the kernel and to this repository's provenance audit |
| Drive content → kernel index | Item metadata and previews cross into local storage; full document content must not |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14.4-01 | Information Disclosure | untrusted binary receiving live Drive credentials | high | accept | No kernel-level containment exists and the contract says so plainly. The mitigations that do exist are applied and checked: the read-only scope requirement (14-03's prohibition), the clean-room provenance of the binary (D-06), and the interstitial's dynamic disclosure line naming both variables, which the UAT script makes the operator read rather than click past. Accepted knowingly — this is the residual risk the whole external tier is built around, not a new one this plan introduces. |
| T-14.4-02 | Information Disclosure | credential values in files | high | mitigate | Neither the spec nor the UAT script contains a value; the spec deliberately runs with the variables unset, and the script instructs the operator to export them into a shell. Pinned by the acceptance criterion that only the variable names appear. |
| T-14.4-03 | Information Disclosure | full Drive document content in the local index | high | mitigate | Stated as a prohibition on this plan and specified as a prohibition in the PRD; the UAT script's criterion-2 observations distinguish a live-fetched preview from stored content. |
| T-14.4-04 | Elevation of Privilege | the Drive binary reaching a trusted directory | high | mitigate | The spec leaves the trusted binary list empty and names the plugin only in the external list; the Makefile target is barred from the trusted build recipes and the manifest generator; an acceptance criterion asserts the recipes are unedited. A trusted-directory copy would silently invalidate every proof in this plan. |
| T-14.4-05 | Spoofing | binary substitution between install and launch | medium | mitigate | Unchanged Phase 11 machinery: the external tier recomputes the content pin from disk before every launch, and the UAT script has the operator confirm a pinned hash on the chip. |
| T-14.4-06 | Repudiation | a health state marked passed that was never reached | medium | mitigate | The UAT script requires unreached states to be recorded as unreached rather than passed, and the human-check block repeats that instruction. |
</threat_model>
