<objective>
Suppress the browser-native tooltips that duplicate and cover the source chip's own popover, without losing any of the text they carried.

Purpose: two hover affordances fire on the same chip today — the app's styled `Tooltip` and the browser's native tooltip rendered from the outer button's native-tooltip attribute — and the native one frequently paints on top of the app's own. Reported live during Phase 13 UAT.

Output: the chip renders one popover; the same health sentence stays reachable by assistive technology; the Playwright suite is updated for whatever locator surface the chip now exposes.

Folded todo: `.planning/todos/pending/2026-08-14-suppress-native-tooltips-under-chip-popovers.md` (web, minor). Design contract: `14-UI-SPEC.md` § G1.

**This plan opens with a decision checkpoint.** The approved UI-SPEC prescribes a specific replacement attribute on the grounds that it "preserves the exact same accessible-name text". That premise does not hold against the current markup, and following it literally changes the chip's accessible name — which ~24 Playwright locators across 13 spec files match on exactly. Task 1 puts that in front of the operator before any edit.
</objective>

  <name>Task 1: Decide the chip's accessible-name semantics before touching the markup</name>
  <read_first>

  <decision>
    Which attribute carries the chip's health sentence once the native-tooltip attribute is removed from the outer chip button: an `aria-label` (making the sentence the button's accessible *name*, per 14-UI-SPEC.md § G1 point 1), or an `aria-describedby` pointing at a visually-hidden sibling (keeping the sentence an accessible *description*, which is the role the removed attribute plays today)?
  </decision>
  <context>
    Both options remove the native tooltip, which is what the todo asks for. They differ in one consequence the UI-SPEC did not account for.

    Today the chip button has no `aria-label`, so its accessible name is computed from its own text content — the display name — and the native-tooltip attribute contributes only an accessible *description*. 14-UI-SPEC.md § G1 states that moving the sentence to `aria-label` "preserves the exact same accessible-name text". It does not: it replaces the name `Household Docs (external)` with the full sentence `Household Docs (external) — synced 5 minutes ago — untrusted external plugin`.

    That is a real behaviour change with a measured blast radius. Roughly 24 Playwright locators across 13 spec files find a chip by `getByRole('button', { name: <display name>, exact: true })` — 09-1-header-touch, 09-chip-menu, 09-plugin-icon, 11-binary-changed-repin, 11-external-tier-badge, 11-untrusted-add, 12-external-rehearsal, 12-tooltip-precedence, 12-zero-match-diagnostic, 13-manifest-unverified, 13-shadowed-advisory, header-branding, smoke-search-filter. Every one of them breaks under `aria-label`, and every future chip locator has to match a sentence rather than a name.

    A further 7 assertions read the removed attribute directly and change under **either** option, so they are not a differentiator.

    Phase 14's own stake in this: the sentence in question is where the untrusted-external-plugin disclosure lands for a Google Drive source, so whichever surface is chosen is the one this phase's later e2e work asserts against.
  </context>
  <options>
    <option id="option-a">
      <name>Follow 14-UI-SPEC.md § G1 literally — `aria-label` on the chip button</name>
      <pros>Implements the approved design contract as written, with no planner deviation to justify later. Simplest component change: two attribute removals and one addition, no new element. The sentence is announced immediately on focus without any description-support caveat.</pros>
      <cons>Changes the chip's accessible name from an identifier to a whole sentence, which is a semantic downgrade (a name identifies; a description elaborates) and makes the announced name change every time the sync timestamp does. Requires editing ~24 locators across 13 spec files, plus every future chip locator. The UI-SPEC's stated rationale for this option is factually incorrect against the current markup.</cons>
    </option>
    <option id="option-b">
      <name>Preserve the current semantics — visually-hidden description plus `aria-describedby`</name>
      <pros>Keeps the accessible name as the display name, so zero Playwright locators change on that axis and the chip stays findable by its name forever. Keeps the sentence in the role the removed attribute actually played (a description), which is the semantically correct home for elaborating text. Honours the UI-SPEC's stated *intent* ("no accessibility regression") more exactly than its literal prescription does.</pros>
      <cons>Deviates from the letter of an approved design contract. Adds one element and one id to the component. The explicit `aria-describedby` overrides the one bits-ui sets on the trigger while the tooltip is open — harmless, because the hidden element carries the identical sentence, but it is a subtlety a future reader has to be told about in a comment.</cons>
    </option>
  </options>
