<objective>
**As a** person who hand-edits `config.toml` and clicks Reload config, **I want to** a save that removes a source and is then rejected for an unrelated typo to still leave the removed source's data out of my index, **so that** one mistyped match field never permanently strands a deleted source's items and sync history in my webspace — or resurrects them as phantom history when I add that source back later.

Purpose: this plan closes the single Critical gap in 07-VERIFICATION.md (2026-08-08, `gaps[0]`, first raised as 07-REVIEW.md's post-07-09 CR-01). `Supervisor.Apply`'s D-07 removed-instance index-cleanup loop sits textually AFTER the `pluginhost.ValidateMatchConfig` check. `Host.Reconcile` has already committed by the time either runs — the removed instance's subprocess is already killed and dropped from the host — but when the vocabulary check fails, `Apply` returns before the cleanup loop is ever reached, so that instance's `items` and `sync_runs` rows are never deleted. Compounding it: that failure branch calls `commitGeneration(newCfg)` — 07-09's own correct fix for the adjacent coordinator-staleness gap — which advances `s.cfg` to `newCfg`. On every subsequent `Apply`, `oldCfg` is `newCfg`, which already lacks the instance on both sides of the diff, so `removedInstances` can never again compute it as removed. There is no retry path: the orphaned rows persist permanently, or are inherited as phantom history if the operator re-adds an instance under the same `[sources.<id>]` key — the exact outcome `DeleteSourceItems`/`DeleteSyncRuns`'s own doc comments and T-07-13 name as the guarantee this cleanup exists to provide. A second failure mode lives in the same loop: with several removed instances, an early instance's delete error returns immediately, abandoning cleanup for every later-sorted instance in the batch, with the same permanence. Both are reachable through the documented, supported hand-edit + `POST /api/config/reload` flow (`ManageSourcesModal.svelte`'s "Reload config" button) with one edit that both deletes a `[sources.<id>]` block and typos a `[webspaces.<name>.match.<other-instance>]` field.

Output: the cleanup is extracted into its own method, called unconditionally as soon as `Reconcile` has committed and before the vocabulary check, iterating the whole removed batch and collecting per-instance failures with `errors.Join` instead of returning on the first; the post-Reconcile region gains one shared `commitGeneration` call and one joined error return; `Apply`'s doc comment gains the index-hygiene half of its contract; and `supervisor_test.go` gains the removed-instance-plus-rejected-save test the verification report names as absent, plus a batch-continuation test, both driven against real launched mock-plugin subprocesses.

**Scope discipline (gap closure).** This plan touches only what closes the one gap. It does not modify, renumber or replan the executed plans 07-01..07-09, and it changes no UI file, no HTTP handler, no config format, no database schema and no plugin contract. 07-VERIFICATION.md's `deferred:` list is empty. The 32 `behavior_unverified_items` are human-verification items pending a live `make dev` session, not gaps, and are NOT planned here. The two Warning findings (`webspaces.go`'s global `last_sync` aggregate, `instance-id.ts`'s unbounded `deriveInstanceId`), the Info finding (`writer.go`'s implicit temp-file mode) and the carried WR-01 `handleChipEdit` race are all recorded non-blockers, all outside this kernel seam, and are explicitly not planned — they belong in a follow-up `/gsd-code-review 7 --fix` pass.

**Recorded planning choices.**

1. **Cleanup placement: textually before the vocabulary check, not merely "un-gated".** `gaps[0].missing[0]` offers "move it ahead of (or make it independent of)". Moving it ahead is chosen because it makes the un-gated property visible at a glance and mechanically checkable (the cleanup call's line number is lower than the `ValidateMatchConfig` call's), whereas "independent of" implemented as a deferred/`defer`-style call would leave the reader re-deriving the ordering every time. The two orderings are behaviourally equivalent — neither check reads state the other writes — so the more legible one wins.
2. **Deleting the removed instance's rows on a save the kernel is REJECTING is correct, not collateral damage — and this is the judgement call at the heart of the plan.** The save is not rejected at the store level: `config.Store.Save`/`Reload` swapped their pointers to `newCfg` before `Apply` was ever called, so the removal is already the config-of-record and already agrees with the file on disk. `Host.Reconcile` then killed the instance's subprocess and dropped it from the launched set. By the time the vocabulary check speaks, the config store, the file, and the plugin host have all committed the removal; the index is the ONLY subsystem still holding the instance's data. Leaving it there is not conservatism — it is the sole remaining disagreement, and it is unrecoverable because the diff that would detect it is destroyed on the same call. The vocabulary rejection is about a *different* instance's match block; it has no bearing on whether the removal happened.
3. **Per-instance failure semantics: continue to the next NAME.** `gaps[0].missing[1]` words it exactly that way, and 07-REVIEW.md's own fix sketch does the same. When an instance's `DeleteSourceItems` fails, that instance is already stranded (T-07-13 needs both deletes), so attempting its `DeleteSyncRuns` anyway buys nothing and muddies the reported error; the batch moves on to the next name. Failures are accumulated and joined.
4. **Error ordering: vocabulary error first, then cleanup failures in sorted-instance order.** This keeps both single-fault cases byte-identical to today's text — the operator-actionable vocabulary message still leads the 500 body (D-09), and a cleanup-only failure still reads exactly as it does now — while a genuine double fault reports both. `errors.Join` drops nils, so no case grows spurious blank lines.
5. **One `commitGeneration` call for the whole post-Reconcile region.** 07-09 left four call sites because each failure branch returned separately; collapsing the region to "clean, validate, commit once, then return the joined error or fall through" reduces that to one. This strictly strengthens 07-09's invariant (a fifth failure path cannot reintroduce a divergent ordering because there is no second site to diverge from) and is the reason this plan supersedes 07-09's `commitGeneration(` count-of-5 acceptance criterion with a count of 2.
6. **Explicitly flagged, deliberately NOT planned: no sweep of rows already stranded on an existing install.** This plan prevents future stranding; it does not retroactively clean rows a pre-fix `Apply` already orphaned. A boot-time reconciliation (delete index rows for any `source` absent from the current config) would be self-healing and cheap, but it is new behaviour beyond the gap's `missing:` list, it changes what a temporarily commented-out `[sources.<id>]` block costs an operator on the next restart, and it deserves its own decision rather than riding a repair plan. Recorded here as an explicit assumption, not silently dropped; it is a candidate follow-up if any install turns out to carry stranded rows.
7. The existing `COVERAGE.md` "No external API integration" declaration stands unchanged — this plan touches only in-repo Go kernel code and adds no external API, SDK or service.
8. No ORM schema files exist in this project (Go plus hand-written SQL over SQLite) and none appear in `files_modified`, so the Schema Push Gate does not fire.
9. 07-RESEARCH.md's Package Legitimacy Audit needs no new entry: this plan installs nothing, and `errors` is stdlib.
10. No edge is silently dropped.
