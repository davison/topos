<objective>
**As a** person editing my topos configuration, **I want to** see my change take effect the moment I save it — and to pull in a hand-edit whenever I choose — **so that** configuring topos never means restarting it and never means guessing whether the running kernel agrees with the file.

Purpose: 07-01 proved the write path but stopped at swapping the config value. Nothing yet relaunches a plugin, re-registers a source with the coordinator, or restarts the scheduler — so an added, edited or removed source would be persisted and then ignored until the next kernel start. Every builder flow in 07-03, 07-04 and 07-05 depends on this machinery existing. This plan builds it, plus the Describe-before-persist capability the two-step new-instance modal needs.

Output: an apply seam that rebuilds the plugin host, coordinator and scheduler in place; a reload endpoint that survives a bad file; live-config reads in every handler; instance-scoped index cleanup; and the kernel-side half of the plugin-type picker.
</objective>

Introduce the apply seam the config store has nowhere to hand a swapped config to today.

New package `kernel/supervisor`. `Supervisor` holds the `*index.Store`, the `*config.Store`, the resolved plugins directory, an `hclog.Logger`, the current `*pluginhost.Host`, the current `*syncer.Coordinator`, the current scheduler's `context.CancelFunc`, and a `sync.Mutex` serialising applies. `NewSupervisor(ctx, idx *index.Store, cfgStore *config.Store, pluginsDir string, logger hclog.Logger) (*Supervisor, error)` performs today's boot sequence: `pluginhost.Discover` over `cfgStore.Expanded().Sources`, `pluginhost.ValidateMatchConfig`, build the coordinator, start the scheduler goroutine under a derived cancellable context. `Host()` and `Coordinator()` return the current values. `Shutdown()` cancels the scheduler context and kills every plugin.

`Apply(ctx context.Context) error` is the seam. Under the mutex it: reads the freshly swapped `cfgStore.Expanded()`; computes the instance-set difference against the currently launched `Host.Plugins()`; cancels the running scheduler's context and waits for it; calls `Host.Reconcile`; runs `pluginhost.ValidateMatchConfig` against the reconciled host; deletes index rows for every instance present before and absent now, via `index.Store.DeleteSourceItems` plus `DeleteSyncRuns` (a re-added instance under the same id must not inherit phantom history); rebuilds the coordinator over the reconciled plugin set; starts a fresh `syncer.Scheduler.Run` under a new derived context — which fires each source's first refresh immediately by its existing design, satisfying D-07's eager reconcile for new and connection-changed instances without a second mechanism; and finally, for any instance whose match block or participating webspace changed but whose connection config did not, dispatches a `Coordinator.Refresh` for that instance so a match-only edit also lands within one sync. On any error, `Apply` restores nothing and returns — the caller decides; the config file and swapped config are already valid by construction because `Store.Save` validated before swapping.

In-flight sync handling (07-RESEARCH.md Open Question 2, decided here): cancel the old scheduler's context immediately and rely on `Coordinator.syncOne`'s existing detached `sync_runs` finalize, exactly as kernel shutdown already does. Do not wait for an in-flight sync to complete and do not add a drain path.

`Host.Reconcile(ctx context.Context, sources map[string]config.Source, logger hclog.Logger) error` in kernel/pluginhost/host.go: for each configured instance not currently launched, or currently launched but whose `config.Source` value differs, launch a replacement via the existing unexported `launch` and kill the old one; kill and drop every launched instance absent from `sources`; leave an unchanged instance's subprocess running untouched, so a save touching one source does not blip every other source's reachability. A launch failure kills whatever this call launched, leaves the previously running set intact, and returns a wrapped error naming the instance — a partial apply must never look successful. Give it the multi-sentence doc comment naming D-06/D-07 that every other exported symbol in this file carries.

`index.Store.DeleteSourceItems(ctx context.Context, source string) error` runs `DELETE FROM items WHERE source = ?`; the existing `ON DELETE CASCADE` clears `webspace_items` across every webspace and the existing `items_ad` trigger keeps `items_fts` consistent, so no new trigger is needed. `index.Store.DeleteSyncRuns(ctx context.Context, source string) error` clears that instance's history. Both follow `ReplaceWebspaceSourceItems`'s signature shape, transaction convention and `fmt.Errorf("index: ...: %w", ...)` wrapping.

Wire it: `kernel/httpapi/config.go` declares a minimal `Applier` interface with `Apply(ctx context.Context) error` — `*supervisor.Supervisor` satisfies it structurally, keeping `httpapi` free of an import on the supervisor package. `ConfigSaveHandler` takes an `Applier` and, after a successful `cfgStore.Save`, calls `Apply`. An apply failure returns 500 `apply_failed` carrying the error verbatim, with the response noting the file was written and the configuration is now in an indeterminate runtime state that a reload can recover — never a silent 200. `routes.go` passes the applier through. `cmd/topos/main.go`'s `runServe` builds the supervisor and passes it to `Router`; `runSync` keeps its current one-shot path but sources its host and coordinator from `NewSupervisor` so there is one construction sequence, not two.
