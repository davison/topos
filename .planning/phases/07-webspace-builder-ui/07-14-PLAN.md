<objective>
**As a** person tidying up a webspace, **I want to** choose "Remove from this webspace" and see that source's chip go away, **so that** the webspace holds what I say it holds — instead of every chip flashing a sync spinner and then nothing changing at all, with no error to explain it.

Purpose: this plan closes 07-UAT.md `G-07-6`. Two independent defects, each individually sufficient to reproduce the exact reported symptom, and both of which must be fixed for the documented behaviour to hold. First, `web/src/lib/config-edit.ts`'s `removeSourceFromWebspace` filters the webspace's `sources` allowlist array directly; for a webspace with no explicit allowlist — the all-participate default, and exactly the shape of the user's reported webspace — filtering an empty array yields an empty array, which `kernel/config/types.go`'s `Webspace.Participates` reads as "every configured instance participates". The write round-trips with a 200 and changes nothing about participation. Its sibling `addSourceToWebspace` has always seeded the full participant set before appending; the symmetric seed was simply never mirrored into the remove direction, and the only test fixture for it starts from a non-empty allowlist, so the case was never exercised. Second, `WebspaceHeader.svelte`'s chip row derives from the `sources` prop verbatim — the kernel-wide `GET /api/sources` list, which `kernel/httpapi/sources.go`'s own doc comment describes as one entry per instance, unfiltered — with no webspace-participation filter anywhere in the file. Even a perfectly correct config write would not make the chip disappear. `AddSourceModal.svelte` already implements the needed predicate correctly for its own picker list, once, and it was never shared.

Output: `participation.ts` — created by 07-11 for the shell discriminator — gains the effective-participation predicate mirroring both the allowlist gate and 07-11's has-match-input rule; `removeSourceFromWebspace` seeds before filtering; the header's chip derivations consume the filtered list while row visibility deliberately continues to consume the unfiltered one; `AddSourceModal`'s inline copy is replaced by the shared helper; and the empty-allowlist fixture the gap names as untested is added alongside a source-scan guard over both component changes.

**Scope discipline (gap closure).** This plan closes `G-07-6` and nothing else. `G-07-3` is 07-11 (whose participation semantics this plan mirrors, and whose `participation.ts` it extends), `G-07-4` is 07-12, `G-07-5` is 07-13 (which this plan waits on for `AddSourceModal.svelte`). No kernel file is touched. No route-level state is narrowed. No chip ordering, styling, tooltip or filter-toggle behaviour changes.

**Recorded planning choices.**

1. **Both defects are fixed in one plan because either alone leaves the bug fully intact.** The diagnosis establishes this by construction: fix the write and the chip still shows, because the header never consulted participation; fix the header and the chip still shows, because the still-empty allowlist resolves to all-participate under the corrected filter's own logic. Splitting them across plans would produce a wave where the reported symptom is unchanged and a reviewer could reasonably believe the fix failed.
2. **The predicate mirrors 07-11's post-fix kernel semantics, not the pre-07-11 ones.** Effective participation is the allowlist gate AND having match input — an explicit match block, or a non-empty `keywords` fallback. `AddSourceModal`'s existing `participatingSet` implements only the first half, which was correct before 07-11 and is incomplete after it: a 07-11 shell would otherwise report every configured instance as a participant, showing a full chip row for a webspace the kernel syncs nothing into. This is why the helper lives in the module 07-11 created rather than being copied out of the modal.
3. **Row visibility and chip content are deliberately driven by different lists.** `shouldShowSourceRows` answers "does this installation have any configured source instances at all"; the chip filter answers "which of them belong to this webspace". The entire chip row block — including the "+" add-source trigger and Refresh all — sits behind the former. Filtering its input would hide the "+" for any webspace with zero participants, which after 07-11 includes every freshly created one, and after this plan includes any webspace whose last source was just removed. That would replace one dead end with another, so the split is load-bearing and is pinned by both a prohibition and a source-scan assertion.
4. **Filtering happens in the header, not at the route.** The route's `sources` state also backs `sourcesByInstance` (the detail pane's display-name and reachability lookup), `staleSources` and `resolveSourceFilters`. Narrowing it would quietly change those surfaces; the defect is in the chip-row derivation and the fix is placed there.
5. **The last-entry-removed case is pinned and documented rather than redesigned.** Removing the final named instance from an explicit allowlist yields an empty allowlist, which the config format can only encode as all-participate — 07-05 recorded this deliberately. For a webspace that still declares a `keywords` fallback, that means the remaining instances rejoin. This is the existing encoding's only representable outcome, and changing it would mean a new config shape and a kernel change, which is out of scope for a gap repair. On the UI-built path it is invisible: such a webspace has no keywords either, so it is an 07-11 shell with no participants at all. A test pins the behaviour so it is a known boundary rather than a future surprise.
6. **Explicitly flagged, deliberately NOT planned.** A source filter selected in the URL (`?sources=`) can name an instance that no longer participates in the current webspace. `resolveSourceFilters` already degrades per member against the configured-instance list, so nothing breaks; the selection simply matches no visible chip. Narrowing it to participants would change URL-persistence semantics settled in Phase 6 (D-02) and is not part of this gap.
7. No package is installed by this plan; 07-RESEARCH.md's Package Legitimacy Audit needs no new row. No ORM schema files exist, so the Schema Push Gate does not fire.
