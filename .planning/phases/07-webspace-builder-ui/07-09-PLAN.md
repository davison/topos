<objective>
**As a** person editing a source's connection details in the webspace builder, **I want to** a save the kernel rejects to leave every source still syncing normally, **so that** one mistyped match field never silently breaks a source's sync until I restart the kernel — the same never-leave-the-running-system-broken promise the whole hot-apply design (D-06) is built on.

Purpose: this plan closes the single Critical gap in 07-VERIFICATION.md (`gaps[0]`, first raised as 07-REVIEW.md's post-07-07/08 CR-01) — a pre-existing defect from this phase's own 07-02 plan, in the exact function that phase wrote as the hot-apply mechanism ROADMAP success criterion 1 depends on. `Supervisor.Apply` stops the scheduler, calls `Host.Reconcile` (which commits its result by mutating the launched plugin set in place — the replaced instance's subprocess is already killed and a new one installed by the time it returns nil), then calls `pluginhost.ValidateMatchConfig`. When that second call fails, the branch beneath it restarts the scheduler against the OLD config and leaves `s.coord` and `s.cfg` at their old values, while `s.host` has already moved on. Any instance whose connection changed in that same save is now represented in `s.coord` by a `*Plugin` whose subprocess is dead — and the restarted scheduler goroutine calls `Coordinator.Refresh` against that dead gRPC client indefinitely, failing every tick with no signal tying the failure back to the rejected save, until some later apply happens to succeed all the way through. One ordinary `PUT /api/config` that both edits a connection and introduces an invalid match field name reaches this exactly.

Output: `Apply` gains a single shared commit site every branch that adopts the new generation goes through, in the one order that is correct; the match-vocabulary branch and the two D-07 index-cleanup branches all route through it; the doc comment is corrected to describe the two-regime contract the code actually implements; and `supervisor_test.go` gains the Reconcile-succeeds/ValidateMatchConfig-fails ordering test the verification report names as absent, proving the fix behaviourally against real launched plugin subprocesses rather than structurally.

**Recorded planning choices.**

1. **Fix direction: option (a), roll forward — chosen deliberately over option (b), roll back.** 07-VERIFICATION.md `gaps[0].missing[0]` offers both. Option (a) is chosen on five grounds. (i) *Totality*: `newCoordinator` is pure in-memory construction over the host's current plugin list and cannot fail, whereas option (b) requires a second `Reconcile` that performs real subprocess launches and can itself fail — leaving no third recourse. (ii) *The store has already swapped*: `config.Store.Save` swaps its pointers at the end of a successful save and `Store.Reload` likewise, both strictly before the handler calls `Apply`, so the new config is already the config-of-record — `ConfigSaveHandler`'s own shipped 500 body says exactly that. Under option (b) the supervisor would become the only subsystem still on the old config, disagreeing with the store, with the file on disk, and with the per-request `cfgStore.Expanded()` reads the 07-07 fix installed in every `/agent/v1` handler. (iii) *The documented recovery path only converges under (a)*: the handler names `POST /api/config/reload` as recovery, and reload re-reads the same still-invalid file — under (a) the retry's reconcile is a no-op and it simply fails the same way, whereas under (b) every retry kills and relaunches the affected subprocesses twice, forever. (iv) *Precedent inside the same function*: the two D-07 index-cleanup failure branches already roll forward, so (a) makes the post-Reconcile branches uniform instead of adding a third shape. (v) *D-08 is satisfied upstream, not here*: "an invalid file on reload keeps the last-good config running" is enforced by `Store.Reload` validating before it swaps, so an invalid file never reaches `Apply` at all; a match-vocabulary rejection is a different class — structurally valid config that only a live post-launch cross-check can reject, by `ValidateMatchConfig`'s own doc comment — and by then no last-known-good exists at the store level either.
2. **A second, previously unreported instance of the same defect family is folded in.** `startScheduler` captures `s.coord` into the `syncer.Scheduler` value at call time. The two D-07 index-cleanup failure branches call it BEFORE assigning the rebuilt coordinator, so the generation they start runs against the old coordinator. This is in scope, not scope creep: `gaps[0].missing[0]` requires "restarting the scheduler against newCfg so its goroutine set matches what s.coord actually holds", which is unachievable while that ordering is inverted.
3. The existing `COVERAGE.md` "No external API integration" declaration stands unchanged — this plan touches only in-repo Go kernel code and adds no external API, SDK or service. The detector's `detected: true` on the phase scope fires on the earlier plans' own prose *about* the coverage checkpoint, not on a real integration.
