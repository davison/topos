<objective>
**As a** person adding a second Signal source, **I want to** click Next and reach the match step, **so that** I am not stopped by a handshake error whose four stated causes — binary path, permissions, owner, architecture — are all false, and whose real cause is a field I left blank because it looked pre-filled.

Purpose: this plan closes 07-UAT.md `G-07-5`. Two confirmed causes fire together. First, `web/src/lib/plugin-fields.ts` declares Signal's `path` field `required: false` and shows its mandatory value only as a placeholder; `ConnectionForm.svelte` renders `required` as nothing more than an asterisk appended to the label — no DOM `required` attribute, no submit-time check, no seeding from the placeholder — so the Connect step submits an absent `path`, `pluginhost.launch` marshals `"path":""` into `WEBSPACES_SOURCE_CONFIG`, and `plugins/signal/main.go:47` prints one line to stderr and exits before `goplugin.Serve`. Second, `launch` never sets `goplugin.ClientConfig.Stderr`, which go-plugin defaults to `io.Discard`, so the child's single explanatory line reaches no surface at all — the kernel log records only `exit status 1`. Cause one creates the failure; cause two makes it undiagnosable, which is why a missing-field error reached UAT as an unexplained blocker. The diagnosis proved by controlled experiment against an ephemeral kernel that a *wrong* path returns 200 and only an *empty* one fails, and that Proton reproduces identically through `webmail_base_url` — so a fix scoped to Signal would leave the class wide open.

Output: the required flags are re-derived from every plugin's own pre-`Serve` guards (paperless: `base_url`, `token`; silverbullet: `base_url`, `token`; proton: `base_url`, `username`, `token`, `webmail_base_url`; signal: `path`), with Signal's path additionally seeded as a real editable default; two pure helpers compute the missing-required set and its message; all three submit paths that can reach a plugin launch call them; and `pluginhost.launch` captures a bounded tail of the child's stderr and appends its last line to the connect error, so the whole pre-handshake-fatal class explains itself from now on, for every plugin and every field.

**Scope discipline (gap closure).** This plan closes `G-07-5` and nothing else. `G-07-3` is 07-11, `G-07-4` is 07-12, `G-07-6` is 07-14. It changes no plugin source file, no proto, no config format, no HTTP request or response shape, and adds no dependency.

**Recorded planning choices.**

1. **The required flags are derived, not patched.** The UAT report names Signal. The diagnosis names Proton as an identical reproduction and observes that even `required: true` was unenforced, so blank Base URL or Token on paperless/silverbullet hit the same wall. The task therefore reads all four `plugins/*/main.go` pre-`Serve` guards and makes the table match them, rather than flipping the two flags that happened to be reported. Anything less leaves the class open by construction.
2. **Only Signal's path gets a seeded default value.** `~/.config/Signal` is genuinely correct on a standard Linux install, which is exactly why it was written as a placeholder in the first place; making it a real value removes the trap without guessing. Proton's `webmail_base_url` gets `required: true` and keeps its placeholder: its account index varies per user, and a wrong default would silently produce broken deep links — a worse failure than a visible empty required field, now that empty required fields are actually visible.
3. **Enforcement lives in a pure helper called by three sites, not in the form component.** `ConnectionForm` is shared by the two-step add flow and the chip menu's Edit connection… modal, and each owns its own submit handler, its own error state and its own request. A guard inside the shared component could not stop any of their requests. The component still gains the DOM `required` attribute — free browser-native prevention and correct assistive-technology semantics — but the load-bearing check is a pure function the submit handlers call, which is also what makes it unit-testable without a mount harness.
4. **Edit connection… is included even though the UAT report reached the defect through the add flow.** Blanking a required field there persists an instance the plugin cannot launch, and the hot-apply reconcile then fails on the very next save. Same helper, same call shape, one extra line — excluding it would knowingly leave a second door to the same wall.
5. **The stderr capture is the recurrence guard the gap's `missing` list asks for, and it is deliberately broader than the gap.** It fires for any pre-handshake fatal from any plugin — including causes no field table could anticipate, like a corrupt binary or a missing shared library — and because `launch` is shared, boot-time launches benefit identically. This is the half that converts every future instance of this class from an unexplained blocker into a one-line answer.
6. **Bounded and synchronized, read after Kill.** go-plugin's `logStderr` goroutine writes to `ClientConfig.Stderr` concurrently; `Client.Kill` waits on the client wait group that goroutine belongs to. So the buffer needs a mutex to be race-clean and a size cap to be memory-safe, and the read must happen after `Kill()` — which is already where the existing connect-failure branch calls it.
7. **Explicitly flagged, deliberately NOT planned.** `DescribePluginHandler` still validates only that the named binary was discovered; it does not check required fields server-side. That is correct for now — the field table is a client-side concern with no wire representation (07-RESEARCH.md's finding that no connection-field schema exists anywhere on the wire), and the stderr capture means a blank field reaching the kernel is now self-explanatory rather than silent. A server-side required-field contract would need a real schema on the wire and belongs to a plugin-contract phase, not a gap repair.
8. No package is installed by this plan; 07-RESEARCH.md's Package Legitimacy Audit needs no new row. No ORM schema files exist, so the Schema Push Gate does not fire.
