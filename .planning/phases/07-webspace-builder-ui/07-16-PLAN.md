<objective>
**As a** person curating what a webspace holds, **I want to** remove a source and see its items leave the stream with its chip, **so that** the webspace on screen is the webspace I just described — instead of a list that still shows the source I removed until I reload the page and wonder whether the removal worked at all.

Purpose: this plan closes 07-UAT.md `G-07-7`. Webspace membership in the stream is a sync-time artifact — the `webspace_items` join rows — and `kernel/httpapi/stream.go` serves the stream from those rows with no read-time participation predicate to fall back on. When a webspace is narrowed, the instance's own `[sources.<id>]` block stays intact, so `Supervisor.Apply`'s `removedInstances` diff is correctly empty and its synchronous cleanup does nothing. The ONLY purge of a de-participated pair is `correlate.SyncSource`'s non-participation branch, reachable only during a sync — and Apply dispatches that sync as `go coord.Refresh(...)` and returns, so `PUT /api/config` answers 200 while the stale rows still exist. The client's `handleRemoveSource` does refetch the stream immediately and correctly; it simply always wins the race and reads pre-purge data. The WR-03 sync poll, which is the one mechanism that could have healed the view afterwards, reloads only the source list and never the stream — so the stale items persist until a manual refresh.

Output: the participation rule the sync path already applies is extracted into one exported predicate; `Supervisor.Apply` diffs old against new participation per `(webspace, source)` and clears each pair that flipped, synchronously, before it returns — a pure local index write with no plugin RPC; and the client's sync-completion poll gains a quiet stream refetch so a purge that had to wait for a later sync also heals on screen.

**Scope discipline (gap closure).** This plan closes `G-07-7` and nothing else. `G-07-1` is 07-15, which this plan depends on because both edit `load()` in the same route file. `G-07-3`..`G-07-6` are closed by 07-11..07-14. No HTTP handler is touched. No sync becomes synchronous. No plugin, proto or config-schema file changes.

**Recorded planning choices.**

1. **The purge is synchronous; the sync is not.** The debug session's rejected alternative is awaiting the eager resync inside Apply — that would make every config save wait on a Match RPC per webspace against a plugin reading a mailbox or an encrypted database, so one unreachable source would make every save feel broken. Clearing a `(webspace, source)` pair needs no plugin at all: it is a delete against the local index. Doing exactly the part that is local, synchronously, is what lets D-06's "save = apply immediately" hold at the stream boundary without coupling saves to source availability.
2. **The predicate is extracted, not duplicated.** The supervisor must decide participation with the same rule `correlate.matchFieldsFor` applies, or the purge and the next sync disagree — clearing rows a sync restores, or leaving rows a sync would clear. `G-07-6` was made of exactly this shape of divergence on the client side. `matchFieldsFor`'s first two conditions move behind a named exported function; its four documented rules and their order are unchanged, and its existing tests pass with unmodified bodies as the proof.
3. **The diff is scoped to webspaces and instances present in BOTH configs.** A webspace deleted from the config is excluded because the clear path upserts the `webspaces` table row inside the same transaction — purging a deleted webspace through it would leave the index asserting that a deleted webspace exists, which is worse than the stale rows. An instance removed from the config is excluded because `cleanupRemovedInstances` already deletes its `items` rows and the join table's existing `ON DELETE CASCADE` already clears it from every webspace. Both exclusions are behaviour-preserving and each is justified by code that already exists.
4. **The purge lives in Apply's post-Reconcile region, beside the D-07 cleanup.** That region already runs unconditionally on every path that reaches it, already collects per-item failures rather than returning early, and already funnels through one commit site — the invariants 07-09 and 07-10 established. The pre-Reconcile failure branch deliberately purges nothing: there, Reconcile's own guarantee means the old generation is genuinely intact and keeps running against the old config, so deleting rows its scheduler is about to rewrite would be churn with no observer.
5. **The client poll refetch is the fallback, not the fix.** With the kernel purging before it answers, `handleRemoveSource`'s existing refetch is correct and needs no change. The poll change covers the case the debug session flags as the worse variant of the same cause: an eager resync that FAILS leaves the rows for a later scheduled sync, and today nothing on screen would ever notice. It is also a general freshness win — a background sync that adds items now shows them.
6. **The poll refetch is quiet.** `load()` sets the loading state as its first statement, which renders the skeleton. Firing it on every sync completion would blank an already-rendered stream on a regular interval. A quiet mode skips the loading transition and, on failure, leaves what is on screen untouched — a failed background refresh must be strictly better than today's behaviour of not refreshing at all, never worse.
7. **Explicitly flagged, deliberately NOT planned — read-time participation filtering in the stream handler.** Applying the webspace's allowlist as a query-time predicate would make stale join rows unobservable regardless of purge timing. It is a larger change to the sync-time correlation model the whole index is built on (KERN-02), it would need the same treatment on search and the agent mirror, and it would mask rather than fix the divergence between the config and the index. The purge keeps the index true to the config, which is the property every other consumer depends on.
8. **Explicitly flagged, deliberately NOT planned — orphaned rows for a webspace deleted from the config.** Nothing purges them today and nothing does after this plan (planning choice 3). They are unreachable from the switcher, and after 07-15 a deleted webspace's name still resolves through the index half of the existence gate exactly as it did before. Recorded as a known boundary; closing it needs a webspace-scoped delete that does not touch the `webspaces` table, which is its own change.
9. **Gap-closure shape, not tracer-first.** This is a repair to a named seam of an already-proven architecture, matching 07-11..07-15's shape.
10. No package is installed by this plan; 07-RESEARCH.md's Package Legitimacy Audit needs no new row. No ORM schema files exist, so the Schema Push Gate does not fire.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser UI → kernel `PUT /api/config` | Loopback-only, unauthenticated per the v1 posture. The document written here decides which sources a webspace pulls from; the response is the user's only signal that it took effect |
| running config → the local index's `webspace_items` join | The config states which sources belong to a webspace; the index materialises it. Any interval where the two disagree is an interval where every consumer — the SPA, the search route, the agent mirror — reads something the operator did not ask for |
| kernel `Supervisor.Apply` → plugin subprocesses | Apply may launch, kill and RPC subprocesses. Anything placed on the synchronous save path that touches this boundary makes save latency depend on external systems |
| indexed items → `/agent/v1` stream mirror | An agent reads the same join rows. A webspace narrowed for privacy reasons that has not yet been purged is disclosing to an agent exactly what the operator just revoked |
