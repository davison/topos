## Phase Goal

**Goal (verbatim from ROADMAP.md):** User can define a webspace, open it in a browser, and see their paperless-ngx documents for that topic as one chronological stream with inline previews and working deep links back to paperless-ngx.

> **MVP-mode note — user story not authored.** MVP_MODE is enabled, but the ROADMAP `**Goal:**` line for Phase 1 is not in canonical `As a / I want to / so that` form (it has an actor and a capability but no explicit outcome clause). Per the MVP planning rules the planner must not invent one. The goal is reproduced verbatim above. To get the bolded user-story framing, run `/gsd-mvp-phase 1` and re-plan.

<objective>
Land the walking skeleton: the thinnest possible path that carries a real paperless-ngx document from the user's home server, through every architectural layer this project will ever have, to a browser — and prove it against real data, not a fixture.

Purpose: every later phase inherits these seams. Proving the gRPC subprocess boundary, the read-only contract, the sync-time correlation boundary, the SQLite index, the loopback HTTP API and the embedded SPA *now*, on one thin path, means an architectural dead end costs one commit instead of ten.

Output: a running `webspaces serve` binary that lists the user's webspaces at `/`, renders their real paperless-ngx documents chronologically at `/w/{webspace}`, and serves the same JSON to any agent at `/api/*`.
</objective>

**`proto/webspaces/v1/plugin.proto` — recommended shape (option-b from Task 1's decision):**

```protobuf
syntax = "proto3";
package webspaces.v1;
option go_package = "github.com/darrendavison/webspaces/sdk/gen/webspaces/v1;webspacesv1";

// SourcePlugin is read-only by construction. No RPC in this service changes
// state in the source system, and none may ever be added — see PLUG-02.
service SourcePlugin {
  rpc Describe(DescribeRequest) returns (DescribeResponse);
  rpc Match(MatchRequest) returns (MatchResponse);
  rpc Fetch(FetchRequest) returns (stream FetchChunk);
  rpc Health(HealthRequest) returns (HealthResponse);
}

message DescribeRequest {}
message DescribeResponse {
  string source_type      = 1;  // "paperless"
  string display_name     = 2;  // "paperless-ngx"
  string contract_version = 3;  // "webspaces.v1"
}

message MatchRequest  { repeated string keywords = 1; }  // exact, case-insensitive (D-03)
message MatchResponse { repeated Item   items    = 1; }

enum LinkFidelity {
  LINK_FIDELITY_UNSPECIFIED       = 0;
  LINK_FIDELITY_EXACT             = 1;
  LINK_FIDELITY_ANCHORED          = 2;
  LINK_FIDELITY_CONVERSATION_ONLY = 3;
}

message Item {
  string source_id                = 1;  // stable, plugin-local id
  string source_type              = 2;
  string title                    = 3;
  string preview                  = 4;  // bounded snippet, never full content
  int64  timestamp_unix           = 5;  // primary sort: real-world time
  int64  secondary_timestamp_unix = 6;  // tie-break: ingestion/receipt time
  LinkFidelity fidelity           = 7;
  string deep_link                = 8;
  repeated string labels          = 9;  // native categorization (paperless tag names)
  map<string, string> provenance  = 10;
  string group_id                 = 11; // chat thread / mail conversation; "" for documents
  string group_label              = 12;
  bool   has_thumbnail            = 13;
}

enum ContentVariant {
  CONTENT_VARIANT_UNSPECIFIED = 0;
  CONTENT_VARIANT_FULL        = 1;
  CONTENT_VARIANT_PREVIEW     = 2;
  CONTENT_VARIANT_THUMBNAIL   = 3;
}

message FetchRequest { string source_id = 1; ContentVariant variant = 2; }

message FetchHeader {
  bool   available            = 1;
  string unavailable_reason   = 2;
  string mime_type            = 3;  // "" when there is no binary rendition
  int64  size_bytes           = 4;
  string text                 = 5;  // extracted text, may be ""
  map<string, string> provenance = 6;
}
message FetchChunk { oneof chunk { FetchHeader header = 1; bytes data = 2; } }

message HealthRequest {}
message HealthResponse { bool reachable = 1; int64 last_sync_unix = 2; string last_error = 3; }
```

**`kernel/index/schema.go` — SQLite schema:**

```sql
PRAGMA journal_mode=WAL;
PRAGMA foreign_keys=ON;

CREATE TABLE IF NOT EXISTS items (
  id                       TEXT PRIMARY KEY,   -- "{source_type}:{source_id}"
  source_type              TEXT NOT NULL,
  source_id                TEXT NOT NULL,
  title                    TEXT NOT NULL,
  preview                  TEXT NOT NULL,
  timestamp_unix           INTEGER NOT NULL,
  secondary_timestamp_unix INTEGER NOT NULL,
  fidelity                 TEXT NOT NULL,      -- "exact" | "anchored" | "conversation-only"
  deep_link                TEXT NOT NULL,
  labels_json              TEXT NOT NULL,
  provenance_json          TEXT NOT NULL,
  group_id                 TEXT NOT NULL DEFAULT '',
  group_label              TEXT NOT NULL DEFAULT '',
  has_thumbnail            INTEGER NOT NULL DEFAULT 0,
  synced_at                INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS webspace_items (
  webspace_name TEXT NOT NULL,
  item_id       TEXT NOT NULL REFERENCES items(id) ON DELETE CASCADE,
  PRIMARY KEY (webspace_name, item_id)
);

CREATE TABLE IF NOT EXISTS sync_runs (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  source_type   TEXT NOT NULL,
  started_unix  INTEGER NOT NULL,
  finished_unix INTEGER,
  status        TEXT NOT NULL,          -- "running" | "ok" | "error"
  error         TEXT NOT NULL DEFAULT '',
  item_count    INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_items_chrono
  ON items(timestamp_unix DESC, secondary_timestamp_unix DESC, id ASC);

-- Stream query: index-only, no plugin involvement.
SELECT items.* FROM items
  JOIN webspace_items ON webspace_items.item_id = items.id
 WHERE webspace_items.webspace_name = ?
 ORDER BY items.timestamp_unix DESC, items.secondary_timestamp_unix DESC, items.id ASC;
```

`items` is a normal rowid table — Phase 3 (KERN-05) can add an external-content FTS5 table over
`items(title, preview)` with `content='items', content_rowid='rowid'` and no migration.

  <context>
This is the one genuine one-way door in Phase 1. The `.proto` plus its generated `sdk/` stubs is what Phase 2 publishes for third-party plugin authors (PLUG-05), and Phases 3, 4 and 5 each add a plugin against it. Once a third party builds against it, changing a field number or an RPC signature is a breaking change with no migration path — unlike a Go refactor, we cannot rewrite their call sites.

The ROADMAP notes require the contract be sketched against *two structurally different sources* — documents and chat — before it is written, even though only paperless-ngx ships this phase. `01-RESEARCH.md` assumption A1 flags its own sketch as unverified against that second source. The three options below differ mainly in how they carry content back on item-open and whether chat/mail grouping is reserved now or retrofitted later.

Locked decisions already made and NOT up for re-decision here: TOML config (D-01), a shared keyword *list* per webspace with no per-source override (D-02), exact case-insensitive matching (D-03), single config file with `${VAR}` secrets (D-04). Every option below carries `repeated string keywords` in `MatchRequest` unchanged.
  </context>
  <options>
    <option id="option-a">
      <name>Unary Fetch — one response carrying bytes</name>
      <pros>Smallest contract; simplest plugin and kernel code; four unary RPCs, no streaming state machine.</pros>
      <cons>A rendition must fit in one gRPC message. The default 4 MB limit means large scanned PDFs need the limit raised globally on both ends, and Phase 3's mailbox backfill / Phase 5's chat history have no natural chunking path — both would need a contract change.</cons>
    </option>
    <option id="option-b">
      <name>Streaming Fetch + reserved grouping fields (recommended)</name>
      <pros>Exactly the shape in this plan's `&lt;interfaces&gt;` block. `Fetch` server-streams a `FetchHeader` followed by data chunks, so renditions of any size work and Phases 3–5 inherit streaming for volume. `Item` reserves `group_id` / `group_label` (chat thread, mail conversation), `secondary_timestamp_unix` (stable tie-break for date-only sources such as paperless `created`) and `labels` now, so chat and mail land as *populated fields*, not as a breaking change. `Describe` lets the kernel identify a plugin without trusting its filename.</cons>
      <cons>Streaming adds a modest amount of plugin-side and host-side code that the paperless plugin alone would not need. Three fields (`group_id`, `group_label`, `has_thumbnail`) ship unused-ish in Phase 1.</cons>
    </option>
    <option id="option-c">
      <name>Unary Fetch for text + a separate streaming FetchContent for bytes</name>
      <pros>Text-only consumers never touch the streaming path; the two concerns are separated in the contract.</pros>
      <cons>Two RPCs to implement and two to document for every plugin author, for a split the kernel does not actually need — the detail pane wants text and rendition together. More surface on a contract we cannot shrink later.</cons>
    </option>
