<objective>
Prove the whole filesystem-source path end to end on one thin slice: a single PDF sitting
in a configured folder becomes a stream item, and its "Open in …" action reaches a
kernel-mediated open route that resolves the real file path from the index alone.

Purpose: every later plan in this phase expands outward from this slice. The two pieces of
genuinely new machinery — the `file://`-scheme deep-link convention plus its kernel-side
rewrite, and the loopback `xdg-open` route — are both proved here, on the executor's best
early-context tokens, before any breadth work (scope classification, recursion, UI form,
external rehearsal) is committed on top of them.

Output: the `plugins/filesystem` module (minimal but production-quality), the kernel open
route and stream rewrite, the OpenInSource local-exec branch, and a hermetic e2e spec that
walks the whole path with a real kernel and a real plugin binary.

Costly decision carried from CONTEXT.md, flagged for the reader: **D-01** fixes the
per-source stable ID as the path relative to the source folder. Index rows, Phase 13
exclusions and dedup all key on it; changing the scheme later forces an index rebuild for
every existing filesystem source. It is implemented here and not revisited.

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Lock the plugin→kernel deep-link signalling mechanism</name>
  <decision>
  How does a filesystem item tell the kernel "this deep link must be opened by the kernel's
  own open route" — given that a plugin subprocess is never told the kernel's listen address
  and never learns its own source instance id?
  </decision>
  <context>
  12-CONTEXT.md D-06 locks the *behaviour* (a loopback kernel endpoint runs `xdg-open` on the
  item's real path, constrained to currently-indexed items) but not the *signalling*. The
  plugin cannot build `http://127.0.0.1:7777/api/items/{source}:{source_id}/open` itself: the
  launch-environment allowlist carries no kernel base URL (verified in 12-RESEARCH.md against
  `docs/plugin-contract.md` and `kernel/config/types.go`), and the contract states a plugin
  never learns its own instance identity.

  Whatever is chosen here becomes a convention in the published plugin contract that Phase 14's
  out-of-repo Google Drive plugin — and any third-party local-path plugin after it — will read
  and build against. Undoing it later means breaking a published contract, not refactoring one
  package. That is why this is a gate rather than a planner judgement call.
  </context>
  <options>
    <option id="option-a">
      <name>file:// deep_link + kernel-side, scheme-keyed rewrite at serve time (12-RESEARCH.md recommendation)</name>
      <pros>No contract version bump and no new launch-environment field. The plugin already
      knows both halves of the real absolute path (its configured root plus the relative
      source_id), so it can build an honest `file://` URI with no new information. The kernel's
      rewrite is keyed on the URL scheme, never on `source_type`, so a future third-party
      local-path plugin gets identical treatment with zero kernel change — consistent with the
      contract's "the kernel holds no built-in table of known plugin types" discipline.
      `validateCorrelatedItem` accepts a `file://` value unmodified today.</pros>
      <cons>The `file://` value stored in the index is never the value served to a client, so
      the index row and the API response disagree by design — a reader has to know the rewrite
      exists. Publishing the convention makes any future change to it a contract break.</cons>
    </option>
    <option id="option-b">
      <name>Thread the kernel's own base URL into WEBSPACES_SOURCE_CONFIG as a new built-in field</name>
      <pros>The plugin builds the final, real URL itself; no serve-time rewrite, no
      index/response divergence.</pros>
      <cons>A genuine contract change with third-party-plugin-author implications: a new
      built-in envelope field plus a documented instance-identity leak (the plugin would also
      need its own source instance id to build the composite item id), directly contradicting
      the contract's existing "a plugin never learns its own instance identity" rule. Much
      larger blast radius for one feature.</cons>
    </option>
    <option id="option-c">
      <name>Something else — describe it</name>
      <pros>Keeps the door open if neither shape above fits how you want the contract to read.</pros>
      <cons>Unscoped; the rest of this phase's plans assume one of the two above.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c (with a description)</resume-signal>
</task>

  2. **Describe (D-05).** `sourceType` is `filesystem`, `displayName` is `Filesystem folder`,

     forward slashes (D-01); `title` is the file's base name; `timestamp_unix` is the file's

     siblings. Before reading, re-validate that the joined absolute path is still inside the
     configured root and refuse otherwise.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → kernel `/api` | Loopback, unauthenticated by design; the new open route is the kernel's second raw-exec surface and the sharpest new attack surface in this phase |
| plugin subprocess → kernel | `Item.source_id` and `Item.deep_link` are plugin-asserted strings that reach index rows and, transitively, a path join on the exec path |
| kernel → local filesystem | The configured source root delimits everything the user consented to expose |
| kernel → `xdg-open` child process | A fixed binary literal plus exactly one server-resolved argument |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-12-01 | Elevation of Privilege | `kernel/httpapi/fsopen.go` exec call | critical | mitigate | Binary name is the fixed literal `"xdg-open"`, never derived from config or request; the sole argument is the server-resolved absolute path; no shell is involved |
| T-12-02 | Tampering | `kernel/httpapi/fsopen.go` path resolution | high | mitigate | The path is joined from the indexed item's own `SourceID` and the configured source `Path`; no request body/query value is read; the joined absolute path is re-checked against the root prefix and refused with `invalid_path` otherwise (covered by a dedicated `../`-escape test) |
| T-12-03 | Elevation of Privilege | open route reachable for non-filesystem items | high | mitigate | The handler requires the indexed item's `DeepLink` to carry the `file://` scheme before resolving anything, so a Signal or WhatsApp instance (also `Path`-configured) can never be driven through this route |
| T-12-04 | Information Disclosure | `file://` deep link stored in the index | low | accept | The absolute path is already derivable from the configured source root plus the item's `source_id`, both of which the loopback API already publishes; storing it adds no new disclosure |
| T-12-05 | Denial of Service | unbounded `xdg-open` child processes from repeated POSTs | medium | mitigate | The child is started fire-and-forget and reaped by a background wait; the route performs no other work, and the loopback-only boundary bounds the caller set to processes already on the machine |
| T-12-06 | Spoofing | plugin asserting a `deep_link` pointing outside its own root | high | mitigate | The kernel never opens the plugin-supplied `deep_link` value — it is used only as a scheme marker; the opened path is recomputed server-side from `SourceID` + configured root and root-prefix-checked |
| T-12-SC | Tampering | npm/pip/cargo installs | high | mitigate | No npm, pip or cargo package is installed by this plan; the only new dependency in this phase is a Go module gated by a blocking legitimacy checkpoint in 12-02 |
</threat_model>
