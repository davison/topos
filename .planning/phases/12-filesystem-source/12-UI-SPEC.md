# Phase 12 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Design system already fully established (Phases 1–11); this phase introduces zero new spacing values, zero new type sizes/weights, and zero new palette hex values.** This is a source-plugin phase (SRC-04), not a UI-polish phase — most of the UI surface a sixth source needs (stream row, thumbnail, plugin icon, match-vocabulary form, extras editor, trust badge, picker catalog tile) already exists and is exercised **unmodified**; see "Explicit Reuse — Zero New UI" below for each generic surface and why it needs nothing new. Exactly **two** genuinely new elements are introduced, both specified in full: F1 (the filesystem connection fields, which also introduces a reusable boolean-checkbox field kind to the shared `ConnectionForm`) and F2 (a new local-exec interaction variant for "Open in Source", required because this phase's deep link — D-06 — is a kernel-side `xdg-open` exec, not a URL a browser tab can usefully navigate to).

## New UI Elements

Two genuinely new elements. Everything else this phase's five success criteria touch is **explicit, verbatim reuse** — see the section immediately below for why each generic surface needs nothing new.

### F1 — Filesystem Connection Fields (`ConnectionForm.svelte` / `plugin-fields.ts`) — introduces the shared Checkbox field kind

**Where:** A new `CONNECTION_FIELDS['topos-plugin-filesystem']` row in `web/src/lib/plugin-fields.ts`, rendered by the existing, unforked `ConnectionForm.svelte` (both `AddSourceModal.svelte`'s two-step new-instance flow and `EditSourceModal.svelte`'s "Edit connection…" flow reuse this component and this row automatically — no per-caller change needed).

**Fields, in order:**
1. `DISPLAY_NAME_FIELD` (existing, unchanged, shared by every plugin type).
2. **Local Path** — `key: 'path'`, `required: true`, `secret: false`, `advanced: false`, **no `defaultValue`** (unlike Signal/WhatsApp's `~/.config/Signal`/`~/.local/share/topos/whatsapp`, an arbitrary local-or-network document folder has no universally-correct default — seeding one risks silently pointing a fresh install at a path that doesn't exist, worse than a visible required empty field). `placeholder: 'e.g. /home/you/Documents or /mnt/nas/shared-docs'` — the two-example placeholder deliberately signals "local or network" up front, since SRC-04 explicitly covers both and a user unfamiliar with the feature might otherwise assume it's local-only.
3. **Include subfolders** — the new checkbox field (see field-kind extension below). `key: 'recursive'`, `required: false`, default unchecked (`false`).
4. `SYNC_INTERVAL_FIELD` (existing, unchanged, `advanced: true`).

Extras (`include_glob`/`exclude_glob`, D-03) need **no row here at all** — they render automatically through Phase 11's already-shipped E6 declared-fields editor in `ConnectionForm.svelte`, driven by whatever the filesystem plugin's own `Describe` response declares (see "Explicit Reuse" below).

**Field-kind extension (net-new, reusable by any future plugin, not filesystem-specific):**
- `ConnectionField` (interface in `plugin-fields.ts`) gains an optional `kind?: 'text' | 'checkbox'` property, **defaulting to `'text'`** — every existing field row in the table omits it and renders byte-identically to today (zero regression to any of the five existing plugin rows).
- `ConnectionField.defaultValue` stays **string-typed and text-field-only**, per its existing doc comment — a checkbox field's initial state is **not** sourced from `defaultValue`. `ConnectionForm.svelte`'s render logic coerces an unset/non-boolean value to `false` (unchecked) directly, matching the "zero value is the safe default" discipline the field itself is named for (`recursive: false` = "don't recurse", the conservative choice for a possibly-huge unfamiliar tree).
- `SourceConfig` (the TS type in `web/src/lib/api.ts`) gains a `recursive?: boolean` field alongside the existing string-typed connection keys — this is the frontend half of the typed-boolean-field decision RESEARCH.md's Open Question 2 recommends (a kernel-side `config.Source.Recursive bool` counterpart is the planner's/backend's task, not this document's).

**Markup (new checkbox row, inserted into `ConnectionForm.svelte`'s existing `{#each primaryFields as field}` loop as a third branch alongside the existing `field.secret` / plain-text branches):**
```svelte
{:else if field.kind === 'checkbox'}
	<label
		for={`conn-${field.key}`}
		class="flex min-h-11 items-center gap-2 text-[14px] leading-[1.4] text-foreground"
	>
		<Checkbox id={`conn-${field.key}`} checked={boolFieldValue(field)} onCheckedChange={(v) => setField(field.key, v)} />
		{field.label}
	</label>
	{#if field.helperText}
		<p class="text-[14px] leading-[1.4] text-muted-foreground">{field.helperText}</p>
	{/if}
```
- `min-h-11` on the wrapping `<label>` keeps the combined checkbox+label row at the existing 44px touch-target floor, even though the checkbox glyph itself is a stock `size-4` (16px) box — clicking anywhere in the label (native `<label for>` behavior) toggles the control, so the tappable area is the full row, not just the 16px box.
- `ConnectionField` gains one more optional string field, `helperText?: string`, used only by the "Include subfolders" row this phase (`'Also scans nested folders. Off scans only this folder's own top level.'`) — every existing field omits it and renders with no helper paragraph, matching today's behavior exactly.

**Reuses:** the new `Checkbox` primitive (shadcn-svelte official registry — see Registry Safety) is the **only** new component import; `label`/`Input` styling conventions are copied verbatim from every existing text-field branch in this same component.

### F2 — Kernel-Mediated "Open in Source" Local-Exec Variant (`OpenInSource.svelte`)

**Why this is new, not reuse:** Every existing source's deep link is a real URL a browser tab can navigate to (a paperless document URL, a SilverBullet page, a Proton webmail search, a WhatsApp/Signal conversation raise). `OpenInSource.svelte` today is unconditionally `<a href={link.url} target="_blank" rel="noopener noreferrer">` — clicking opens a new tab pointed at that URL. D-06's kernel-mediated open endpoint is different in kind: the kernel's `/api/items/{id}/open` route execs `xdg-open` server-side and returns a small JSON acknowledgement (`{"opened": true}` on success, an error body on failure) — it is **not** a page. Using the existing plain-`<a>` behavior against this route would flash open a new, confusing browser tab showing raw JSON text for a fraction of a second before the user's attention returns to the real desktop app window `xdg-open` just launched — a visibly broken-looking interaction for what D-06 calls "the full criterion-3 experience."

**Trigger condition (no wire/contract change):** `OpenInSource.svelte` distinguishes the two behaviors by inspecting `link.url` itself — a **same-origin, relative path beginning with `/api/`** (the shape the kernel's rewrite of a `file://`-scheme deep link produces, per RESEARCH.md's Architecture Pattern 3) triggers the new fetch-based interaction below; every other URL shape (the `http(s)://` and `mailto:`-style absolute URLs every existing source already emits) keeps today's plain `<a href target="_blank">` behavior completely unchanged. This mirrors the kernel-side rewrite's own discipline (keyed off URL shape, never off `source_type`) so a future third-party local-path plugin gets the identical treatment for free, with zero additional frontend branching per plugin type.

**Interaction (local-exec branch only):**
1. Renders as a `<button type="button">` (not an `<a>`) styled identically to the existing non-`iconOnly` `Button` markup (`variant`/size/icon unchanged — visually indistinguishable from today's link button at rest).
2. On click: `fetch(link.url, { method: 'POST' })` (verb per RESEARCH.md's worked kernel-route example — if the kernel implementation lands on a different verb, only this one string changes; the interaction contract below is verb-agnostic). No page navigation occurs; the button's own label never changes on a **successful** open (the desktop's own file handler window appearing is the confirmation — echoing a redundant in-app success state would be noise, same reasoning Phase 11's E5 gives for its own silent-except-icon-swap copy confirmation).
3. **Failure only:** the button's visible label swaps to `Couldn't open` (`text-destructive`, same swap-then-revert mechanic as Phase 11 E5's `Copy`→`Check` icon swap) for **2.5 seconds**, then reverts to the normal `Open in {displayName}` label; the button's `title` attribute updates for that same window to carry the kernel's specific error detail (e.g. `Couldn't open — file may have moved or been removed.`), giving a hovering/screen-reader user the concrete reason without a persistent alert or a new dialog. The button is **not** disabled during the brief in-flight window — the exec call is fire-and-forget and typically resolves near-instantly (no loading spinner state needed; if the fetch is still pending past a frame or two, no additional treatment is specified — this is a sub-second local operation, not a network-bound one).
4. `windowOnly`/`AppWindow`-vs-`ArrowUpRight` icon selection (existing `fidelityAffordance` logic) is **unchanged** — D-06 declares this deep link at navigating fidelity (`fidelity: 'exact'`, matching every other file-precision deep link in the app), so the existing `ArrowUpRight` icon and `Open in {displayName}` label/title copy apply verbatim; F2 changes only the click mechanism (fetch vs. navigate) and the failure-state label swap, never the icon or the at-rest copy.
5. The `iconOnly` (mobile takeover) variant of this component gets the identical fetch-vs-navigate branch — same trigger condition, same failure swap (icon-only context: the button's `title`/`aria-label` carries the failure detail since there is no visible label to swap).

**Discretion resolved — "open containing folder" secondary affordance (CONTEXT.md's Claude's Discretion list):** **Deferred, not built this phase.** Recommendation: keep `OpenInSource.svelte` to the single primary action specified above. Introducing a second local-exec affordance (e.g. `xdg-open`-ing the parent directory) in the same phase that introduces the *first* local-exec interaction pattern doubles the new interaction surface for zero success-criterion benefit — none of Phase 12's five success criteria name it. Revisit once the single-action pattern above has shipped and proven itself; the fetch-based trigger condition above is written generically enough (keyed on URL shape) that a second `/api/items/{id}/open-parent`-style route could reuse the identical interaction mechanics later without revisiting this component's core branch.
