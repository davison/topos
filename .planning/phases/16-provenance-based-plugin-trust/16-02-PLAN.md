<objective>
Make tier a pure function of provenance. `Dirs.Trusted` and `Dirs.External`
become search paths only: the kernel finds a binary by name in either
directory, then asks `EvaluateTrust` what tier it holds. A first-party binary
earns trust wherever it lives; a dropped file earns nothing wherever it lives.

Purpose: this is D-11 and ROADMAP success criterion 1 verbatim — the
structural change that closes the "trust tier is directory-location" attack
surface, and the change every TRUST-04 escalation test in plan 16-03 asserts
against.

Output: provenance-driven `DiscoverAllTiered` and `resolveBinaryDetailed`,
`launch` reading tier from the same authority, the rewritten `PluginsConfig`
doc contract, and every existing Go suite in `kernel/pluginhost`,
`kernel/httpapi`, and `kernel/supervisor` green against the new model.
</objective>

Rewrite tier derivation so it is computed per binary from provenance, never from
which `Dirs` field yielded the hit (D-11).

**`resolveBinaryDetailed`.** Keep `validatePluginBinaryName` as the unchanged
FIRST statement (the CR-01 confinement contract). Keep the search order
`Trusted` then `External` — that order now decides only WHICH FILE wins a name
collision, never what tier it holds. Change the return signature to
`(path string, trust Trust, shadowed bool, err error)`: after a regular file is
found, call `EvaluateTrust(dirs, name, path)` and return its result. Keep
`ResolveBinary`'s existing `(path, tier, err)` signature as the thin wrapper it
already is, sourcing `tier` from `trust.Tier`, so the many existing call sites
compile unchanged.

Rewrite the collision handling. The D-14 rule "trusted copy wins, external copy
ignored" is obsolete because neither copy is trusted by virtue of its directory.
The replacement: when `name` resolves to a regular file in `Dirs.Trusted` AND a
regular file of the same name exists in `Dirs.External`, evaluate the trust of
BOTH paths and prefer the one that evaluates to `TierTrusted`; if both evaluate
the same way, keep the current first-match-wins ordering. Either way emit an
`hclog.Warn` naming the colliding binary, both paths, and which one won and why
(its evidence, or the absence of evidence) — a shadow must never be silent, and
the operator must be able to see which bytes are actually about to run. Set
`shadowed = true` whenever the collision existed at all, so the existing
`LaunchAdvisoryShadowed` surface keeps working. Also emit each
`trust.Diagnostics` entry via `logger.Warn` naming the binary, so a malformed or
wrongly-keyed manifest file is visible to the operator rather than swallowed.

**`DiscoverAllTiered`.** Replace both `tierOf[name] = Tier...` assignments with a
per-binary evaluation. Build the candidate set by listing both directories
(`DiscoverAllBinaries` per directory, unchanged), then for each distinct name
call `EvaluateTrust` against the path that `resolveBinaryDetailed`'s ordering
would pick, and tag the result. A tamper-refusal error from `EvaluateTrust` must
NOT abort the whole listing — the binary is still discoverable (the picker and
`DescribePluginHandler` must keep seeing it) but is tagged `TierExternal` so no
listing consumer can ever infer trust from a refusal; the refusal itself is
re-asserted at launch, which is the only place that runs code. Keep the function
signature, its sorted+de-duplicated output, its empty-and-missing-directory
legitimacy, and its side-effect-free (no logger) contract exactly as they are.
Document in the doc comment that this call now hashes every discovered binary
and caches nothing: a replaced binary is never served from a stale trust
decision, and the added per-call cost on the picker and describe endpoints is
the accepted price of that guarantee.

**`Tier` doc comments.** Rewrite `Tier`, `TierTrusted`, `TierExternal`, and
`Dirs` so they state the new contract: `Tier` is derived exclusively from
verifiable provenance — a link-time build-manifest entry or a validly-signed
release manifest (D-10) — and never from a directory, a filename, a config key,
or anything a plugin declares about itself. `Dirs.Trusted` and `Dirs.External`
are pure search paths; their names are retained only for config compatibility.
Cite D-11 and note that the link-time arm is the transitional half Phase 17
retires.

**`launch` (host.go).** `launch` currently calls `resolveBinaryDetailed` and
then re-evaluates trust in its own gate. Collapse that: take the `Trust` value
the resolver already produced, and gate on it directly — a non-nil error or a
`Tier` other than `TierTrusted` where trust was expected produces the existing
`manifestUnverifiedError` (reason `manifest_unverified`, unchanged wire
vocabulary) populated with `cause` from the evaluation. `Tier == TierExternal`
falls through to the EXISTING pin block completely untouched — do not alter the
pin logic, the `describeOnly` skip, `hashAndLookupPin`, or any pin error shape
(TRUST-03). Assign `manifestHash` from `trust.Hash` for a trusted launch. Ensure
trust is evaluated exactly once per launch, and still before `exec.Command` is
constructed.

**`kernel/config/types.go`.** Rewrite `PluginsConfig`'s `ExternalDir` doc comment
so the sentence asserting trust is derived purely from which directory a binary
resolved from is gone, replaced with the provenance framing: both `Dir` and
`ExternalDir` are search paths the kernel looks in; tier is decided per binary by
`pluginhost.EvaluateTrust` from a link-time build-manifest entry or a
validly-signed release manifest; placing a binary in either directory grants
nothing on its own. Keep the terse, decision-ID-citing style the rest of the
struct uses and keep every existing resolution/default/omitted-value sentence
intact. Leave `Pins`' doc comment's substance alone — external-tier pinning is
unchanged (TRUST-03) — but correct the one clause that explains pins apply to
"a trusted-dir binary" in directory terms so it reads in provenance terms.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| config.toml → kernel | Operator- or attacker-editable `[plugins] dir` / `external_dir` values selecting where the kernel searches |
| plugins directories → kernel | Files dropped into either configured directory |
| kernel → HTTP clients | `tier`, `launch_failure`, `launch_advisory` fields the web UI branches on |
