**On-disk format (D-05/D-06/D-07/D-08).** Two sibling files live in a plugin
directory beside the binaries. `ProvenanceManifestSuffix` is `.provenance.json`
and `ProvenanceSignatureSuffix` is `.provenance.sig`; a manifest at
`<base>.provenance.json` is signed by `<base>.provenance.sig`. Versioned
basenames (e.g. `topos-plugins-v0.1.0.provenance.json`) let multiple manifests
coexist per D-08.

The manifest is UTF-8 JSON with `ProvenanceSchema` = `topos.provenance.v1` in a
top-level `schema` field, a `release` object carrying `repo`, `tag`, `os` and
`arch`, and a `plugins` array whose entries carry `name`, `sha256`, `version`
and `contract`. `contract` names the gRPC contract generation the binary was
built against — use `topos.v1`, matching the `proto/topos/v1` package this repo
already generates from; this is the field Phase 17's DIST-03 mismatch check
consumes. `sha256` is lowercase hex validated with the existing `isHexDigest`.

The signature file is UTF-8 JSON with `ProvenanceSignatureSchema` =
`topos.provenance.sig.v1` in `schema`, plus `key_id`, `algorithm` (only
`ed25519` is accepted) and `signature` (standard base64 of the 64-byte
ed25519 signature). **The signature covers the manifest file's raw bytes
verbatim** — never a re-serialized or canonicalized form — so verification
never depends on JSON field ordering or whitespace.

**Producers (the ONE producer discipline, mirroring `FormatManifest`).**
`BuildProvenanceManifest` takes a release descriptor plus entries and returns
deterministic manifest bytes: entries sorted by `name`, two-space indented,
trailing newline. `SignProvenanceManifest` takes those exact bytes, a key id
and an `ed25519.PrivateKey`, and returns the signature-file bytes. Both are
exported so `cmd/topos-provenance` and this package's tests share one producer
and never hand-format either file.

**Accepted key set (D-03).** `ProvenanceKey` pairs an `ID` string with an
`ed25519.PublicKey`. Keys reach the kernel through exactly two link-time paths
and no runtime path: `embeddedProvenanceKeys`, a compiled-in slice literal in
this file (declare it EMPTY in this task — plan 16-04 adds the real
topos-plugins key), and `provenanceKeysExtra`, an unexported string var
populated only via `go build -ldflags "-X github.com/davison/topos/kernel/pluginhost.provenanceKeysExtra=<spec>"`.
Give `provenanceKeysExtra` the same doc discipline `buildManifest` carries:
link-time data only, never read from a file, env var, or config at run time,
and state that this is the D-12 seam a dev/e2e build uses to trust its own
locally signed fixtures. `ParseProvenanceKeys` and `FormatProvenanceKeys` are
the round-trip pair over the spec shape `keyid=<base64 pubkey>` joined by
commas, sorted by key id; reject any segment with no `=`, an empty id, or a
base64 value whose decoded length is not `ed25519.PublicKeySize`, naming the
offending segment — never silently drop an entry. `AcceptedProvenanceKeys`
returns a defensive copy of the effective set (override when installed,
otherwise embedded plus parsed extras).

**Test seam (D-12).** `OverrideProvenanceKeys(keys []ProvenanceKey) (restore func())`
mirrors `OverrideBuildManifest` exactly: package-level guarded state, a
`sync.RWMutex`, defensive copies, a returned restore func that puts the previous
state back, and a doc comment stating it MUST NEVER be called from production
code. Keep this seam cleanly factored — D-12 requires it stay the injection
point Phase 17's dev-loop work can reuse.

**Sentinel and verifier.** `ErrProvenanceUnverified` follows
`ErrManifestUnverified`'s doc discipline: name every collapsed cause (no
manifest file present, missing or malformed signature file, unknown key id,
signature does not verify, platform mismatch, no entry for this binary, digest
mismatch) and state explicitly that verification never demotes-and-runs (D-13).

`VerifySignedProvenance(dirs Dirs, name, path string) (hash string, evidence string, err error)`
computes `HashBinary(path)` FIRST (reuse only — never a second hashing
implementation), then scans each non-empty directory in `dirs` for entries whose
name ends in `ProvenanceManifestSuffix`. For each candidate, in order: refuse to
read more than `MaxProvenanceManifestBytes` (set it to 1 MiB) so a hostile file
cannot exhaust memory; read the sibling signature file; require `algorithm` is
`ed25519`; resolve `key_id` against `AcceptedProvenanceKeys`; run
`ed25519.Verify` over the manifest's raw bytes; then parse the JSON and require
`schema` equals `ProvenanceSchema` and that `release.os`/`release.arch` equal
`runtime.GOOS`/`runtime.GOARCH`. A candidate failing any of those steps
contributes NO evidence — it is recorded as a named diagnostic string (naming
the file and the specific cause), never an error that aborts the scan, because
one junk file in a directory must not veto a valid manifest beside it. From a
candidate that passes all steps, look up the entry whose `name` equals `name`:
absent means this manifest simply does not cover this binary (no evidence);
present with a digest equal to the computed hash returns success with `evidence`
naming the manifest file; present with a digest that differs is a TAMPER
REFUSAL — return a wrapped `ErrProvenanceUnverified` naming the binary, the
manifest file, and the on-disk digest, and stop the scan. Per D-08, any single
passing candidate grants trust; the scan continues past non-covering candidates.

**The authority (D-10 coexistence, one verifier with two evidence sources).**
`Trust` is a struct carrying `Tier Tier`, `Hash string`, `Evidence string` and
`Diagnostics []string`. `EvaluateTrust(dirs Dirs, name, path string) (Trust, error)`
is the single place trust is decided:
  - Ask the link-time arm (`VerifyTrustedBinary`). Success sets
    `Tier = TierTrusted` and `Evidence = "build-manifest"`.
  - Otherwise ask the signed arm (`VerifySignedProvenance`). A tamper refusal
    from that arm returns immediately with the wrapped error. Success sets
    `Tier = TierTrusted` and `Evidence` to the manifest filename.
  - Both arms declining because the binary is simply not named anywhere is NOT
    an error: return `Tier = TierExternal`, empty `Evidence`, nil error. This is
    the "no evidence, therefore no trust" state — external-tier semantics, not a
    trusted-tier refusal.
  - A link-time arm digest MISMATCH (name present, bytes differ) is a tamper
    refusal exactly as today: return the wrapped error, never a silent demotion.
  - Carry every diagnostic string out through `Trust.Diagnostics` so a caller
    holding a logger can emit them; `EvaluateTrust` itself stays side-effect free
    (no logging, no caching, no package-level mutable state beyond the guarded
    test seam) so concurrent and interrupted evaluations always re-read the same
    on-disk facts.

Create `cmd/topos-provenance`, the release-side and operator-side CLI over the
same code path the kernel launch gate uses. It takes a subcommand as its first
argument and refuses loudly, non-zero, with a usage line on stderr when the
subcommand is absent or unknown — mirroring `cmd/topos-manifest`'s
zero-argument refusal exactly.

`keygen` takes `--key-id` and `--out-dir`. It generates an ed25519 keypair with
`ed25519.GenerateKey`, writes the private key to `<out-dir>/<key-id>.key` with
mode 0600 (standard base64 of the seed, single line, trailing newline) and the
public key to `<out-dir>/<key-id>.pub` (standard base64, single line). It prints
ONLY the `FormatProvenanceKeys` spec for the new public key to stdout — the
string a build recipe passes to `-ldflags -X ...provenanceKeysExtra=` and the
value plan 16-04 embeds. The private key is never printed to stdout or stderr
and never logged.

`sign` takes `--key-id`, `--repo`, `--tag`, `--version`, `--contract` (default
`topos.v1`), `--os` (default `runtime.GOOS`), `--arch` (default `runtime.GOARCH`),
`--out-dir`, and either `--key-file` or `--key-env` (default env var name
`TOPOS_PROVENANCE_SIGNING_KEY`, so CI passes the secret through the environment
and never through argv where it would appear in a process listing). Remaining
positional arguments are plugin binary paths; zero binary paths is a loud
non-zero refusal, exactly like `topos-manifest`. It hashes each binary through
`pluginhost.ManifestEntriesForBinaries` (reusing the existing one-hashing path),
builds the manifest via `BuildProvenanceManifest`, signs those exact bytes via
`SignProvenanceManifest`, and writes `<out-dir>/<repo-basename>-<tag>.provenance.json`
and its `.provenance.sig` sibling. It prints the two written paths to stdout, one
per line, and nothing else.

`verify` takes `--dir` (required) and optional repeatable `--name` arguments. With
no `--name`, it verifies every plugin binary present in `--dir` whose filename
carries `pluginhost.PluginBinaryPrefix`; with `--name`, only those binaries. For
each, it calls `pluginhost.VerifySignedProvenance` against a `Dirs` whose
`Trusted` field is `--dir`. It prints one line per binary naming the binary and
either the manifest file that vouched for it or the specific failure cause, and

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugins directory → kernel | Operator- or attacker-writable files (`*.provenance.json`, `*.provenance.sig`, plugin binaries) crossing into the kernel's trust decision |
| release signing key → published artifact | The ed25519 private key held outside this repo; only its public half crosses into the kernel |
| kernel process → plugin subprocess | `exec.Command` on a binary the trust decision just approved |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-01 | Spoofing | `VerifySignedProvenance` manifest scan | high | mitigate | ed25519 signature verified over the manifest file's raw bytes against a link-time-only accepted key set; unknown key id, bad signature, or a signature over different bytes each yield no evidence and a named diagnostic |
| T-16-02 | Elevation of Privilege | Renamed signed binary shadowing another plugin name | high | mitigate | The manifest binds `name` → `sha256` (D-05); a lookup by the resolved binary name fails for a renamed artifact, so the signature proves origin AND identity |
| T-16-03 | Tampering | Accepted key set injected at run time | high | mitigate | Keys come only from `embeddedProvenanceKeys` (compiled-in) or `provenanceKeysExtra` (`-ldflags -X`); no file, env var, or config path exists, and `OverrideProvenanceKeys` carries an explicit never-in-production doc prohibition |
| T-16-04 | Tampering | Binary swapped between hashing and `exec.Command` (TOCTOU) | medium | accept | Evaluation completes before `exec.Command` is constructed; the residual final-component window is documented as narrowed, not eliminated, matching the Phase 12 `EvalSymlinks` precedent |
| T-16-05 | Information Disclosure | Private signing key handled by `topos-provenance` | high | mitigate | `keygen` writes the private key at mode 0600 and never prints it; `sign` reads it from a file or a named env var, never argv (where it would appear in a process listing) |
| T-16-06 | Denial of Service | Hostile oversized or deeply nested manifest JSON | low | mitigate | `MaxProvenanceManifestBytes` (1 MiB) caps the read before parsing; a malformed candidate is a named diagnostic, never a scan-aborting error |
| T-16-07 | Repudiation | A junk manifest file silently vetoing a valid one beside it | medium | mitigate | Per-candidate failures are recorded as named diagnostics carried out via `Trust.Diagnostics` and logged by the caller; the scan continues (D-08) |
| T-16-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install tasks in this plan — the verifier uses standard-library `crypto/ed25519` only and adds no module dependency (asserted by the `golang.org/x/crypto` acceptance criterion) |
