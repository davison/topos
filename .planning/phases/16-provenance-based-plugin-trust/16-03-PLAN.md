Create `kernel/pluginhost/escalation_test.go`, a suite whose single job is to
prove each escalation path named in the standing security todo is closed. Open

each test drives the REAL resolver and launch gate, and each is accompanied by a
proof that it goes red when its gate is removed.

**Case 1 — config edit.** An operator (or an attacker with config write access)
points `[plugins] dir` at a directory of their choosing containing an unsigned
binary. Model this by constructing `Dirs{Trusted: attackerDir}` where
`attackerDir` holds a real built plugin binary with no link-time manifest entry
and no signed manifest beside it, then resolving it. Assert the tier is
`TierExternal`, and additionally assert through `launch` that a real (non-trial)
launch of it with no pin recorded returns an error satisfying
`errors.Is(err, ErrPinMismatch)` and creates no subprocess. The point the
assertion must capture: changing the search path changed nothing about trust.
Run the same assertion a second time with the SAME binary reached through
`Dirs{External: attackerDir}` so the case proves path-independence rather than
one lucky placement.

**Case 2 — file drop.** A binary is dropped straight into the directory the
running kernel already treats as its trusted plugins directory, alongside
binaries that DO carry evidence. Build a directory holding two binaries: one
covered by an installed link-time manifest, one not. Assert the covered binary
resolves `TierTrusted` and the dropped one resolves `TierExternal` from the same
`Dirs` value in the same call — the discriminator is evidence, not the
directory they share. Assert `DiscoverAllTiered` over that directory returns
both names with those two tiers. Assert the dropped binary's `launch` refuses
with no subprocess created.

**Case 3 — shadowing.** An attacker places an unsigned binary under the NAME of
a plugin that legitimately carries provenance, aiming to inherit its trust. Sign
a manifest naming `topos-plugin-mock` with the digest of the REAL mock binary,
place that manifest in the directory, then place DIFFERENT bytes at the path
`topos-plugin-mock`. Assert the resolution is a refusal — `errors.Is(err,
ErrProvenanceUnverified)` — not a demotion to `TierExternal`, because the
manifest positively vouches for a different digest under that name (D-05: names
are bound to hashes, so the signature proves origin AND identity). Add the
sibling case where the manifest does not name the shadowing binary at all: that
one is `TierExternal`, not a refusal, and both outcomes must be asserted
distinctly so a future change that collapses them is caught. Also cover the
cross-directory shadow: the same name present in both configured directories,
one copy with evidence and one without, resolves to the copy with evidence and
logs the collision by name.

**The fail-first proof.** TRUST-04's wording is "a committed test that fails if
its gate is removed", so the suite must demonstrate that property rather than
assert it in prose. Add a test that exercises each of the three cases against a
deliberately weakened trust decision installed for the duration of that test
only — the simplest honest mechanism is a package-level test-only hook in the
suite that substitutes a "grant `TierTrusted` to anything found in
`Dirs.Trusted`" evaluation, restored via `t.Cleanup`, and asserts that under
that substitution each of the three cases' core assertions would NOT hold. If
introducing such a hook requires a production-code seam, do NOT add one: instead
implement the proof as a documented, skipped-by-default test guarded by an
environment variable that the acceptance criterion below drives explicitly, and
state in the file header exactly which line of `discover_binaries.go` a
maintainer deletes to see the suite go red. The gate this file guards must be
demonstrably falsifiable one way or the other.

Every test name reads as the escalation path it closes (for example
`TestEscalation_ConfigEditCannotGrantTrust`). No case in this file may pass
without exercising the real `EvaluateTrust` path.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| config.toml → kernel | Attacker-controlled `[plugins] dir` value (escalation path 1) |
| filesystem → kernel | Attacker-dropped file in a configured plugin directory (escalation paths 2 and 3) |
| test suite → maintainer confidence | A green suite asserting a security property holds |
