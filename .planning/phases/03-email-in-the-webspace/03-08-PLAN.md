<objective>
Close the two code-side items of gap **G-03-1** in `03-UAT.md`, whose root cause the debug session at `.planning/debug/proton-bridge-no-such-user.md` established as ENVIRONMENTAL: `PROTON_BRIDGE_PASS` holds a 37-character symbol-heavy string that cannot be a Bridge-generated app password. Upstream `proton-bridge`'s `CheckAuth` base64url-decodes the presented password as step 1, compares the vault password as step 2, and matches the email address only as step 3; upstream `gluon`'s `getUserID` then returns one single error for every rejected `(username, password)` pair. So a wrong password makes the correct address and every alias fail identically — and this plugin passes credentials through verbatim, with the code path audited clean.

**The credential correction itself is a user action and is deliberately NOT planned here.** No task in this plan edits `.env`, reads a secret, or attempts a login against the real Bridge. What is plannable is the reason this took four verification rounds to diagnose: the diagnostic surfaces pointed at the wrong knob.

Two items, in one vertical slice:

1. **The runtime diagnostic is silent on a misconfiguration it can detect for free.** Bridge renders its app password with `base64.RawURLEncoding` (`proton-bridge` `pkg/algo/encode.go`), so the alphabet is exactly `A-Za-z0-9-_`. A configured token holding anything else is provably not a Bridge app password — a fact available at the moment LOGIN is rejected, at zero cost, without touching the network and without inspecting anything but the token's character set. Today the operator gets the server's bare rejection string and nothing else.

2. **The live-Bridge test's own hint actively misdirects.** The trailing parenthetical in the `t.Fatalf` on `conn.Login`'s failure branch (`live_bridge_test.go` ~line 160) cites a prior phase summary and tells the reader the problem is settled and environmental in a way that points at the account name. The debug session records this as a *contributing cause of the four-round persistence*: it steered every subsequent round at the username, which Bridge never even examines when the password fails to decode.

**Where the fix is wired, and why it is not inside `Health`.** The gap's third `missing` item names the Health path. Wiring the check into `client.connect`'s LOGIN-failure branch satisfies that literally — `Health` returns that error verbatim as `LastError` — and, from the same one call site, also reaches the surface the gap was actually *reported* from. Measured, not assumed: `kernel/httpapi/sources.go`'s `sourceStatusesFrom` sets `LastError: run.Error`, taken exclusively from the kernel's own `sync_runs` history and never from a plugin's `HealthResponse` (the A-PLUG-04 rule established in 02-02). The red-dot detail the user reads is therefore built from `Match`'s error — which is `client.connect`'s error. A hint installed inside `Health` alone would have been correct, tested, and invisible exactly where it was needed.

**Warning-grade, never a gate.** The predicate runs only *after* a LOGIN has already been rejected, and only appends text. There is no branch anywhere in this plan in which a token's shape prevents a dial, a LOGIN, or a plugin from constructing. This is a deliberate hedge against the one thing this repository cannot verify: that Bridge's password alphabet will never widen.

Purpose: this gap cost four verification rounds not because the defect was subtle but because two diagnostic surfaces asserted the wrong cause with confidence. Fixing the credential without fixing the surfaces leaves the next occurrence to cost the same again.

Output: one new dependency-free Go file, a small change to one function in `client.go`, one new test file, and one corrected string in an existing test — with the test hint and the runtime advice reduced to a single shared constant so they cannot diverge again.
</objective>
