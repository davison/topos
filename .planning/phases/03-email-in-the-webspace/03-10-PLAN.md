<objective>
Close gap **G-03-3** in `03-UAT.md` (severity minor, status failed): clicking "Open in Proton Mail" in the detail pane opens `https://mail.proton.me/u/1/inbox` — the inbox view, with no message selected and no label filter.

`toItem` builds `{webmail_base}/{label-leaf}` (for the user's real data, `/u/1/house%2Bhome`). Proton webmail addresses custom labels and folders by an internal id; only system views have name-addressable paths. The constructed path resolves to nothing, and Proton redirects to the inbox. `03-RESEARCH.md` Pitfall 5 had already ruled out a per-message URL (no confirmed mapping from an IMAP `Message-Id`/UID to Proton's internal webmail message id), and its Open Question 2 explicitly recorded the label slug format as *unconfirmed, to be verified live* — the ANCHORED fallback chosen at planning time was never actually addressable.

The fix is the candidate `03-UAT.md`'s own gap entry proposes: a hash-based search link into the account's All Mail view, pre-filled with the message's subject — a form Proton webmail does honour, still honestly declared ANCHORED. It puts the user in front of a short, filtered list containing the message instead of the top of an unfiltered inbox.

**User-visible outcome** (ROADMAP Phase 1 Success Criterion 4, the contract this phase inherits — the ROADMAP `**Goal:**` line for Phase 3 is not in `As a / I want to / so that` form, so no user story is invented here, following 03-05/03-06/03-09's precedent; run `/gsd-mvp-phase 3` if one is wanted): *"Every item carries an 'open in source' affordance that lands on the exact document, and declares its link fidelity."* For email, "exact" is unavailable and honestly declared as anchored — but anchored must still mean *adjacent to the message*, which is precisely what failed.

Task 2 corrects the two operator-facing definitions of `webmail_base_url` that this change makes false — the same class of stale, confidently-wrong documentation that cost this phase four diagnosis rounds in G-03-1.
