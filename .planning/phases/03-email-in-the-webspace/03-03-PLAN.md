<objective>
Full-text search within a webspace (KERN-05), landing end to end from the SQLite
index through a new kernel HTTP route. After this plan a caller — curl, the SPA
built in plan 03-04, or a future agent — can ask a webspace for the items
matching a query and get them back ranked, with highlighted snippets, across
every source configured in that webspace.

The index schema was deliberately shaped for this in Phase 1: `items` is a normal
rowid table specifically so an external-content FTS5 table can be added over
`items(title, preview)` with no migration, and `kernel/index/schema.go`'s own
comment says so. 03-RESEARCH.md ran that exact design against this repository's
pinned `modernc.org/sqlite` dependency and confirmed the table, the triggers,
`bm25()` and `snippet()` all work, including the interaction between the table's
`TEXT PRIMARY KEY` and `content_rowid='rowid'`.

This plan is independent of the email plugin — it searches whatever is already
indexed — so it runs in wave 1 in parallel with the email tracer.

Purpose: email is the first source that brings enough volume to make scrolling
insufficient, which is why search is paired with it; but the search capability
itself stands on the index, not on any one source.

Output: the `items_fts` virtual table and triggers, `Store.Search`, and
`GET /api/webspaces/{webspace}/search?q=`.
</objective>

Add to `kernel/index/store.go`:

- Two package-level constants naming the snippet delimiters. Use the ASCII
  control characters STX (hex 02) as the opening delimiter and ETX (hex 03) as
  the closing delimiter, chosen because no real subject line or preview text can
  contain them, so a delimiter can never be mistaken for source content. Export
  them so the HTTP layer and the docs can name the same values.

- `ftsQuery(raw string) string`, the query sanitizer. Split the raw text on
  whitespace; for each field strip any double-quote characters; drop fields that
  become empty; wrap each surviving field in double quotes so FTS5 treats it as a
  literal phrase; join with spaces, which is FTS5's implicit AND; append an
  asterisk to the final term so an in-progress word prefix-matches. Return the
  empty string when no field survives. Handing the user's raw search-box text
  straight to MATCH is what turns a lone quote or a leading hyphen into a syntax
  error instead of a result set, so no caller may bypass this helper.
- `Search(ctx context.Context, webspaceName, rawQuery string) ([]SearchResult, error)`.
  Return an empty slice and a nil error immediately when `ftsQuery` yields an
  empty string. Otherwise run the query selecting the identical column list
  `StreamItems` selects, plus `snippet(items_fts, -1, <open>, <close>, '…', 12)`
  and `bm25(items_fts)`, `FROM items_fts JOIN items ON items.rowid =
  items_fts.rowid JOIN webspace_items ON webspace_items.item_id = items.id WHERE
  webspace_items.webspace_name = ? AND items_fts MATCH ? ORDER BY rank ASC LIMIT
  50`. Both parameters are bound, never concatenated. Order ascending because
  bm25 returns a more-negative score for a better match. Scan and unmarshal
  exactly as `StreamItems` does. If the query itself fails with an error whose
  text mentions fts5, return an empty slice and a nil error rather than
  propagating — the sanitizer makes that unreachable in principle, and a
  malformed query must degrade to "no results" rather than a 500; any other error
  propagates wrapped as usual.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser / any loopback caller -> kernel search route | The `q` query parameter and the `{webspace}` path segment are untrusted input reaching a SQL query |
| indexed item content -> search response | Item titles and previews originate in the user's own sources but are authored by third parties (email senders, document contents) and flow back out through `snippet()` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-15 | Information Disclosure | `Store.Search` webspace scoping | high | mitigate | The query joins `webspace_items` on a bound `webspace_name` parameter with no code path that omits the join; a store test asserts an item associated only with another webspace is never returned |
| T-03-16 | Tampering | SQL construction in `Store.Search` | high | mitigate | Both the webspace name and the sanitized FTS5 query are bound parameters; no string concatenation builds any part of the SQL, asserted by an acceptance grep |
| T-03-17 | Denial of Service | Raw user text reaching the FTS5 `MATCH` operator | medium | mitigate | `ftsQuery` quotes every term as a literal phrase, so no user input can be interpreted as query syntax; a residual fts5 error is caught and degraded to an empty result set instead of a 500; results are capped at 50 rows |
| T-03-18 | Elevation of Privilege | Search bypassing the `/agent/v1` per-source read grants | high | mitigate | No `/agent/v1` mirror of the search route is registered; the route exists only under `/api`, and the omission plus its reason are documented in `docs/api.md` |
| T-03-19 | Tampering | Search reaching a source plugin at request time | medium | mitigate | `SearchHandler` takes only `*index.Store`, the same structural isolation `StreamHandler` uses — `kernel/httpapi` cannot import `kernel/pluginhost`, so the handler is incapable of a plugin call rather than merely avoiding one |
| T-03-20 | Information Disclosure | Snippet content echoing untrusted item text back to a caller | low | accept | Snippets are plain text in a JSON string, escaped by `encoding/json`; the rendering side's obligation to treat them as text rather than markup is a separate control owned by plan 03-04, and the delimiters chosen are control characters that cannot occur in source content |
</threat_model>
