<planner_resolutions>
Three judgment calls this plan LOCKS. An executor must not re-litigate them.

**R1 — The stream pane uses `max-md:invisible`, not `max-md:hidden`.**
09.1-UI-SPEC.md's Scroll Preservation section proposes `max-md:hidden` and claims the DOM node
"and therefore its native scroll offset" stays alive. That claim is wrong: `display: none`
destroys the scrollable box, and browsers reset `scrollTop` to 0 when it returns. D-01's
"the stream's scroll position is preserved for the return trip" is a LOCKED decision, so the
mechanism must actually preserve it. `visibility: hidden` (Tailwind `invisible`) keeps the
layout box — so the scroll offset survives — while still removing the subtree from the tab
order and the accessibility tree, which is the other property the takeover needs. The stream
also keeps a full-width sizing utility at this band so its content does not reflow while
concealed. Task 3's e2e spec pins the preserved offset as a behaviour assertion, so this
resolution is gated, not asserted.

**R2 — Mobile e2e runs via a per-spec viewport override, not a new Playwright project.**
CONTEXT.md leaves the mobile e2e strategy to discretion. `make e2e` runs
`--project=$(E2E_PROJECT)`, defaulting to `chromium` — a new `mobile-*` project would NOT run
in the default gate, and a spec outside the gate is exactly the "manual check that has to be
remembered" the project convention forbids. `test.use({ viewport })` is test-scoped and
composes with the worker-scoped `configSpec`, so the mobile specs run inside the existing
chromium project with zero config change. `web/playwright.config.ts` is deliberately NOT in
this plan's `files_modified`.

**R3 — The back control routes through the route, not through raw history in the component.**
09.1-UI-SPEC.md's bar anatomy proposes `onclick={() => history.back()}` inside DetailPane.
A bare `history.back()` is correct only while a takeover history entry actually exists; in
every other state (a desktop-width resize with a stale selection, a defensive re-render) it
would navigate the user out of the app. The route owns `page.state`, so the route owns the
close decision and passes it down as `onback`. D-03's requirement — one popstate path shared by
the visible control and the phone's back button — is preserved exactly, because the route's
handler calls back into history whenever the takeover entry is live.
</planner_resolutions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| source data -> browser DOM | item titles and previews originate in external stores (email, chat, documents) and are rendered by the SPA; they are untrusted text |
| browser history -> app state | `page.state` is user/attacker-controllable through history manipulation and crosses into the app's rendering decisions |
| SPA -> external source app | the open-in-source control hands control to a source-authored URL in a new browsing context |
