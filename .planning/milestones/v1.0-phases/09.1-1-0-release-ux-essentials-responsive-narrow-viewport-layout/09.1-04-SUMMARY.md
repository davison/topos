# Phase 09.1 Plan 04: Header Touch Adaptation Summary

**Below 768px the chip actions trigger stops hiding behind a hover state a touchscreen can never produce (`max-md:opacity-100`), chip health detail becomes reachable via a native `title` bound from the existing tooltip string, and the decorative branding lockup drops out to give the webspace switcher room — a widened structural guard plus a 9-case tap-driven e2e spec pin all of it, composed cleanly with wave 1's auto-collapsing header and overflow-containment fix.**

## Performance

- **Duration:** ~1h
- **Tasks:** 2 of 2 completed
- **Files modified:** 3 modified, 1 created

## Accomplishments

- `SourceChip.svelte`'s `⋮` actions trigger now carries `max-md:opacity-100` alongside (never replacing) its existing `group-hover:opacity-100` and `group-has-[:focus-visible]:opacity-100` reveal clauses (planner_resolutions R1) — below 768px it needs nothing to reveal from because it is never hidden there; at 768px and above the pre-existing hover/keyboard-only reveal (Phase 6's G-06-3b fix) is untouched.
- The filter button now binds `title={tooltipText}` — the exact same derived string the desktop `Tooltip` renders — as a native, long-press-accessible touch degrade for chip health detail (planner_resolutions R2). The inner display-name `title` is left in place and documented as a deliberately separate, nested affordance.
- `WebspaceHeader.svelte`'s branding lockup (app icon + wordmark + tagline) gains `max-md:hidden`, the one element this phase drops outright below 768px since it carries no affordance; the chip overflow popover needed no narrow-width special case, since `visibleChipCount`'s `ResizeObserver`-driven measurement is already width-driven at every width.
- `source-chip-pill.test.ts` gained two new assertions (touch-reveal presence, native-`title` presence) inside/alongside the existing "reveal scoping" describe, per RESEARCH Pitfall 2's explicit call to widen the guard deliberately rather than let it coincidentally still pass.
- `web/e2e/specs/09-1-header-touch.spec.ts`: 9 cases, all tap-driven (a single `.hover()` call total, isolated to the one desktop-reveal case), proving every header affordance CONTEXT.md names is reachable at 390x844 and that desktop behaviour at 1280x900 is unchanged.
- Re-ran wave 1's full `09-1-mobile-takeover.spec.ts` (11 cases) as a regression check per the orchestrator's wave-1-outcomes brief — all still pass, confirming the chip-pill changes compose cleanly with the auto-collapsing header and the `measureEl` overflow-containment fix.

## Decisions Made

- Followed all three `planner_resolutions` exactly as locked (R1 additive `max-md:opacity-100`, R2 `title={tooltipText}` reusing the existing derived value, R3 `size-8` sub-floor unchanged, no `size-11`).
- **Live-verified geometry, not assumed:** at 390px, `WebspaceHeader`'s reserved trailing space (the `Refresh all` button plus the add-source trigger plus the overflow trigger's own reserved width) leaves room for exactly one participating chip inline. A second participating chip pushes the "all chips fit inline?" check into the overflow-mode budget calculation, whose further-reduced budget (minus the overflow trigger's own width and two more gaps) is smaller than even one chip's width — so 2+ participating chips means **zero** chips stay inline, all deferred to the popover. This is a real, pre-existing property of `visibleChipCount`'s algorithm, not something this plan changed.
- Because of that, the e2e fixture configures **two webspaces sharing one kernel** (`attachedWebspace` per webspace, same three mock instances): a single-chip webspace for the inline-trigger cases (1-5, 7-9) and a three-chip webspace, all deferred, for the overflow case (6) — still one kernel per spec file (D-02), just two `[webspaces.*]` blocks in one `config.toml`.
- Case 3 (filter toggle round trip) surfaced a genuine, correct interaction live: selecting the chip makes `Clear filters` appear in the trailing reserved group, which widens that reservation enough to push even the single-webspace's one chip into the overflow popover. The affordance did not silently disappear — it relocated to the same overflow popover case 6 already proves reachable — so the spec's second (deselecting) tap goes through the popover rather than re-querying the same inline element.
- `page.route`'s `route.fetch()` + `route.fulfill({ response })` pattern (borrowed from `09-chip-menu.spec.ts`) threw `Route is already handled!` under `hasTouch: true` in case 2; switched to `route.continue()`, which still observes the request without a second explicit fetch/fulfill pair.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - blocking issue] `route.fetch()`/`route.fulfill({ response })` double-handled the refresh request under `hasTouch: true`**
- **Found during:** Task 2, case 2 ("Refresh now is reachable and genuinely wired")
- **Issue:** The exact pattern `09-chip-menu.spec.ts` uses (`const response = await route.fetch(); await route.fulfill({ response });`) threw `Error: route.fulfill: Route is already handled!` — the request appears to be observed/handled twice under this test's touch-emulated interaction, unlike the hover-driven original.
- **Fix:** Switched to `await route.continue()`, which still flips `refreshRequestSeen = true` on interception and lets the real request through, without the fetch/fulfill pair that collided.
- **Files modified:** `web/e2e/specs/09-1-header-touch.spec.ts`
- **Verification:** Case 2 passes; the assertion still proves a real `POST /api/sources/mock-01/refresh` round trip via the polled `refreshRequestSeen` flag.
- **Committed in:** `3fd4911` (Task 2 commit; found before the first commit of this file, so no separate fix commit was needed)
