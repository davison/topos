## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `handleChipEdit`'s describePlugin race silently reverted a faster click's vocabulary**
- **Found during:** Task 3, writing uat-10-describe-race.spec.ts's own race scenario for the first time
- **Issue:** `web/src/routes/w/[webspace]/+page.svelte`'s `handleChipEdit` sets `editInstance`/`editMode`/`editVocabulary` synchronously, then `await`s `describePlugin` before writing the resolved vocabulary back into the same shared `editVocabulary` `$state` value, with no check that the invocation's own `(name, kind)` still matched the current edit session by the time the await resolved. Empirically confirmed via a route-interception probe: opening "Edit match settings…" on a mock-backed chip (its request delayed), then before it resolves opening the same on a mockstrict-backed chip, correctly showed the mockstrict chip's "Tags" field immediately — but once the delayed mock response landed, it silently overwrote `editVocabulary` back to mock's own "Labels" field, even though the modal was still showing the mockstrict instance. This is exactly 07-UAT.md item 10's "carried advisory" (07-UAT.md test 10: "User previously accepted as a non-blocking advisory; re-offer, may skip") — accepted through Phase 7, never actually fixed. The plan's own must_haves for this task require the ported spec to prove "the second click's state always wins" as a genuine regression gate, which the shipped code could not honestly satisfy.
- **Fix:** Added a staleness check (`if (editInstance !== name || editMode !== kind) return;`) immediately after the `describePlugin` await resolves (both the success and the catch-block failure paths), before either `editVocabulary` or the later unconditional `editOpen = true` can execute. A response whose own target no longer matches the current edit session is discarded rather than applied.
- **Files modified:** `web/src/routes/w/[webspace]/+page.svelte`
- **Verification:** Rebuilt the SPA and kernel binary; re-ran the same route-interception probe — the mockstrict chip's "Tags" field now stays visible both immediately and after the delayed mock response lands, and "Labels" never appears. Re-ran the FULL existing suite after the fix: `npx playwright test --project=chromium` (24/24 pre-existing + new specs green), `npm run test` (607/607 vitest), `npm run check` (0 errors, only pre-existing unrelated warnings). Final `make e2e` run: 26/26 green.
- **Committed in:** `945aed2` (Task 3 commit)

## Issues Encountered

- Confirmed via empirical probe (not assumed) that `ConnectionForm.svelte`'s native HTML `required` attribute intercepts a genuinely empty `fill('')` at the browser's own constraint-validation layer, before the app's `onsubmit`/`missingRequiredFields` JS guard ever runs — an empty value produces zero describe-plugin requests but no visible app-level message. Resolved by clearing the field with a single space, which satisfies native `required` (non-empty) while still failing the JS guard's own `trim() === ''` check — the exact case `ConnectionForm.svelte`'s own doc comment names as the JS guard's "load-bearing" scenario, distinct from the native attribute's "first line of defence" one.
- Discovered (also via empirical probe, before writing the final spec) that `resolveNewInstanceId` blocks advancing past the Connect step on a blank Display Name regardless of the required connection field's own state — not named explicitly in the plan's action text for uat-05/uat-06's two-step/one-step flows, but necessary for either flow to reach the step the plan describes. Added a Display Name fill to both specs ahead of the relevant "click Next"/submit step.
- uat-06's initial deep-equality baseline (captured before any save) failed once against the post-save `beta` snapshot, differing only by a newly-present `keywords: []` — root-caused to the kernel's canonical writer having no `omitempty` tag on `Webspace.Keywords` (matching 07.1-04-SUMMARY.md's own prior finding), so ANY save anywhere in the document normalizes every webspace's keywords field, not only the one edited. Fixed by seeding `keywords: []` explicitly in the fixture for both webspaces up front, so the baseline already matches the writer's steady state and the deep-equality assertion is isolated to genuine over-reach.
