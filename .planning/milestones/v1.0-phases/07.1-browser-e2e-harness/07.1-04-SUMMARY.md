## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `DescribePluginHandler` 404'd for an already-configured `topos-plugin-mock` instance**
- **Found during:** Task 2, writing clause 2's re-add flow (the "+" picker's one-step existing-instance add against `mock-02`)
- **Issue:** `kernel/pluginhost.DiscoverBinaries` conflates two different concerns behind one filtered result: (a) the UI-policy question "should this plugin type be OFFERED as a brand-new instance" (mock is deliberately excluded, `ExcludedPluginBinaries`) and (b) the security question `DescribePluginHandler` asks, "is this a real binary DiscoverBinaries would find" (T-07-09). Because both shared the SAME filtered list, describing an instance that was ALREADY legitimately configured — not being offered as new — also 404'd whenever its plugin type happened to be mock. This structurally broke the re-add flow for every mock-typed instance, which is the ENTIRE fixture surface this whole phase's D-07 decision mandates.
- **Fix:** Split `DiscoverAllBinaries` (raw listing, no exclusion) out of `DiscoverBinaries` (still filtered, unchanged behavior for its existing callers). `DescribePluginHandler` now calls `DiscoverAllBinaries`; `PluginTypesHandler` (the "+ New <type>…" picker list) is untouched and still excludes mock.
- **Files modified:** `kernel/pluginhost/discover_binaries.go`, `kernel/httpapi/config.go`
- **Verification:** `go test ./kernel/pluginhost/... ./kernel/httpapi/...` — all pass, including the new regression test proving mock is describable while staying excluded from `/api/config/plugin-types`; `uat-02`/`uat-03` specs pass end to end
- **Committed in:** `e5dd090` (Task 2 commit)

**2. [Rule 1 - Bug] Symlinked plugin binaries were invisible to plugin discovery entirely**
- **Found during:** Task 2, same investigation as deviation 1 above — after fixing the mock-exclusion bug, the SAME 404 persisted
- **Issue:** `os.ReadDir`'s `DirEntry.Type()` reports a symlink's own mode bits (`fs.ModeSymlink`), which `fs.FileMode.IsRegular()` unconditionally reports `false` for. `web/e2e/fixtures/plugin-binaries.ts`'s `linkPluginBinaries` deliberately SYMLINKS plugin binaries into each fixture's temp plugins directory (07.1-01's own documented decision, to avoid copying `bin/plugins/` wholesale) — so `DiscoverBinaries`/`DiscoverAllBinaries` found NOTHING in the hermetic e2e harness at all, for any plugin type, not only mock. Live production installs never hit this (the `plugins`/`e2e` Makefile targets `go build` real files), which is why it went unnoticed until this harness's own symlink-based fixture exercised it.
- **Fix:** `DiscoverAllBinaries` now follows one level of symlink via `os.Stat` (which resolves symlinks, unlike `os.ReadDir`'s own `DirEntry.Type()`) before judging regular-file-ness; a dangling symlink is skipped rather than erroring the whole listing.
- **Files modified:** `kernel/pluginhost/discover_binaries.go`
- **Verification:** `go test ./kernel/pluginhost/...` — new `TestDiscoverBinaries_FollowsSymlinkedBinaries` (including a dangling-symlink case) passes; confirmed live via the full `uat-02`/`uat-03` spec runs, which only pass with both fixes applied
- **Committed in:** `e5dd090` (Task 2 commit)

**3. [Rule 1 - Bug] `page.addInitScript`'s MutationObserver threw and silently aborted before assigning the arm/disarm bridge functions**
- **Found during:** Task 2, first full run of clause 3
- **Issue:** `observer.observe(document.documentElement, ...)` throws `TypeError: parameter 1 is not of type 'Node'` because `page.addInitScript` runs before the document has any content parsed — `document.documentElement` can still be `null` at that exact point. The thrown error aborted the whole init script before `window.__armSkeletonObserver` etc. were ever assigned, so every later `page.evaluate` call referencing them failed with "not a function".
- **Fix:** Observe `document` itself (always exists from the very start, unlike `documentElement`) with `subtree: true` — sees every insertion anywhere in the page identically.
- **Files modified:** `web/e2e/specs/uat-02-remove-source-items.spec.ts` (within Task 2's own scope, no separate commit)
- **Verification:** live debug run confirmed the arm/disarm functions are defined throughout; full spec passes
- **Committed in:** `e5dd090` (Task 2 commit)

**4. [Rule 1 - Bug in my own test design, self-corrected before commit] Clause 3/4's skeleton-flash guard was contaminated by the Refresh control's own permitted foreground load**
- **Found during:** Task 2, first full run of clause 3 after fix 3 above — the guard failed with 1 skeleton insertion where 0 was expected
- **Issue:** `handleRefreshSource` performs TWO things on every click: an immediate, non-quiet foreground `load()` in its own `finally` block (fetch #1 — legitimately allowed to flash the skeleton, same carve-out as every other user-initiated load) AND unconditionally arms `ensurePolling()`'s later background quiet refetch (fetch #2, ~2s later). Arming the observer immediately on click (my original design) caught fetch #1's own PERMITTED flash and wrongly attributed it to the background path.
- **Fix:** Track stream-endpoint fetch count; wait for fetch #1 (unarmed), THEN arm, THEN wait for fetch #2 — isolating exactly the window between the foreground load and the background poll's own quiet tick. Applied identically to clause 4's failed-background-refetch case (fetch #1 is left to succeed normally; only fetch #2 onward is made to fail), since a manual refresh's own foreground failure legitimately surfaces the outage state and is a different, already-covered code path.
- **Files modified:** `web/e2e/specs/uat-02-remove-source-items.spec.ts`
- **Verification:** live debug run confirmed 0 skeleton insertions in the correctly-isolated window (previously 1); full spec passes, including the failed-refetch case (row count unchanged, no outage copy, 0 skeleton insertions)
- **Committed in:** `e5dd090` (Task 2 commit)

**5. [Rule 1, documented departure from a must_haves clause that does not hold against the shipped writer] uat-03's D-20 shell assertion checks emptiness, not key absence**
- **Found during:** Task 3, before writing any assertion — verified directly against `kernel/config`'s canonical writer rather than assumed
- **Issue:** The plan's `must_haves` (and Task 3's action text) call for asserting the ABSENCE of the `keywords`/`sources`/`match` keys on a UI-created shell, distinguishing it from a webspace written with merely-empty collections. Empirically verified (a standalone `toml.Marshal` reproduction against the real `Webspace` struct, and cross-checked against `kernel/config/config.go`'s own comment "toml.Marshal already emits `[]` for a nil slice") that `Webspace.Keywords`/`Sources`/`Match` carry no `omitempty` tag — the canonical writer ALWAYS emits `keywords = []` and `sources = []`, and an empty `match` table renders as a present `[webspaces.<name>.match]` header. Key absence is therefore not a signal the shipped writer can ever produce; asserting for it would either always fail or, worse, silently pass by accident on an unrelated parser quirk.
- **Fix:** Assert genuine EMPTINESS instead (`(ws.keywords ?? []).toEqual([])`, etc.) — the strongest distinguishing signal the shipped writer actually offers, and still catches a shell written with any stray content.
- **Files modified:** `web/e2e/specs/uat-03-empty-shell-first-source.spec.ts` (file-header comment documents this departure explicitly, per the plan's own `<output>` instruction to record any UAT clause that could not be asserted exactly as written)
- **Verification:** spec passes; the emptiness assertion correctly distinguishes the shell state from the populated state later in the same test (`sources` length 1, `match` exactly 1 key after the add)
- **Committed in:** `3ea6e18` (Task 3 commit)
