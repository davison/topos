# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**No `03-CONTEXT.md` exists** (user chose to proceed without `/gsd-discuss-phase`) and no sketch findings exist. Per the roadmap's own phase notes, this phase "extends the Phase 1/2 UI contract with one new renderer (email body) and one new control (search box) — no new interaction model." Everything not explicitly called out below is inherited verbatim from `01-UI-SPEC.md`/`02-UI-SPEC.md` — this document does not re-derive the design system, spacing scale, typography, or base palette. Design decisions below with no prior CONTEXT to draw on are made prescriptively by this research pass and flagged `(default)`.

**No new agent-facing UI surface.** Neither SRC-01 nor KERN-05 has an AGENT-01/02 dimension — same "no UI surface" note Phase 2 made for its own agent-permission requirement.

**No "mark read" affordance exists anywhere in this UI, by design.** SRC-01 criterion 2 ("reading an email inside webspaces never marks it read in Proton") is a backend/protocol guarantee (`BODY.PEEK`, `EXAMINE` — see `03-RESEARCH.md` Pattern 1), proven by an automated test, not a UI control. The UI must not introduce a read/unread toggle, badge, or indicator of any kind — doing so would imply state this system deliberately never touches.

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn-svelte (already initialized — `web/components.json` present, confirmed this session: `style: "new-york"`, `baseColor: "slate"`, `cssVariables: true`) |
| Preset | Unchanged from Phase 1/2 — Tailwind CSS v4, dark-mode-only, no light/dark toggle |
| Component library | `bits-ui` (unchanged) |
| Icon library | `@lucide/svelte` (unchanged; new icons this phase: `Search`, `X`) |
| Font | Inter (variable), unchanged |

**One new shadcn block required: `input`.** Confirmed via `ls web/src/lib/components/ui/` this session — the project has `alert`, `badge`, `button`, `card`, `scroll-area`, `separator`, `skeleton`, `tooltip` installed, but no `input`. The search box (E1 below) needs it. This is the only new registry block this phase introduces; see Registry Safety.

**No new components beyond `SearchBox.svelte`.** The email body renderer needs zero new UI code — it reuses `DetailPane.svelte`'s existing `content.rendition?.mime_type === 'text/html'` iframe branch verbatim (the exact branch SilverBullet's rendered markdown already exercises). Search results reuse `StreamRow.svelte`'s existing visual shape (see E2 below) rather than a new row component, keeping the "no new interaction model" framing literal, not just directional.

**Visual hierarchy:** unchanged from Phase 1/2 — the stream/results list remains the primary focal point; the search box is a persistent secondary control in the header (same tier as the source-filter chips), never competing with the stream for attention.

## Color

**Unchanged from Phase 1/2 — no new tokens.** `#020617`/`#0f172a`/`#1e293b` dominant/secondary/border, `#60a5fa` accent, `#f87171` destructive, `#4ade80` success, `#fbbf24` warning — all live today in `web/src/app.css`.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#020617` (slate-950) — unchanged | Page background, stream/results pane |
| Secondary (30%) | `#0f172a` (slate-900), border `#1e293b` — unchanged | Cards, header, detail pane, search box surface |
| Accent (10%) | `#60a5fa` (blue-400) — unchanged | "Open in {display_name}" CTA, links, focus rings, selected stream/result row |
| Destructive | `#f87171` (red-400) — unchanged | Destructive actions (none new this phase); unreachable-source health dot |

Accent reserved for: exactly the same list as Phase 2 — "Open in source" CTA, inline text links, focus-visible rings, the selected stream/result row indicator, and the active source-filter chip. **Explicitly not used for:** the search box's focus state beyond the standard focus ring, or the sender field (plain `--foreground`/`--muted-foreground` text, same treatment as the date field it sits beside). This keeps the accent budget uncontaminated by the two new surfaces this phase adds. (Search-result matched-term emphasis was originally weight-only, not accent or any color — see the superseded rule under Typography above; it is now the dedicated `--warning` amber, still never the accent blue.)

## UI Considerations

> Populated by the ui-phase UI-consideration probe (Step 9.5) and lifted by plan-phase's
> `## UI Considerations` lift rule via the identical rule as SPEC `## Edge Coverage`. Shape-rooted UI *state*
> coverage (empty / loading / error / populated / partial / overflow / zero-one-many / long-text).
> Empty-state and error-state COPY live in `## Copywriting Contract` above — this section covers
> state coverage and REFERENCES those rows rather than restating the copy (de-dup).

Probe run (ui-consideration-probe engine, post-verification per Step 9.5) over 5 elements: E1 search-box (interactive-control, new), E2 search-results-list (list-collection, new), E3 sender field in stream-row + detail-pane (list-collection/media extension, not a new element), E4 detail-pane email HTML body (media, reuses an existing branch verbatim), E5 health chip for the email/Proton source (nav, inherited pattern, new source_type only). Element kinds and all resolutions confirmed with the user this session. **36 applicable considerations: 16 covered, 1 backstop, 19 dismissed (with reasons), 0 unresolved.** (The table also retains a few informational rows beyond the probe's applicable set — E4 populated/zero-one-many and E5 populated/zero-one-many — kept for inheritance clarity.)

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | E1 search-box | ✅ covered | Query starts empty; the stream renders unfiltered by search — identical to today's default view, zero visual change until the user types. |
| loading | E1 search-box | ✅ covered | While a debounced (~300ms) request is in flight, the box itself never disables or shows its own spinner — the loading state lives in the results region (E2), not the input. |
| error | E1 search-box | ✅ covered | A failed search request never disables or clears the box; the box stays fully interactive while the results region shows the inline error copy (E2 error row). |
| populated | E1 search-box | ✅ covered | Non-empty query shows the "Clear search" (×) icon button; typing further updates results on each debounce tick, no explicit submit action required. |
| partial | E1 search-box | ➖ dismissed | No partial concept for a single text input. |
| overflow | E1 search-box | ✅ covered | Standard `<input>` horizontal-scroll-within-field behavior for query text exceeding the field's width — no custom truncation. |
| zero-one-many | E1 search-box | ➖ dismissed | A single control, not a collection. |
| long-text | E1 search-box | ✅ covered | Arbitrarily long query text scrolls within the fixed-width field; the raw string is never interpolated into rendered copy unescaped — the empty-results heading interpolates `{query}` as plain text content (Svelte's default text binding), never `{@html}`. |
| empty | E2 search-results-list | ✅ covered | Zero matches for a non-empty query renders the "No matches for…" heading + body (Copywriting Contract) — visually distinct from the unfiltered stream's own empty state, never the same "Nothing here yet" copy. |
| loading | E2 search-results-list | ✅ covered | Debounced request in flight reuses the existing stream-load skeleton treatment (Phase 1's skeleton rows) — no new skeleton design. |
| error | E2 search-results-list | 🧪 backstop | A search-request failure (kernel unreachable / index error) is rare — kernel and SPA share one process, same rationale as Phase 1's own stream-load-error backstop row — and awkward to exercise without deliberate fault injection; held out as backstop per that precedent. |
| populated | E2 search-results-list | ✅ covered | One row per match, reusing `StreamRow.svelte`'s exact visual shape (thumbnail/title/date/sender/tags), with the preview region replaced by the FTS5 `snippet()` text; matched terms render via the shared amber `.search-highlight` class (see Typography's superseded-rule note — G-06-1, Phase 6 plan 06-05), not a font-weight change. Rows render in the order the API returns them (bm25 rank ascending) — never re-sorted client-side. |
| partial | E2 search-results-list | ✅ covered | A result whose snippet is empty (title-only match) omits the snippet line — the same "title + metadata only" degrade `StreamRow` already applies when `item.preview` is empty; no new fallback rule. |
| overflow | E2 search-results-list | ➖ dismissed | Inherits the stream pane's own independent-scroll contract (Phase 1) unchanged — searching doesn't introduce a second scroll region. |
| zero-one-many | E2 search-results-list | ✅ covered | One match renders a single full-width row (no pagination chrome, same rule as the stream's own zero-one-many row); results are capped at 50 (`03-RESEARCH.md`'s `LIMIT 50`) with no "load more" affordance this phase — explicit MVP scope, not a gap. |
| long-text | E2 search-results-list | ➖ dismissed | Same clamp/truncate rules as `StreamRow` (title one line, snippet two-line clamp) — the snippet is additionally bounded server-side by `snippet()`'s own token-count parameter. |
| empty | E3 sender field (stream row + detail pane) | ✅ covered | `item.group_label` is empty for paperless/SilverBullet items (03-RESEARCH.md Pitfall 4) — the sender segment is omitted entirely from both surfaces, never an empty label or "Unknown sender" placeholder; non-email items render exactly as they do today, zero visual change. |
| populated | E3 sender field (stream row + detail pane) | ✅ covered | `StreamRow` renders `group_label` as the first item in the metadata strip, before the date; `DetailPane` renders it as its own line directly under the title, before the date+labels row — both plain text, no "From:" prefix. |
| long-text | E3 sender field (stream row + detail pane) | ✅ covered | Stream-row sender is a `shrink-0` inline span inside the existing `.stream-row-meta` clipped strip; detail-pane sender truncates to one line with ellipsis (same treatment as the webspace title), with the full value exposed via a `title` attribute on hover. |
| overflow | E3 sender field (stream row + detail pane) | ➖ dismissed | Covered by the long-text row's clip/truncate rule; no separate overflow behavior. |
| loading / error / partial / zero-one-many | E3 sender field (stream row + detail pane) | ➖ dismissed | `group_label` is a plain string field on an already-loaded item, not its own async collection — no independent load/error/partial state exists for it. |
| empty | E4 detail-pane email HTML body | ✅ covered | A plain-text-only email (no HTML part) falls through to the existing `content.text` branch (whitespace-preserved text block) — inherited Phase 1 text-content behavior, not new. |
| populated | E4 detail-pane email HTML body | ✅ covered | Sanitized email HTML renders in the already-existing `content.rendition?.mime_type === 'text/html'` iframe branch (`DetailPane.svelte`) — zero new branch, zero new component; email is simply a second source returning `text/html`, the exact condition SilverBullet's rendered markdown already satisfies. |
| loading / error / overflow / long-text / partial / zero-one-many | E4 detail-pane email HTML body | ➖ dismissed | Fully inherited from Phase 1/2's already-resolved detail-pane rows (skeleton while loading, generic error alert + retry, iframe-internal scroll, never pushes pane layout) — email introduces no new branch logic beyond the mime-type check above. |
| error | E5 health chip (email/Proton source) | ✅ covered | Bridge-unreachable renders the existing `destructive`-tone dot + "{display_name} — unreachable since {relative}" tooltip (Phase 2's unchanged Copywriting Contract row) — satisfies SRC-01 criterion 5's UI half with zero new UI code; see Copywriting Contract note on the backend-owned "actionable" half. |
| empty / populated / loading / partial / zero-one-many / overflow / long-text | E5 health chip (email/Proton source) | ➖ dismissed | Fully inherited from Phase 2's already-resolved E1 rows — email/Proton is simply a third `source_type` flowing through the same generic chip component; no per-source branching exists or is needed. Empty (no health report yet for the Proton source) renders Phase 2's neutral/muted "unknown" dot until the first `Health()` resolve — never a false-green flash (dismissed-as-inherited, user-confirmed this session). |

**Dedup (SRC-01 criterion 3) has no independent UI row above** because it requires no new UI logic: a message merged across several matched labels arrives as one `Item` whose `labels` array already contains every matched label, and `StreamRow.svelte`'s existing `{#each item.labels as label}` loop already renders one `Badge` per array entry — the same mechanism that already renders multiple paperless tags on one row. One row, multiple label badges, is the correct and already-covered visual proof of dedup; no plan task should add a new rendering path for it.
