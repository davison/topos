<objective>
Close the single remaining blocking gap in `03-VERIFICATION.md`'s `gaps:` block, promoted from `03-REVIEW.md` CR-01: `plugins/proton/go.mod` declares `golang.org/x/net v0.26.0`, a release affected by CVE-2024-45338 / GO-2024-3333 — non-linear HTML tokenization with respect to input length, a CPU/memory-exhaustion DoS. The affected package is `golang.org/x/net/html`, the tokenizer behind `github.com/microcosm-cc/bluemonday`, and `plugins/proton/body.go`'s `RenderSanitizedEmail` runs `bluemonday.SanitizeBytes` over the HTML body of an arbitrary inbound email with nothing upstream filtering the bytes. This plugin is the first source in the codebase to run a third-party HTML parser over fully attacker-chosen input, which is what turns a stale pin into a security finding.

**Exploitability correction — read this before writing any commit message.** The gap report and the review both describe this as reachable in the running plugin. Direct measurement against the current tree shows that is true of the *declared* contract but NOT of any binary this repository builds. This repo is a `go.work` workspace of six modules. `make build` compiles every plugin in workspace mode, where MVS takes the maximum requirement across the whole workspace: `golang.org/x/net` already resolves to **v0.56.0** for `plugins/proton`, far past the v0.33.0 fix boundary. Only a module-scoped resolution (`GOWORK=off`) selects v0.26.0 — and `plugins/proton` cannot even build that way today, because its go.mod deliberately omits the requires that the workspace-local `sdk` module supplies (documented in its own trailing comment). So the shipped plugin binary has never compiled the affected tokenizer.

That does not make the finding false; it relocates it. The defect is in the module's **declared** dependency contract, which is what a security scanner reads, what an SBOM records, what any module-scoped consumer resolves, and — given this project's stated constraint that the plugin contract be "documented enough for third-party source plugins" — what a third-party plugin author inherits by copying this manifest. It is also a live trap: the workspace only masks it while some other module's transitive graph happens to pull a higher version, which is an accident of `golang.org/x/tools`' requirements, not a guarantee. Fix the declaration, and fix the reason nobody noticed.

**User-visible outcome** (ROADMAP Phase 3 Success Criterion 1, quoted verbatim — the ROADMAP `**Goal:**` line is not in `As a / I want to / so that` form, so no user story is invented here, following the precedent 03-05 and 03-06 set and 03-VERIFICATION.md's own MVP-mode note endorsed): *"Emails in Proton folders or labels matching the webspace keyword appear in the stream with sender, subject, and date, and **render their body inline in the detail pane**."* The body-rendering path is functionally complete as of 03-06; this plan makes the dependency that path runs on declare a version that cannot hang the plugin on a malicious message, and leaves the rendering output byte-identical.

This is one vertical slice, not a layer: the declared manifest → the resolved build list → the sanitizer the detail pane's body passes through → an assertion that the same class of drift cannot recur silently in any of the six modules.

Purpose: the bump alone is a two-line edit that would be re-broken by the next dependency change nobody audits. The durable half of this plan is the repo-wide floor guard, which simultaneously discharges the gap's second `missing` item ("check `plugins/silverbullet` for the same stale pin") as a permanent invariant over all six modules rather than a one-time manual check.

Output: two changed version strings and three added checksum lines in `plugins/proton`, one new boundary test in the existing render suite, one new repo-wide audit test with its negative-control fixture, and a recorded, evidence-backed correction to the finding's exploitability analysis.
