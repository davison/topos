<objective>
Close gap **G-03-2** in `03-UAT.md` (severity major, status failed): the email detail pane is unreadable. The user's screenshot showed every image as a broken icon and email-supplied text colours sitting dark-on-dark against the fixed dark pane.

Two deliberate, individually-correct decisions compound into one unreadable pane:

1. `plugins/proton/plugin.go`'s `fetchFull` already extracts the message's `text/plain` part into `FetchResponse.Text` for **every** message — and then, whenever an HTML part also exists, additionally emits the sanitized HTML rendition. `web/src/lib/components/DetailPane.svelte` prefers a `text/html` rendition whenever one is present, so the plain text that was already fetched is never displayed.
2. The rendition is served under `Content-Security-Policy: default-src 'none'; ...; sandbox` (the tracking-pixel defence, T-03-10/T-03-11), so no `img` can ever load — every one renders as a broken-image placeholder — while `emailSanitizePolicy` deliberately lets `color`/`background-color` through, so a light-background email design paints near-black text inside the dark wrapper.

The user's direction is explicit: **prefer plain text when available**, keep the sanitized dark-theme HTML rendition as the fallback for HTML-only emails, and preserve the standing security posture. This plan does exactly that, and additionally makes the kept fallback readable — because the gap's own truth requires no dark-on-dark text and no broken-image litter for HTML-only mail too, not only for mail that happens to carry a plain-text alternative.

**User-visible outcome** (ROADMAP Phase 3 Success Criterion 1, quoted verbatim — the ROADMAP `**Goal:**` line for this phase is not in `As a / I want to / so that` form, so no user story is invented here; this follows the precedent set by 03-05 and 03-06 and is surfaced rather than silently worked around. Run `/gsd-mvp-phase 3` if a real user story is wanted for this phase): *"Emails in Proton folders or labels matching the webspace keyword appear in the stream with sender, subject, and date, and **render their body inline in the detail pane**."* They render — but not readably, which is the half this plan finishes.

This is one vertical slice through every layer the change touches: the plugin decides which representation is the content → the kernel's unchanged item route carries that decision as the presence or absence of a rendition → the shared pane renders the body region from the shape it was handed. Task 1 is the end-to-end tracer for a message that has both parts; Task 2 gives the chosen representation the pane it deserves; Task 3 repairs the fallback the HTML-only case still uses.

Purpose: SRC-01's "and stays readable there" contract (the phase goal's own words) is unmet on the surface the user actually reads. Every prior round proved the body *arrives*; none proved it can be *read*.

Output: one representation-choice branch and one named predicate in the plugin, three new seeded fixture messages, one new Go test file, four readability rules in the theme wrapper with their assertions, one new pure UI decision function with its decision table, and one rewritten body region in the shared detail pane.

<assumption_delta_decision>
**Noun:** the content field the detail pane treats as the item's primary representation.

**Decision: `promote`.** The extracted plain text is promoted from an unused secondary field to the primary representation for a Proton email whenever it carries renderable content; the sanitized HTML rendition is demoted to the fallback for messages that have no such text.

**Rationale:** the preference is resolved once, in the producing plugin, so exactly ONE representation is emitted per message — the pluralization the detector warned about (a second rendition path plus a preference order carried by every consumer) never materializes downstream. The kernel and the pane keep a single primary field each and need no source identity to interpret it.

**What would force a revisit:** a second source that legitimately needs both representations delivered simultaneously with a consumer-side choice. At that point the preference becomes contract surface (a field on `FetchResponse`) rather than a producer-local branch. Nothing in the current five-source roadmap requires that.
</assumption_delta_decision>
