    Add the kernel's link-session surface. Short-poll, not SSE: no handler in this codebase streams today, and a poll loop is the lower-risk transport for a phase framed as managed risk. The rotating code's own validity drives the browser's poll cadence.

    **`kernel/supervisor/supervisor.go`.** Add `SuspendInstance(ctx, name) (resume func(context.Context) error, err error)`. It looks the named instance up in the running `Host`; when absent it returns a no-op resume and no error. When present, it reconciles the Host against the current source map minus that one instance — stopping its subprocess and releasing its store lock — and returns a resume closure that reconciles the instance back. Take the same lock `Apply` takes and respect the same generation discipline, so a suspension can never interleave with a config apply. The suspension is deliberately narrow: it removes exactly one instance and touches no scheduler state, no index rows, and no other plugin.

    **`kernel/httpapi/whatsapplink.go`.** Declare a `Suspender` interface with that one method (satisfied structurally by `*supervisor.Supervisor`, matching how `Applier`/`Fetcher`/`HealthProber`/`Refresher` are already declared in this package). Declare a small spawner seam too — a function type that starts the link subprocess and returns a line-reader — so the handler's tests can drive it without a real binary.

    Implement an in-memory `linkSessionStore` keyed by an unguessable session id, holding per session: the subprocess handle and its cancel func, the latest `linkEvent` received, a terminal state once one arrives, the resume closure from `SuspendInstance`, and a deadline. A background reader goroutine per session consumes the subprocess's newline-delimited JSON stdout and updates the latest event. A single reaper terminates sessions past their deadline. Cap the number of concurrent sessions at a small constant and reject beyond it, so a stuck browser cannot accumulate subprocesses.

    Three handlers:
    - `WhatsAppLinkStartHandler(pluginsDir, suspender, logger)` — `POST /api/config/whatsapp-link`, body `{plugin, path, instance}` where `instance` is optional (present for the D-03 Re-link flow, absent for the D-02 Add-Source flow). In this exact order: decode; validate `plugin` against `pluginhost.DiscoverAllBinaries(pluginsDir)` and refuse an unknown name with 404 `plugin_binary_not_found` BEFORE anything is executed, because directory listing and never a caller-supplied value is the authority over what may be launched; reject an empty `path`; suspend `instance` when non-empty; spawn the binary in machine-readable link mode via `exec.CommandContext` with the resolved discovered path (never a path from the request body) and an explicit, minimal environment; register the session; respond with the session id and the current state.
    - `WhatsAppLinkPollHandler` — `GET /api/config/whatsapp-link/{session}`, returning the latest event's state, the `png_data_uri` and `expires_in_seconds` when the latest event is a QR, and the error code/message when it is an error. On a terminal state (paired, error, timeout) the handler runs the resume closure and retires the session after this response, so the caller sees the outcome exactly once and the suspended instance comes back up.
    - `WhatsAppLinkCancelHandler` — `DELETE /api/config/whatsapp-link/{session}`, killing the subprocess, running the resume closure, and retiring the session.

    Map the plugin's store-in-use error code to a `whatsapp_store_in_use` API error with a message naming the running instance, and any other plugin failure to `link_failed` carrying the plugin's own message. Every response uses `WriteJSON`/`WriteError` — one envelope, one `schema_version`, no second shape. Register nothing on `/agent/v1`: this is a mutating, human-only surface and the agent namespace registers zero non-GET routes.
