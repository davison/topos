<objective>
Close the browser half of G-08-1's AND-gate.

Two of the gap's three contributing conditions live in `QRPanel.svelte`: the
liveness poll interval is the QR code's own validity window
(`schedulePoll(seconds * 1000)`, up to 60s on whatsmeow's first code — the one a
user actually scans), and there is no panel state between `qr` and `success`,
so the plugin's own 5-65s post-pair login window renders as a stale code with a
countdown that resets on every poll. Together they make a successfully-scanned
session visually indistinguishable from a dead one.

This plan ships the consumer half FIRST, deliberately. `applySession`'s `switch`
currently falls through to `default: break` for any unrecognised state — which
schedules no further poll. If plan 08-06 taught the plugin to emit
`pairing_accepted` before this component knew what to do with it, the panel would
stop polling entirely at the exact moment the user is waiting. Consumer
tolerance lands first; the producer follows in wave 2.

Purpose: a completed pairing becomes visible to the user within seconds, and the
window in which a user is tempted to cancel a succeeding session is both short
and explicitly labelled as progress.
Output: an amended wire contract (docs/api.md), an amended UI contract
(08-UI-SPEC.md), a widened `WhatsAppLinkState`, and a QR panel that polls on its
own clock.

Note on shape: this is gap-closure remediation of an already-shipped vertical
slice, not a fresh phase — there is no tracer task, because the path being fixed
already runs end to end. The genuine end-to-end proof (a `qr → poll →
pairing_accepted → paired` walk with a realistic expiry) is plan 08-07's
Playwright case, which is where this phase's standing "any UI work extends the
e2e suite" rule (`docs/testing.md`, Phase 07.1 D-11) is discharged for this
change.
</objective>
