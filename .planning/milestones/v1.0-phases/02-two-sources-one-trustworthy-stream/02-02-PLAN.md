<objective>
Turn "we synced once at startup" into an operable sync system: a background
scheduler, a per-source coordinator that refuses to run two syncs for the same
source at once, and an HTTP surface that tells the UI which sources exist, which
are reachable, which are syncing right now, when each last synced, and what broke.

This is the layer Phases 3-5 inherit. Every plugin added later gets scheduling,
deduplication and health reporting for free by being a configured source — which
is exactly why the coordinator must be the *only* way a sync starts. If the
scheduler, the refresh routes and the CLI can each reach the correlation engine
directly, the single-flight guarantee has a hole and the "is it syncing" signal
becomes unreliable, which then makes the health UI lie.

Purpose: KERN-04's scheduler + coordinator + manual refresh, and PLUG-04's health
reporting, merged kernel-side into one honest per-source view.
Output: `kernel/syncer`, two-phase `sync_runs` writes, and three new HTTP routes.

Locked decisions this plan implements (from `02-CONTEXT.md`):
**D-05** a background scheduler replaces Phase 1's startup-only trigger, with a
global `sync_interval` defaulting to 15 minutes, an optional per-source override,
and the startup sync retained as each source's first scheduled run; **D-06** the
per-plugin coordinator is single-flight — a refresh arriving while that plugin is
already syncing coalesces into and reports the in-flight run, never queued and
never parallel — and is the single source of truth for health and sync state that
Phases 3-5 inherit; **D-07** manual refresh is exposed per source and as
refresh-all via kernel POST endpoints returning the sync-run status, with the
in-flight signal driven by a running `sync_runs` row (this plan ships the kernel
half; plan 02-03 ships the UI half); **D-08** health is a kernel-side merge of the
plugin `Health` RPC and `sync_runs` history (this plan ships the merge; plan 02-03
ships the chips).
</objective>

## Flagged Assumptions (unresolved probe rows)

The spec-less edge probe returned `KERN-04` and `PLUG-04` as
**`unclassified` / `unresolved`** — no shape category could be assigned
automatically. Surfaced here rather than dropped, with the planner's working
assumption for each:

- **A-KERN-04:** "Dedups refreshes" means *coalesce into the in-flight run*, not
  *queue behind it* and not *reject with an error* (D-06 locks this). A caller
  whose request coalesced receives the in-flight run's outcome and is told it
  coalesced, rather than a distinct "already running" failure. If the executor
  finds a case where a caller genuinely needs a fresh run rather than the
  in-flight one, that is a design question to surface, not to resolve silently.
- **A-PLUG-04:** A plugin's own `HealthResponse.last_sync_unix` /
  `last_error` are **not** trusted as the sync history. The plugin's `Health`
  RPC is treated purely as a live reachability probe; last-sync time and
  last-error come from the kernel's own `sync_runs` table, because the kernel is
  the single source of truth for when a sync actually happened (D-06). A plugin
  that reports a rosier history than the kernel recorded must not be able to
  turn a health chip green.
