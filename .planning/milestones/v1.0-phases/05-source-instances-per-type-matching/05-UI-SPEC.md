# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Inheritance note:** Phases 1–4 (`01-UI-SPEC.md` through `04-UI-SPEC.md`) already established the design system, spacing scale, typography, and color palette — `web/src/app.css` ships these as live CSS custom properties today. Phase 5 does **not** re-derive them and adds **zero new UI surfaces, zero new components, zero new colors**: per ROADMAP.md and 05-CONTEXT.md, this phase is a kernel identity/contract rewire (named source instances, per-type typed matching, config-writable-only-by-hand) — the real source-surface redesign is deliberately deferred to Phase 6 (`UI-07`/`UI-08`/`UI-09`/`UI-11`). This contract exists to cover exactly two places where the rewire is visible to a human:

1. **Source display names become user-authored, not developer-fixed** (KERN-06) — every place the UI already shows a source's display name (filter chips, health chips, "Open in {source}" CTA, stale-item tooltip) now reads a config-authored, potentially long, potentially duplicated-looking-but-guaranteed-unique string instead of a short hardcoded one. This changes what those existing surfaces must tolerate, even though their visual design is unchanged.
2. **Rendition presentation moves from three duplicated per-plugin stylesheets into one kernel-owned stylesheet** (D-11, folded into this phase because it also breaks `FetchResponse`) — this is a **parity requirement**, not a new visual design: the detail-pane iframe must look pixel-identical after the move. This contract documents the exact tokens/rules that parity is measured against.

No new shadcn component, no new icon, no new color token, no new copy pattern is introduced by this phase.

### Rendition Content Contract (D-11 — kernel-owned stylesheet parity requirement)

The kernel's new `kernel/httpapi/item.go` wrap/sanitize/theme pipeline **must reproduce the following tokens and rules exactly** — verified today by three independent, near-identical `themeStyle`/`signalThemeStyle` constants in `plugins/proton/body.go`, `plugins/silverbullet/render.go`, and `plugins/signal/render.go`, which this phase consolidates into one. This is the visual acceptance test for D-11: a rendition rendered before and after the move must be visually indistinguishable, for all three content shapes.

**Shared base (all three content shapes — this is the "kernel stylesheet" floor):**

| Rule | Value |
|------|-------|
| `color-scheme` | `dark` |
| Document background | `#0f172a` |
| Document text color | `#f1f5f9` |
| Body padding | `16px` |
| Font family | `-apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Helvetica, Arial, sans-serif` (the rendition's own system-font stack — deliberately **not** the SPA's Inter/16px chrome) |
| Base font size / line height | `15px` / `1.6` |
| Link color | `#60a5fa` (accent — the **only** place accent may appear inside a rendition; hover `#93c5fd`) |
| Scrollbar (standards) | `scrollbar-width: thin; scrollbar-color: rgba(148, 163, 184, 0.35) transparent;` on `:root` |
| Scrollbar (WebKit fallback, pre-Chromium-121) | `::-webkit-scrollbar` 10px, thumb `rgba(148, 163, 184, 0.35)` (hover `rgba(148, 163, 184, 0.6)`), track transparent, `border-radius: 9999px`, `border: 2px solid transparent`, `background-clip: padding-box` |
| Self-contained | No `@import`, no `url()`, no external fetch of any kind — the wrapped document must never cause a second network request |

These scrollbar/color values are the resolved-`rgba()` equivalent of `web/src/app.css`'s `--muted-foreground` (`#94a3b8` = `rgb(148, 163, 184)`) mixed via `color-mix()` — do not introduce a new literal color here; carry the existing resolved value forward verbatim.

**Content-shape profile: email (was `plugins/proton/body.go`)**

- Headings `h1`–`h6`: color `#f1f5f9`, weight 600, `margin-top: 1.4em; margin-bottom: 0.5em` (h1 `1.6em`, h2 `1.35em`, h3 `1.15em`)
- `p { margin: 0.75em 0; }`, `ul/ol { padding-left: 1.5em; margin: 0.75em 0; }`, `li { margin: 0.25em 0; }`
- `code`: background `#1e293b`, color `#f1f5f9`, `padding: 0.15em 0.4em`, `border-radius: 4px`, `font-size: 0.9em`, monospace stack; `pre`: background `#1e293b`, `padding: 12px`, `border-radius: 8px`, `overflow-x: auto`
- `blockquote`: `border-left: 3px solid #1e293b`, `margin: 0.75em 0`, `padding-left: 1em`, color `#94a3b8`
- `hr`: `1px solid #1e293b`, `margin: 1.5em 0`
- `img { display: none !important; }` — **email-specific**: images can never load under the rendition CSP (no subresource permitted), so they are hidden rather than shown as broken icons (this is the tracking-pixel/broken-image fix from Phase 3, T-03-09)
- `table`: `border-collapse: collapse; width: 100%; margin: 0.75em 0`; `th, td`: `border: 1px solid #1e293b; padding: 6px 10px; text-align: left`

**Content-shape profile: markdown (was `plugins/silverbullet/render.go`)**

- Identical to the email profile above in every rule **except** `img { max-width: 100%; }` (not hidden) — SilverBullet pages may legitimately reference local/embedded images that DO load under that plugin's CSP, unlike email.

**Content-shape profile: chat (was `plugins/signal/render.go`)**

- No headings/lists/blockquote/table rules apply (transcripts don't produce that markup) — only the shared base plus:
- `img { display: none !important; }` (same reasoning as email — no subresource permitted)
- `.run { display: flex; flex-direction: column; margin: 16px 0; }`; `.run.own { align-items: flex-end; }`; `.run.other { align-items: flex-start; }`; `.run .bubble + .bubble { margin-top: 4px; }`
- `.sender-name { font-size: 14px; font-weight: 600; color: #f1f5f9; margin-bottom: 4px; }`
- `.bubble { max-width: 75%; border-radius: 12px; padding: 8px 16px; }`; `.bubble.other { background: #1e293b; }`; `.bubble.own { background: #0f172a; border: 1px solid #1e293b; }`
- `.bubble .body { font-size: 15px; font-weight: 400; line-height: 1.6; white-space: pre-wrap; overflow-wrap: anywhere; }`
- `.bubble .tombstone { font-size: 15px; line-height: 1.6; font-style: italic; color: #94a3b8; }`
- `.bubble .quote { font-size: 14px; font-weight: 400; font-style: italic; color: #94a3b8; white-space: nowrap; overflow: hidden; text-overflow: ellipsis; margin-bottom: 4px; }`
- `.bubble .timestamp, .bubble .edited-suffix { font-size: 14px; font-weight: 400; color: #94a3b8; margin-top: 4px; }`
- `.bubble .attachment { display: inline-block; font-size: 14px; font-weight: 400; color: #f1f5f9; background: #334155; border-radius: 999px; padding: 4px 12px; margin-top: 4px; }`
- `.bubble .reaction { font-size: 14px; font-weight: 400; color: #94a3b8; margin-top: 4px; }`
- **Hard rule (04-UI-SPEC.md, carried forward unchanged):** the accent hex `#60a5fa` may appear **only** on the shared base's `a` (inline link) rule — never on `.bubble`, `.sender-name`, or `.timestamp`. This protects the 10% accent budget from per-participant color differentiation. `plugins/signal/render_test.go`'s `TestRenderTranscript_NoAccentColourOnBubbleSenderOrTimestamp` is the existing regression test for this rule and must be relocated (not dropped) alongside the code it tests, per 05-RESEARCH.md's Task Ordering step 7.

**Implementation note (not a design decision — flagging for the plan):** these three profiles are near-identical (shared base + 1–2 differing rules). The kernel-owned stylesheet should express them as one shared block plus small per-shape deltas (mirroring how similar they already are today), not three independently-authored stylesheets — that duplication is exactly what D-11 exists to remove. How the deltas are composed (CSS classes on the `<html>`/`<body>` root vs. separate `<style>` blocks per shape) is left to planning; the tokens above are fixed regardless of that mechanism.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **Unchanged pattern** from Phase 2: `"Open in {display_name}"`. **Changed data source**: `{display_name}` now comes from the item's own source *instance* (via `GET /api/sources`, keyed by instance identity) instead of a hardcoded plugin-kind lookup table — e.g. two Proton instances now correctly read "Open in Home email" and "Open in Work email" rather than both reading "Open in Proton Mail". |
| Filter chip label | `{display_name}` — unchanged pattern, same changed data source as above. |
| Health chip label + tooltip | Unchanged copy patterns from Phase 2 ("{display_name} — synced {relative_time} ago", "{display_name} — last error {relative_time} ago: {error_message}", "{display_name} — unreachable since {relative_time}") — same changed data source. |
| Stream row / search result stale tooltip | Unchanged: "{display_name} is currently unreachable — this item may be out of date." — same changed data source. |
| Detail pane error state | Unchanged: "Couldn't load this item" / "{display_name} didn't respond. It may be offline — try again, or open it directly in {display_name}." — same changed data source. |
| Fallback when `display_name` is unavailable client-side | **Changed from Phase 1/2**: falls back to the instance id (the config map key, e.g. `home-email`) — never the deleted `SOURCE_DISPLAY_NAMES` hardcoded friendly-name map, and never the bare plugin kind (`proton`). This matches D-08's "index mirrors config truth" and D-09's "`display_name` defaults to the instance key" — the UI's fallback and the config's own default are now the same value by construction, so there is no third, UI-invented fallback string to keep in sync. |
| Config load failure (D-05 unknown match field, D-09 duplicate display_name) | **No UI surface.** These are startup-time kernel errors (D-05: "fail loudly, naming the field and the plugin"; D-09: "duplicates are rejected loudly at config load") — the process does not start, so there is nothing for the SPA to render. Out of scope for this contract by design, noted here so the checker doesn't look for missing copy. |
| Destructive confirmation | N/A — unchanged, this phase introduces no destructive UI actions. |
