<objective>
Prove the whole Signal vertical end to end on one thin path: the kernel accepts a
local-path source with no base_url/token, the Signal plugin opens Signal Desktop's live
SQLCipher database strictly read-only, refuses an unrecognised schema version by name,
resolves the decryption key from whichever shape the install actually uses, and turns the
matched conversations' message history into conversation-day digests that appear in the
webspace stream alongside documents, notes and mail — with the database byte-identical
afterwards.

Purpose: SRC-02's risk is concentrated entirely in "read a live third-party Electron
app's encrypted database without ever touching it". Proving that path first, against the
user's real 194 MB database, is what makes the rest of the phase safe to build. Every
later plan expands outward from this slice.

Output: a working `plugins/signal` cgo module, a relaxed kernel config contract for
local-path sources, and Signal digests visible in the browser.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Lock the SQLCipher driver and link strategy</name>
  <decision>Which Go SQLCipher driver and linking strategy does the Signal plugin use to open Signal Desktop's live, WAL-mode `db.sqlite` read-only, and is a `go.mod replace` pin to a non-canonical fork authorised?</decision>
  <context>
04-RESEARCH.md Open Question 1 names this as the one finding that, if wrong, invalidates
the rest of the phase's plumbing, and asks for a hard go/no-go before any digest or
matching code is written. Two facts verified during research drive it:

  - `mutecomm/go-sqlcipher/v4` — the driver named in `.claude/CLAUDE.md` — last released
    `v4.4.2` on 2020-12-07 and statically bundles a SQLite core from that era, years
    before SQLite 3.51.3 (2026-03-13) fixed a WAL-reset **database-corruption** bug.
    ROADMAP.md pins `>= 3.51.3` as a floor precisely because of that bug, and Signal
    Desktop's database is a live, actively-written WAL database. The locked package
    fails the phase's own safety requirement.
  - `mattn/go-sqlite3`'s `libsqlcipher` build tag — the recommended replacement — comes
    from upstream PR #1109, open since November 2022 and in no tagged release. Using it
    requires a `replace` directive to a fork, or vendoring the patch.

The undo cost of this choice is **costly, not one-way**: `dsn.go` is the seam, so a later
swap is a driver change plus a Makefile/go.mod change with no data migration and no
broken published contract. It is gated here for a different reason — a `go.mod replace`
to a single-maintainer, untagged fork is a supply-chain decision the audit in
04-RESEARCH.md flags `[SUS]` and explicitly requires a human to authorise before pinning.

Also confirmed on this machine this session: the `sqlcipher` system package is **not**
installed (`pacman -Qi sqlcipher` returns nothing), `~/.config/Signal/sql/db.sqlite`
exists at 194 MB with a live `-shm`/`-wal` pair, and `~/.config/Signal/config.json`
carries the **legacy plaintext `key`** shape (64 hex characters; no `encryptedKey`, no
`safeStorageBackend`).
  </context>
  <options>

Arch `extra/sqlcipher` 4.14.0-1 already carries the 3.51.3 baseline. No large C blob in the repo. `mattn/go-sqlite3` itself is a canonical, heavily-used module.</pros>
      <cons>Needs a `go.mod replace` to a fork carrying unmerged PR #1109 (supply-chain trust, pinned by commit). Needs the `sqlcipher` system package present at build and run time on every machine that builds the plugin. The fork must be re-verified whenever it is bumped.</cons>
    </option>
    <option id="option-b">
      <name>Vendor a fresh SQLCipher amalgamation built from sqlcipher/sqlcipher source</name>
      <pros>Exact, self-chosen SQLCipher/SQLite version independent of any distro or fork. No third-party fork trust at all. Nothing to install on the target machine beyond OpenSSL.</pros>
      <cons>Real build-system burden: autotools generation of `sqlite3.c`, explicit `-lcrypto` linkage, and a multi-hundred-KB vendored C file this repo must keep current itself — a maintenance duty none of the existing plugins carry.</cons>
    </option>

      <name>Pin the jgiannuzzi/go-sqlite3 sqlite3mc branch by pseudo-version</name>

      <cons>A single-maintainer personal fork referenced by an untagged commit pseudo-version — the `[SUS]` verdict in 04-RESEARCH.md's Package Legitimacy Audit. Long-term maintenance is one person's spare time, and the cipher scheme is SQLCipher-compatible rather than SQLCipher itself.</cons>
    </option>
    <option id="option-d">

      <pros>Simplest DSN-driven API, no fork pin, the package named in the project's own stack document.</pros>

**digest.go.** For every matched conversation, read every message in the database with no
time window (D-08), bucket by local calendar day using `time.Unix` on the millisecond
`sent_at` converted with `.In(time.Local)` and keyed by `Format("2006-01-02")` (D-04).
`time.Local` is correct here and needs no config knob: the kernel is a desktop-local
process by project constraint, so its local timezone is the user's — note that in the
comment. For each (conversation, day) with at least one message, build one item: title is
the conversation name, an em dash, the message count, and the word `message` for exactly
one or `messages` otherwise, composed here so the frontend needs no pluralization logic
(D-02); preview is the day's last two-to-three messages in chronological order, each
rendered as the sender's name, a colon, a space, and the message text, newline-joined,
then truncated by rune count via a `Snippet` helper copied from
`plugins/proton/body.go` (D-02); timestamp is the day's last message (D-04). The preview
is the ONLY message text on the item — every other field carries metadata only, because
the preview is exactly what the kernel indexes into FTS and D-03 permits nothing beyond
it. Build `source_id` from the conversation id and the day's `2006-01-02` string joined by
a colon and encoded with `base64.RawURLEncoding`, mirroring `plugins/proton`'s
`encodeSourceID`/`decodeSourceID` pair so the id is URL-path-safe and reversible; the
determinism is load-bearing, because `kernel/index.ReplaceWebspaceSourceItems` upserts by
source_id and that is what makes today's digest update in place instead of duplicating.

**plugin.go.** Mirror `plugins/proton/plugin.go`. Constants: source type `signal`, display
name `Signal`, contract version `webspaces.v1`. `Describe` returns those three verbatim.
`Match` returns an empty successful response for an empty keyword list and for zero
matched conversations — never an error, so a webspace with no Signal content is empty
rather than failed. Any key-resolution, open or schema failure returns a gRPC error
prefixed `signal: `, using `codes.Unavailable` for a database or keyring failure and
`codes.FailedPrecondition` for the schema-version ceiling; check the other plugins before
introducing any further code. `toItem` sets `GroupId` to the conversation id (the proto
field is documented for exactly this), leaves `GroupLabel` empty per the UI contract, sets
`Fidelity` to `LINK_FIDELITY_CONVERSATION_ONLY`, sets `DeepLink` from `deeplink.go`, sets
`Labels` to the matched conversation name, sets `HasThumbnail` false, and copies the
five-key `Provenance` map shape verbatim with `source_system` set to the Signal config
directory path. `Fetch` switches on the variant exactly like proton's: THUMBNAIL returns
`Available: false` with a fixed reason; FULL and PREVIEW return `Available: false` with a
named reason in this task and are implemented in plan 04-03 — a stub that fills without an
architectural change, because the Fetch entry point, its variant dispatch and its
read-only re-open path all exist here. `Health` attempts key resolution, a read-only open
and the schema guard, returning `Reachable: false` with a `LastError` naming the specific
failing step; it never returns a gRPC error. Every log line is count-only and step-named:
never a key, never a conversation name, never message text.

**deeplink.go.** Build the `sgnl://` deep link with the doc-comment discipline of
`plugins/proton/deeplink.go` — explain the fidelity choice inline and cite the decision.
For a 1:1 conversation whose record carries an E.164, target that contact's conversation
via the `signal.me` phone form under the `sgnl` scheme, escaping the embedded value. For a
group, and for a 1:1 with no E.164, emit the bare `sgnl://` scheme, which raises Signal
Desktop. Both are honestly conversation-only fidelity, which CONTEXT.md fixes. The link is
never empty, because PLUG-03's sync-time validation rejects an item with an empty
deep_link.

**web/src/lib/api.ts.** Add `signal: 'Signal'` to `SOURCE_DISPLAY_NAMES`. This is the only

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Signal Desktop `db.sqlite` → plugin process | The user's entire message history crosses here. Message bodies are untrusted input; the file itself must never be altered. |
| `~/.config/Signal/config.json` / OS keyring → plugin process | Decryption-key material crosses here. |
| plugin subprocess → kernel (gRPC) | Items cross a process boundary into the unencrypted local index. |
| `config.toml` → kernel config loader | Operator-controlled paths cross into filesystem access. |
