<assumption_delta_decision>
**Seam detected:** singular→plural / derived→addressable. Before this phase
the only addressable source noun in the HTTP API is the *source instance*
(`config.sources` key — `/api/sources`, `/api/sources/{name}/refresh`). The
*plugin type* existed only as a string field (`source.plugin`) and as a
discovery list (`GET /api/config/plugin-types`), never as a thing you could
address.

**Noun now primary for icon identity:** the **plugin binary**
(`source.plugin`, e.g. `topos-plugin-mock`).

**Decision: `promote`.** The plugin binary becomes a first-class addressable
noun under a new `/api/plugins/{plugin}/…` namespace, rather than hanging the
icon off an instance route (`/api/sources/{name}/icon`) which would have made
the icon a per-instance detail it is not — two instances of one binary have
byte-identical icons, and a per-instance route would have implied otherwise
and forced N cache entries for one asset. Rationale is the same one
`09-UI-SPEC.md` Fix 10 gives for not keying on `source_type`: `source_type`
is *also* only learned by launching, so it buys nothing over the binary name
while being unavailable to the catalog surface entirely.

**Accepted debt (named, not hidden):** the plugin-type noun is addressable but
only *populated* via an instance launch — a plugin binary with zero configured
instances has never reached `Describe`, so its icon is a 404 and the catalog
renders `Puzzle` (09-UI-SPEC.md Fix 11, Group 2). **What would force a further
promote:** a plugin catalog that must show real icons *before* any instance is
configured. The mechanism already exists in one plugin
(`plugins/whatsapp/describeonly.go` + `pluginhost.DescribePluginType`) — a
config-free describe-only launch mode generalised to every plugin would make
the icon learnable from the binary alone. Explicitly out of scope here.

Advisory only — this block records the decision, it blocks nothing.
</assumption_delta_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin subprocess → kernel | `DescribeResponse.icon`/`icon_mime` are attacker-influenced bytes from the kernel's perspective: a plugin binary is separately built, potentially third-party (Phase 999.1), and its Describe payload has never before carried opaque bytes the kernel re-serves. |
| kernel → browser | `GET /api/plugins/{plugin}/icon` returns plugin-supplied bytes with a plugin-influenced Content-Type into the kernel's own origin. |
| browser → kernel | The `{plugin}` path segment is untrusted user/URL input reaching a lookup key. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-01 | Elevation of Privilege (stored XSS) | `kernel/httpapi/pluginicon.go` | high | mitigate | A plugin-supplied SVG may carry `<script>` or event-handler payloads. The `<img>` render path neutralises them, but the route is directly navigable in the kernel's own origin. Task 2 serves every icon with `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`, `X-Content-Type-Options: nosniff` and `Content-Disposition: inline`, so a directly-navigated SVG executes nothing and cannot reach the kernel API from that document. |
| T-09-02 | Spoofing / Tampering | `kernel/pluginhost/host.go` icon capture | high | mitigate | A plugin could declare an arbitrary Content-Type (e.g. `text/html`) to get the kernel to serve active content. Task 2 enforces a kernel-side mime allowlist of exactly `image/svg+xml` and `image/png`; anything else drops the icon entirely (treated as "no icon declared"), so the plugin cannot choose the served Content-Type outside that set. |
| T-09-03 | Denial of Service | `kernel/pluginhost/host.go` icon capture | medium | mitigate | An unbounded `icon` field would let one plugin pin arbitrary memory in the kernel for the process lifetime. Task 2 enforces `MaxIconBytes = 65536` at capture time and drops (never truncates) an oversized icon, and never fails the launch over it. |
| T-09-04 | Information Disclosure | `PluginIconHandler` path param | medium | mitigate | `{plugin}` is untrusted URL input. Task 2 rejects any value containing a path separator or `..` before lookup, and the lookup itself is an exact-match over an in-memory map of launched binaries — the handler never touches the filesystem, so traversal is structurally impossible rather than filtered. |
| T-09-05 | Tampering (supply chain) | `plugins/mock/assets/icon.svg` | low | mitigate | Embedded third-party-derived asset. Task 2 requires a four-key provenance comment (project, file, version/commit, license) above the `//go:embed` directive. Lucide is ISC-licensed, permitting redistribution of a modified copy. Not an npm/pip/cargo install — no package-legitimacy gate applies to this phase. |
| T-09-06 | Repudiation | icon caching | low | accept | A stale cached icon after a plugin rebuild is possible under the immutable `Cache-Control`. Accepted: icon bytes are static per binary build, the ETag still allows revalidation, and a hard reload resolves it — no security consequence. |
