<objective>
**As a** person who wants a webspace for a new topic, **I want to** type a name into "+ New webspace" and have it actually be created, **so that** I can then compose it by adding sources — instead of being told my brand-new, deliberately-empty webspace declares neither a keywords fallback nor any match block.

Purpose: this plan closes 07-UAT.md's single blocker, `G-07-3`. Creating a webspace from the UI has never once succeeded on any installation. `kernel/config/config.go`'s `validateWebspaces` (line 323, established by 05-03 D-01/D-06) unconditionally requires every `[webspaces.<name>]` block to declare either a non-empty `keywords` fallback or at least one `match` block, and `config.Store.Save` runs that full-document validation synchronously on every `PUT /api/config`. `CreateWebspaceModal` — per 07-03/07-04's deliberate D-14 two-write design, spelled out in 07-UI-SPEC.md line 60 — writes an empty shell first (`{keywords: [], sources: [], match: {}}`) and populates match/allowlist in a later, separate PUT. The two decisions were made in different phases and are mutually exclusive at the instant the first write is submitted. Compounding it, `Webspace.Participates` reads an empty `sources` allowlist as "every configured instance participates" (Phase 5 D-03), so even a narrow relaxation of line 323 alone would still be caught by `validateFallbackCoverage` on any install that has at least one `[sources.*]` block — which is every real install. This is a cross-phase contract conflict, not a coding bug in either component, and it is why UAT tests 11 and 12 are `blocked` rather than merely failing.

Output: `Webspace.IsEmptyShell` names the empty-webspace state once; `validateWebspaces` short-circuits it before any per-webspace check, leaving `validateFallbackCoverage` and every other rule byte-identical; `correlate.matchFieldsFor` refuses to fan an empty keywords fallback across a plugin's vocabulary, so a shell correlates nothing rather than risking everything; `config-edit.ts`'s `addSourceToWebspace` stops seeding a shell's allowlist with every configured instance, so the very next write after creation is also valid; a new `web/src/lib/participation.ts` holds the client-side mirror of these document semantics (and is extended by 07-14); and `store_test.go` gains the live round-trip through `config.Store.Save` that 07-03's pure-shape unit test could never have been.

**Recorded design decision — D-20 (this is the decision `G-07-3.missing[0]` demands).**

The debug session (`.planning/debug/create-webspace-rejected-empty.md`) offers three shapes. **Option (a) is chosen: a participation-aware exemption in validation for a genuinely source-less shell.**

1. **Why not (c) — "single-write create-and-seed-first-source".** It is unimplementable on the flow that most needs it. A first-run install has zero `[sources.*]` blocks, so a create modal that requires a first source to be picked has nothing to offer; D-10's zero-webspaces empty state exists precisely to host first-run creation. Rejected on reachability, not on effort.
2. **Why not (b) — "the modal's single PUT writes a document that already satisfies the invariant".** Every representable form of (b) means inventing match input the user never typed — most obviously seeding `keywords = ["<webspace name>"]`. That silently makes a brand-new webspace all-participate against a guessed term, and the UI has no keywords editor through which the user could ever see or remove it. A webspace must never quietly acquire matching rules its creator did not ask for. Rejected on honesty.
3. **What (a) actually is.** An "empty webspace shell" is defined by three simultaneous conditions — no `keywords`, no `match` blocks, and no `sources` allowlist — and is a legitimate, loadable config state meaning "a webspace that exists and matches nothing yet". Requiring all three is what preserves strictness: the shape "allowlists an instance but declares nothing for it to match" is NOT a shell and still fails loudly, which is the operator typo the existing message was written for. `validateFallbackCoverage` is not modified at all; the exemption short-circuits before it.
4. **The safety obligation (a) creates, and how it is discharged.** Before this change, "participating instance, no block, empty keywords" was unreachable — validation guaranteed it away. It is now reachable, and `matchFieldsFor`'s fallback branch would fan an empty `Keywords` slice across every field of the plugin's declared vocabulary, handing the plugin `{conversations: []}`. A plugin that reads an empty value list as "no constraint" would return its entire corpus. So `matchFieldsFor` gains the mirror rule: no explicit block AND no keywords means this instance does not participate in this webspace, and `Match` is never called for it. **This is the load-bearing half of the fix, not a nicety** — the whole point of a shell is that it correlates nothing.
5. **Why the client must mirror it rather than infer it.** With this rule, "effective participation" is `allowlist gate AND has-match-input`. `addSourceToWebspace`'s existing "seed the allowlist from every configured instance when it starts empty" (correct, and load-bearing for a hand-written webspace being edited in the UI for the first time) is wrong for a shell: it would make the first added source drag every other instance into the webspace, and `validateFallbackCoverage` would then reject the write for the uncovered ones. The seeding therefore becomes shell-aware. `participation.ts` exists so this predicate is written once; 07-14 extends the same module for the chip row.
6. **Explicitly flagged, deliberately NOT planned.** With zero `[sources.*]` blocks configured, `WebspaceHeader`'s entire chip row — including the "+" add-source trigger — is gated behind `shouldShowSourceRows`, which requires at least one configured instance. A genuinely fresh install can therefore create a webspace and then have no UI affordance to add its first source. This is pre-existing, is not named in any of the four UAT gaps, and changing it means changing 02-UI-SPEC E1/E5. Recorded here rather than silently ridden along; surfaced to the developer as a follow-up.
7. No package is installed by this plan; 07-RESEARCH.md's Package Legitimacy Audit needs no new row. No ORM schema files exist in this project, so the Schema Push Gate does not fire. COVERAGE.md's "No external API integration" declaration stands.
