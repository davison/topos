# Phase 7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Inheritance note:** Phases 1–6 already established the design system, spacing scale, typography, color palette, and the header's chip-row mechanics (`WebspaceHeader.svelte`, `SourceChip.svelte`) — `web/src/app.css` ships every token below as a live CSS custom property today, unchanged by this phase. This phase's own job is different in kind from every prior one: it is the first phase to add **forms, modals, menus, and destructive confirmations** to an app that has so far been purely read/view. Every table below states plainly whether it is unchanged, extended, or genuinely new. Nothing in this document introduces a new spacing value, font size, font weight, or hex color — it only adds new **usage sites** for the existing scale/palette (most notably: the first real, non-health-dot use of `--destructive`).

**Scope (per ROADMAP.md / 07-CONTEXT.md):** KERN-08 (config write path), UI-12 (webspace builder UI) — webspace switcher + creation, "+"-picker with two-step new-instance / one-step existing-instance flow, chip edit menu (connection vs. match config, remove-from-webspace), "Manage sources…" escape hatch (instance delete, webspace delete, Reload config), secret-field env-var contract, and search-promotion filter chips. No new sources (Phase 8), no agent chat, no change to the plugin contract's read-only guarantee.

**Visual hierarchy (extends Phase 6's note):** The stream list is still the primary focal point; the header stays a secondary chrome surface even as it gains its first interactive-forms surface. Modals, dropdowns, and the "Manage sources…" escape hatch are strictly tertiary — they exist only while summoned and never persist on-screen, so the stream + detail pane remain the thing the eye returns to once a builder action completes. The single new *persistent* header addition (filter chips, when a permanent filter is active) is deliberately visually lighter than the source-chip row it sits below — a secondary status readout, not a second row competing for primary attention.

## Webspace Switcher (D-10, D-13)

**Replaces** the static `<h1>{webspace}</h1>` title in `WebspaceHeader.svelte` with a `WebspaceSwitcher.svelte` button that opens a `DropdownMenu`.

### Anatomy

Trigger: `[webspace name, Display role 28px/600/1.2, truncated]` + a `ChevronDown` icon (16px, `text-muted-foreground`) immediately after the text, vertically centered — the whole trigger is one `<button>`, `variant="ghost"`, no visible border/background at rest (reads as a heading, not a form control, until hovered/focused, at which point the existing ghost-button `hover:bg-muted` affordance signals it's interactive).

Menu content (in order):
1. One item per configured webspace, in config-declared order (never alphabetized — same stability rule as the source chip row): webspace name (Label role, 14px/400/1.4), a leading checkmark-equivalent (`aria-current="true"` + `font-semibold` weight, not a separate icon — the *current* webspace is the only item using the 600 weight, keeping this within the two-weight budget) marking the active one. Clicking a non-active item navigates to that webspace's route.
2. Separator.
3. `+ New webspace` — leading `Plus` icon (16px), opens the **Create Webspace modal** (below).
4. Separator.
5. `Manage sources…` — no icon (text-only, deliberately the plainest item in the menu so it doesn't visually compete with the two icon-led action items above it), opens the **Manage Sources modal** (below). This is the *only* other item in this menu — D-13 is explicit there is no broader settings surface.

### Root redirect & empty state (D-10)

`/` is a redirect-only route: to the last-visited webspace (persisted client-side, e.g. `localStorage`), falling back to the first webspace in config order if none was visited yet, falling back to the **zero-webspaces empty state** if none exist.

**Zero-webspaces empty state** (full-page, centered, replaces the entire header+stream region):
- Heading role (20px/600/1.2): `No webspaces yet`
- Body role (16px/400/1.5), `text-muted-foreground`: `A webspace pulls related items from your sources into one view. Create one to get started.`
- Primary CTA button (`variant="default"` — filled `--primary`): `Create webspace` — opens the same Create Webspace modal as the switcher's `+ New webspace` item.

### Create Webspace modal

`Dialog`, `max-w-md` (448px). Title (Heading role): `New webspace`. One field: `Name` (Label above, 4px gap, text input below) — this is the config map key (`[webspaces.<name>]`), so the modal's helper text (Label role, `text-muted-foreground`) reads: `Used in the URL and the switcher above — lowercase, no spaces recommended.` No source picker in this modal (sources are added afterward via the "+" chip-row trigger, per D-11) — creating a webspace here always produces an empty webspace with **no** `sources` allowlist yet (D-14's explicit allowlist is written the first time a source is actually added). Footer: `Cancel` (ghost) / `Create webspace` (default, filled). On success, navigates to the new webspace immediately (it is now the "current" one for the root-redirect's last-visited memory).

## Add-Source Picker & Two-Step Modal (D-11)

### Trigger

A dashed-border circular button, `size-11` (44px, matching the chip row's own height for visual alignment), `rounded-full border border-dashed border-border text-muted-foreground hover:border-primary hover:text-primary`, containing a centered `Plus` icon (20px). `aria-label="Add source"`. Positioned in the chip row immediately after the last visible chip / the overflow "+N" trigger (whichever renders), **before** the `ml-auto` reserved trailing group (`Clear filters` / `Refresh all`) — it is reserved trailing space in the same sense those two already are (never pushed into the overflow popover, always reachable in one tab stop). The dashed border is deliberate: it is the one "add new" affordance in a row otherwise made of solid-border data chips, so it reads as structurally different at a glance, not just smaller.

Clicking it opens a `Popover` (same primitive already used for the overflow trigger) listing:
- **Existing configured instances** not already in this webspace's participant set — each row: display name (Label role) + plugin type (Label role, `text-muted-foreground`, e.g. `paperless-ngx`). Clicking opens the **one-step "add existing instance" modal** below.
- A separator (only if both groups are non-empty).
- **`New {plugin type}…`** — one row per discovered-but-unconfigured plugin binary (leading `Plus` icon, 14px). Clicking opens **Step 1** of the two-step modal below. `plugins/mock` is excluded from this list (RESEARCH.md Open Question 1, resolved): it is a developer reference fixture, never a real source a user knowingly adds, and its presence here would only invite an accidental add in a real deployment.
- If both groups are empty (every discoverable plugin type already participates in this webspace), the popover shows a single disabled-style row (Label role, `text-muted-foreground`, no hover state): `All available sources are already in this webspace.`

### One-step modal — add an existing instance

`Dialog`, `max-w-md`. Title: `Add {display_name} to {webspace}`. Body: the **match-fields form** (below) only — no connection fields, since the instance already has them. Footer: `Cancel` / `Add source` (default, filled).

### Two-step modal — configure a new plugin-type instance

`Dialog`, `max-w-lg` (512px, wider than the single-step forms since Step 1 carries more fields). A two-dot step indicator (Label role, `text-muted-foreground`, current step `text-foreground font-semibold`) reading `1. Connect` / `2. Match` sits above the title so the user always knows where they are and that a second step follows.

**Step 1 — "Connect {Plugin Type}"** — connection fields, static per plugin type (not Describe-derived; Describe carries only match vocabulary, never connection-field shape — RESEARCH.md's load-bearing finding). Fields shown, in order:

| Plugin type | Fields (all optional unless marked required) |
|---|---|
| paperless-ngx | Display name, Base URL *(required)*, API Token *(required, secret — see Secret Field Contract)*, API Version |
| SilverBullet | Display name, Base URL *(required)*, API Token *(required, secret)*, CA Certificate Path |
| Proton / IMAP (email) | Display name, Base URL *(required)*, Username *(required)*, API Token *(required, secret — used as the IMAP password)*, Webmail Base URL |
| Signal | Display name, Local Path (default shown as placeholder text: `~/.config/Signal`) |

Every plugin type additionally gets a collapsed **Advanced** disclosure (a plain `Button variant="ghost" size="sm"` toggle, Label role, `Advanced options`) containing `Sync interval override` (text input, placeholder `Use webspace default`) — kept out of the primary field flow since it's rarely touched.

Footer: `Cancel` (ghost, left) / `Next` (default, filled, right). Submitting Step 1 trial-launches the plugin (kernel-side, per RESEARCH.md Pattern 3) and calls `Describe` — nothing is persisted yet. Two outcomes:
- **Success:** advances to Step 2, pre-populated with the returned match vocabulary.
- **Trial-launch/Describe failure** (RESEARCH.md Pitfall 4's documented fallback): an inline `Alert` (`variant="destructive"`, existing `ui/alert` component) renders above the footer: `Couldn't verify this connection.` with a secondary action button `Save anyway` (ghost) beside `Next`. `Save anyway` persists the connection-only instance immediately (closes the modal; the new chip appears in an unreachable/error health state, consistent with any other unreachable source) and surfaces a one-line follow-up in the same success path the modal used: `Saved. Add match settings from {display_name}'s menu once it can connect.` The user is never blocked from saving a connection they know is correct even if the kernel can't verify it live yet.

**Step 2 — "Match settings"** — see the shared **Match-Fields Form** below, titled `Match settings for {webspace}`. Footer: `Back` (ghost, left) / `Add source` (default, filled, right). Submitting writes both the new `[sources.<id>]` block and this webspace's `[webspaces.<name>.match.<id>]` block, plus extends the webspace's `sources` allowlist per D-14, in one save.

### Match-Fields Form (shared by both flows)

One labeled field per entry in the plugin's `match_vocabulary` (Describe RPC, or — for an existing instance — the same vocabulary read from the already-launched plugin). Field name is title-cased for the label (e.g. `tags` → `Tags`, `folders` → `Folders`, `conversation_names` → `Conversation Names`). Each field is a plain text input accepting **comma-separated values**, mapped to the config's `[]string` shape — helper text (Label role, `text-muted-foreground`, 4px below the input): `Comma-separated. Matches if any value is present.` A field left blank is omitted from the written match block entirely (never written as an empty-string entry — an empty value list is itself a load-time validation failure per 05-CONTEXT.md, so the form must not produce one).

## Chip Edit Menu (D-12)

`SourceChip.svelte` gains a third revealed-on-hover/keyboard-focus control, alongside the existing refresh button: an `EllipsisVertical` icon button (`size-8`, same treatment and same documented below-44px exception as the refresh control per 06-UI-SPEC.md's G-06-3b precedent — a second small control nested inside the 44px pill, the pill's filter body remaining the primary 44px target). Order within the pill, trailing to leading: `[dot + name (primary filter button)] [refresh, size-8] [⋮ edit menu, size-8]`. `aria-label="Edit {display_name}"`. Opens a `DropdownMenu`, `stopPropagation`'d exactly like the refresh button so it never also toggles the chip's filter state.

Menu content:
1. `Edit connection…` — leading `Pencil` icon. Opens a `Dialog` (`max-w-md`) reusing Step 1's field set for that instance's plugin type, pre-filled with current values (secret field shows the env-var name it currently references, never a value — see Secret Field Contract). A persistent notice banner (Label role, `text-muted-foreground`, inside a `bg-muted rounded-md p-3` block above the fields, not a dismissible `Alert`) reads: `Changes here apply to every webspace using {display_name}.` Footer: `Cancel` / `Save changes`.
2. `Edit match settings…` — leading `Pencil` icon. Opens the shared Match-Fields Form scoped to *this webspace only*, pre-filled from the current `[webspaces.<name>.match.<id>]` block. Footer: `Cancel` / `Save changes`.
3. Separator.
4. `Remove from this webspace` — plain text item, `text-destructive` on hover/focus (signals its weight without needing the full AlertDialog treatment reserved for irreversible data loss — see Destructive Confirmation Contract below for why this one is lighter-weight than instance/webspace deletion).

Full instance deletion is deliberately **not** offered from this menu — it lives only in the "Manage sources…" modal (D-13), so there is exactly one place in the app that can delete a source instance outright, never two competing entry points for the same irreversible action.

## Manage Sources Modal (D-13)

`Dialog`, `max-w-lg`. Title: `Manage sources`. Two sections, each a plain vertical list (`divide-y divide-border`, no card-per-row chrome — this is a dense management list, not a second chip row):

**Source instances** — one row per configured instance across the whole config (not scoped to the current webspace): display name (Label role) + plugin type (Label role, muted) on the left; `Edit` (ghost, `Pencil` icon, opens the same Edit Connection modal as the chip menu) and `Delete` (ghost, `text-destructive`, `Trash2` icon) buttons on the right. `Delete` opens the **instance deletion AlertDialog** (below).

**Webspaces** — one row per configured webspace: name (Label role) on the left; `Delete` (ghost, `text-destructive`, `Trash2` icon) on the right — no `Edit` here (editing a webspace's own composition happens in its own header, not this modal). `Delete` opens the **webspace deletion AlertDialog** (below).

Footer (outside both lists, separated by a border-top): `Reload config` button (`variant="outline"`, leading `RotateCw` icon — deliberately a different icon from the per-source `RefreshCw` so the two "reload" concepts are never visually conflated: one re-reads a source's data, the other re-reads the config file) + trailing helper text (Label role, `text-muted-foreground`): `Re-reads config.toml and applies any hand-edited changes.` On failure, an inline `Alert` (`variant="destructive"`) replaces the helper text: `{kernel's verbatim error message}. The previous configuration is still running.` — the modal stays open, nothing else in the app changes.

## Destructive Confirmation Contract

First phase with real destructive UI actions — this is the first genuine, non-health-dot usage of `--destructive` on an interactive control anywhere in the app. Two tiers, deliberately different weights because their actual blast radius differs:

| Action | Confirmation | Copy |
|---|---|---|
| Remove source from this webspace | Chip menu item alone (no modal) — the action is reversible in one more click (re-add via "+") and destroys no data, only this webspace's participation | N/A — item itself reads `Remove from this webspace`; hover/focus tints it `text-destructive` as the only signal |
| Delete source instance (Manage sources…) | `AlertDialog` — irreversible, deletes config + kills the plugin process + removes indexed items across every webspace that used it | Title: `Delete {display_name}?` Body: `This removes {display_name} from every webspace and deletes its indexed items. This can't be undone.` Buttons: `Cancel` (ghost) / `Delete` (`variant="destructive"`) |
| Delete webspace (Manage sources…) | `AlertDialog` — irreversible, removes the webspace's own config block (filters, match blocks, allowlist) | Title: `Delete {webspace}?` Body: `This removes the webspace and its filters. Source instances and other webspaces are unaffected.` Buttons: `Cancel` (ghost) / `Delete` (`variant="destructive"`) |

Both `AlertDialog` confirmations use the shadcn-svelte `alert-dialog` wrapper (new this phase — see Registry Safety); neither uses a type-to-confirm text field — a single deliberate click plus the named, specific consequence in the body copy is judged sufficient friction for a local single-user desktop tool (consistent with the project's existing no-auth, loopback-only trust posture), and matches the user's own stated preference for a working flow over extra ceremony.

## Secret Field Contract (D-15)

Every secret field (`API Token`) in every connection form renders as: `Label` (`API Token`) → text input whose value is the **environment variable name**, not the secret (placeholder: `PAPERLESS_TOKEN`) → immediately below, a small inline badge reflecting whether that variable is currently set in the kernel's own environment:

- **Set:** `CircleCheck` icon (14px, `text-success`) + Label-role text `Set` in `text-success`.
- **Not set:** `CircleAlert` icon (14px, `text-warning`) + Label-role text, `text-warning`: `Not set — add it to .env and restart before this source can connect.`

The badge is live-checked against the *currently-typed* variable name (debounced, same request pattern as the modal's own save dry-run — no new validation path, just an additional read-only lookup) so typing a different variable name updates the badge without requiring a save first. Saving with an unset variable still succeeds (D-15) — the badge is informational, never a submit blocker. The secret's real value is never fetched, displayed, or transmitted to the browser at any point in this contract.

## Search-Promotion Filter Chips (D-16–D-19)

### Save-as-filter affordance

A text button, Label role, `variant="ghost" size="sm"`, appears immediately trailing the search box (same row, `SearchBox.svelte`'s container) whenever the search box holds a non-empty query that is **not already** an active filter term: `Save as filter`. Clicking it appends the current query to the webspace's `filter` list (D-18) and clears the search box back to empty — the newly-saved term now narrows the whole webspace permanently, and the cleared search box is ready for the next *refining* search (per D-18's "further searches refine within that filter"). No confirmation — appending a filter term is reversible with one click on its own chip's `×` (below), so it does not meet this document's Destructive Confirmation Contract bar.

### Filter chip row

Renders directly below the source-chip row (its own line — never merged into the source-chip row's `flex-nowrap` overflow measurement, since permanent filters and per-source health/filter are two different concepts sharing the same header) whenever the active filter stack is non-empty. Each filter chip:

- Shape: `rounded-md` (not the source chip's `rounded-full`) — the single deliberate geometric difference that makes a filter chip legible as "a different kind of thing" at a glance, satisfying D-19's "visually distinct from source chips" without inventing a new color.
- Content: leading `Filter` icon (14px, `text-muted-foreground`), the term itself quoted (Label role, `text-foreground`): `"boiler"`, trailing `X` button (`size-8`... constrained down to fit the chip's own `h-8` — see spacing exception below) to remove that one term.
- Background/border: `bg-muted border border-border` (the same neutral surface tokens as everything else in this palette — no new hex value, per the Color table).
- Removing a chip (`×`) writes the updated `filter` list immediately through the same save path as everything else in this document (D-17) — no confirmation, symmetric with the no-confirmation "Save as filter" action above.

## Save / Reload State & Error Surfacing (D-03, D-06, D-08, D-09)

One shared visual pattern used by every modal/action in this document that writes config, so the user learns it once:

- **In flight:** the submit button shows its existing label with a loading state (`disabled`, existing `Button` disabled treatment — no new spinner component; reuses the same visual language `SourceChip`'s spinning `RefreshCw` already establishes for "something is happening," but the button itself does not need its own spinner given saves are sub-second per RESEARCH.md).
- **Validation failure (D-09):** an `Alert` (`variant="destructive"`) renders inside the modal, above the footer buttons, with the kernel's own error message **verbatim** (already names field + plugin, per the existing load-time validator) — no UI-authored paraphrase, no second validation copy to maintain.
- **Hash-conflict rejection (D-03):** same `Alert` placement, fixed copy regardless of which modal triggered it: `Config changed on disk — review and retry.` The modal stays open with the user's entered values intact (nothing is discarded); the header/stream silently refresh once the kernel has reloaded the newer file, so the user's next attempt starts from current state.
- **Success:** the modal closes; the affected chip/row/filter appears or updates in place (D-07's eager reconcile makes this visible within one sync, not one interval) — no toast, no success banner. A closed modal returning to a visibly-updated header **is** the success signal, consistent with this app's existing no-toast convention (Phases 1–6 never introduced one).
