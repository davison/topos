  <action>
Create `SECURITY.md` at the repository root, following GitHub's recommended
shape: a `## Supported Versions` section and a `## Reporting a Vulnerability`
section, under a `# Security Policy` title.

Supported Versions: state honestly that topos is pre-1.0 and publishes no
support matrix — security fixes land on `main` and there is no older maintained
branch — followed by a two-column table with a single `main` row so the section
is machine-readable in GitHub's expected shape rather than prose-only.

Reporting a Vulnerability: direct reporters to this repository's private
vulnerability reporting rather than a public issue, linking the advisory intake
path directly. Then, the part that makes this file worth more than a template:
describe what a vulnerability actually means in this project's threat model,
grounded in what topos is. State the baseline — a locally-run, single-user
desktop tool whose kernel binds loopback only and has no authentication on its
HTTP API in v1, which is the deliberate and documented security boundary, not an
oversight, and is therefore not itself a finding. Then name the report classes
that matter most: anything that could cause a plugin to mutate a source data
store it is required to only read; anything that could leak a credential or
secret out of config, environment, or logs; anything that lets content from a
source execute in the embedded web UI, such as an unsanitised rendition escaping
the kernel's content boundary; and anything that lets an agent read a source it
was not granted. Close with an acknowledgement-time commitment of 7 days.

Do not invent a reporting email address, a PGP key, or a bounty. The private
reporting channel is the whole intake path.

Then enable that channel on the repository through the REST API — this is a
repository setting, and doing it here rather than leaving it as a manual
click-through is the difference between a working link and a dead one. Use the
private-vulnerability-reporting endpoint for `davison/topos` with the HTTP
method that enables it. Confirm the resulting state by reading the same endpoint
back; if the read endpoint is unavailable on the installed CLI or API version,
fall back to confirming the enabling call itself returned success, and record
which of the two confirmations was used in the plan SUMMARY.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| External security researcher → project maintainer | A vulnerability report must reach the maintainer without first becoming public knowledge |
| Repository settings → GitHub API | Enabling private vulnerability reporting is a repository-settings write performed with the operator's own `gh` credentials |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-12 | Information Disclosure | Absent private disclosure channel forcing public issue filing | high | mitigate | `SECURITY.md` directs reporters to the repository's private advisory intake, and this plan enables that intake through the REST API in the same task so the link is live rather than dead. |
| T-10-13 | Repudiation | A vulnerability report with no stated acknowledgement window silently going unanswered | medium | mitigate | `SECURITY.md` states a 7-day acknowledgement target, giving a reporter a defined point at which to escalate. |
| T-10-14 | Spoofing | An invented reporting address or PGP key in `SECURITY.md` creating a channel nobody actually monitors, which an attacker could observe going unread | medium | mitigate | No alternative channel is invented; the private advisory intake is the sole path, asserted by an automated gate over the file's content. |
| T-10-15 | Information Disclosure | `SECURITY.md` presenting the documented loopback/no-auth v1 boundary as an unknown, inviting duplicate low-value reports that bury a real one | low | accept | The file states the boundary explicitly as deliberate and documented, and names the report classes that do matter — cheap triage clarity rather than an enforced control. |
| T-10-16 | Tampering | SvelteKit scaffold instructions under `web/` leading a contributor to build or run the SPA in a way that bypasses the kernel's embedding step, shipping or testing a stale UI | medium | mitigate | `web/README.md` is replaced with a pointer to the real build path; an automated gate asserts the scaffold instructions are gone. |
</threat_model>
