<objective>
Establish the repository's publishing path: a cgo-free build entry point in the
Makefile, a tag-triggered release workflow that attaches the built binaries plus
sha256 checksums to a GitHub Release, and a nightly workflow that only builds
when something actually changed.

Purpose: Success criterion 6. Today the repo has exactly one workflow (`ci.yml`)
which tests but never publishes, and no git tag has ever been pushed. Nothing
downstream in this phase can honestly describe how to install topos until the
publishing path exists and has been proven against the real GitHub API.

Output: `.github/workflows/release.yml`, `.github/workflows/nightly.yml`, and
two new Makefile targets (`plugins-portable`, `build-portable`) mirroring the
existing `test-portable`/`test` cgo split.

This plan verifies against the real GitHub Actions service. That is not
optional: a workflow that has never run is an untested assertion, and every
failure mode this phase's research flagged (missing `permissions: contents:
write`, a build step that needs a system C library the runner does not have, an
asset glob that matches the wrong set) is invisible until a run happens. The
verifications therefore push commits and a throwaway tag to `origin`, and clean
up after themselves.

The Signal plugin binary is the one genuinely open question — it is the repo's
only `CGO_ENABLED=1` build and dynamically links the *system's* SQLCipher, so a
binary built on `ubuntu-latest` carries no guarantee of running on an arbitrary
user's distro. Task 1 deliberately ships the portable set first and Task 2 asks
the user to decide, with Task 1's real run as evidence.
</objective>

  <context>
Task 1 shipped the four portable plugin binaries and deliberately left Signal
out, because it is the one plugin in this repo that cannot be built the same way
as the others. `plugins/signal` builds `CGO_ENABLED=1` with the `libsqlcipher`
build tag and **dynamically** links the *system's* SQLCipher library (see the
`signal` target's own comment in the Makefile, and the Phase 04-01 decision in
STATE.md pinning the `jgiannuzzi/go-sqlite3` sqlcipher fork). A binary built on
GitHub's `ubuntu-latest` runner links against Ubuntu's `libsqlcipher.so`; this
project's own stated target platform is Arch. There is no guarantee the
published binary starts on a user's machine, and CI never runs the binary it
builds — only links it — so the failure is invisible until a human downloads it.

The plugin additionally refuses to run below SQLite 3.51.3 (a WAL-reset
corruption fix), so a binary linked against an older distro SQLCipher fails
loudly at startup rather than silently — which is the good case. The bad case is
a soname mismatch producing a dynamic-loader error with no explanation of why.

`make signal` is already documented as the local build path in
`plugins/signal/README.md`, including the per-distro package names.

Whichever option is chosen, Task 3 applies it to BOTH workflows and Plan 10-04
records it in `docs/releasing.md`. This is a reversible decision: it is a change
to two YAML files and can be flipped in either direction at any time.
  </context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → repository contents | A workflow-minted token can create tags and releases; over-scoping it hands write access to a build script |
| Marketplace action → runner | A third-party action executes arbitrary code with the job's token and filesystem |
| Published release asset → downloader's machine | A user executes a downloaded binary with their own privileges, against their own personal-data stores |
| System package feed → build | `apt-get install` (option-a only) pulls a C library the shipped Signal binary dynamically links |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-01 | Elevation of Privilege | `release.yml` / `nightly.yml` `GITHUB_TOKEN` scope | high | mitigate | Job-level `permissions: contents: write` as the sole entry in both workflows; no workflow-level grant, no `write-all`. Asserted by an acceptance criterion in Tasks 1 and 3. |
| T-10-02 | Tampering | Third-party marketplace action supply chain | high | mitigate | Official `actions/*` only, at the exact `@v7` pins `ci.yml` already uses; release creation and upload go through the runner-preinstalled `gh` CLI rather than a marketplace release action. Asserted by a `uses:` enumeration criterion. |
| T-10-03 | Tampering / Repudiation | Published release binary substituted or corrupted in transit | medium | mitigate | `sha256sum` over the exact shipped asset list, published as `checksums.txt` on every release and every nightly, generated in the same step that publishes so the two cannot drift. |
