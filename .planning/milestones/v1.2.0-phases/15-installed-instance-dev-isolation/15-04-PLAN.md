<objective>
Make dev isolation a mechanical gate rather than a convention: a dev run
refuses to start if it would read or write anything the installed instance
owns, and the dev loop moves off port 7777 so the installed instance can hold
it (ISOL-01, ISOL-02).

Purpose: the checkout already isolates its config, index, and plugin
directories per checkout. Two holes remain. First, plugin *stores* are declared
per source in the dev config, and the template ships with no source tables at
all — so the natural way to get a working dev source is to copy a block from
the production config, which points the dev run's WhatsApp session store or
Signal read at the same path the installed instance uses. Second, the dev loop
still binds 7777, which is the installed instance's port. Neither hole is
visible until it has already done damage, so both get a pre-flight refusal.

Output: `cmd/topos-devguard` (a build-time helper in the shape of
`cmd/topos-manifest`, using the kernel's own config loader so there is never a
second TOML parser), the dev port move across all three places that name it,
a stale-dev-config port-consistency check, and the dev-config template's
per-checkout plugin-store convention.
</objective>

  <behavior>
    - A config whose index, plugin directories, and every source path resolve inside the checkout reports zero violations and exits 0.
    - A config whose index path resolves inside the topos state root reports exactly one violation naming the index key and exits non-zero.
    - A config that omits the external plugin directory key reports a violation, because an omitted key resolves to the platform data default inside the state root.
    - A source whose store path resolves inside the state root reports a violation naming that source's own key path.
    - A source whose path is a read-only source location outside the topos roots — a chat application's own directory, a document tree — reports no violation.
    - A path exactly equal to a root reports a violation.
    - A sibling directory whose name shares a leading string with a root but is a different directory reports no violation.
    - Multiple violations are all reported in one run, in a stable order keyed by config path, identical across repeated runs.
    - The config file's own path inside the topos config root is itself a violation.
    - Warn-only mode reports the identical findings and exits 0.
    - The expected-port mode reports a violation when the config's listen port differs from the expected value, naming both.
  </behavior>
  <action>
Create `cmd/topos-devguard`, a small command in the root module taking a required config path flag, an optional warn-only flag, and an optional expected-port flag.

Load the config through `kernel/config`'s own store constructor and read the expanded form. This is the whole point of writing this in Go rather than in shell: the guard and the kernel see one document, parsed once, by one parser, with the same defaulting and the same environment expansion.

Derive the two protected roots the same way the kernel derives its own locations: the config root is the directory the kernel's XDG config-path resolution produces, minus the file name; the state root is the platform data directory the kernel's external-plugin default is built from, minus the trailing external-plugins directory name. Derive both from the same environment variables the kernel reads, with the same fallbacks, so a machine with a non-default data home is protected at its real location rather than at an assumed one.

Collect the candidate paths with their config key paths: the config file's own path; the index path; the trusted plugin directory as the kernel resolves it; the external plugin directory as the kernel resolves it *including the omitted-key default*; and each source's own store path. Expand a leading home marker on any candidate the loader does not already expand, then make each absolute and clean it.

Decide containment on path components, not on strings: a candidate is inside a root when it is equal to the root or when the root is a proper ancestor after both are cleaned and made absolute. A directory whose name merely begins with the root's name is a different directory and must not be reported. Write this as one small function used by every candidate so no call site can implement the check slightly differently.

Report every violation in a single pass, sorted by config key path so output is stable regardless of Go's map iteration order. Each line names the config key, the resolved path, and which root it falls inside. Exit non-zero when there is at least one violation.

Warn-only mode prints the identical report to standard error behind a loud, multi-line banner stating that isolation is being deliberately bypassed and listing every permitted path, then exits 0. There is no partial mode and no per-key suppression — either the guard refuses or it announces everything it is letting through.

Expected-port mode compares the config's own listen port to the expected value and reports a distinct violation naming both when they differ. In warn-only mode this too is a warning rather than a refusal.

Give the command a package doc comment stating what it exists to prevent, in the concrete terms of the defect class: a dev run reading the installed instance's config (which resolves real credentials from the environment), writing its index, or re-linking a chat session whose store the installed instance is using.

Write `cmd/topos-devguard/devguard_test.go` covering every case in the behavior block, each building a config file and directory tree under `t.TempDir()` and setting the config-home and data-home environment variables into that tree so no case can touch the developer's real directories. Include a case that runs the guard twice over a config with several violations and asserts the two outputs are byte-identical.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Dev config → the installed instance's config and state | A dev run reads a config that resolves real credentials from the environment and writes an index and plugin stores; pointing it at the installed instance's locations crosses into live personal data. |
| Dev kernel → the loopback port the installed instance owns | Two kernels contending for one port, with a browser proxy pointed at whichever won. |
| Guard escape hatch → the isolation guarantee | An opt-out is a deliberate hole in the control this plan adds. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-16 | Information Disclosure | dev run reading the installed instance's config | high | mitigate | The guard refuses before any child starts when the config path, index, plugin directories, or any source store path resolves inside the topos config or state root; the check runs regardless of test-seam overrides. |
| T-15-17 | Tampering | dev run writing the installed instance's index or plugin stores | high | mitigate | Same pre-flight refusal, extended to the omitted-external-directory default, plus a dev-config template that documents and demonstrates the per-checkout store convention so the natural path is the safe one. |
