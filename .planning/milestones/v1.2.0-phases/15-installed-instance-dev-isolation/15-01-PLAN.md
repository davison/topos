<objective>
Prove the installed layout end to end: a published release's artifacts are
downloaded, checksum-verified, and placed under `$PREFIX` in the FHS shape
INST-01 specifies, and the installed kernel discovers its plugins from
`$PREFIX/lib/topos/plugins` with no config change (INST-03).

Purpose: this is the phase's riskiest architectural claim. The kernel today
resolves a relative `[plugins] dir` against its own executable's directory,
which for an installed `$PREFIX/bin/topos` points at `$PREFIX/bin/plugins` —
a directory `make install` never creates. Until that resolution is proven
against real binaries in the real layout, every later install task is built
on an assumption.

Output: `scripts/install.sh`, `make install`, a hermetic `make install-check`
gate driven from a fixture release (no network, no credentials), the kernel's
installed-layout plugin resolution plus its unit tests, and the operator-facing
`docs/install.md`.
</objective>

Wire ONE path from `make install` through to an installed kernel launching an installed plugin. No latest-version resolution, no uninstall, no signal — those are later plans.

Create `scripts/install.sh`, a bash script (`set -euo pipefail`) taking the version as its single positional argument and reading two environment variables: `PREFIX` (default `/usr/local`) and `TOPOS_RELEASE_BASE_URL` (default `https://github.com/davison/topos/releases`). The base-URL variable exists purely as a test seam, exactly as `DEV_KERNEL_CMD` does for the `dev` recipe — it changes WHICH release is fetched, never which checks run. Accept the version with or without a leading `v` and normalise to a single tag form.

Sequence the script as: preflight, stage, verify, then place — placement must not begin until verification has fully succeeded, so an abort leaves `$PREFIX` untouched.

1. Preflight: require `curl`, `sha256sum`, and `mktemp` on PATH, failing with a message naming the specific missing tool (the pattern the `dev` recipe uses for `ss`).
2. Stage: create a work directory with `mktemp -d`, removed by an EXIT trap. Fetch `$TOPOS_RELEASE_BASE_URL/download/<tag>/checksums.txt` into it with `curl -fsSL` (`-f` so an HTTP error is a non-zero exit, not a saved error page).
3. Derive the asset list from the second column of checksums.txt — this file is the manifest. Do not hardcode a second asset list anywhere; that is precisely the drift release.yml's own one-place-only `ASSETS` comment guards against. Validate every derived relative path against an allowlist shape: exactly `topos`, or `plugins/` followed by a plugin binary name of lowercase letters, digits and hyphens. Reject anything absolute, anything containing a parent-directory segment, and anything else, naming the offending line and aborting.
4. Download each asset from `$TOPOS_RELEASE_BASE_URL/download/<tag>/<basename of the relative path>` into the staging directory at its full relative path (creating the `plugins` subdirectory), because the published asset names are flat basenames while checksums.txt records the relative path.
5. Verify: run `sha256sum -c checksums.txt` with the staging directory as the working directory. A non-zero exit aborts with a named failure before anything has been written to `$PREFIX`.
6. Place: create `$PREFIX/bin` and `$PREFIX/lib/topos/plugins`. If either cannot be created or written, fail with a message naming the exact directory and telling the operator to re-run under `sudo make install`; the script must resolve this by reporting, not by running any privilege-escalation command itself. Install each file by copying it to a temporary name inside its own destination directory, applying mode 0755, then completing with `mv -f`. Renaming within the destination directory is what makes the replacement atomic and what lets an already-running kernel or plugin subprocess be replaced without a text-file-busy failure — never write directly over the destination path.
7. Report: print the resolved tag, `$PREFIX`, and every path written.

Add three things to the Makefile, each with the explanatory comment block this file's targets all carry: `PREFIX ?= /usr/local`; an `install` target that passes its version argument through to `scripts/install.sh`; and an `install-check` target that runs `scripts/install-smoke.sh`. Register both new targets in the `.PHONY` list. Follow the `dev`/`e2e` precedent for passing a version: accept it as a make variable (`make install VERSION=1.1.0`) so the recipe stays a normal target rather than a goal-name hack.

Run `scripts/install.sh` against it with `TOPOS_RELEASE_BASE_URL` pointed at that tree as a `file://` URL and `PREFIX` set to a temp directory. Then assert the far end of the path: start `$PREFIX/bin/topos serve` against a generated config whose `[plugins] dir` is the stock relative value and whose `[server] listen` is an ephemeral port and whose `[index] path` is inside the temp tree, with `HOME`/`XDG_CONFIG_HOME`/`XDG_DATA_HOME` all pointed into the temp tree, and assert over the HTTP API that the mock source's plugin launched and synced. In cmd/topos/main.go, split the executable lookup out of `pluginsDir` into a pure, testable `resolvePluginsDir(cfg *config.Config, exeDir string) string`, leaving `pluginsDir` as the thin wrapper that calls `os.Executable()` and passes `filepath.Dir(exe)`. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub release CDN → operator's machine | Untrusted bytes cross here: the kernel binary and every plugin binary the operator will then execute. |
| checksums.txt content → local filesystem paths | The manifest's second column is attacker-influenced text used to build local write paths. |
| `$PREFIX` → the operator's system | Install writes into a directory that may be shared with unrelated software and may be root-owned. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-15-01 | Tampering | scripts/install.sh download step | high | mitigate | Every asset's SHA-256 is checked against that release's own checksums.txt with `sha256sum -c` before any byte is placed in `$PREFIX`; a mismatch aborts and leaves `$PREFIX` untouched (Task 3 corrupted-asset case). Default base URL is HTTPS and `curl -f` makes an HTTP error a non-zero exit rather than a saved error page. |
| T-15-02 | Tampering | checksums.txt path parsing | high | mitigate | Derived relative paths are matched against an allowlist shape (`topos`, or `plugins/` plus a lowercase-alphanumeric-hyphen plugin name); absolute paths and parent-directory segments are rejected by name before any file is created (Task 3 traversal case). |
| T-15-03 | Elevation of Privilege | `$PREFIX` placement | medium | mitigate | The script contains no privilege-escalation invocation (asserted by a negative grep); an unwritable prefix fails loud and names the escalated re-run for the operator to perform deliberately. |
| T-15-04 | Denial of Service | replacement of a running binary | medium | mitigate | Placement copies to a temporary name inside the destination directory and completes with `mv -f`, so a running kernel or plugin subprocess is never truncated and never causes a text-file-busy abort (Task 3 live-replacement case). |
| T-15-05 | Spoofing | installed-layout plugin resolution | medium | accept | The resolution probe selects a directory, not a binary; trust remains derived from the kernel's link-time build manifest (`VerifyTrustedBinary`), which this plan does not weaken. An attacker who can write `$PREFIX/lib/topos/plugins` already has the access needed to replace `$PREFIX/bin/topos` itself. |
| T-15-SC | Tampering | package-manager installs | low | accept | This plan adds no npm/pip/cargo dependency. `npm ci` invocations inside existing targets install from the committed lockfile only; no new package enters the tree, so no legitimacy audit applies. |
</threat_model>

## Assumption-delta decision

The detector fired `pluralization` ("alongside") and `chosen` ("configurable
PREFIX") on this phase's scope.

- **Primary noun:** *a topos instance*, identified by its config file path.
  There is no longer one topos on this machine; there are an installed instance
  and a dev instance, and the config path is what distinguishes them (the
  `--config`/`TOPOS_CONFIG` precedence 14-01 established already made this the
  identity, ahead of it being needed).
- **Decision:** `promote`. The config path is treated as the instance identity
  throughout this phase; the home/XDG default becomes one variant (the installed
  instance) rather than "the" config. Plan 15-04's isolation guard is written
  against a config path, not against a notion of "the" installation.
- **Second signal (`chosen`, PREFIX):** `promote`. The installed layout becomes a
  relationship the kernel models (`resolvePluginsDir`'s existence probe) rather
  than a constant. No prefix value is compiled into any Go source — asserted by
  Task 2's tests, which build every layout under `t.TempDir()`.
