<objective>
Split the dev/test config path from the operator's production config, so a kernel built in this checkout (or any git worktree of it) never reads, launches from, or writes to `~/.config/topos/config.toml`, its `plugins.dir`, or its index.

Purpose: this is the precondition for every later plan in Phase 14. Phase 13 UAT already burned on it once — a worktree kernel read the production config, discovered the *main* checkout's plugin binaries, and the build-manifest gate correctly refused all six trusted plugins. Phase 14 makes it sharper still: the operator's production config is about to start carrying live Google OAuth environment references, and Phase 14's UAT runs dev kernels.

Output: a `--config` flag and `TOPOS_CONFIG` env var on `topos serve`/`topos sync`, a per-checkout generated `config.dev.toml` the `make dev` loop uses by default, and the split documented in `docs/testing.md`.

Folded todo: `.planning/todos/pending/2026-08-14-separate-real-config-from-dev-configs.md` (kernel, major).
</objective>

  </read_first>
  <action>
    Give both subcommands an explicit config path, resolved once in `main` and threaded down, replacing the zero-argument `configPath()` lookup that `setup` performs today.

    Precedence, highest first: the `--config <path>` flag; then the `TOPOS_CONFIG` environment variable; then `$XDG_CONFIG_HOME/topos/config.toml`; then `$HOME/.config/topos/config.toml`; then the bare relative `config.toml` fallback the current code already returns when the home directory cannot be resolved. Keep the last three branches byte-identical in behaviour to the existing `configPath()` — this task adds two higher-precedence sources, it does not restate the XDG rules.

    Parse the flag with a per-subcommand `flag.FlagSet` (`flag.ContinueOnError`, output routed to `os.Stderr`) built inside `main` after the subcommand switch selects `serve` or `sync`, over `os.Args[2:]`. Accept both `--config <path>` and `--config=<path>` (a `FlagSet` gives both for free). An unrecognised flag or a `--config` with no value exits 2 through the existing `usage()`/`os.Exit(2)` path; update the usage string to `usage: topos <serve|sync> [--config <path>]` and mention `TOPOS_CONFIG` on a second stderr line.

    Resolve a relative flag or env value **verbatim against the process working directory** — do NOT route it through the absolute-vs-`os.Executable()` rule that `pluginsDir` and `externalPluginsDir` apply to `cfg.Plugins.Dir`/`cfg.Plugins.ExternalDir`, and do NOT call `os.Executable()` here at all. 14-PATTERNS.md suggests reusing that rule; reject that suggestion and record why in a comment on the resolver: the dev loop starts the kernel through `go run`, whose executable lives in a throwaway build directory, so an executable-relative config path would resolve into a temp directory that never holds a config file. A path typed on a command line is expected to mean what the shell means by it.

    Thread the resolved path through as an explicit parameter: `runServe(path string)`, `runSync(path string)`, `setup(ctx, logger, path)`. `setup` keeps every existing behaviour it has today — the `bootstrapConfig` first-run gate, the re-load through `config.NewStore` after a bootstrap write, and returning the ORIGINAL load error when the failure was not `os.ErrNotExist` — it just stops computing the path itself. `bootstrapConfig` already creates the parent directory at mode 0700, so a `--config` pointed at a not-yet-existing path in a fresh directory bootstraps exactly like a fresh production install does; do not add a second directory-creation path.

    Keep the resolver exported to the package (an unexported function is fine) and reachable from a test without running a kernel — the new test file drives it directly, with no config file, no index, and no plugin subprocess.

    In cmd/topos/configpath_test.go write a table test over the precedence chain, using `t.Setenv` for `TOPOS_CONFIG`, `XDG_CONFIG_HOME` and `HOME` so no case reaches the developer's real environment. Cover, at minimum: flag beats env; flag beats XDG; env beats XDG; XDG beats the home fallback; an empty `TOPOS_CONFIG` is treated as unset (matching how the existing code treats an empty `XDG_CONFIG_HOME`); a relative flag value is returned unchanged rather than joined to any other directory; an absolute flag value is returned unchanged.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| shell/CLI → kernel | `--config` and `TOPOS_CONFIG` are operator-supplied strings that select which file the kernel parses and which index and plugin directory it then resolves from |
| generated dev config → kernel | `config.dev.toml` is generated from a tracked template by make and then freely hand-edited; it selects `plugins.dir`, which decides which binaries are launchable as trusted |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14.1-01 | Tampering | `--config` / `TOPOS_CONFIG` path selection in `cmd/topos/main.go` | medium | accept | The operator already fully controls their own config file and the process they start; a flag choosing between two files they own adds no privilege. Existing config validation (`config.Validate`, the bare-filename `Source.Plugin` guard, the external-tier pin check) runs identically for every path, so a dev config cannot launch anything a production config could not. |
| T-14.1-02 | Elevation of Privilege | generated `config.dev.toml` `plugins.dir` | medium | mitigate | The template writes an absolute path under the current checkout only; the trusted-tier build-manifest gate (Phase 13 D-12/D-13) still verifies every binary launched from it, so a dev config pointing at a stale or foreign `bin/plugins` fails loudly rather than launching unverified binaries. |
| T-14.1-03 | Information Disclosure | tracked `config.dev.example.toml` and generated `config.dev.toml` | high | mitigate | Template ships no credential fields at all; its head comment states the environment-reference rule; `/config.dev.toml` is gitignored so a hand-added `${VAR}` block (or, against the rule, a literal) cannot be committed by accident. Pinned by the acceptance criterion that `git check-ignore` succeeds. |
| T-14.1-04 | Denial of Service | `dev-config` regeneration | low | mitigate | Generation is create-only; an existing dev config is never overwritten, so a `make dev` cannot destroy the operator's edited dev configuration. |
</threat_model>
