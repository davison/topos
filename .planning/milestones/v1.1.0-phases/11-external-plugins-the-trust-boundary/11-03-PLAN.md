</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| kernel -> browser SPA | Trust facts (tier, hashes, failure reason) cross to a client that must render, never decide |
| kernel -> agent callers (/agent/v1) | The same merge feeds an automated, grant-filtered surface |
| published documentation -> third-party plugin author | What the docs promise is what the kernel must actually do |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-15 | Information Disclosure | `describePluginResponse.env_var_names` | high | mitigate | Only referenced NAMES are serialized; a test sets distinctive values for the referenced variables and asserts neither value appears anywhere in the response body |
| T-11-16 | Spoofing | client-side trust rendering | high | mitigate | `tier`, `binary_hash`, `pinned_hash` and `launch_failure` are all kernel-computed; the client has no code path that derives trust, only fields it displays |
| T-11-17 | Information Disclosure | launch-failure merge -> /agent/v1 | medium | mitigate | Grant filtering stays applied after the merge; a test asserts an ungranted launch-failed source is structurally absent from the agent response |
| T-11-18 | Tampering | UI action gated on error text | medium | mitigate | The re-pin action is gated on the closed-vocabulary `launch_failure` field; a copy edit to `last_error` can never enable or disable a remedial action |
| T-11-19 | Repudiation | documentation drift | medium | mitigate | The contract's allowlist section is asserted against the implemented list in this plan's acceptance criteria, so the doc cannot silently diverge from `allowedEnv` |
| T-11-SC | Tampering | npm/pip/cargo installs | low | accept | No new package-manager dependency; nothing to gate |
</threat_model>
