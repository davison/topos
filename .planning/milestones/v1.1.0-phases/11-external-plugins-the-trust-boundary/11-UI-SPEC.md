# Phase 11 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Design system already fully established (Phases 1–9); this phase introduces zero new spacing values, zero new type sizes/weights, and zero new palette hex values.** Every visual decision below reuses an existing token, existing component primitive, or an existing icon already imported somewhere in `web/src` — see each element's "Reuses" note. This is a feature phase (PLUG-06..09), not a polish phase: six genuinely new UI elements are introduced (untrusted confirm interstitial, chip trust badge, picker trust badge + label, chip re-pin menu action + re-pin confirmation dialog, chip pinned-hash footer, extras form), all specified in full below because none of them exist in the codebase yet — CONTEXT.md's D-01 through D-15 lock the interaction/data shape; this document locks the pixels, copy, and component reuse.

## New UI Elements

Six new elements, all additive to already-shipped components. None replace existing behavior for a trusted-tier source — every element below is conditionally rendered only when `tier === "external"` (badge, label) or a specific new failure state exists (`launch_failure === "pin_mismatch"`, the re-pin action/dialog/footer), so a trusted-only user sees **zero** visual change from this phase.

### E1 — Untrusted-Source Confirm Interstitial (D-05, D-14)

**Where:** A new Dialog step inserted into `AddSourceModal.svelte`'s existing two-step flow, between a successful `describePlugin` trial-launch (Step 1, "Connect") and Step 2 ("Match") — but **only** when the selected plugin's tier is `external`. Reuses the exact `Dialog`/`DialogContent`/`DialogHeader`/`DialogTitle`/`DialogFooter` primitives every other step already uses; `max-w-md` (matches the existing-instance modal's width — this step has no form fields of its own beyond the confirm box, so it doesn't need Step 1's `max-w-lg`).

**Reuses:** `Dialog` primitives (unchanged), `Alert`/`AlertDescription` for the error path (unchanged component, new copy), `Input` for the type-to-confirm box (unchanged component).

**Layout, top to bottom:**
1. `DialogTitle` (Heading role): `Add an untrusted source`
2. Body paragraph (Body role, `text-foreground`): explanation copy (see Copywriting Contract)
3. A `rounded-md border border-border bg-card p-3` info block (matches the visual weight of Fix 11's catalog tile border, a deliberately "read carefully" affordance) containing, each on its own line (Label role, monospace for the hash line only — `font-mono text-[14px] leading-[1.4] break-all`):
   - `Binary: {binary_name}`
   - `Pinned hash (SHA-256): {full_hash}` — full 64-hex-char hash, `break-all` so it wraps rather than overflowing the dialog
4. Env-disclosure paragraph (Body role, `text-muted-foreground`) — see Copywriting Contract for the exact two variants (zero vs. non-zero referenced vars)
5. Type-to-confirm control: a `label` (Label role) reading `Type {binary_name} to confirm`, then an `Input` bound to local state, `placeholder={binary_name}`
6. `DialogFooter`: `Cancel` (ghost, unchanged pattern) / `Add untrusted source` (primary `Button`, `disabled` until the typed value === `binary_name` exactly, case-sensitive — accidental-click protection per D-05's own framing, not a security control)
7. On submit failure, the existing `Alert variant="destructive"` pattern renders below the type-to-confirm control, same copy conventions as every other save-failure path in this file (`CONFIG_CONFLICT_MESSAGE` fallback, etc.)

**Interaction:** Cancelling returns to Step 1 ("Connect") with all typed connection values intact — same `resetFlowState`-adjacent pattern the existing `Back`/`Cancel` controls already use elsewhere in this file. Confirming proceeds to Step 2 ("Match") exactly as a trusted-tier plugin's successful Describe already does today; the pin write itself (the new `[plugins].pins` map entry) rides the same single `putConfig` call Step 2's `submitMatch` already issues — no extra network round trip.

### E2 — Chip / Picker Trust Badge (D-06, D-07, D-08 lineage)

**Where:** Overlaid on every rendered `PluginIcon` instance whose underlying plugin binary is `tier === "external"` — three call sites: `SourceChip.svelte`'s `[dot][icon][name]` row, `AddSourceModal.svelte`'s Group 1 ("Add to this webspace") existing-instance rows, and Group 2 ("Install a new source") catalog tiles.

**Reuses:** `CircleAlert` (`@lucide/svelte/icons/circle-alert`) — the exact icon `SecretField.svelte` already imports and colors `text-warning` for "this needs attention"; this phase reuses that established visual vocabulary rather than introducing a new glyph (e.g. a shield icon) for a conceptually-adjacent-but-visually-inconsistent signal. Deliberately **not** the health-dot's plain colored circle — a second small dot next to the existing health dot would read as a second health signal, not a distinct trust signal.

**Markup contract (both scales share this shape, only sizes differ):**
```
<span class="relative inline-flex shrink-0">
  <PluginIcon plugin={...} size="..." />
  {#if tier === 'external'}
    <span
      class="absolute -bottom-1 -right-1 flex items-center justify-center rounded-full {backdropSize} {backdropBg}"
      aria-hidden="true"
    >
      <CircleAlert class="{glyphSize} text-warning" />
    </span>
  {/if}
</span>
```
- **Chip scale** (icon `size-3.5`/14px): backdrop `size-3.5` (14px) circle, `bg-card` (matches the chip's own `bg-card` surface — the backdrop exists purely so the badge glyph doesn't visually merge into whatever color the identity icon's own baked pixels happen to be directly behind it); glyph `size-2.5` (10px).
- **Picker/menu scale** (icon `size-4`/16px, used in `AddSourceModal` Group 1/Group 2 rows): backdrop `size-4` (16px) circle, `bg-popover` (matches `PopoverContent`'s own Fix-8 surface token); glyph `size-3` (12px).
- `aria-hidden="true"` on the backdrop wrapper — the badge is redundant with the adjacent text label (E3 below) and the chip's own tooltip; it must never be the *only* channel conveying "untrusted" to an assistive-tech user.
- **No pill widening, no chip-wide tinting** (D-06, verbatim) — the chip's outer `h-11` pill, border, and background are byte-identical to a trusted-tier chip; only the icon corner gains the overlay.

### E3 — Picker "Untrusted" Label (D-07, D-08)

**Where:** `AddSourceModal.svelte`'s picker rows, both groups, appended after the existing text content whenever that row's plugin is `tier === "external"`.

**Reuses:** the exact `text-[14px] leading-[1.4] font-medium tracking-wide uppercase` treatment Fix 11's own group headers (`Add to this webspace` / `Install a new source`) already established — same Label role, same tracking/weight/case convention, only the color channel differs (`text-warning` instead of `text-muted-foreground`).

**Layout:**
- **Group 1** (existing-instance rows, two-line `display_name`/location layout): the label renders as a third, small line beneath the location line — `text-[14px] leading-[1.4] font-medium tracking-wide text-warning uppercase`, copy `Untrusted`.
- **Group 2** (catalog tiles, single-line `[icon] {pluginTypeLabel}` layout): the tile becomes `flex items-center justify-between gap-1.5` (widened from `flex items-center gap-1.5`) so the label right-aligns within the same row — `<span class="ml-auto text-[14px] leading-[1.4] font-medium tracking-wide text-warning uppercase">Untrusted</span>` trailing the plugin name.

### E4 — Chip Menu: "Trust Updated Binary" Action + Re-Pin Confirmation Dialog (D-03)

**Where:** `SourceChip.svelte`'s existing `DropdownMenuContent` (the Phase 9 per-chip menu) gains one new conditional item, rendered **only** when that source's status carries the new machine-readable pin-mismatch signal (kernel-published field — see `<code_context>`/RESEARCH.md Pitfall 2's recommendation for an explicit field, never a `last_error` string match).

**Reuses:** `DropdownMenuItem` (unchanged primitive), placed as the **first** item in the menu (before `Refresh now` — a source that can't launch can't usefully be refreshed either, so this action takes priority when both would otherwise be visible; in practice `Refresh now` should itself be `disabled` in this state, since there is nothing running to refresh). Icon: `ShieldCheck` (`@lucide/svelte/icons/shield-check`) — chosen over `RefreshCw`/`RotateCw` (both already mean something else in this exact menu — "sync now" and "reload config" respectively, per Fix 5/Fix 7) to keep "re-establish trust" visually and semantically distinct from either.

**Menu item copy:** `Trust updated binary…` (trailing ellipsis — signals it opens a further confirmation, matching the existing `Edit connection…`/`Re-link…` ellipsis convention in the same menu).

**Re-pin confirmation dialog** (new `Dialog`, `max-w-md`, opened by the menu item):
1. `DialogTitle` (Heading role): `Binary changed`
2. Body paragraph (Body role): see Copywriting Contract
3. Hash block (`rounded-md border border-border bg-card p-3`, same treatment as E1's block):
   - `Previously pinned: {old_hash_short}` (short form, Label role, monospace)
   - `Currently on disk: {new_hash_full}` (full form, Label role, monospace, `break-all`)
4. `DialogFooter`: `Cancel` (ghost) / `Trust updated binary` (primary `Button`, `disabled` while the re-pin `putConfig` call is in flight — same in-flight-disable pattern every other write in this app already follows)
5. Failure surfaces through the same `Alert variant="destructive"` + `CONFIG_CONFLICT_MESSAGE` pattern every other save path in `AddSourceModal.svelte`/`EditSourceModal.svelte` already uses.

**Chip health-state coupling:** the chip's health dot renders `destructive` tone (`DOT_TONE_CLASS.destructive`, unchanged mapping) and its tooltip text switches to the new "binary changed" branch (see Copywriting Contract) whenever this state is active — inserted into `SourceChip.svelte`'s existing `tooltipText` `$derived.by` branch chain, checked alongside the existing `syncing`/tone branches (this state takes priority over the plain `destructive`/"unreachable" wording, since the cause and remedy are different and specific).

### E5 — Chip Menu: Pinned-Hash Footer (D-08)

**Where:** `SourceChip.svelte`'s `DropdownMenuContent`, appended after the final `DropdownMenuSeparator`/`Remove from this webspace` item — rendered **only** for `tier === "external"` sources (trusted-tier sources have no pin to show, per D-04).

**Reuses:** no new primitive — a plain `div` styled to match `DropdownMenuItem`'s own inset (`px-2 py-1.5`), since this is a static info row, not a selectable action (no `DropdownMenuItem`/`onSelect`).

**Layout:**
```
<DropdownMenuSeparator />
<div class="flex items-center justify-between gap-2 px-2 py-1.5 text-[14px] leading-[1.4] text-muted-foreground">
  <span class="truncate font-mono" title={fullHash}>Pinned: {shortHash}</span>
  <button type="button" onclick={copyHash} aria-label="Copy pinned hash" class="shrink-0 text-muted-foreground hover:text-foreground">
    <Copy class="size-3.5" aria-hidden="true" />
  </button>
</div>
```
- `shortHash` = first 12 hex characters + `…` (e.g. `a1b2c3d4e5f6…`); `fullHash` lives in the native `title` attribute (hover reveals the complete value without a second control) and is also what the copy button actually copies to the clipboard — the *displayed* string is always short, the *copied* value is always the complete 64-hex-char hash (matches D-08's "short copyable form" wording exactly: short to look at, complete when copied).
- On successful copy, the `Copy` icon swaps to `Check` (`@lucide/svelte/icons/check`, `text-success`) for ~1.5s, then reverts — a lightweight, silent confirmation, no toast/alert (copying a hash for manual comparison is a convenience action, not one that needs ceremony). On a clipboard-API failure (permissions, unsupported context), the control silently no-ops — no error surfaced, since the fallback (select-and-copy the visible short form manually) remains available via the same `title`-revealed full value.

### E6 — Extras Form: Declared Fields + Free-Form Editor (D-12, D-13, D-15)

**Where:** `ConnectionForm.svelte`, appended after the existing primary-fields list and the existing "Advanced options" disclosure — rendered whenever the selected plugin type declares ≥1 extras key via its `Describe` response, **or** the instance already has ≥1 saved extras value (so an already-configured instance with extras never loses visibility into them even if a newer Describe response stops declaring one of the keys). Reused unforked by both `AddSourceModal.svelte`'s Step 1 ("Connect") and `EditSourceModal.svelte`'s "Edit connection…" flow, exactly like every other section of this component today.

**Reuses:** `Input` (unchanged), `SecretField` (unchanged — declared extras keys with the `secret`-ish hint render through this exact component, identical treatment to a secret connection field), `Button` (ghost, `size="sm"`, matching the existing "Advanced options" toggle button's own styling) for `Add field`, `Trash2` (`@lucide/svelte/icons/trash-2`, `size-3.5` — reusing `ManageSourcesModal.svelte`'s established remove-row icon/size exactly) for per-row removal.

**Layout, top to bottom, inside a `flex flex-col gap-4` block matching the rest of this component:**
1. Section label (Label role, `text-muted-foreground`, `font-medium tracking-wide uppercase` — identical treatment to the picker's group headers): `Provider-specific settings`
2. **Declared fields** (only the keys the plugin's `Describe` response actually declared this session): each renders exactly like an existing primary connection field — `label` + `Input` (or `SecretField` if the declaration's secret-ish hint is set), `{label}{required ? ' *' : ''}`. The declared default (if any) renders **only** as the `Input`'s `placeholder` — never pre-filled into the bound value (D-14: "declared defaults are display-only, never auto-filled" — a malicious plugin cannot get its suggested default silently saved).
3. Sub-label (Label role, `text-muted-foreground`): `Additional fields` — always rendered beneath the declared fields (or as this section's only content, when the plugin declares zero extras keys but the free-form editor is still how a user adds provider-specific values the plugin didn't declare, per D-15's "older kernel + newer plugin still workable" framing).
4. **Free-form rows**, one per undeclared extras key already present or newly added: `flex items-center gap-2` — key `Input` (`class="w-1/3"`, `placeholder="Key"`), value `Input` (`class="flex-1"`, `placeholder="Value"` — same `SecretField`-style `${VAR}` unwrap/wrap convention `ConnectionForm.svelte` already uses for connection fields, since extras values follow the identical `${VAR}`-reference secrets rule), remove button (`Button variant="ghost" size="icon" class="size-8"`, `aria-label="Remove field"`, `<Trash2 class="size-3.5" />`).
5. `Add field` button (ghost, `size="sm"`, leading `Plus` icon `size-4` — same icon already imported in this file's sibling `AddSourceModal.svelte`) below the free-form rows, appending one new empty key/value row to local state.
6. **Validation:** a free-form key that is empty, or that duplicates either a declared key or another free-form row's key, blocks submit — surfaced through the existing `connectError`/`error` `Alert` this component's callers already render, with copy `Every extra field needs a unique key.` (checked at the same submit-time point `missingRequiredFields` already runs, not a live-typing validation — consistent with how required-connection-field validation already works in this file's callers).
