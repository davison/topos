<objective>
Accept Signal Desktop's newest database schema version — after re-proving, against the real
database, that accepting it is safe — and get the operator's INSTALLED instance actually
recovered.

The Signal source is refusing to sync behind `guardSchemaVersion`'s deliberate safety floor
(surfaced during Phase 15 UAT, 2026-08-19). That refusal is designed behavior: the plugin reads a
database it does not own, whose owner migrates it without warning, and the guard exists so a
schema change surfaces as a loud stop rather than as silently wrong digests.

This is a rerun of the flow precedent 260805-lry established, and it is cheap precisely because
that precedent left tooling behind: `plugins/signal/schema_readset.go` (the committed read-set
declaration) and `plugins/signal/live_schema_test.go` (the opt-in live verification) already
exist. **This task builds no new tooling. It re-runs what is there, reads the number off the
result, and bumps.**

What is genuinely new since the precedent is the deployment path, and it is the part most likely
to be got wrong: Phase 15 shipped an installed instance, and Signal now runs from the external
trust tier under a SHA-256 content pin. Rebuilding the dev binary — all the precedent had to do —
now fixes nothing the operator can see.

Purpose: restore the Signal source in the instance the operator actually uses, without ever
converting a designed fail-loud guard into a rubber stamp.

Output: a raised ceiling carrying a third dated provenance entry; the rebuilt binary placed into
the external tier; a re-pinned, green, correctly-rendering Signal source; and a refreshed schema
acceptance record in the SUMMARY.
</objective>
