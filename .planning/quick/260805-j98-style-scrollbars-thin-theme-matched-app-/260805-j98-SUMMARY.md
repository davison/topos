## Decisions Made

- Named the three derived tokens `--scrollbar-thumb`, `--scrollbar-thumb-hover`, `--scrollbar-track` — the plan specified them by role ("a resting thumb color, a hover thumb color, and a track color") without literal names.
- Scoped the test's "each derived property references var()" assertion (Test 4) to the two `color-mix()`-based declarations only, not the plain `--scrollbar-track: transparent;` declaration. The plan's own action text specifies the track token as the bare keyword `transparent`, which by construction cannot contain a `var(--...)` reference — a literal reading of Test 4 against all three properties would be self-contradicting against the plan's own Move 2(a) instructions. This scoping preserves the stated intent (palette drift-proofing for actual colors) without manufacturing an unsatisfiable assertion.
- Used `:root` (not `html` or `*`) as the selector for the inherited `scrollbar-width`/`scrollbar-color` rule, matching the plan's "a rule on the root element" instruction and Firefox/Chromium's documented support for scoping these properties at `:root`.

## Verification Environment Findings (why the fix looked broken when it wasn't)

The `2604de1` fix was correct on first landing, but three stacked dev-environment problems made it invisible during re-verification — recorded here because each is a recurrence risk:

1. **`make dev` does not rebuild plugin binaries.** It runs `go run ./cmd/webspaces serve` + Vite only; the kernel launches whatever already sits in the configured plugins dir. Plugin code changes silently don't take effect until the plugin build targets are re-run. (Follow-up candidate: make `dev` depend on the plugin build targets, or have the kernel log each plugin binary's mtime at launch.)
2. **The kernel loses its port race silently under `make dev`.** A stale, manually-started `./bin/webspaces serve` (pre-fix, from 13:43) held `127.0.0.1:7777`; every subsequent `make dev` kernel died instantly on bind failure while Vite kept running and proxied the browser to the stale kernel. Two orphaned plugin process generations (10:58, 13:43) were also found and killed. (Follow-up candidate: `make dev` should fail loudly — or refuse to start — when 7777 is already bound.)
3. **`go run` breaks exe-relative plugin discovery.** `[plugins] dir = "plugins"` resolves relative to the executable, which under `go run` is a go-build cache temp path. Fixed by pinning the user's `~/.config/webspaces/config.toml` to the absolute `.../bin/plugins` path (with an explanatory comment). This also explains the historical habit of manually running `./bin/webspaces serve` — `make dev` had likely never worked for plugin discovery on this machine.

Diagnosis was confirmed at each step by curling the live kernel's `/api/items/{id}/content` and counting scrollbar rules in the served document (0 before the process cleanup, present after).

## Architecture Concern Raised at Approval (follow-up)

The user flagged that hardcoding theme styles (now including scrollbar rules) inside each plugin's `themeStyle` is not scalable once plugins become external with independent developers/lifecycles (the 999.1 plugin-ecosystem backlog direction). Assessment: the clean seam is to move document wrapping + theming (and, for untrusted third-party plugins, sanitization) from the plugins into the kernel's content-serving boundary (`kernel/httpapi/item.go`), so plugins return content and the kernel owns presentation. This is a plugin-contract change and belongs with the Phase 5 contract work or the ecosystem milestone's contract stabilization — captured as a pending todo (see `.planning/todos/pending/`).
