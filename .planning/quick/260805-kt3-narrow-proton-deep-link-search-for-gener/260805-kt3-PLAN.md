<objective>
Narrow the Proton "open in source" deep link so a generic subject stops matching a crowd.

Today the link is an All Mail search over the message's subject alone (03-10). That is precise
when the subject is distinctive and useless when it is "Invoice". The plugin already holds two
more discriminating facts about every message it indexes — the sender's address and the
message's date — and neither is currently encoded into the link.

Purpose: shrink the Proton result set toward the one intended message using only information
the plugin already has, without weakening a single security or honesty property 03-10 locked in,
and without ever excluding the target message from its own search.

Output: an extended `webmailSearchDeepLink` taking a criteria value instead of a bare subject; a
test file that keeps every 03-10 assertion and adds the new ones; a live verdict from the user's
real Proton account on the parameter names this plan can only guess at; and the two
operator-facing descriptions of `webmail_base_url` brought back in step with reality.
</objective>

<locked_constraints>

These come from Phase 3 plan 03-10 and from the task brief. They are NOT open for
reconsideration during execution. Each has an ID; task actions cite the ones they implement.

| ID | Constraint |
|----|------------|
| L-1 | The link is built ONLY from configured input plus fields the plugin already fetched for this message. No absolute URL literal in shipped source. |
| L-2 | The link is inert against sender-authored text. No value a sender can write may alter URL semantics beyond becoming a search term. |
| L-3 | A criterion is absent from the link when the field it is built from is absent. Never a search for the empty string; never a search for the `(no subject)` display placeholder. |
| L-4 | Free-text criteria are rune-capped, by rune-slice truncation, using the file's ONE existing truncation rule. |
| L-5 | Fidelity stays `LINK_FIDELITY_ANCHORED`. This plan improves precision; it does not discover a per-message URL and must not claim `EXACT`. |
| L-6 | The date criterion is conservative — wide enough that the target message can never be excluded by it. |

**Interpretation note on L-3, decided here and flagged for the Task 2 checkpoint.** 03-10's
original truth read "a message with no subject produces the All Mail view with no search fragment
at all" — true then because the subject was the ONLY criterion. Under a multi-criterion link the
faithful reading is per-criterion: a message with no subject carries no `keyword` parameter, and
the "no fragment at all" case is what naturally results when no criterion has a value. A
subjectless message from a known sender therefore gets a sender+date link rather than a bare
All Mail view. This is strictly more useful and preserves the actual security property L-3
protects (no empty-string search, no placeholder search). Both cases are asserted separately in
Task 1's table so neither can regress silently.

**The asymmetry that made Task 2 blocking rather than advisory.** 03-10 could not make things
worse: a URL form Proton did not recognise degraded to a redirect to the inbox, which was exactly
that gap's pre-fix behaviour. This change COULD have made things worse. If A-4 had been wrong —
Proton wanting milliseconds and receiving seconds — the bounds would have landed in 1970 and the
search would have returned nothing, replacing today's broad-but-containing result list with an
empty one. No automated test in this repository could detect that. The checkpoint blocked, and
its pass condition was that the target message be VISIBLE in the result list, not merely that the
page loaded — the verdict returned is a bare "approved," which per the plan's own resume-signal
contract means exactly that: all criteria honoured, nothing to correct. **Honesty note on the
evidence gap:** the approval did not include the address-bar URL Proton would have canonicalized
the link into, which the plan called out as "worth more than any other evidence this checkpoint
can gather." Every row above is therefore recorded as CONFIRMED-BY-BEHAVIOR (the link worked,
observed end-to-end) rather than CONFIRMED-BY-CANONICALIZED-URL (the exact wire-level parameter

acknowledged gap in the strength of evidence, not a promotion to the stronger claim the plan

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| IMAP server -> plugin | Envelope fields (Subject, From personal name, From address) are attacker-authored: any sender chooses their own display name and, within their own domain, their own local part. INTERNALDATE is server-set and not sender-controlled. |
| plugin -> composed URL string | Attacker-authored text is embedded into a URL the user may click. This is the boundary 03-10 hardened for the subject; this plan extends the same hardening to the sender. |
| composed URL -> user's browser | The user, not the plugin, decides whether the URL is ever dereferenced. The plugin opens no connection to the webmail host. |
